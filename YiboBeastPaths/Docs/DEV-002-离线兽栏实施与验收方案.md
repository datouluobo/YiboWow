计划版本：**1.9**。本文为开发方案；当前 1.8.2 的交付范围为桑蚕数据及显示优化。

日期：2026-10-27。状态：**API 源码与已有证据核对、方案整理完成；两端完整采集边界待实机核验，业务代码未实施，未发布。**

本文是 DEV-002 的实施入口，与[版本任务清单](离线兽栏与拥有状态-版本任务清单.md)、[Core API13 公共支持契约](../../YiboCore/Docs/API-v13-YBP离线兽栏公共支持契约.md)配套。已确认需求不重新决策：Retail、Mists 路线保持独立；离线兽栏依赖 Core；跨服务器查看本客户端本地已有兽栏快照的猎人；同时查看随身与兽栏，分别记录时间，读取失败保留历史。“已拥有”、路线隐藏／筛选、噩兆四色识别属于 DEV-005。

## 2. 两端原生 API 与采集边界

| 职责 | Retail 适配候选 | Mists 适配候选 | 共享层约束 |
| --- | --- | --- | --- |
| 随身列表 | `C_StableInfo.GetActivePetList()` | `GetStablePetInfo(index)` 扫描已核验的随身范围 | 随身表示可携带列表，不能只用 `UnitGUID("pet")` 的当前召唤宠物替代 |
| 兽栏列表 | `C_StableInfo.GetStabledPetList()` | 同一旧全局 API 扫描已核验的兽栏范围 | 扫全部数据，不抓 UI 当前页、搜索结果或可见按钮 |
| 单槽复核 | `C_StableInfo.GetStablePetInfo(index)` 返回结构或 nil | 全局 API 返回 icon、name、level、family、talent 等位置值 | 两种签名分开解析；返回 nil 不自动等于空槽 |
| 数量交叉核对 | `C_StableInfo.GetNumActivePets/GetNumStablePets()` | 同名数量 API，已有 3／63 实机样本 | 数量不是容量；与列表相等只是必要检查之一，不足以证明数据新鲜完整 |
| 兽栏交互状态 | `C_StableInfo.IsAtStableMaster()` 加事件会话 | `PET_STABLE_SHOW/CLOSED` 会话；原生界面可见性辅助诊断 | 事件／UI 可见不等于服务器数据就绪；重载可能丢失 show 事件 |
| 外观 | PetInfo 的 `displayID` | `C_PlayerInfo.GetPetStableCreatureDisplayInfoID(index)` | 可选显示字段；缺失不清空已有基础列表，也不推断来源／颜色 |
| 范围 | 原生 `Constants.PetConsts_PostCata` 与列表槽位；具体值待采样 | 原生 UI 候选 5 个随身、10×20 个兽栏槽 | 不在共享层硬编码 205；运行常量可能被 UI 插件改写，需要来源和上界核验 |
| 更新信号 | `PET_STABLE_SHOW/UPDATE/CLOSED`、`PET_INFO_UPDATE`；职业／法术变化按需要观察 | `PET_STABLE_SHOW/UPDATE/CLOSED`，`UNIT_PET(player)`、`UNIT_NAME_UPDATE(pet)`、`SPELLS_CHANGED` 等候选 | 仅监听本端实际存在且验证有用的事件；所有触发合并，不能按事件名推断已成功采集 |

Retail PetInfo 可观察的候选字段包含 slotID、图标、名称、等级、家族、专精、displayID，以及 petNumber、creatureID 等；后两者的稳定性及来源含义未在本机证明。DEV-002 不把它们当作跨会话唯一宠物键或路线来源。Mists 首期也不要求取得宠物永久唯一 ID。

Retail 原生 UI 单独读取兽王额外槽，并在总数显示中防止额外宠物重复计数。因此不能直接采用“Mists 的 1–5 随身／其余兽栏”规则，也不能直接把两个列表长度相加为唯一宠物总数。探针必须记录两列表全部 slotID、额外槽、数量与原生界面对应关系；有／无兽王额外宠物及切换专精分别核对。正式适配按已证实的原生归属展示，额外引用须标注；未确认前不做跨组去重或总体数量宣称。名字和外观相同的两只宠物不得合并。

原生 UI 的排序／过滤可能改变可见列表，但采集必须读取原始 API 列表；零搜索结果不能保存为空兽栏。Mists 的 NDui Plus 曾把页面常量改为每页 200、一页；这是 UI 布局观察，不是新增 API 容量保证。原生界面和常用 UI 插件各保留一组对照。

## 3. 采集提交规则

以下是实施约束；各目标的“已核验场景”须由阶段 P0 的报告补齐，当前尚不能打开正式写入门槛。

1. 顺序检查实际目标、猎人职业、Core API13／就绪／能力／方法、当前角色 ID、业务存档结构。任一身份或依赖不明，停止兽栏写入，保持路线。
2. 一次读取先进入临时结果，记录采集世代、角色 ID、目标/build、触发、交互状态、读取前后数量、槽位覆盖、基础字段错误。记录序号用于判断过期回调；时间使用持久化时间，不用会话 `GetTime()` 作为采集日期。
3. 全部基础行结构有效、无截断／重复非法槽位、已核验范围完整、前后数量及列表一致，并在已核验数据就绪场景中获得稳定重复读数，才可提交该组。重复相等也可能是旧缓存，不能脱离场景条件单独证明新鲜。可选外观缺失单独标为未知，不阻塞基础查看。
4. 确认空组要求与非空组同等级的覆盖、就绪和稳定性证据，且数量为 0、原始列表／槽位一致。登录初期零值、未打开过兽栏的 nil、异常、缺 API、受限值、关闭后缓存均不作为清空依据。
5. 成功一次性替换该组 `items` 并更新成功时间；失败仅记录尝试状态，保留该组上次成功数据和时间。不把部分新行与旧行拼成完整快照。缺少历史时显示尚未采集，不显示 0。
6. 打开／更新兽栏时优先以同一采集批次验证两组再共同提交。若发生跨组移动而仅一组可靠，新观察暂存，不覆盖旧成对快照；标为待同步，等待两组一致。其它已证明互不影响的单组更新可独立提交，保留各自时间。旧异时两组只作历史查看，不相加为当前唯一总数。
7. 关闭兽栏使在途读取世代失效；角色／目标变化、清理操作、依赖失效也取消旧回调。关闭后如允许读取，必须单独核验其新鲜性；首期默认保留历史，不凭缓存刷新成功时间。
8. 初始候选调度复用旧探针的 0.25 秒合并与 1.25 秒复读以采样比较；不是固定成功等待时长。正式重试必须有次数／时限上界，无事件不轮询，达到上界标 unavailable 并等待下次有效触发。最终参数在 P0 后确定。

只读采集，不调用移动、驯服、召唤、放生、改名或设置专精 API。不开原生兽栏、不代替玩家交互，不解开受限数据；返回受限／不可持久化值时保留历史并记不可读。战斗／死亡等状态纳入取样，不用 `pcall` 成功作为可序列化保证。

## 4. 数据所有权与 schema 草案

沿用各客户端各自 WTF 中的 `YiboBeastPathsDB` 和 `YiboBeastPathsDebugDB` 全局身份。建议新增 `YiboBeastPathsDB.offlinePets` 子树，schema 从 1 开始；旧路线 selectedPet、visible、路线参数及 debug 数据原样保留。此处为设计，未创建子树或修改任何用户存档。

| 层次 | 建议字段／语义 |
| --- | --- |
| offlinePets | schema、target、characters；新子树写目标戳，不给旧路线数据伪造历史目标；不自动跨客户端导入 |
| characters[Core ID] | active、stable；角色名称与显示优先读取 Core 身份副本，不建另一套可写目录 |
| 每组成功快照 | items、capturedAt、captureID、sourceBuild、coverage（已验证规则标识／范围）、completeness=complete |
| 每组尝试状态 | lastAttemptAt、status、reason；状态区分 never、available、unavailable、partial、stale；partial 不替换成功 items |
| items | 本批次原生槽位、名称、图标、等级、家族；可选专精／外观；Retail 额外槽关系单独记录。槽位只是快照地址，不是宠物永久身份 |

未知／更高 schema、非表结构、目标戳冲突：保留原值，停止兽栏读写并提示，路线可继续。合法旧路线库只增量创建新子树；迁移成功后才切换 schema，失败不覆盖原数据。不自动导入探针诊断库或把探针 `latest` 当业务快照。不持久化 Core 内部表、Frame、函数、API 返回对象引用或受限值。

快照没有每日／每周重置，不按时间删除；打开页面只读取，不刷新采集时间。清理通过 Core `character-cleanup:2` owner，按组 capturedAt 处理延后删除；较新的一组不能庇护另一组过期数据。清理时使在途旧采集失效。清理 owner 会话中只注册一次，关闭页面不注销清理责任。

## 5. Core 集成、独立路线与展示

最低门槛固定 API13 及 12 项能力：runtime:1、events:1、characters:1、character-identity:1、character-name-format:1、character-cleanup:2、account-view:2、account-character-admission:1、account-surface-budget:2、account-entry:2、builtin-entry-bar:3、localization:1。逐项检查实际使用方法，详见[公共支持契约](../../YiboCore/Docs/API-v13-YBP离线兽栏公共支持契约.md)。界面实施若增加输入等需求再补能力，不复制 Core 实现。

- 保留已批准的 OptionalDeps 边界，不将整个路线插件改为 RequiredDeps。Core 缺失、禁用、旧版、缺能力或未就绪，只停止兽栏增强；玩家入口明确提示安装／启用、升级或等待。就绪后立即重试，处理原生 ADDON_LOADED 与 CORE_READY，重复通知不重复注册。
- 依赖不可用时的提示由现有独立命令／语言引导路径承担，使用同一双语资源、按既有独立提示例外处理；这不建立兽栏的本地语言服务或替代窗口。增强成功后全部业务 UI 使用 Core.Locale:Get，手动语言只由 Core 管理。
- 当前 Mists `Maintenance/CoreDebugAdapter.lua` 已登记同 owner 的独立维护设置面板。新增页面前需协调 owner／Locale 一次登记，并把适用设置聚合到唯一业务设置入口，避免独立维护面板与页面托管设置生成两个同名导航。关闭维护页不得注销兽栏页；兽栏失败也不得使原维护功能重复初始化。路线渲染不依赖增强初始化成功。
- 准入：Core 目录中的猎人 + 至少一次成功兽栏快照，包括已知空兽栏；只有随身数据不展示。跨服同名按 GUID 分开。遵守 Core 隐藏、等级过滤、排序和服务器范围；首次使用明确可选全部服务器，不另造持久范围开关。
- 账号页采用角色摘要与选中角色的随身／兽栏详情，显示各组上次采集时间和当前读取状态；列表可滚动，长列表可达。Core 提供窗口壳、预算、设置、入口。主视图和最多 20 名角色的悬停预览投影同一快照与状态，不建立第二份权威数据；具体布局在业务 UI 阶段完成验收。
- 缺历史显示“尚未采集”，失败有历史显示“暂不可读取，显示上次记录”；两组异时显示各自时间，不显示实时库存承诺。没有符合准入的角色时提示用猎人访问兽栏采集。
- 默认仅 Core 入口；业务独立入口由 Core 管理三通道及其全部八种组合。首期无跨业务消费，不新建宠物 Service／Provider；不注册路线拥有目标。

## 8. 实机取样步骤与验收矩阵
