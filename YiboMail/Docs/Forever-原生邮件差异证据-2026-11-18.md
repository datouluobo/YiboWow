# Forever 原生邮件差异证据

固定来源：[Gethe/wow-ui-source Forever MailFrame](https://raw.githubusercontent.com/Gethe/wow-ui-source/3d8abb1da73acd38e412e24fb3f99454a6392346/Interface/AddOns/Blizzard_MailFrame/MailFrame.lua)。提交及内容SHA256保存在`_NonRelease/MailForever/NativeSource-20261118/MailFrame-Source.json`；未复制源码到产品实现。

| 边界 | 镜像观察 | 对重构的影响 / 尚缺证据 |
| --- | --- | --- |
| 原生控件 | 旧式正文编辑框、发送按钮、收发页和附件按钮集合存在 | 目标适配可按具名控件绑定；第三方皮肤、玩家build和实际可调用性待证 |
| 容量 | 接收16、发送12槽 | 读取动态常量并检查实际控件集合，不根据旧7槽布局截断；真实末槽待样本 |
| 收件 | 原生按邮件索引/附件槽取物品及金币 | 共享队列仍需确认更新/成功信号、重排与失败；源码调用不能证明插件的调用限制 |
| 退回/删除 | 原生按InboxItemCanDelete决定删除或退回，财物删除有确认 | 独立目标资格复核，不沿用MoP的zhCN系统正文例外；受保护行为和COD待样本 |
| 发币 | 原生按钮经过安全转移流程设置金额后发信 | 不推定旧按钮脚本重放就能完成确认；必须观察原生确认、实际发送结果和草稿清理 |
| 刷新 | 原生使用C_Mail.CanCheckInbox调度CheckInbox | Forever既有只读扫描不强拉；若后续接入需遵守节流，不能照搬MoP直接拉取行为 |

关键差异已由“仅猜API”推进到“静态调用/控件有出处”，运行时限制仍未明确，不能据此启用或宣称完整收发安全通过。下一份客户端证据由YiboMailForeverProbe0.1.1集中采集：开关与切页、按本人需要取件、装填/撤下/正常发送、自然COD/退回及失败、切角收件、最后退出恢复。完整清单见整体方案第6节。
