## 续补：关箱与当前包验收

Forever 关箱、离开世界时按 MoP 行为释放派生的在途查询数据，保留存档与历史；同步订阅者在关闭通知中重建的缓存也会释放。新增 SessionLifecycleSpec 已复现旧行为并验证修复、重复关箱、离线重建、重新开箱及旧回调取消。当前4个 Mail/Vault 两目标候选完成实际包清单、逐文件运行字节、干净/保留旧文件覆盖及存档恢复离线回放，共7组通过；这替代“最近改动只有源码测试”的状态，仍不代替真实客户端验收。

## 续补：拍卖和附件采集

- Forever 按客户端原生的成交、到期、撤销、竞得、被超过及发票主题模板识别拍卖信，补上无发票拍卖退回信的分类和退信排除；成交/待结算发票保存原生买家名称，与 MoP 历史详情字段一致。分类使用客户端动态名称，不依赖 Core 所选界面语言。
- Forever 附件快照保留原生名称与图标，供收件搜索、附件汇总、公共物品快照及取件历史使用；物品缓存未就绪时也能查看已观测名称与图标。发件人未返回时按 MoP 归一为空字符串，修复收件搜索 `table.concat` 因 nil 报错；不持久化本地化“未知”标签。
- 主题模板匹配收拢为共享纯业务工具，MoP 扫描与两端历史筛选复用；原生模板列表和 API 读取仍在目标扫描器。晚到的附件名称/图标、拍卖类别和买家变化会触发快照发布，但不改邮件签名或误建新邮件/发现历史。
- 新增 `InboxMetadataSpec.lua`，真实 Forever 清单覆盖中英原生模板与相反 Core 语言、无发票拍卖信、原生发票买家、附件元数据晚到后的 revision、搜索/汇总、取件确认后拍卖成交历史和存档恢复；未知发件人搜索报错已先复现再修复。Harness 原生附件名称改为与已有 ItemResolver 夹具一致的 `NativeItem<ID>`，避免通用占位名与名称搜索用例矛盾。

## 首轮补齐

1. **Ctrl 点击同类物品装填**：原共享 NativeUI 只监听旧式 `ContainerFrameItemButton_OnModifiedClick`。将背包点击原生绑定分别放入已加载的 `Mists/Compose.lua`、`Forever/Compose.lua`；共享 UI 只处理 Ctrl、发件页、游标条件及装填结果。Forever 监听 `HandleModifiedItemClick` 传入的 ItemLocation，按实际包号/格号装填，不按合并背包父框推测包号；装备位置、无位置链接不触发装填。Mists 保持原入口；绑定可重复调用但只注册一次，原函数及返回值保留。
2. **材料背包范围**：Forever 仅在原生 `Enum.BagIndex.ReagentBag` 明确为 5 时将其加入 Compose 的随身候选范围；快捷装填和规则寄复用同一 BagItems。未报告此包时沿用既有普通背包范围；Mists 范围不变。不扫描银行。
3. **部分载入的退信/清理结果确认**：共享 Returns 原先固定要求操作后载入数量等于 `min(100, 总数)`，导致 Forever 已载入少量邮件时，即使收到成功事件、总数下降且保留行一致，仍无法完成操作。现依目标的 `STABLE_INBOX_LIMIT` 判断完整窗口约束；Forever 允许保持部分载入，MoP 保留稳定 100 封窗口要求。成功与更新事件、总数减一、已知保留行顺序/身份一致的要求仍保留；只接纳新增尾行，不自动操作尾行。

新版原生入口的固定源码依据：[ContainerFrame.lua](https://raw.githubusercontent.com/Gethe/wow-ui-source/3d8abb1da73acd38e412e24fb3f99454a6392346/Interface/AddOns/Blizzard_UIPanels_Game/Mainline/ContainerFrame.lua)、[ItemLocation.lua](https://raw.githubusercontent.com/Gethe/wow-ui-source/3d8abb1da73acd38e412e24fb3f99454a6392346/Interface/AddOns/Blizzard_ObjectAPI/Mainline/ItemLocation.lua)。源码和模拟说明适配依据，不替代当前客户端及背包皮肤验收。

## 用户游戏内手测

1. 重载后打开邮箱发件页，按 Ctrl 点击有多个堆叠的可邮寄物品，检查同类物品装填、已有附件和手动正文正常；重复点击不重复装填。若有材料背包，核对其中的同类堆叠也进入装填/规则匹配。此步可只装填后撤下，无需真实发送。
2. 自然遇到邮件尚未全部载入时，按需要退回一封或清理符合 MoP 条件的空信，检查队列完成、账号计数和历史；无需特意制造大量邮件。没有样本保持待验。
3. 有自然拍卖邮件时，核对拍卖/玩家来源筛选，成交记录的买家悬停信息，以及到期/撤销信不会进入退信队列。取件后在历史中核对拍卖成交筛选；无需为测试专门挂拍。
4. 检查现有物品邮件的名称搜索、附件汇总图标；正常退出回登后查看离线快照与历史，确认已观测名称和图标仍在。未知发件人样本无需刻意制造。
5. 关闭邮箱后查看历史快照和在途量，再重新打开，核对内容不丢失；保持平常操作即可，不需要反复制造邮件。
6. 打开 Core 中邮件的业务设置，确认 Forever 显示原生金币确认说明，窄窗口无文字/标题重叠；未开邮箱时 `/yma scan` 应提示先打开邮箱，开箱后显示本会话语言的扫描结果。

## 架构与交付边界

迁移职责为原共享 UI 内的客户端背包点击绑定，已收归两目标 Compose 适配；共享装填及 Returns 业务仍只有一份。Core 现有 ItemResolver/ItemPicker 不提供此点击订阅或可移动物品槽位采集契约，本次不增通用能力、不绕过业务数据所有权；已有 Core API13、能力最低版本及调用保持，无 CAP 接入变化。

续补迁移单元为主题模板的纯匹配算法，原生模板目录及发票/附件 API 仍由 Mists/Forever 目标扫描器拥有。Core ItemResolver 的现有调用保持；保存原生邮件提供的名称/图标属于 Mail 自身业务快照，不新增本地 GetItemInfo 回退或跨业务数据访问。Store 增量发布及 History 筛选共享改动已回归 MoP，无新增 Core 能力接入或最低版本变化。

设置/扫描提示续补继续使用现有 Core 设置工作台和 localization:1/API13，新增静态文字采用稳定ASCII key与中英文资源；无新增Core能力或接入范围变化，不改CAP台账。客户端差异通过既有目标配置表达，公共排版/命令呈现留在Common；未触及加载/初始化/存档迁移职责。

沿用 `YiboMail_Forever.toc`/`YiboMail_Mists.toc`，玩家加载名仍为 `YiboMail.toc`；无 TOC/XML/间接引用变更、无旧路径新增。实际客户端身份、Core 就绪/API/能力写库前检查、单次生命周期初始化及原生 hook 幂等保持；SavedVariables 仍为两目标原身份/schema，无迁移或跨目标导入。旧代码残留不新增加载引用，当前源码联接不等于玩家包覆盖验收。代码和离线验证完成，客户端及发行范围未全部完成，不宣告可发布。
