# Mail 悬停倒计时与 Vault 拍卖时间

2026-11-23。适用 Mail Mists 1.4.0-api1、Forever 0.3.0-api1 与 Vault Mists 1.3.0-api1、Forever 0.7.0-api1 的后续工作树。新增的预估和待核实时间只投影到 Mail 悬停的「最早到期」列，沿用该列的显示设置、Core 角色范围和隐藏规则。主窗口、登录提醒和库存依旧读取原有扫描结果。

## 数据归属与核对

- Mail 从发件成功和 Core 账号角色得到在途邮件，以服务器发件时间加普通邮件 30 天、COD 3 天估算。包含没有物品附件的已知寄件。升级补录双方均无更晚扫描的近期成功发件。扫描实信后逐封替换为原生期限，消失的已知邮件在去向未核实时保留负数倒计时。超过待核实保留期后退出悬停。[暴雪经典版邮件规则](https://us.media.blizzard.com/manuals/wow/wow-classic-manual-enUS.pdf)
- Vault 复用既有「本人拍卖」采集，把已验证的无竞价上架投影为带精确 `endsAt` 的条件期限。只有原生到期事件确认已识别的本人上架流拍，才保存 `endedAt`。仅有时间档位的上架可以等明确事件；成交、取消、未确认消失不算流拍。最新上架状态与退件依据由 Vault 保存，流拍证据保留 90 天。[Mists 5.5.4 原生拍卖声明](https://github.com/Gethe/wow-ui-source/blob/5.5.4/Interface/AddOns/Blizzard_APIDocumentationGenerated/AuctionHouseDocumentation.lua) · [Forever 原生拍卖声明](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/AuctionHouseDocumentation.lua)
- Mail 悬停经 Core 可选读取 `vault.items` 1.2 的 `GetAuctionTimings`。对已知流拍使用事件时间加 30 天估算，实信按物品、数量与时间证据逐封去重，多个同样的退件分别消耗对应观测。退件随后离开收件箱时，其已扫到的证据继续抵消预估。没有兼容的 Vault 时，保留 Mail 自有悬停内容。[公开契约](../../Docs/YiboVault-Mail-API-v1-契约.md)
- Mail 旧试作保存的拍卖预估会被清理，Mail 只保存自有在途、待核实邮件和原生退件的抵消证据。Vault 同样只保存自己观察的拍卖事实。两个插件的 TOC 各自依赖 Core，既有 `mail.items` 接口及仓储对 Mail 的可选读取保持原行为。

## 加载与适配

- Mail 悬停／邮件证据是共享单元，源码 `YiboMail_Mists.toc`／`YiboMail_Forever.toc` 加载 `Common/Expiry.lua`。Vault 拍卖时间与保留规则在 `Common/AuctionTiming.lua`，Mists 原生采集迁到 `Mists/AuctionHouse.lua`，Forever 继续由 `Forever/Auction.lua` 处理。两个 Vault 目标 TOC 各自引用对应采集器；各玩家包加载默认 `YiboMail.toc`／`YiboVault.toc`，目标 Interface 为 Mists 50504、Forever 16001。
- 写库前沿用目标身份、Core 就绪、API14 及既有最低能力检查。拍卖事件归 Vault；注册由已存在的幂等初始化保护。保留 `YiboMailDB`、`YiboMailForeverDB`、`YiboVaultDB`、`YiboVaultForeverDB` 与各自 schema。角色清理连同该角色的证据。Mists 旧包覆盖残留的根目录 `AuctionHouse.lua` 已从新链移除；旧 Mail 引用边界保持。复用 Core 角色目录、账号视图、版本化契约与 Mail owner 的中英文资源，未增加 Core 能力门槛。

两端分别实测。Mists 使用 Core 1.13.0，Forever 使用 Core 0.3.0。两个客户端的 `YiboMail`、`YiboVault` 均是指向仓库源码的目录联接。实测 ZIP 时，先退出游戏、备份 `WTF`，将原有联接暂存到 `AddOns` 外，再把同目标 ZIP 的两个实体目录解压到客户端的 `Interface/AddOns`。在 Core 的「显示与入口」打开一个 Mail 入口，并在其悬停字段中显示「最早到期」。

1. **流拍退件去重。** 在装上测试包后打开拍卖行的「本人拍卖」，让 Vault 采集一笔可以自然流拍的挂单。尽量用当前唯一可跟踪的退件做样本。保持同一角色在线等待流拍，先别开邮箱，记录 Mail 悬停是否出现「拍卖退件」。若只取得时间档位，流拍前可以没有「若流拍」。看到「拍卖退件」后打开原生邮箱并等列表更新，先不取件。对比原生剩余期限和 Mail 悬停，预期这封信改用原生期限，预计项消失。若同时还有其他未扫退件，预计项可以对应那些邮件。之后可正常领取该封，再关箱和重登，确认旧预计项没有回来。如果开箱前始终没有「拍卖退件」，记为未建立预计，去重本身留待有样本时重测。
2. **负数倒计时重登。** 优先用已缓存、临期且可以自然到期的低价值邮件。到期前开箱一次让 Mail 保存原生期限。到期后再次开箱，确认原信不在且扫描已更新，然后关箱查看悬停，预期出现「待核实 -…」。记录时间和数值，通过游戏菜单完整退出，再登录同角色。先不打开邮箱，立刻查看同一悬停，预期待核实项及负值仍在。显示精度允许短间隔内数值相同。已经出现负数的样本可以直接测试完整退出与重登；没有样本时这项保留待测。已超出 Mail 待核实保留期的记录无需恢复。
3. **基本联动。** 用同账号两名已被 Core 识别的角色走一次正常寄件。收件角色开箱前，Mail 悬停显示「在途」；扫到后只按实信期限显示。新增预计项出现在悬停，原有主窗口和登录提醒仍以扫描结果为准。可在关键项测完后于插件列表禁用 Vault，核对 Mail 自有倒计时仍能显示。
