## 3. 必测样本

1. 已知空邮箱、普通空信、金币信、COD 信、单附件、多附件。
2. 两封完全相同发件人/主题/附件邮件；列表顺序变化后再次扫描。
3. 普通玩家邮件、系统邮件、AH 成交/过期/取消邮件、明确退回邮件。
4. 当前可见数为 99、100，以及 `total > current` 的积压邮箱。
5. 邮件打开后立即扫描、等待物品信息加载、重载 UI、断线重连。
6. 只读扫描后某封邮件消失，确认状态保持 `unverified` 而不是推断已收取。

### 3.1 复现与提交步骤

1. 开启 `/ymp events on` 和 `/ymp watch on`，打开邮箱后执行 `/ymp mail`；保持窗口打开，等待自动 `MAIL_INBOX_UPDATE` 采样。每次场景前后再手动执行 `/ymp mail`，确保有明确的对照样本。
2. 分别观察两封完全同内容邮件、移除其中一封后的列表，以及 99、100、`total > current` 的积压邮箱。保存每次的 `current/total/unscanned`、重复签名组和 `CHANGE` 行。签名相同只说明无法唯一配对，不能给其中一封推断服务器身份。
3. 在玩家自愿进行普通收件操作时，使用原生邮箱逐次点击取非 COD 附件、取金币；有现成背包空间不足的场景时再观察失败路径。COD 只读取头部与附件，不要求付款取信。观察 `mail.player-action`、`MAIL_INBOX_UPDATE`、`MAIL_SUCCESS`、`MAIL_FAILED`、`UI_ERROR_MESSAGE` 与之后的扫描。探针不执行这些操作，`pending-update` 也不代表成功。
4. 关闭邮箱并再执行 `/ymp mail`；即使 API 仍返回旧列表，`coverage` 也应为 `unavailable`。之后 `/reload` 并重新打开邮箱，重复同签名与剩余时间观察。
5. 正常退出或 `/reload` 后，提供 SavedVariables `YiboMailStage0Probe.lua`。可用 `_NonRelease/YiboMailStage0Probe/Tools/AnalyzeSavedVariables.lua` 提取摘要；原始样本用于核对附件槽位、刷新时序与客户端 build。

阶段一正式插件的扫描器、匹配、公共 API 和 Core 页面仍等待本节只读场景评审。收件队列还需另行确认原生 API 的玩家交互要求、索引重排、部分收取、背包容量与失败恢复；发件装填属于后续阶段。
