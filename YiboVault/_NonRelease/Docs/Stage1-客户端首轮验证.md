> 日期：2026-09-25
> 范围：首版背包与装备来源；不是阶段 1 最终验收。

## 落盘结果

- `YiboVaultDB` schema `1`，全局 revision `83`，账号中保留 `3` 个角色的数据。
- 当前角色的背包 `0..4` 共 `5` 个位置均为 `known`，含 `93` 条物品位置记录、堆叠数量合计 `1,143`。
- 当前角色装备槽 `1..19` 完整覆盖，记录 `17` 件装备，状态为 `known`。
- 其它两个角色的背包 `5` 个位置与装备各 `1` 组均为 `stale`，当前角色采集没有覆盖它们。

## 结论与后续

插件依赖 Core 加载，SavedVariables 已写入，背包与装备首次全量采集成功。下一步检查正式事件路径：移动背包物品后由 `BAG_UPDATE_DELAYED` 更新受影响容器，且不需要手动执行 `/yva scan`。

## 背包跨容器移动验证

- 用户在 NDui 显示的四个装备背包之间移动一整组物品；界面不显示 API 使用的数字 bag ID。
- 移动前后聊天状态：revision `305 → 307`，记录 `105 → 105`，当前角色总数量 `1,069 → 1,069`。
- 落盘后当前角色 bag ID `0..4` 均为 `known`；装备仍为 `known`。账号中其它角色继续保持各自的 `stale` 状态。
- 结论：无需 `/yva scan` 的背包事件更新路径通过；两个变更容器使 revision 各推进一次，跨容器移动保持记录数和总数量。
- 聊天状态未输出两个具体的变更 bag ID，因此本次不记录其编号。NDui 显示的四个独立背包对应 WoW 容器 ID `1..4`；背包总包为 ID `0`。

## 内容未变时重复扫描验证

- 后续测试期间背包内容已多次变化，因此本节采用本次截图与落盘快照作为独立基准，不沿用跨容器移动测试的数量。

- 本次 SavedVariables 快照与状态一致：当前角色 `101` 条记录、总数量 `1,347`，`6` 个来源位置为 `known`，错误数 `0`；其它角色维持各自的 `stale` 状态。
- 结论：在两次状态读取之间没有物品变化的前提下，完整扫描结果与缓存一致时不会推进 revision，重复扫描幂等性通过。

## 个人银行接入后的客户端复测

- Core 物品仓库页搜索物品 ID `13544`，合计 `2`、位置明细 `2`：当前角色个人银行容器 `11` 格 `19` 数量 `1`；另一角色陈旧背包 `4` 格 `21` 数量 `1`。这确认银行记录进入统一查询，同时保留其它角色的陈旧位置标识。
- 结论：NDui `BANKFRAME_OPENED` 后全银行容器扫描、状态记录和查询页明细通过首轮客户端检查；未打开银行时没有误记为已知位置。
- 尚未通过截图确认关闭再打开同内容银行时 revision 不变；后续可与公会银行验收一并检查。所有后续对照使用各自当轮现场状态，不复用历史数量。
- 后续复扫样本：用户确认是同一角色，且银行物品完全未移动；报告成功 `8/8`、失败 `0`，状态为 revision `641`、记录 `246` 条、当前角色缓存量 `3,095`，银行已知位置 `8`、陈旧位置 `0`。相较之前 revision `596`、记录 `126` 条、缓存量 `307`，期间其它物品位置也有变化；revision 是全来源全局值，且缺少复扫前的即时 `/yva status`，因此不能用这两个状态读数判定银行复扫是否推进 revision。
- 同角色个人银行关闭重开复测：截图中的登录后基线为 revision `718`、角色记录 `218` 条、缓存量 `1,934`，个人银行已知 `0`、陈旧 `8`、错误 `0`；打开后报告扫描成功 `8/8`、失败 `0`，状态变为已知 `8`、陈旧 `0`、错误 `0`，revision、记录数和缓存量仍为 `718` / `218` / `1,934`。用户确认后续状态输出是在关闭并重新打开个人银行后读取，最终值仍为 `718` / `218` / `1,934`，银行已知 `8`、陈旧 `0`、错误 `0`。
- 结论：同一角色的个人银行关闭并重开后，已知页数、缓存记录、缓存总量和 revision 均保持稳定；重复扫描幂等性通过。首次打开将已有的 `8` 个位置从陈旧刷新为已知，但没有改变物品记录或全局 revision。

## 公会银行事件问题与修复记录

- 首次接入复测反馈：用户打开公会银行后没有看到扫描完成提示；当时 `/yva status` 显示公会银行已知 `0`、陈旧 `0`、错误 `0`。该状态只能说明当时没有已落盘页签，尚不能区分打开事件未送达、扫描尚未结束或启动异常。
- 后续截图显示公会银行 UI 已打开，但 `/yva status` 仍为 `idle（尚未收到打开事件）`。这确认正式插件路径没有收到 `GUILDBANKFRAME_OPENED`，与阶段 0 探针已收到该事件的样本形成差异。
