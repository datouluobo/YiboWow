# Yibo 系列总纲

> 文档性质：系列产品方向与协作原则。具体功能范围、接口和验收以各插件产品文档及实施方案为准。  
> 当前主要目标客户端：魔兽世界熊猫人之谜经典版。  
> 更新日期：2026-10-16。当前验收与发行核对见[仓库当前状态总览](仓库当前状态总览.md)，近期安排见[后续开发任务清单](后续开发任务清单.md)。

## 1. 产品使命

Yibo 服务使用多个角色的玩家，减少他们为了完成目标而记录、查找和记忆大量角色信息的负担。

玩家可以提出一个目标，也可以接收插件基于已启用目标与已确认状态给出的提示。Yibo 应回答：**如何实现、由哪个角色执行、现在能做哪一步、还缺什么，以及哪些部分已经完成。**

装备、专业、技能、物品、货币、进度和锁定状态是形成答案的依据。账号视图既要支持玩家核对这些事实，也要把事实转化为有理由、可追溯的行动建议。

一个完整答案至少包括：

1. **目标**：玩家想取得、制作、解锁或完成的对象及其稳定身份。
2. **候选角色**：各角色满足的条件、缺口和推荐理由；需要多角色配合时，说明分工。
3. **行动路径**：当前步骤、后续步骤、相关地点或游戏系统，以及可跳转的业务页面。
4. **状态依据**：来源、观察时间和确定程度；未扫描、过期、预计与已确认分别呈现。
5. **完成判据**：由明确的游戏信号或玩家确认关闭目标，不凭数据缺失推断完成。

## 2. 用户场景

### 玩家提出目标

- “我想制作这件装备”：找出学会配方且达到要求的角色，核对材料位置、数量和冷却，列出需要转移或补充的物品。
- “我想完成这条传说任务线”：比较角色进度、前置条件、当前可执行步骤和已完成阶段。
- “我想获得这个坐骑”：展示已验证的来源与条件，再结合角色的相关进度判断下一步。

### 插件提示机会

- 某角色的已监控专业冷却恢复，可以处理玩家关注的项目。
- 邮件快到期且含有玩家目标所需的物品，提示登录对应角色核实或领取。
- 某角色的已启用周期目标接近重置，仍有可执行步骤。

提示必须有明确的目标、证据和时效；优先级受玩家的关注设置影响。插件只在已收录且规则可靠的目标范围内提出结论。

## 3. 系列结构与数据所有权

| 层次 | 职责 | 数据归属 |
|---|---|---|
| YiboCore | 统一角色身份与目录、服务器/角色范围、排序、中性角色事实、账号窗口、入口、设置工作台、缓存清理和通用展示能力 | `YiboCoreDB` 保存 Core 自己的角色事实与偏好 |
| 业务插件 | 采集并解释一个业务领域；提供业务页面、快照、状态、操作与可选的只读接口 | 各插件持有自己的 SavedVariables |
| YiboTaskHub 目标与行动协调 | 管理主动添加目标、来源进度和统一任务投影；复杂任务链分期扩展 | TaskHub 保存用户目标与自身设置；来源业务继续拥有业务快照 |

Core 是共同底座，业务插件是可独立演进的功能模块。Core 不代替业务插件解释配方、邮件、首领或任务规则；业务插件不重复维护角色目录、账号窗口壳、入口生命周期和通用设置界面。部分工具型插件可以独立运行，并在 Core 可用时提供可选接入。

### 模块版图与近期规划

| 领域 | 插件 | 在系列中的主要作用 |
|---|---|---|
| 角色事实与统一界面 | `YiboCore` | 提供角色目录、专业等级等中性事实和统一账号框架 |
| 构筑与装备 | `YiboBuilds` | 保存角色构筑、天赋、雕文及装备快照 |
| 资源与物品 | `YiboCurrency`、`YiboVault` | 分别展示货币与物品库存、位置和来源；现有功能已实机验收 |
| 周期与进度 | `YiboTodo`、`YiboAltoBoss`、`YiboLegendary`、`YiboReputation` | 分别处理周期活动、首领/副本锁定、传说任务与声望 |
| 任务与收藏信息 | `YiboQuestBlocker`、`YiboMounts` | 提供任务规则与坐骑来源等专门能力 |
| 邮件与专业 | `YiboMail`、`YiboCrafting` | 邮件工作台与账号配方查询已实机验收；Crafting 固定目录及三态范围沿用产品说明 |
| 目标与行动 | `YiboTaskHub` | 已交付主动添加目标与统一投影；数量分配、预留及复杂物流任务链见后续计划 |
| 独立或可选工具 | `YiboAutoOpen`、`YiboBeastPaths` | 保持各自的操作或路线功能，按实际价值选择是否向目标系统提供信息 |

该表描述职责和方向，不表示所有插件目前都有可供其它插件调用的公共 API。现状以各插件 TOC、运行时代码与产品文档为准。

## 4. 跨插件协作原则

1. **事实各有来源。** 专业等级等中性事实由 Core 提供；库存由 Vault、邮件由 Mail、周期活动由 Todo 等领域所有者提供。同一事实不在多个 SavedVariables 中建立互相竞争的权威副本。
2. **通过公开结果协作。** 消费者检查提供者的接口版本和能力，使用只读查询、明确范围、状态、观察时间、revision 与变更通知；不读取其它插件的私有数据库结构。
3. **可选来源允许降级。** 某模块未安装、接口不兼容或来源未扫描时，结论标明缺少依据；不能把未知当作零、未完成或已完成。
4. **区分持有方式。** 背包和银行中的实体库存、拍卖行上架物品、待取邮件附件分别计数和说明；需要转移、领取或重新扫描的步骤必须显式列出。
5. **同一范围得出同一结论。** 主页面、悬停和行动提示按 Core 给出的同一角色切片查询；业务模块对同一状态使用同一套判断与格式化。
6. **规则由负责的业务域维护。** 目标协调能力组合模块提供的条件与结果，不在 Core 中复制各领域规则。

现有的 [Vault / Mail Public API v1 契约](YiboVault-Mail-API-v1-契约.md) 是这一协作方式的具体样本。Mail 提供邮件附件及已交付的在途投影，Vault 已通过 Core 可选接入并选择唯一来源，同时保留待取状态和数据归属；实际版本和方法以现行 API 文档为准。

## 5. 目标到行动的模型

目标到行动的完整方向按以下过程组织；TaskHub 当前已交付主动添加目标与来源进度，复杂推荐、数量分配和任务链按实际需求扩展：

```text
选择目标或收到提示
  → 解析已收录的目标与完成条件
  → 从各业务模块读取角色事实和业务状态
  → 比较候选角色、条件缺口及数据可信度
  → 展示可执行步骤与推荐理由
  → 观察游戏事件或接受玩家确认
  → 更新目标进度与后续行动
```

目标应使用稳定的物品、配方、任务、首领或其它业务 ID；名称用于展示，不作为唯一存储键。第一批目标从已收录对象、业务页面和游戏内上下文入口选择，逐类验证规则、完成信号及跨角色差异。

推荐是对**玩家所选目标**的帮助：它可以列出多个可行角色，并解释时间、已有材料、当前进度或角色切换成本等可验证差异。玩家的偏好决定哪些目标值得提醒；算法不将所有未完成内容自动升级为待办。

完成状态按作用域区分角色、本账号和周期。对于缺少可靠完成信号的项目，保持“待确认”或提供玩家手动确认，不把一次观察扩大为永久完成结论。

## 6. 当前维护与后续顺序

用户于 2026-10-16 确认现有功能已实机收口；Legendary／Todo 完整英文适配、BeastPaths 后续宠物开发、TaskHub 复杂任务链为三项延期工作。当前版本发行状态按证据核对，详见[状态总览](仓库当前状态总览.md)。

最近两天先完成文档状态与入口整理、延期任务记录及无限首次验证计划。无限开测时间待确认；首次验证从 1 级新角色可用能力开始，专业、收藏、邮件、跨角色和周期条件逐项具备后补测，见[验证计划](无限公测首次验证计划.md)。

公测后按条件继续三项延期工作。TaskHub 先选一个真实跨角色闭环，所需配方查询、库存、邮件和冷却能力逐项按公开契约接入；其它增强方案作为候选，不自动加入当前排期。每新增一种目标，须能说明玩家获得的决策价值、可靠数据来源、目标客户端验证方式和长期维护成本。

## 7. 产品验收尺度

Yibo 的成效不只由记录多少字段、覆盖多少对象衡量。对一个已支持的目标，玩家应能在账号范围内：

- 找到可行角色和推荐理由；
- 看出当前能执行的下一步，以及跨角色资源或前置条件的缺口；
- 分辨已确认、预计、过期和未扫描的信息；
- 从建议进入负责的业务页面核对并行动；
- 在完成后看到正确的角色级、账号级或周期状态。

当证据不足时，诚实显示需要登录、打开窗口或重新扫描的具体来源，也是合格答案的一部分。
