# 货币与声望：API 发现目录与角色快照规则

确认日期：2026-11-12。状态：**规则已确认，重构待实施**。

适用 `YiboCurrency` 与 `YiboReputation` 的 Mists、Forever 目标。本文是两插件后续目录发现与快照重构的共同规则来源；具体 API 契约、存档迁移及版本验收由各插件实施文档补充。本文不表示运行代码已经采用该方案。

## 1. 产品与架构边界

- 原生项目通过本客户端 API 发现并读取，保存账号曾发现项目的并集；同一账号所有角色均未发现的项目可以不显示，不要求预置完整原生目录。
- API 发现有效项目就加入目录，包括有效数量为 0 的项目。后续归零、当前角色列表缺项或一次空列表都不自动移除项目。
- Mists 与 Forever 平级。同一插件的发现、合并、刷新调度、快照状态及展示逻辑尽量共用一份实现；目标专用 API、事件、返回格式和确认过的业务差异留在各自适配层。
- 共用代码不等于共用存档。两目标使用各自既有 SavedVariables 身份和数据，禁止相互导入或混合目录。
- Currency、Reputation 各自是自身目录、采集和快照的权威所有者；共用本文规则不表示二者直接读取对方数据库或共用业务实现。Core 继续负责角色身份、范围、托管界面与公共能力，不接管货币或声望业务。没有实际需求时不新建跨插件通用目录服务。

## 2. 目录、角色快照与显示设置

| 数据 | 含义 | 约束 |
| --- | --- | --- |
| 账号发现目录 | 本目标账号曾发现过的有效货币／阵营 | 按稳定 ID 合并，保存 API 名称、图标、类型等可用元数据和发现／更新时间；名称不作主键 |
| 角色快照 | 指定角色实际采集到的数量或声望状态 | 使用 Core 角色唯一标识，分别保存值、状态和观察时间；可记录来源以便迁移与诊断 |
| 显示设置 | 主表、悬停、关注及排序选择 | 与目录存在性、余额是否为零相互独立；目录刷新不得重置玩家选择 |

货币使用 `currency:<ID>`、物品使用 `item:<ID>` 等稳定来源身份，声望使用稳定阵营 ID。相同名称、相同数字但来源不同的项目不能自动合并。目录中存在项目不代表所有角色都有有效快照，也不代表游戏已将其设为账号共享。

动态名称保留游戏 API 原文，玩家自定义名称不被自动改写。类型、范围及特殊规则只记录已确认信息；未知字段保持未知，不根据客户端名称推断。

“保存目录”包括运行时合并到插件存档数据，并通过游戏正常的重载／退出保存机制落盘，不要求插件自行写磁盘。

## 3. 发现与主动查询

1. 在客户端身份、Core 就绪与所需能力检查通过后，读取当前角色的原生列表。
2. 列表中取得有效稳定 ID 和项目身份信息后，将其合并到账号目录；不要求数量大于 0。
3. 对账号目录中的已知 ID，主动调用适用的详情查询 API，尝试补齐当前角色列表未展示的项目。按 ID 查询取得有效项目身份时同样可加入目录。
4. 只有经过适配层校验的读数才能更新当前角色快照。函数调用成功不等于返回内容有效；占位结果、未知 ID、不可用字段或语义未确认的返回值不得当作有效项目／余额。
5. 各角色登录后重复上述流程，目录取并集。不能将当前角色的查询结果写给离线角色，离线角色使用自身最近快照。
6. 原生变化事件触发相应刷新；合并高频请求，失败时采用有限重试。具体事件、就绪时机与重试策略在各端验证，不为目录 ID 做无界枚举或逐帧查询。

主动调用查询 API 不等于强制服务器补发数据。若客户端确有异步申请与完成通知，取得证据后在目标适配层接入；未验证前不假定存在此能力。

分类折叠、隐藏／未使用分组、登录加载中和 API 失败可能影响枚举范围。实现须识别扫描完整性，避免为了读取数据永久改变玩家原生面板的展开或筛选设置。读到有效项目可以增量合并，部分失败不能使整个目录被覆盖为空。

## 4. 零值、缺项与历史状态

| 本次结果 | 快照处理 | 展示语义 |
| --- | --- | --- |
| 有效项目，明确返回数量 0 | 更新当前角色的值和观察时间 | 已确认零；目录与显示设置保留 |
| 有效项目，明确返回非零数量／声望状态 | 更新当前角色的值和观察时间 | 本次有效观察 |
| 列表未列出，但按 ID 查询有效 | 按有效详情更新 | 列表缺项不阻止详情读取 |
| 列表缺项，详情也无法确认 | 不构造零值；保留已有值及原观察时间 | 有旧值则标明历史／待刷新，无旧值则未知／未采集 |
| API 报错、不可用或返回语义未确认 | 保留已有有效数据，不更新成功观察时间 | 按实际原因标记失败／未知，不伪装为已刷新 |
| 成功读取空列表 | 本次可见发现集合为空；不清除账号目录和其他角色快照 | 空列表本身是正常结果；已知 ID 的详情查询仍独立进行 |

“未发现”“未采集”“历史”“已确认零”不可互相替代。账号汇总只累计口径适用且数值有效的记录；缺少角色数据时说明覆盖不全，不能用零补齐并显示为完整总计。账号共享项目不得按角色重复求和，需由业务插件根据已确认范围处理。

## 5. 目录生命周期与迁移

- 自动采集只增量合并和更新元数据，不因单次缺项、余额归零、角色隐藏或删除某个角色快照而自动删除目录项。
- 显示／隐藏、关注／取消关注不会改变目录及快照。清理目录属于独立、明确的用户操作；本文不要求立即新增清理界面。若提供破坏性清理，遵循“数据与缓存”末尾风险说明及确认规范。
- MoP 旧存档中实际取得有效数据的原生项目可迁入发现目录，并保留其角色快照和稳定 ID 对应的显示设置；有效零值也可迁移。仅存在于旧固定目录但从未取得有效数据的项目不必自动加入。
- 旧固定目录中尚无发现证据的用户偏好应保留，后续发现同 ID 时可恢复；不能借目录缩减删除历史事实或重置设置。
- Currency 已有物品代币、自定义物品和玩家文本单独保留；若旧物品项实际对应原生货币，须有明确 ID 对应及数量口径证据后迁移，禁止按名称自动转换或重复计入总计。
- 重构保持各目标 SavedVariables 身份。具体 schema、迁移幂等性、旧文件覆盖加载、旧快照恢复及必要备份方案在实施前确定，不借重构跨目标导入数据。

## 6. Currency 的落实边界

- 金币通过适用金币 API 读取，作为基础项目保留；原生货币由列表发现和已知 ID 详情查询形成目录。
- 物品代币及自定义物品继续通过物品数据来源处理，与原生货币共用目录合并、显隐设置和展示框架；不能用货币列表替代所有物品追踪。
- 当前余额、周获取量、上限及重置时间分别验证字段和语义，不把缺失字段填为 0，也不将一种 API 的字段名直接当成另一端契约。
- 设置中的项目应来自动态目录和保留的物品来源，不要求两端具有同样项目数量。相同交互使用共享代码。

## 7. Reputation 的落实边界

- 任一角色通过适用 API 发现有效阵营 ID，即进入本目标账号阵营目录；目录覆盖各角色已发现阵营的并集，不预填所有阵营。
- 详情查询有可用且已验证的按阵营 ID 接口时，主动查询已知阵营；未具备该能力时保留已观察快照并标明未知／历史，不把列表缺失解释为中立或进度 0。
- 按角色保存声望等级、原生进度值与阈值、类型和范围等已确认数据。进度 0 可能只是本等级起点；不得用“0”代替完整声望状态。
- 普通声望、友好度及其它特殊类型由 Reputation 解释；本级进度、累计进度、会话变化和账号共享等规则必须按各目标已确认的类型与 API 数据计算，未知类型不套普通阈值。
- 账号目录不等于账号共享声望；某角色发现阵营不能据此给其他角色填同一值。关注清单使用阵营 ID 并保留顺序，悬停继续投影关注阵营和同源角色快照。
- 可复用目录积累、状态和刷新原则；不将 Currency 的余额校验、加总和周上限逻辑复制到 Reputation。声望具体接口与特殊类型属于后续取证范围，不因本文被视为已验证。

## 8. 证据与后续验收

已有 Currency 证据：2026-11-12 Mists 5.5.4（project 19）探针读到 33 行，含 4 个分类、29 个货币 ID，29 次详情查询成功，行失败 0。Forever 1.60.1（project 18）列表返回 0 行；用户确认当前角色原生货币列表确实为空，作为正常空列表样本。Forever 的非空货币详情与更新仍待自然样本。列表完整标记只覆盖当时可见行，不代表全部可能货币。以上不证明动态目录重构已验收。

后续实现应覆盖：

- 两角色依次发现不同项目，目录正确取并集；先登录空列表角色也能正常工作。
- 新发现有效零值也入目录；花完归零不丢项目和偏好；未知 ID／占位返回不误入目录。
- 已知 ID 不在当前列表时主动查询；有效零、查询失败、未采集和历史值正确区分。
- 折叠／隐藏分类、部分扫描失败、登录未就绪与高延迟时不清空目录、不伪造完整快照。2026-11-12 用户确认复用 MoP 未打开货币面板仍可采集的实机证据，不要求为折叠分类专门重复进游戏；折叠／隐藏和部分失败通过离线模拟检查，未打开面板不作为折叠状态已实测的证据。
- 同名不同来源／不同 ID 不误合并，账号共享与按角色数据不重复汇总。
- 原主表／悬停设置、声望关注顺序、物品自定义目录及既有角色快照正确迁移；重复初始化和重复迁移不新增副本。
- 重载、完整退出恢复及保留旧文件覆盖更新分别验证；共用改动回归所有受影响目标。

已通过的同客户端、相同加载字节和声明范围证据复用；新增目录、迁移和状态行为须单独验证。离线模拟、客户端通过、发布检查及实际发布分别登记。
