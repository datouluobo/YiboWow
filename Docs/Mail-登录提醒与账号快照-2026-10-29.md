## 已确认路径与修复

1. **登录提醒的完整上下文**：Page:OnLogin 延后 5 秒调用 BuildContext；原来通过 GetVisibleCharacters 和自定义顺序获取完整 Core 角色目录，首次使用会产生带 domains 的深复制共享缓存。Core 增加通用 `account-identity-context:1`，Mail 提醒使用 `identityOnly=true`；隐藏角色、页面准入、等级／范围、排序、自定义顺序、预览规则由原 Core 路径处理。Core 自定义顺序改用现有身份查询，BuildContext 的范围选择复用已有定义，避免两个间接入口又加载完整目录。默认完整上下文／GetAllCached 契约保持。
2. **为阵营而读取完整目录**：联系人 Current 之前取得轻量当前角色后，又遍历完整目录取 faction，好友状态读取也会走这条路径。Core `character-identity:2` 在原身份投影中添加已有 faction，未知保持 nil。Mail 联系人、公开在途／库存查询、行动来源、迁移、名称匹配和常用联系人均使用公开身份投影，不再调用 GetAllCached。没有把业务数据迁入 Core。
3. **邮箱关闭时的规则扫描**：身份域变化会间接调用 SendRules:Changed(true)，即使没有打开邮箱也会构建背包匹配结果。现在只有邮箱打开时才执行 rematch，规则版本与失效仍推进；打开后现有路径重新匹配，发送中的状态保护保持。
4. **空迁移预热在途缓存**：未执行过 LegacyTransfers 迁移时，原来会遍历全部角色调用 GetTransfers，即使数据库没有旧发送。先只检查是否存在需要审查的旧 in-transit 记录；没有则完成迁移标记，不加载目录／在途索引。存在旧发送时仍执行完整匹配与原审查，历史不删。
5. **重复提醒调度**：同一次 UI 会话的 OnLogin 仅安排一个回调，回调完成后不重建；到期再次确认开关，关闭提醒后不显示。上下文、角色数组和摘要在回调返回后可释放，仅保留原来的去重状态，不持有完整账号上下文。

6. **在途服务双重复制**：原 GetTransfers 在 Mail 复制缓存结果，Core.Contracts 随后再做一次边界隔离。现在本地私有查询供已注册的服务回调返回，Core 完成一次隔离；直接 Mail API 仍复制。没有公开内部缓存引用或提供“跳过复制”的公共参数，缓存版本与结果保持。真实 Core→Vault 测试验证服务没有 Mail 预复制、直接 API 有复制，双方结果均可独立修改。

## Core 契约和接入要求

先完成 Core 实现、契约与真实上下文对照，再接入 Mail。最低仍为 API13，Mail Mists 新增必须能力 `character-identity:2`、`account-identity-context:1`；缺少任一能力使用现有双语升级提示，停止在 InitializeDatabase 之前，不保留本地完整目录回退。**更新时 Core 与 Mail 必须一起更新并 reload**；仅版本号或“Core 已加载”不能证明新能力存在。

文档：[轻量账号上下文](../YiboCore/Docs/API-v13-轻量账号上下文.md)、[角色身份](../YiboCore/Docs/API-v11-轻量角色身份.md)。Core account-view:2 及既有 API13 保持，不改第三方默认完整快照；能力1身份消费者继续兼容。新上下文仅供页面准入逻辑只依赖身份字段的调用使用，不能将依赖 domains 的页面强制套用。

## 离线存档是否必须常驻

当前 Mail 的账户 SavedVariables 是同一份 Lua 数据；无论角色是否在线，完整记录都随此插件数据加载。账户库存、统一摘要、提醒和在途匹配需要离线角色的当前证据，因此不能把所有离线角色数据都卸掉。**历史明细没有必要一直以完整展开的表常驻**；当前实现仍然如此，本轮没有修改该存储格式。

后续较小边界的方案是保留热摘要／当前邮箱／完整匹配证据，将旧历史明细按块序列化、压缩，查看时解码；解码缓存设置容量与生命周期。压缩字符串仍占内存，不能称为零占用；搜索／导出和在途判定必须保持原值、时间、多重性与不确定结果。因为在途匹配会读 discovered／collected 历史，归档前必须保留可重建且语义一致的收发证据索引，不能直接按日期隐藏历史导致寄达结果改变。

若要登录时连历史压缩数据也不载入，需要独立按需加载的档案模块及存档迁移；客户端提供按插件加载的 LoadAddOn／IsAddOnLoadOnDemand，[客户端 API 声明镜像](https://github.com/Gethe/wow-ui-source/blob/classic/Interface/AddOns/Blizzard_APIDocumentationGenerated/AddOnsDocumentation.lua)可核对。该接口不是对某一角色／某几行 SavedVariables 的随机磁盘读取，也不等同于加载后可安全卸载。此方案还涉及目标清单、安装目录／存档身份、首次转换、旧包覆盖及完整退出恢复，不能在本轮用“把表设为 nil”替代，否则后续保存可能丢数据。

上述是设计边界，未新增档案插件、压缩库、格式迁移或删除路径。是否实施、具体分块和恢复方案应以可验证设计另行落实；保留完整历史仍是约束。

## 目标、入口与后续验收

Core 的身份与账号框架是 Mists／Retail／Forever 共享通用能力，没有新增客户端专用 API 或目标实现复制；Mail 修改的是既有共享账号／收件人／业务查询和 Mists 旧在途审查、既有业务依赖检查。未新增目标、TOC、XML、技术名、安装目录、SavedVariables 身份、schema 或 Slash。Mists 沿用 YiboMail.toc／YiboMailDB；Forever 草稿沿用原目标清单／YiboMailForeverDB，不加载本轮 Mists Bootstrap／提醒／寄件 UI；共享 Items 仍经过其当前角色限制，最低身份1即可使用原字段，不外推为 Forever 新功能已接入。

Mail 基础依赖在业务写库之前检查 Core 就绪／API13／全部能力，新检查不注册第二份入口或事件，初始化原幂等保持。既有目标身份保护继续沿原入口，不把 TOC／已加载等同于可写；未修改路由职责或旧文件覆盖链。构建引用和离线已验，但新字节误目标保护、干净安装／覆盖、语言显示、reload 及完整退出恢复仍待客户端证据；Forever 不新增发行 profile，不宣告可发布。CAP-004／007 记录实现与业务接入，CAP-005 记录公开查询仍隔离；未触及业务保持原状态。
