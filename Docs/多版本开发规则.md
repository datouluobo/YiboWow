# Yibo 多版本开发规则

> 状态：已确认
>
> 最近修订：2026-10-20。本文规定目标架构与发行方式；具体插件的实现、实机验证和发布状态须分别记录。
>
> 适用范围：Yibo 系列插件面向多个客户端、资料片、规则集或产品目标的适配、开发、测试和发行。
>
> 目标：在同一代码仓库内复用稳定的产品逻辑，同时隔离不同目标的 API、数据目录和发行包，避免版本条件分支扩散到共享业务代码。

## 一、最终方案

Yibo 的多版本插件采用以下模式：

- 一个 Git 仓库；
- 每个插件沿用自己的项目与 CurseForge 项目；
- 一套共享架构；
- 每个受支持的产品目标各自拥有适配层和数据层；
- 正式玩家安装包默认按已支持的产品目标独立构建与发布；
- 每个插件的 GitHub Release 提供一份全目标源码与公开文档归档；
- 不复制维护三套完整源码；
- 简单稳定插件可以采用本文明确记录、逐目标验证的单包兼容例外。

“同一插件项目”指该插件各目标的源码、问题跟踪、版本历史和 CurseForge 项目共用；“独立安装包”指每个玩家安装 zip 只包含一个目标客户端实际需要的 TOC、Lua、数据和资源。GitHub 全目标归档用于源码查阅与开发，包含该源码快照中已有的各目标实现，不按客户端重复生成，也不作为默认直接安装包。

架构允许逐步增加目标，实施只覆盖明确需要且能够验证的目标与插件。默认先用 MoP 与一个新目标、Core 与一个代表性业务插件跑通完整流程，再扩展范围；目标目录、接口和数据按实际需求建立。功能适用、已有实现、实机验证与正式发布是不同状态，须在对应插件记录中区分。

## 二、目录命名

目录按 Yibo 实际支持的产品目标命名，不照搬客户端内部的 `Classic`、`Mainline` 等实现分类。当前示例目标为 `Retail`、`Mists` 和 `Forever`；未来新增目标直接使用其产品名称或仓库约定名称。

目标 ID、目录、包名 slug、源码与实际加载 TOC、CF 发布元数据统一遵循 [多版本目标与发行标识规范](多版本目标与发行标识规范.md)。该规范是标识命名的唯一来源，机器配置位于 `Tools/ReleaseProfiles.psd1`；新增目标须同步登记，不自行创造别名。

标准目录结构：

以下为按需扩展的结构示例，不要求提前创建所有目录。

```text
YiboMounts/
├─Common/
├─Retail/
├─Mists/
├─Forever/
├─<FutureTarget>/
├─YiboMounts_Retail.toc
├─YiboMounts_Mists.toc
└─YiboMounts_Forever.toc
```

目录含义：

- `Common/`：跨目标客户端稳定复用的代码；
- `Retail/`：正式服专用代码与数据；
- `Mists/`：熊猫人之谜经典版专用代码与数据；
- `Forever/`：无限专用代码与数据；
- `<FutureTarget>/`：未来新增产品目标的专用代码与数据。

不得新增无实际产品意义的中间层，例如：

```text
Flavor/Mainline/
Flavor/Classic/
```

客户端的内部实现分类只允许出现在 TOC、能力探测或构建配置中，不作为业务源码目录命名。

## 三、共享代码规则

共享代码只依赖 Yibo 定义的稳定业务接口，不直接依赖某个目标的专用 API、ID 或规则。

适合放入 `Common/` 的内容包括：

- 数据模型；
- 账号与角色快照结构；
- 状态模型和状态格式化；
- 账号矩阵、表格和 Tooltip 布局；
- 排序、过滤和分页；
- 设置页面；
- Core 注册与页面生命周期；
- 通用诊断和错误处理；
- 目录查询和来源格式化。

共享代码不得散布如下形式的版本判断：

```lua
if isMists then
    -- Mists API
elseif isForever then
    -- Forever API
end
```

少量版本选择只能出现在运行时入口或 Core 能力层。业务代码应调用统一接口，例如：

```lua
local info = Addon.Runtime.API:GetMountInfo(mountID)
```

而不是直接调用某个版本的原始 API。

### 触及即迁移

后续代码修改按“触及即审查，适用即迁移”推进。以本次涉及的完整职责单元为边界，将客户端专用 API、事件、规则与静态目录归入对应目标目录，包括既有 MoP 的 `Mists/`；跨目标稳定的模型、界面和算法保持共享，按需归入 `Common/`。共享代码中的客户端差异提取到适配层或必要运行时入口，通过稳定契约消费，不复制整套共用实现。

未触及的旧模块保留原位，作为迁移库存；同一文件中的无关职责不自动纳入本轮重构。既有维护例外（如 YiboBeastPaths）继续按对应章节执行。纯文档、换行与空白修改不触发运行代码迁移。

实施前明确职责、调用方和受影响目标，尽量将保持行为不变的迁移与功能调整分步实施、分别验证。同步更新目标 TOC、XML、间接加载、资源路径、测试夹具及构建引用，检查旧路径不再参与加载。迁移期间尚在原位的共享文件可继续由目标清单引用，无需一次性搬迁全插件。

本规则与 Core 公共能力“触及即接入”同时执行：本次涉及且有适用公共能力的逻辑按项目约定接入。收尾在相关插件实施记录中列明迁移单元、受影响目标、保留范围与理由、离线结果及实机待验项；共享代码或契约变更须检查所有受影响的已支持目标。

### 目录迁移的升级兼容

插件技术名、玩家安装目录及每个目标既有 SavedVariables 身份保持稳定。目录迁移本身不重置数据、不改变存档身份；业务 schema 改动须另行设计并验证旧数据升级、失败保护与目标隔离。

默认按用户直接覆盖解压、旧文件仍存在的场景设计加载链。新清单仅加载当前版本文件；旧 Lua、XML 和资源残留不得导致旧实现执行、重复初始化或重复事件／入口注册。特别审查客户端可能优先选择的旧 TOC，以及 XML 和间接加载路径，不能只检查新 TOC 的直接 Lua 引用。目标识别错误时在写库前停止，不由插件运行时尝试删除磁盘文件。

每次发布验证干净安装及已声明升级起点的覆盖更新，首次目录迁移包含迁移前的代表性发行版本。模拟验证与目标客户端实测分别记录；更新工具的清理、覆盖与卸载行为须有该工具的实际证据。具体用例、证据和无法覆盖升级时的处理遵循 [发布包约定](../发布包约定.md#覆盖更新与升级验收)。目录迁移完成、覆盖升级通过、目标功能通过与可发布分别判定。

## 四、客户端适配层规则

每个目标目录负责把目标客户端 API 转换成共享层可使用的统一接口。

示例：

```text
Mists/
├─API.lua
├─Data.lua
└─SourceFacts.lua

Forever/
├─API.lua
├─Data.lua
└─SourceFacts.lua
```

适配层负责：

- 客户端 API 调用；
- API 参数和返回值转换；
- API 缺失、延迟和错误处理；
- 版本专用事件；
- 版本专用 ID；
- 版本专用数据读取；
- Secret Values、保护调用和现代 Tooltip 等限制的降级。

适配层向共享层提供稳定语义，例如：

```lua
API:GetCharacterIdentity()
API:GetCurrency(currencyID)
API:GetReputation(factionID)
API:GetMountInfo(mountID)
API:GetCollected(mountID)
```

如果两个客户端当前恰好使用相同 API，也仍应优先通过适配接口调用，以便后续客户端更新时集中修复。

多个目标在参数、返回值、事件与业务语义均一致且经过验证时，可以引用同一份适配实现；共享业务与页面继续调用统一接口。接口示例仅说明语义，实施前须检查现有公开能力，不代表仓库已有同名 API。

## 五、数据目录规则

版本专用数据必须放入对应产品目录，不得把不同客户端的 ID 混入共享目录。

例如：

```text
Mists/
├─MountCatalog.lua
├─CurrencyCatalog.lua
└─SourceFacts.lua

Forever/
├─MountCatalog.lua
├─CurrencyCatalog.lua
└─SourceFacts.lua
```

共享层只定义数据结构和查询协议，不定义具体客户端的：

- NPC ID；
- 任务 ID；
- 货币 ID；
- 坐骑 ID；
- 声望 ID；
- 配方或物品 ID；
- 区域和地图 ID；
- Boss 锁定 ID。

数据目录应优先使用稳定的业务 ID，并保留来源客户端、内容版本和验证状态。

## 六、TOC 规则

本节统一执行[多版本目标与发行标识规范第2.1节](多版本目标与发行标识规范.md#21-多目标-toc-与运行入口规则2026-10-26)；仓库 `AGENTS.md` 已将其列为后续插件开发的强制约束。新建、适配或修改加载职责时逐项审查并记录结果，维护例外须有明确范围；不能把某插件已通过的业务验证外推到其它插件。

默认每个支持的目标客户端提供独立加载清单，例如：

```text
YiboMounts_Retail.toc
YiboMounts_Mists.toc
YiboMounts_Forever.toc
```

源码目标清单须按统一标识规范使用已验证的后缀。正式服产品目标保持Retail，源码唯一清单使用_Mainline.toc，不另建_Retail.toc或同内容开发别名。独立安装包输出插件默认TOC文件名；其它新客户端须先验证实际识别行为。源码清单名、客户端加载名与CurseForge版本标签分别校验。

每个目标的 TOC 声明与实际加载结果必须满足：

1. 声明目标客户端实际的 `Interface`；
2. 使用目标客户端实际认可的 flavor 元数据；
3. 只引用 `Common/` 和对应产品目录中的文件；
4. 不引用其它产品目录的实现文件；
5. 在客户端实际 Beta 或实机环境确认后再标记为正式支持。

新目标的 Interface 数字和 flavor 标识在 Beta 或实机环境确认前不得凭空写死。不能因为两个目标采用相近的 UI 架构，就直接假定它们可以共用 TOC。

迁移后的多目标源码默认 TOC 仅作为经过验证的缺目标提示入口，不承载旧版默认业务、不声明业务存档或发布就绪API；目标清单负责实际运行链。独立玩家包统一将选定目标清单输出为默认 TOC，不附带源码提示入口或其它目标清单。新客户端先验证其实际选择行为；维护例外按已批准范围执行。

单包兼容例外可使用多 TOC，或经所有声明目标验证的多 Interface/条件加载清单。每个目标必须明确实际加载的文件；未匹配目标须安全停止，不得借助“加载过期插件”扩大支持范围。仅增加 Interface 数字不能证明兼容。

## 七、构建与发行规则

统一构建入口按插件与产品目标接收参数，当前已接入的示例：

```powershell
.\Tools\Build-ReleasePackages.ps1 -Addon YiboCore -Target Mists
.\Tools\Build-ReleasePackages.ps1 -Addon YiboVault -Target Mists -Channel CurseForge
.\Tools\Build-ReleasePackages.ps1 -Addon YiboCore -Target Mists -ValidateOnly
```

Core 与 Vault 为首批；2026-10-15 已将现有 14 个单目标插件接入统一脚本，完成原入口转调、版本/Interface/静态 Lua 引用校验、CF 目标包、GitHub 全目标归档及分目标归档。BeastPaths 通过维护包构建器保留现有多 TOC/XML 内容并采用 universal 命名，共 15 个插件统一命名函数。未登记的新目标直接停止；通用 XML 或条件清单解析仍未扩展。CI 可调用相同入口，BigWigs Packager 等工具按需采用，不作为架构成立或本地构建的前置条件。

玩家安装包构建必须从目标 TOC 读取文件清单，而不是复制整个源码目录。

每次玩家安装包构建必须执行：

1. 解析目标 TOC；
2. 复制 TOC 引用的文件；
3. 检查所有引用文件存在；
4. 检查未引用的其它产品目录没有进入发行包；
5. 复制目标版本所需资源；
6. 运行目标版本的 Lua 语法检查；
7. 运行目标版本的目录和清单校验；
8. 生成目标版本安装包；
9. 输出包内文件清单和目标客户端信息。

单包兼容例外按其声明目标集合校验各加载清单和共享资源。GitHub 全目标源码归档按公开文件规则收集，不受“只包含一个目标”限制。两个渠道的内容边界、命名与归档规则以根目录 [发布包约定](../发布包约定.md) 为准。

推荐产物命名：

```text
YiboMounts-retail-v0.7.0-curseforge.zip
YiboMounts-mists-v0.7.0-curseforge.zip
YiboMounts-forever-v0.1.0-curseforge.zip
```

各产品目标是独立发布流，版本号独立递增；文件名把目标 slug 放在版本号之前。目标专属修复只提升本目标版本，共享改动按受影响范围回归并分别决定发布。共同发布可以使用相同版本号，但不要求长期保持一致；无限等新目标可以从自己的 Beta 或首发版本起步。具体字段顺序与示例以 [目标与发行标识规范](多版本目标与发行标识规范.md) 为准。

目标专属修复只构建和发布受影响目标；共享代码或公共契约变化须核对所有已支持目标的影响并完成相关回归，再发布需要更新的包。GitHub 归档记录源码版本或提交标识，并列出包含的目标、对应插件版本、最低 Core/API 要求和验证状态；归档包含目标实现不构成该目标正式兼容声明。

## 八、发布平台规则

同一个 CurseForge 项目可以发布多个目标客户端文件，但每个文件必须准确标记其实际支持的游戏版本。

正式发行优先采用 RareScanner 式分发：

- MoP 用户下载 Mists 包；
- 无限用户下载 Forever 包；
- Retail 用户下载 Retail 包；
- 不要求用户下载包含其它客户端代码的通用包。

### 单包兼容例外

单包兼容适用于功能稳定、目标间差异很小且发布节奏一致的插件。例外须在本节或对应插件规则中明确记录，并满足：

1. 列出实际声明支持的目标，不使用未经验证的“全版本支持”标签；
2. 各目标的 API、事件、保护操作、目录可用性和加载方式分别验证；
3. 差异集中在入口或适配模块，不扩散到业务与页面；
4. 每个目标只加载适用文件，按实际加载结果检查运行时隔离；
5. 一个 CF File 只标记该包通过验证的目标；TOC 声明与上传元数据保持一致；
6. 差异或发布节奏扩大时，回到目标独立安装包方式，保留共享源码。

当前允许按这些条件评估 YiboAutoOpen；评估完成前不改变其既有兼容声明。GitHub 全目标源码归档单独遵循渠道规则，不需要申请玩家单包兼容例外。

## 九、Core 与业务插件规则

### YiboCore

YiboCore 按已接入目标的实际需求渐进完善统一运行时与能力层，职责包括：

- 当前目标客户端识别；
- Interface 和能力探测；
- 角色身份适配；
- 账号、规则集和角色范围；
- 通用数据领域存储机制；
- 统一 UI 与页面注册；
- flavor 相关诊断。

当某个目标采用无传统 Realm、按规则集划分生态或其它非传统角色范围时，Core 不得继续把 Realm 作为唯一范围维度。对应适配应支持该目标的账号共享数据、规则集边界和独立进度语义。

Core 负责通用身份、范围、界面和连接；库存、配方、声望、首领、任务周期等业务规则及其目标适配由业务所有者维护。业务 SavedVariables 继续由各插件负责；通用存储机制不改变所有权。

### 业务插件

业务插件按实际使用情况遵循：

- 使用 Core 的插件通过其公开接口注册，并检查最低 API/能力版本；原本可独立运行的插件维持其可选集成边界；
- 通过适配层读取客户端数据；
- 版本专用静态目录放入对应产品目录；运行时业务快照由自身 SavedVariables 保存，并按目标及实际账号/规则集范围隔离；
- 不在共享页面代码中直接判断多个客户端 API；
- 不重复实现 Core 的角色目录、窗口、入口和范围选择。

## 十、各插件特殊规则

### YiboMounts

从无限首发开始建立 `Forever/` 坐骑目录，后续按内容补丁追加坐骑和来源。

不要把无限坐骑与 MoP 历史坐骑混合到同一份运行时目录中。坐骑 Tooltip、目录查询和缓存框架可以共享，坐骑 ID、来源事实和收藏 API 必须按产品目标隔离。

### YiboBeastPaths

YiboBeastPaths 进入维护阶段，业务内容保持现有潘达利亚隐藏猎人宠物路线与 Mists、Retail/Mainline 支持范围。后续按实际问题修复 bug、处理必要兼容更新，并对受影响范围回归。

该插件不纳入本轮多版本架构试点或集中迁移，保留现有打包和加载方式。新增功能、目标或整体迁移须有后续明确需求，再单独确定范围。

### YiboAutoOpen

YiboAutoOpen 功能相对单一、稳定，允许评估一个玩家安装包覆盖多个已验证目标。Core 继续保持可选增强；跨目标兼容不以安装 Core 为基础条件。

评估至少覆盖背包读取、容器允许目录、物品使用、拾取与绑定确认、安全暂停、重试隔离、重载与设置保存。相同 itemID 也须核验在各目标的用途和允许条件；共用同一逻辑不代表共用全部允许目录。

通过第八节例外条件后，可按实际目标集合发布单个 CF File，包名使用 `universal`，并标记已验证版本。后续新增目标仍须单独验收；若操作权限、业务逻辑或发布节奏出现较大差异，则按默认方式分包。

### YiboTodo

MoP 的诺米、半山农场和 MoP 专业冷却不得直接作为无限内容复用。无限的专业、营地、Blueprint 和 Legacy Challenge 等内容按真实接入需求建立独立目录，具体数据、周期和可观测性验证后才启用；可复用待办状态模型、冷却模型和账号矩阵。

### YiboBuilds

装备、天赋、雕文、专精和幻化读取必须通过产品目标适配层。不得把 MoP 的固定插槽、雕文数量或天赋结构假设放入共享模型。

### YiboQuestBlocker

新目标默认采用保守模式。自动接任务、自动拒绝、自动放弃和第三方自动化插件适配必须在目标客户端实际验证后单独启用，不得因为另一个版本可用就默认迁移。

## 十一、测试规则

每个产品目标都必须拥有独立测试矩阵：

```text
YiboMounts/
└─_NonRelease/Tests/
   ├─Mists/
   ├─Forever/
   └─Retail/
```

单包兼容也按每个声明目标分别记录结果，不以单一包共用验收结论。共享测试用例可以复用，目标专用场景与实机证据分别保存。

至少覆盖：

- TOC 加载和引用完整性；
- Lua 语法；
- API 能力探测；
- 当前角色采集；
- 离线角色快照；
- SavedVariables 迁移；
- 账号范围和角色范围；
- 未知、延迟和错误状态；
- `/reload`；
- 入口、页面和悬停预览；
- 目标客户端的保护 API 和战斗锁定行为。

任何一个目标客户端未完成实机验证时，只能标记为开发版或 Beta 支持，不得在发布说明中写成正式兼容。

## 十二、新目标迁移顺序

已有插件从 MoP 基线增加一个新目标时，按以下顺序实施：

1. 把现有 MoP 逻辑识别并收拢到 `Mists/`；
2. 把跨版本的 UI、模型和业务协议提取到 `Common/`；
3. 建立目标目录和目标 TOC；
4. 实现目标 API 适配层；
5. 建立目标数据目录；
6. 为目标添加独立测试；
7. 修改构建脚本支持目标参数；
8. 生成目标独立玩家安装包；已记录的简单插件例外生成声明目标集合的兼容包；
9. Beta 实机验证后再发布正式支持。

不得先复制整个插件目录再分别修改两份。若两个版本已经出现重复业务代码，应优先回收稳定部分到 `Common/`，将差异收敛到目标目录。

上述是默认迁移步骤；维护阶段插件按其专门规则处理。一次只承诺本轮明确范围，完成实现与验证后再扩大插件或目标集合。

## 十三、验收标准

一个插件完成多目标适配，必须同时满足：

- 共享代码中没有散落的客户端 API 分支；
- 每个目标客户端拥有已验证的加载清单，默认独立 TOC；单包兼容符合已记录例外；
- 每个目标独立玩家安装包只包含该目标所需文件，兼容包只包含其声明集合需要的文件；
- 每个插件的 GitHub 全目标归档有明确源码标识、目标版本与验证状态清单，和玩家安装包用途清晰区分；
- 版本专用 ID 没有进入共享目录；
- 目标客户端的 API 能力经过实机验证；
- SavedVariables 不会因不同产品目标互相污染；
- CurseForge 文件标签与实际支持目标一致；
- 未验证的目标不会写入正式兼容声明；
- 目标专用内容更新收敛在对应产品目录和构建配置；共享逻辑或契约更新完成受影响目标的相关回归。

纯规范文档修订只核对条款、交叉引用及现有状态描述，无需运行插件或新增架构测试。规则修订不自动意味着现有构建脚本或插件已完成迁移。

本规则文档是 Yibo 后续所有多版本开发、构建和发行的统一约束。若未来需要增加新的客户端、资料片、规则集或产品目标，或改变目录命名、分包策略和共享层边界，应先更新本文档，再实施代码变更。

## 十四、无限目标准备与阶段门

2026-10-18无限测试客户端目录与15个插件的源码联接已就绪，登录、探针与实机采样仍待验证；路径维护见[客户端源码联接](客户端源码联接.md)。阶段状态与采样清单集中维护在[无限公测首次验证计划](无限公测首次验证计划.md)；以下规则适用于后续Forever目标的真实开发。

1. **规则准备阶段**：确认目标命名、证据要求、数据归属、采样条件、验收与发行门槛。探针实现、客户端联接、产品目标目录、TOC和构建配置在对应开发任务启动后按实际需求建立；当前准备不改变已有支持范围。
2. **环境就绪门槛**：真实客户端可安装并登录，记录安装位置、实际GetBuildInfo、项目标识、语言、目标产品来源及加载情况。Interface数字、目录名或单个常量不能独立证明目标识别正确；缺少识别依据时保持待确认。
3. **新角色采样门槛**：1级角色只验可读身份、基础事件、已有背包／装备与样本保存。未学习专业、没有收藏、未访问邮箱／银行等均记录前置条件，具备后再测；空返回、接口存在与业务支持分别判定。
4. **身份与数据范围门槛**：通过重载／重登核对身份稳定；角色独立、账号共享与规则集隔离需要各自对照样本。探针阶段使用自身样本引用，不作为正式Core角色ID；范围未知时保持隔离，不能按显示名或传统Realm猜测合并。
5. **业务适配门槛**：一个来源先取得有对象、有变化、有时效／覆盖边界的真实样本，再明确最小公开契约。Core先验证身份、保存与通用页面，一个业务来源先形成闭环；其它插件按实际解锁条件推进，TaskHub消费已验证来源。操作型增强另验原生限制与安全条件。
6. **证据门槛**：每个结论携带构建、角色条件、采样范围、时间、原始结果类型、状态与复测触发。静态检查、模拟返回和其它目标的成功记录作为开发证据，与无限实机结论分开登记；一次样本不能外推整个账号、全部专业或全部规则集。
7. **生命周期与发行门槛**：客户端更新或若发生删档时保留旧样本的构建与阶段，按影响范围重新确认，不跨环境自动复用进度。正式数据迁移须单独设计与验证；构建配置按实际已有实现及客户端元数据登记，保留开发／待验证标记。目标实现、实际加载、数据隔离及必要实机验收完成后，才升级兼容声明与发行状态。业务仍按本文既有数据所有权与能力协作规则接入。
