# Yibo 多版本开发规则

> 状态：已确认
>
> 适用范围：Yibo 系列插件面向多个客户端、资料片、规则集或产品目标的适配、开发、测试和发行。
>
> 目标：在同一代码仓库内复用稳定的产品逻辑，同时隔离不同目标的 API、数据目录和发行包，避免版本条件分支扩散到共享业务代码。

## 一、最终方案

Yibo 的多版本插件采用以下模式：

- 一个 Git 仓库；
- 一个插件项目；
- 一套共享架构；
- 每个受支持的产品目标各自拥有适配层和数据层；
- 各客户端发布独立安装包；
- 不复制维护三套完整源码；
- 不使用一个包含所有客户端代码的正式玩家发行包。

“同一插件项目”指源码、问题跟踪、版本历史和 CurseForge 项目可以共用；“独立安装包”指每个 zip 只包含一个目标客户端实际需要的 TOC、Lua、数据和资源。

## 二、目录命名

目录按 Yibo 实际支持的产品目标命名，不照搬客户端内部的 `Classic`、`Mainline` 等实现分类。当前示例目标为 `Retail`、`Mists` 和 `Forever`；未来新增目标直接使用其产品名称或仓库约定名称。

标准目录结构：

```text
YiboMounts/
├─Common/
├─Retail/
├─Mists/
├─Forever/
├─<FutureTarget>/
├─YiboMounts_Retail.toc
├─YiboMounts_Mists.toc
└─YiboMounts_Forever.toc
```

目录含义：

- `Common/`：跨目标客户端稳定复用的代码；
- `Retail/`：正式服专用代码与数据；
- `Mists/`：熊猫人之谜经典版专用代码与数据；
- `Forever/`：无限专用代码与数据；
- `<FutureTarget>/`：未来新增产品目标的专用代码与数据。

不得新增无实际产品意义的中间层，例如：

```text
Flavor/Mainline/
Flavor/Classic/
```

客户端的内部实现分类只允许出现在 TOC、能力探测或构建配置中，不作为业务源码目录命名。

## 三、共享代码规则

共享代码只依赖 Yibo 定义的稳定业务接口，不直接依赖某个目标的专用 API、ID 或规则。

适合放入 `Common/` 的内容包括：

- 数据模型；
- 账号与角色快照结构；
- 状态模型和状态格式化；
- 账号矩阵、表格和 Tooltip 布局；
- 排序、过滤和分页；
- 设置页面；
- Core 注册与页面生命周期；
- 通用诊断和错误处理；
- 目录查询和来源格式化。

共享代码不得散布如下形式的版本判断：

```lua
if isMists then
    -- Mists API
elseif isForever then
    -- Forever API
end
```

少量版本选择只能出现在运行时入口或 Core 能力层。业务代码应调用统一接口，例如：

```lua
local info = Addon.Runtime.API:GetMountInfo(mountID)
```

而不是直接调用某个版本的原始 API。

## 四、客户端适配层规则

每个目标目录负责把目标客户端 API 转换成共享层可使用的统一接口。

示例：

```text
Mists/
├─API.lua
├─Data.lua
└─SourceFacts.lua

Forever/
├─API.lua
├─Data.lua
└─SourceFacts.lua
```

适配层负责：

- 客户端 API 调用；
- API 参数和返回值转换；
- API 缺失、延迟和错误处理；
- 版本专用事件；
- 版本专用 ID；
- 版本专用数据读取；
- Secret Values、保护调用和现代 Tooltip 等限制的降级。

适配层向共享层提供稳定语义，例如：

```lua
API:GetCharacterIdentity()
API:GetCurrency(currencyID)
API:GetReputation(factionID)
API:GetMountInfo(mountID)
API:GetCollected(mountID)
```

如果两个客户端当前恰好使用相同 API，也仍应优先通过适配接口调用，以便后续客户端更新时集中修复。

## 五、数据目录规则

版本专用数据必须放入对应产品目录，不得把不同客户端的 ID 混入共享目录。

例如：

```text
Mists/
├─MountCatalog.lua
├─CurrencyCatalog.lua
└─SourceFacts.lua

Forever/
├─MountCatalog.lua
├─CurrencyCatalog.lua
└─SourceFacts.lua
```

共享层只定义数据结构和查询协议，不定义具体客户端的：

- NPC ID；
- 任务 ID；
- 货币 ID；
- 坐骑 ID；
- 声望 ID；
- 配方或物品 ID；
- 区域和地图 ID；
- Boss 锁定 ID。

数据目录应优先使用稳定的业务 ID，并保留来源客户端、内容版本和验证状态。

## 六、TOC 规则

每个支持的目标客户端提供独立 TOC：

```text
YiboMounts_Retail.toc
YiboMounts_Mists.toc
YiboMounts_Forever.toc
```

每个 TOC 必须：

1. 声明目标客户端实际的 `Interface`；
2. 使用目标客户端实际认可的 flavor 元数据；
3. 只引用 `Common/` 和对应产品目录中的文件；
4. 不引用其它产品目录的实现文件；
5. 在客户端实际 Beta 或实机环境确认后再标记为正式支持。

新目标的 Interface 数字和 flavor 标识在 Beta 或实机环境确认前不得凭空写死。不能因为两个目标采用相近的 UI 架构，就直接假定它们可以共用 TOC。

根目录是否保留不带产品后缀的默认 TOC，必须根据实际客户端加载行为决定。若默认 TOC 可能导致错误客户端加载错误代码，应删除或只作为经过验证的兼容回退入口。

## 七、构建与发行规则

构建脚本按产品目标接收参数：

```powershell
.\Tools\Build-ReleasePackages.ps1 -Addon YiboMounts -Target Mists
.\Tools\Build-ReleasePackages.ps1 -Addon YiboMounts -Target Forever
```

构建脚本必须从目标 TOC 读取文件清单，而不是复制整个源码目录。

每次构建必须执行：

1. 解析目标 TOC；
2. 复制 TOC 引用的文件；
3. 检查所有引用文件存在；
4. 检查未引用的其它产品目录没有进入发行包；
5. 复制目标版本所需资源；
6. 运行目标版本的 Lua 语法检查；
7. 运行目标版本的目录和清单校验；
8. 生成目标版本安装包；
9. 输出包内文件清单和目标客户端信息。

推荐产物命名：

```text
YiboMounts-v0.7.0-retail-curseforge.zip
YiboMounts-v0.7.0-mists-curseforge.zip
YiboMounts-v0.1.0-forever-curseforge.zip
```

版本号可以按产品目标独立递增。无限尚处于 Beta 或首发准备阶段时，不要求与 Mists 使用同一版本号。

## 八、发布平台规则

同一个 CurseForge 项目可以发布多个目标客户端文件，但每个文件必须准确标记其实际支持的游戏版本。

正式发行优先采用 RareScanner 式分发：

- MoP 用户下载 Mists 包；
- 无限用户下载 Forever 包；
- Retail 用户下载 Retail 包；
- 不要求用户下载包含其它客户端代码的通用包。

一个 zip 同时包含多个 TOC 的方案仅用于内部测试、开发者包或确有必要的简单插件。它不是 Yibo 多版本正式发行的默认方案。

## 九、Core 与业务插件规则

### YiboCore

YiboCore 必须提供统一的运行时和能力层，至少负责：

- 当前目标客户端识别；
- Interface 和能力探测；
- 角色身份适配；
- 账号、规则集和角色范围；
- 数据领域存储；
- 统一 UI 与页面注册；
- flavor 相关诊断。

当某个目标采用无传统 Realm、按规则集划分生态或其它非传统角色范围时，Core 不得继续把 Realm 作为唯一范围维度。对应适配应支持该目标的账号共享数据、规则集边界和独立进度语义。

### 业务插件

业务插件必须：

- 通过 Core 的统一接口注册；
- 通过适配层读取客户端数据；
- 通过自身产品目录保存业务数据；
- 不在共享页面代码中直接判断多个客户端 API；
- 不重复实现 Core 的角色目录、窗口、入口和范围选择。

## 十、各插件特殊规则

### YiboMounts

从无限首发开始建立 `Forever/` 坐骑目录，后续按内容补丁追加坐骑和来源。

不要把无限坐骑与 MoP 历史坐骑混合到同一份运行时目录中。坐骑 Tooltip、目录查询和缓存框架可以共享，坐骑 ID、来源事实和收藏 API 必须按产品目标隔离。

### YiboBeastPaths

YiboBeastPaths 的业务内容是潘达利亚隐藏猎人宠物路线。

当前只维护：

- Mists 包；
- Retail/Mainline 包中已经验证的内容。

除非无限未来明确加入对应宠物与路线，否则不得创建 `YiboBeastPaths_Forever.toc`，也不得在 CurseForge 中宣称支持无限。

### YiboTodo

MoP 的诺米、半山农场和 MoP 专业冷却不得直接作为无限内容复用。无限应新增独立的专业、营地、Blueprint 和 Legacy Challenge 数据目录，但可复用待办状态模型、冷却模型和账号矩阵。

### YiboBuilds

装备、天赋、雕文、专精和幻化读取必须通过产品目标适配层。不得把 MoP 的固定插槽、雕文数量或天赋结构假设放入共享模型。

### YiboQuestBlocker

新目标默认采用保守模式。自动接任务、自动拒绝、自动放弃和第三方自动化插件适配必须在目标客户端实际验证后单独启用，不得因为另一个版本可用就默认迁移。

## 十一、测试规则

每个产品目标都必须拥有独立测试矩阵：

```text
YiboMounts/
└─_NonRelease/Tests/
   ├─Mists/
   ├─Forever/
   └─Retail/
```

至少覆盖：

- TOC 加载和引用完整性；
- Lua 语法；
- API 能力探测；
- 当前角色采集；
- 离线角色快照；
- SavedVariables 迁移；
- 账号范围和角色范围；
- 未知、延迟和错误状态；
- `/reload`；
- 入口、页面和悬停预览；
- 目标客户端的保护 API 和战斗锁定行为。

任何一个目标客户端未完成实机验证时，只能标记为开发版或 Beta 支持，不得在发布说明中写成正式兼容。

## 十二、新目标迁移顺序

新插件适配无限时，按以下顺序实施：

1. 把现有 MoP 逻辑识别并收拢到 `Mists/`；
2. 把跨版本的 UI、模型和业务协议提取到 `Common/`；
3. 建立目标目录和目标 TOC；
4. 实现目标 API 适配层；
5. 建立目标数据目录；
6. 为目标添加独立测试；
7. 修改构建脚本支持目标参数；
8. 生成只包含目标文件的发行包；
9. Beta 实机验证后再发布正式支持。

不得先复制整个插件目录再分别修改两份。若两个版本已经出现重复业务代码，应优先回收稳定部分到 `Common/`，将差异收敛到目标目录。

## 十三、验收标准

一个插件完成多目标适配，必须同时满足：

- 共享代码中没有散落的客户端 API 分支；
- 每个目标客户端拥有独立 TOC；
- 每个正式发行包只包含目标客户端代码和数据；
- 版本专用 ID 没有进入共享目录；
- 目标客户端的 API 能力经过实机验证；
- SavedVariables 不会因不同产品目标互相污染；
- CurseForge 文件标签与实际支持目标一致；
- 未验证的目标不会写入正式兼容声明；
- 后续内容更新只需要修改对应产品目录和构建配置。

本规则文档是 Yibo 后续所有多版本开发、构建和发行的统一约束。若未来需要增加新的客户端、资料片、规则集或产品目标，或改变目录命名、分包策略和共享层边界，应先更新本文档，再实施代码变更。
