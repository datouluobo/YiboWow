日期：2026-10-09。状态：**运行代码与自动化已完成，客户端待验收**。用户暂定紧凑 v2 并要求相邻区域共用一条线，已恢复开发。版本：TaskHub 0.1.0、Todo 1.1.3、Core 工作树 1.10.0 / API v11；未提交、未推送、未发布。

## 实际交付

- YiboTodo 注册 `action.todo` v1.0 Provider `YiboTodo:profession-cooldown`，输出当前已纳入自身监控的神纹布冷却。Query 要求显式 `scope.characterIDs`，空范围不扩为账号；coverage 按角色 ID 给出已知、明确无工作、未观察、部分与过期。
- 来源复用自己的 Model/Snapshot／State／Schedule 和观察记录。groupID、配方与产物信息见 [O1 映射](行动中心-O1-专业冷却字段映射.md)。现有模型未观察时为 unknown；未学习为 unknown 加 recipe-unlearned 原因。中心不建立自己的冷却判断。
- 冷却可用只输出 preparation；冷却中保留 active + blocked，跨来源重置变为 stale + unknown。观察时间只取该冷却组真实记录，不借用另一配方扫描时间。技能不足和未学习保留理由；图中制造／物流例子未进入真实业务输出。
- `YiboTodoDB.actionTodo` 保存 sourceEpoch、单调 revision 与可再生投影指纹元数据；epoch 在数据库新建时生成并持久保存。同一来源快照在时效边界前复用内存投影；数据或周期变化更新 revision。元数据既不拥有冷却事实，也不保存第二份可编辑任务。
- 来源变化先提交投影 revision，再发 Core CHANGED；同帧变化合并，查询先提交 revision 也不会吞掉后续失效通知。直接制作单图标快速刷新路径同样通知中心。Snapshot 对已观察的零冷却也安排日常边界刷新，避免源页面仍显示旧的可制作、中心已显示过期；测试覆盖来源模型同步转 estimated。
- TaskHub 先订阅再发现，按兼容契约调用 Query；来源错误只影响自身。注销立即清掉其缓存。查询与投影不广播同一变化，缓存只留内存。按来源声明的 nextChangeAt／validUntil 安排定时失效。
- 任务身份由 capability、providerID、epoch、itemKey、cycleKey 组成；按执行角色投影，受益者不自动成为执行者。共同候选与重复记录只计一份唯一工作，来源完成后全部投影同步移除。
- Core 中注册 `taskhub` 页面与 `yth` 入口；主命令 `/yth`，刷新 `/yth refresh`。注册前已搜索全工作区 SLASH_*，没有该命令冲突，无旧别名。TOC 只强依赖 Core。
- 主页面共用表头，当前角色在前、其他角色在后，来源筛选只改变投影。任务单行；行只绘制一条底部分隔线，连续区域不各自画外框。高度不足按实际可用高度分页，显示当前／总页与剩余行，复用 Core 窗口、范围和角色排序。
- 自有数据库仅保存展示设置；页面与入口仍由 Core 托管，无业务设置内容时不创建空设置页。O2 `previewEnabled=false`，正式悬停、HUD、提醒仍在 O4。

## 客户端下一步

已核对 Core、Todo、TaskHub 三个 AddOns 目录均为指向本工作区的 Junction。新增 TOC 文件后完整退出并进入游戏，启用三个插件，使用 `/yth`：

1. 对已监控且专业适用的角色核对神纹布与待办页面的源状态、观察时间和周期。开专业界面前为待核实；确认冷却可用后显示准备，实际制作后转冷却等待。
2. 切换角色，核对当前角色与其他角色列表归属、全服务器／单服范围与短名显示；重载后不重复计量。
3. 关闭神纹布监控，确认中心退出该项；无来源、明确无工作、专业未采集分别提示。
4. 拖小窗口，验证单行、省略文字与详情提示可读，分页与底部状态不裁切；检查每处相邻行／分区边界只有一条线。
