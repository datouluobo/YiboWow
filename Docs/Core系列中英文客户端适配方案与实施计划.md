# Core 系列中英文客户端适配方案与实施计划

## 1. 文档状态

- 状态：已确认，待实施
- 目标版本：后续 Core 版本及业务插件渐进迁移版本
- 适用范围：`YiboCore`、所有依赖 `YiboCore` 的业务插件，以及后续独立适配的 `YiboBeastPaths`
- 方案原则：Core 先完成语言基础设施和公共界面重构；业务插件按“新增即遵循、触及即迁移、达到阈值后收尾”逐步适配

## 2. 目标与完成标准

### 2.1 目标

在不破坏中文客户端现有体验的前提下，使 Yibo 系列插件在中英文客户端中均可正常使用：

- `zhCN`、`zhTW` 客户端使用中文资源。
- 其它客户端语言使用英文资源。
- 正式版本自动跟随 WoW 客户端语言。
- 英文翻译缺失时安全回退到中文。
- 非发布探针可以强制预览中文或英文，并报告缺失英文资源。
- 业务数据使用稳定 ID 与显示文本分离，避免本地化文本成为数据主键。

### 2.2 “正常使用”的边界

英文客户端的关键日常路径必须完整可理解，包括：

- 页面标题、导航和字段名称
- 设置项、按钮、入口和常见操作
- Broker、小地图入口及悬停摘要
- 常用 Tooltip、状态、错误和确认提示
- 静态业务目录中的名称、分类和状态
- 英文文本下的窗口、表格、设置页和 Tooltip 布局

以下内容允许按渐进策略处理：

- 低频诊断和开发探针文本
- 已保存历史快照中的旧显示文本
- 玩家自定义短名、NPC 名称和其它自定义内容
- WoW API 返回的动态名称；只要求插件不额外覆盖其客户端原生语言

## 3. 语言策略

### 3.1 语言选择和回退

| 客户端语言 | 使用资源 | 说明 |
|---|---|---|
| `zhCN` | 中文 | 简体中文客户端 |
| `zhTW` | 中文 | 暂使用中文资源 |
| 其它语言 | 英文 | 英文作为海外客户端回退语言 |

正式版本不提供插件内语言切换设置，语言由客户端环境决定。开发和验收使用非发布探针提供强制语言预览。

### 3.2 翻译资源职责

- `YiboCore` 提供公共语言服务、语言判断、回退、格式化和缺失报告能力。
- Core 自己维护窗口、账号视图、设置工作台、入口和通用状态文本。
- 每个业务插件维护自己的页面、设置、状态、Tooltip 和静态目录翻译资源。
- 独立插件可以复用 Core 的语言服务；如果不接入，则必须遵循同一项目级规范。

### 3.3 文本与数据边界

- 稳定 ID、枚举值、数据库字段和业务状态不使用本地化文本作为主键。
- 静态业务目录保存稳定 ID，并按语言提供显示名称。
- 动态 WoW 数据优先使用客户端 API 返回值。
- 不为了语言适配迁移或重写历史 SavedVariables 中的玩家数据。

## 4. 项目级开发规范

### 4.1 新代码规则

- 新增玩家可见文本必须使用统一语言资源。
- 页面、字段、入口、设置项、状态和 Tooltip 必须能够在中文与英文资源之间切换。
- 新增静态业务目录必须使用稳定 ID，并提供对应显示文本。
- 不得使用中文显示文本作为数据匹配或持久化主键。
- 新增 UI 必须检查英文文本的自然宽度、换行和溢出。

### 4.2 触及即迁移规则

修改以下任一内容时，必须迁移该用户可见区域内的相关文本：

- 页面或页面注册元数据
- 设置区或设置控件
- Tooltip 或悬停摘要
- 状态生成器、错误处理和确认框
- 静态目录、字段定义或显示格式化逻辑

迁移边界以用户可见的 UI 或业务区域为单位，不要求每次修改都扫描整个插件。

### 4.3 兼容规则

迁移期间允许旧代码暂时保留直接字符串，以支持渐进推进；但：

- 新代码不得继续增加此类字符串。
- 被修改区域内的玩家可见文本必须一并迁移。
- 发布前检查必须报告剩余硬编码文本和缺失英文资源。
- 旧字符串只作为过渡，不作为新的业务插件接口。

## 5. 实施阶段

### 阶段 0：规范和清单

目标：在修改代码前固定语言边界和验收口径。

交付物：

- 本方案文档
- Core 公共文本清单
- 业务插件玩家可见区域清单
- 翻译 key 命名和资源组织规范
- 静态检查与发布前检查规则
- 中英文客户端验收清单

完成门槛：规范可以指导新代码，并能判断一个区域是否已完成适配。

### 阶段 1：YiboCore 完整重构

目标：让 Core 成为稳定的语言基础层和公共 UI 语言来源。

工作范围：

- 语言服务和当前客户端语言判断
- 中文/英文资源加载与回退
- 文本格式化和参数插值
- 非发布强制语言预览
- 缺失英文资源报告
- 账号总览和角色档案
- 统一设置工作台
- 页面导航、入口和范围控件
- Broker、小地图悬停
- Tooltip、状态、错误和确认框
- Core 字段、静态目录和公共元数据

完成门槛：

- Core 玩家可见文本全部接入统一语言资源。
- 中文客户端功能和显示回归通过。
- 英文预览覆盖 Core 公共页面和入口。
- 英文长文本不存在明显截断、重叠或横向滚动问题。
- 缺失翻译和硬编码检查可以生成报告。

### 阶段 2：检查与验收工具

目标：让语言规范可以持续执行，而不是依赖人工记忆。

检查内容：

- 新增或修改区域中的玩家可见硬编码文本
- 不存在的翻译 key
- 缺少英文资源的 key
- 静态目录缺少稳定 ID 或英文显示名
- 页面、字段、入口未接入统一语言资源
- 英文布局中的固定宽度、换行和 Tooltip 高度风险

执行方式：

- 开发阶段允许报告，不阻塞普通修改。
- 发布前必须查看并处理报告。
- 待整体迁移稳定后，再评估是否将关键规则升级为硬性门禁。

### 阶段 3：业务插件渐进迁移

不预先固定全部业务插件的迁移顺序。每次业务插件发生功能开发或维护时，按以下流程执行：

1. 识别本次涉及的用户可见区域。
2. 将新增文本接入语言资源。
3. 将被修改区域内的相关旧文本一并迁移。
4. 同步处理静态目录、状态、Tooltip 和错误提示。
5. 运行中文回归、英文预览和发布前检查。
6. 记录该插件当前适配覆盖度与已知例外。

该流程适用于 `YiboAltoBoss`、`YiboCurrency`、`YiboLegendary`、`YiboQuestBlocker`、`YiboReputation`、`YiboTodo` 及后续新增的 Core 业务插件。

### 阶段 4：单插件收尾

当某业务插件的英文适配达到约 80% 的用户可见覆盖度后，安排一次集中收尾：

- 补齐关键路径和常用操作。
- 清理剩余页面、设置、入口、字段和 Tooltip 文本。
- 完善静态目录和状态标签。
- 检查英文客户端中的窗口尺寸、表格宽度和换行。
- 在中文和英文客户端分别进行功能回归。
- 记录低频诊断、历史快照和自定义文本等允许保留的例外。

“80%”按用户可见区域加权计算，不按代码行数或字符串数量计算。关键日常路径必须达到 100% 才能进入收尾确认。

### 阶段 5：YiboBeastPaths 独立适配

`YiboBeastPaths` 不依赖 `YiboCore`，在 Core 生态稳定后单独评估：

- 复用 Core 语言服务；或
- 遵循同一项目规范并保留独立语言模块。

其独立 UI、路线数据和非发布调试工具按自身结构建立对应的文本清单和验收范围。

## 6. 验收策略

每个阶段使用三层验证：

1. 静态检查：发现硬编码文本、缺失 key 和缺失英文资源。
2. 非发布语言预览：快速检查中文/英文 UI、长文本和回退行为。
3. 实际客户端回归：验证 WoW 动态数据、页面交互、布局和保存数据兼容性。

### 中文客户端验收重点

- 现有中文文本没有异常变化。
- 页面、设置、入口、悬停和 Tooltip 仍可正常使用。
- 历史数据和用户自定义内容不被覆盖。
- 静态目录和动态 API 名称显示正确。

### 英文客户端验收重点

- 关键日常路径可完整理解和操作。
- 不出现明显的空文本、内部 key 或错误回退。
- 表格、按钮、设置页和 Tooltip 不截断或重叠。
- 静态业务目录使用英文显示名称。
- 动态 WoW 数据遵循客户端语言。

## 7. 风险与控制措施

| 风险 | 控制措施 |
|---|---|
| Core 改造影响全部业务插件 | 先完成 Core 公共 UI 和兼容接口，再推动业务迁移 |
| 英文文本导致布局溢出 | 使用文本测量、动态宽度、换行和中英文双端回归 |
| 业务插件长期停留在混合语言 | 维护区域清单、覆盖度和收尾状态 |
| 翻译 key 遗漏 | 正式版中文回退，非发布探针报告缺失项 |
| 历史数据被误迁移 | 只改变显示层，不改写历史 SavedVariables |
| 动态名称被错误翻译 | 优先使用 WoW API 返回值，不覆盖客户端原生名称 |
| 规范执行依赖人工 | 发布前检查报告，后续逐步增加自动化门禁 |

## 8. 后续执行顺序

当前只确定 Core 阶段和项目级规范。业务插件的具体迁移顺序不预先固定，待 Core 完成后，根据：

- 实际功能开发触及情况
- 各插件的用户可见区域覆盖度
- 静态检查暴露的问题
- 英文布局和动态数据风险

重新安排后续工作。

## 9. 方案结论

本方案采用长期渐进式本地化迁移：Core 先完成一次完整语言重构，建立稳定的语言服务、项目规范和验收工具；业务插件在新增或维护时按区域逐步迁移，并在达到约 80% 用户可见覆盖度后集中收尾。该方式优先保护中文客户端稳定性，同时持续提高英文客户端的可用性和完整度。
