# YiboCore、YiboVault、YiboMail 联合实施计划

> 状态：实施中；2026-09-28。Vault 背包、装备、银行、公会银行与 AH 已完成主要客户端检查，仓储页与 Tooltip 已有截图验证。Vault 自有邮箱附件采集通过自动测试，用户反馈邮件基础游戏内测试正常；大量邮件仅部分可见的边界仍待验证。YiboMail 尚未上线，双插件适配待其公开 API 可用后实施。首个实际调用方确定为 YiboCurrency。
>
> 范围：三个插件的开发顺序、跨插件契约、首轮集成与验收门槛。产品功能范围仍以 [Vault 产品方案](YiboVault-产品边界与开发路线图.md) 和 [Mail 产品方案](YiboMail-产品边界与开发路线图.md) 为准。

## 1. 目标与最终职责

| 插件 | 数据与功能所有权 | 对其它插件提供的能力 |
|---|---|---|
| YiboCore | 角色目录、服务器/角色范围、统一账号窗口、入口、设置工作台、角色缓存清理和中性角色事实 | 现有 Public API v6；角色与范围上下文、页面/入口/设置/清理注册 |
| YiboVault | 背包、装备、个人银行、公会银行及本人 AH 上架商品的物品/容量缓存；物品身份、汇总、角色仓储视图、搜索和 Tooltip | 版本化的只读物品查询、容器容量与变更通知；可选消费其它插件提供的物品来源 |
| YiboMail | 邮箱扫描、邮件快照和生命周期、附件/金币、到期状态及后续收发辅助 | 版本化的只读邮件与附件来源查询、状态及变更通知 |

Vault 的实体物品、AH 和精简邮箱附件快照保存在 `YiboVaultDB`；Mail 将在 `YiboMailDB` 保存自己的完整邮件快照。两插件可独立安装。双插件共存时，Vault 应优先消费 Mail 的公开附件接口，并按角色只选一份来源；Core 不保存业务快照。

### 技术边界决定

物品、容器容量及其聚合属于 Vault 的业务域：Core 提供账号页壳、角色目录、范围和通用 UI 能力，YiboVault 页面呈现仓储视图并持有来源数据；本轮不新增 Core 物品来源协议。Vault 已有独立邮箱附件来源；YiboMail 完成公开只读来源 API 后再接入更完整的邮件来源。若确有跨业务域共享的运行时能力缺口，再单独提出向后兼容的 Core 增量变更。

## 2. 开发顺序与依赖

| 阶段 | 前置条件 | 主要交付 | 完成门槛 |
|---|---|---|---|
| 0. 冻结契约与客户端边界 | 现有产品方案 | 物品身份、来源/状态、范围、事件及版本草案；Vault/Mail 游戏 API 验证记录 | 用示例数据能完整表达实体库存、AH 上架、邮件附件及未采集/不可用状态 |
| 1. Vault 基础缓存与首版 API | 阶段 0 的 Vault 模型 | 背包与装备采集、角色/容器局部更新、统一查询服务及只读物品查询 API；接入现有 Core 角色与清理接口 | 重复采集幂等，更新一个容器不改写其它位置；消费者能查询已缓存物品并区分已知空与未采集 |
| 2. Vault 来源与界面扩展 | 阶段 1 | 银行、公会银行、本人 AH 上架采集；Core 页面/入口/设置；全物品搜索与按角色的仓储/容量视图 | 储存区容量来自成功扫描元数据；背包与个人银行整合展示，容量/空位统计范围清楚；实体与 AH 小计可追溯 |
| 3. Mail 快照与公开来源 | 阶段 0 的 Mail 契约 | YiboMail 独立邮件扫描、状态/到期模型、Core 页面/悬停、`YiboMail.Items` 只读接口和事件；当前尚未启动 | 完成后达到 100 封可见边界、重复邮件、未扫描数量及生命周期规则验收；查询不暴露私有 DB |
| 4. Vault 与 Mail 共存 | Vault 自有邮箱来源、Mail 公开 API 完成 | 可选 Mail 适配器、来源能力检查与变更订阅；优先 Mail、回退 Vault 自有快照 | 同一角色邮件来源只计一次；Mail 不可用时 Vault 仍可独立采集 |
| 5. 实际消费者与稳定化 | Vault 阶段 1；首个消费者按 Vault API 可用性启动 | 首个调用方 YiboCurrency 从物品管理场景接入；之后再评估其它消费者；迁移/容量/缓存清理说明 | 消费者只调用 Vault 公共 API；币种计数与物品库存不重复累计；无需为了新查询逐个角色重新扫描已有缓存 |

YiboMail 是独立的后续工作流，目前尚未启动。Vault 邮箱附件来源已先行实现；Mail 完成扫描、页面和稳定只读来源 API 后，再实施 Vault 的提供者切换。消费者通过能力检查决定读取哪些来源。Mail 后续主动收件与发送辅助另按 Mail 产品方案推进。

- [Mail 客户端验证记录](../YiboMail/_NonRelease/Docs/Stage0-客户端验证记录.md)
- [Core API v6 增量接入指南](../YiboCore/Docs/API-v6-业务插件增量接入指南.md)
- [阶段 0 契约烟雾测试](../YiboVault/_NonRelease/Tests/Stage0ContractSpec.lua)
- [阶段 0 非发布客户端探针](../_NonRelease/YiboStage0Probe/README.md)

正式 Slash 命令已完成全工作区 `SLASH_*` 占用检查并冻结为 Vault `/yva`、Mail `/yma`。Vault 的精简邮箱附件采集已实现，仍须完成客户端验收；Mail 自身阶段一及双插件集成等待 Mail 阶段 0 剩余场景评审。

### 3.1 游戏客户端验证

- Vault 分别验证背包、装备、个人银行、公会银行、本人 AH 上架列表的读取条件、事件、刷新范围和未完整暴露情形。记录物品链接中哪些变体字段会影响“同一种物品”的判断。
- Mail 验证当前客户端收件箱的可见数量、总数、附件/金币/COD、剩余时间、退回标记和 AH 发票字段。不能读取的字段在契约中标为可选。
- 两端都记录角色、服务器、公会、容器/邮件的稳定标识和时间来源；不依靠尚未验证的客户端行为设计自动操作。

### 3.2 共享记录约定

来源记录至少包含 `sourceID`、`itemID`、可用时的完整 `itemLink`/变体身份、`quantity`、位置或来源匹配键、`observedAt`、`state`，以及可确认的所属角色或公会。角色来源携带 `characterID`；公会银行以公会/服务器/页签为位置身份，并记录访问角色但不按访问角色重复计数。Mail 来源再携带邮件匹配键、期限估算和待取状态；AH 来源单列上架数量及可读取的价格/期限。字段的最终名称、类型和可空规则在阶段 0 冻结。

接口区分以下语义：来源插件未加载、位置从未采集、来源暂不可用、已有陈旧缓存、成功采集且为空、成功采集且有记录。已知空只能由一次成功的对应位置/邮箱扫描得出。Vault 的玩家界面仍按产品方案只显示已缓存的记录，不将 API 状态直接变成缺失警告。

不同来源在不同时刻采集。阶段 0 还须定义汇总的时间语义及记录何时退出“当前已知”合计；物品从 AH、邮件转入背包时只能依据已确认的扫描或操作更新相应来源，不凭另一来源的变化推断它已消失。查询应保留来源时间，避免把跨时间快照误读为实时精确持有量。

### 3.3 两个公共接口草案

- **Mail 提供**：`YiboMail.Items` 的按角色/范围查询、来源状态查询、接口版本/能力查询及带 `characterID`、变更范围、`revision` 的通知。返回只读副本或不可变投影；同内容不重复广播。
- **Vault 提供**：按 `itemID` 或物品身份查询、按 Core 角色/服务器范围过滤、按实体/AH/邮件来源取明细与小计、状态/更新时间/`revision` 和变更订阅。调用方可区分物品 ID 汇总与严格变体汇总。
- 两端只约定公开结果，不让消费者读取 `YiboMailDB` 或 `YiboVaultDB`。接口版本与能力按提供者分别声明；Core 的 `API_VERSION` 不代替业务接口版本。
- Vault 阶段 1 的 API 先发布背包与装备来源；后续银行、AH 和 Mail 按能力增量加入，调用方可检查来源能力，无须等待全部采集器完成才开始消费 Vault。
- 阶段 0 明确范围参数的默认语义。跨插件后台查询优先显式传入服务器/角色范围；账号页面与 Tooltip 可从 Core 当前视图构造同一范围参数，避免查询结果随其它页面的选中状态意外变化。

### 3.4 接口分类与现有快照兼容

| 类别 | 本计划中的对象 | 兼容承诺 |
|---|---|
| 公共稳定接口 | Core Public API v6（现有）；Mail 的邮件来源 API、Vault 的物品查询 API（各自阶段验收后发布） | 明确版本、状态、结果与事件契约 |
| Core 接入点 | Vault/Mail 注册账号页、入口、设置与角色清理 | 遵循 Core 当前注册契约；注册回调不成为其它业务插件的数据 API |
| 插件内部实现 | 扫描器、SavedVariables 结构、Vault 的 Mail 适配器 | 不供其它插件直接依赖 |
| 规划接口 | 尚未完成阶段验收的来源能力与后续收发操作 | 标为规划中，不能写成当前可调用接口 |

Core 当前的 `economy-items` 只为已登记的货币物品采集角色计数，不能当作全量库存；YiboCurrency 已依赖它。本轮保留其现有行为，Vault 不把它再当一份物品来源重复相加。YiboBuilds 的装备快照还保存附魔、宝石和构筑状态；Vault 只采集物品资产所需的装备位置/身份，不能覆盖或替代 Builds 的业务快照。若未来让现有插件改用 Vault，须另立兼容迁移任务，先保证已有页面和缓存语义。

## 4. 各插件实施项

### YiboCore

1. 核对现有 Public API v6 的角色目录、页面、入口、设置、角色清理和事件接口是否足够支撑两插件。当前代码已有相应入口，先以现有 API 实现。
2. 补齐 API v6 接入文档：明确 `RegisterSettingsPanel` 与既有 v5 页面/入口 API 的关系，以及业务插件如何获得同一范围与角色顺序；标明公共稳定接口、Core 接入点与内部实现。
3. 只有出现经具体场景证明的通用缺口时才新增可选 Capability；保持 v5/v6 的既有语义与旧插件兼容。

### YiboVault

1. 建立 SavedVariables schema、迁移与角色/容器局部更新规则；公会银行按公会和页签标识管理，避免将其误记为角色个人资产。
2. 建立一套物品身份、数量汇总和位置查询实现，供主窗口、Tooltip 和公开 API 共用；实体库存、AH 上架和邮件待取数量分别可核对。背包/装备采集稳定后先发布只读 API，后续来源按能力增量扩展。
3. 通过 Core 注册账号页面、设置和入口。入口点击打开主页面；按产品方案不展示入口库存悬停。
4. 完成 Core 账号工作台中的全物品搜索与按角色仓储/容量视图；Core 提供页面壳和角色上下文，Vault 提供物品来源数据及按储存区聚合的容量摘要。背包与个人银行分别整合展示，不要求用户按包或格子浏览。
5. 在 Tooltip 编码前，先设计并评审 Yibo 自有的样式与信息规则，参考 Altoholic、BagSync 的信息组织但不复刻；之后再接入同一 Vault 查询服务。
6. Vault 自行采集可见邮箱附件，并将其作为 `external` 来源。等 YiboMail 交付稳定只读附件 API 后，再做可选 Mail 适配：检测版本/能力、按角色切换来源、订阅变更；Mail 不可用时回退 Vault 自有快照，不把未扫描邮箱计为已知零。
7. Vault API 可用后，让首个真实消费者 YiboCurrency 从其物品管理场景接入；明确货币计数和可堆叠物品库存的分工，避免重复累计。已有 Vault 缓存应直接可查，无需消费者触发重扫。

### YiboMail

1. 建立邮件匹配、扫描覆盖、状态迁移与归档模型。相似邮件不能凭主题或发件人静默合并；邮件消失不能自动推断收取或退回。
2. 在玩家打开邮箱时采集当前客户端可见邮件；记录可见数、游戏返回总数、未扫描数量和扫描时间，明确 100 封可见边界。
3. 通过 Core 注册邮件账号页、悬停预览、设置和角色缓存清理。主页面与预览使用同一份邮件快照和状态判断。
4. 发布只读 `Items` API；Vault 使用该接口消费待取附件，Mail 自身不依赖 Vault。后续收取/发送改变来源时按同一事件契约更新。

## 5. 集成验收场景

1. 仅安装 Vault：已采集的背包/装备/银行/AH 和邮箱附件记录均可查询；未打开过的邮箱保持未扫描状态。
2. 仅安装 Mail：邮件扫描、主页面、悬停和附件 API 可独立使用。
3. 同时安装：Vault 对每个角色只采用一份附件来源，优先兼容的 Mail 公共来源；同一附件不因两套缓存而重复计数，实体小计不含邮件附件或 AH 上架。
4. Mail 再次扫描、收取或归档后，Vault 对相关物品刷新；无变化时不产生重复通知或重复附件。
5. 删除角色缓存后，两插件各自清理该角色数据；账号级设置、联系人和与角色无关的规则保留。
6. 已缓存角色可以被 YiboCurrency 直接查询；未登录或未访问过的位置不被解释成零库存。
7. Mail 当前只暴露部分邮件时，Vault 只能汇总已扫描附件；不能把游戏返回总数当作附件明细或完整库存。
8. 同一公会银行页签由多个角色访问后仍只计一次；不同时间采集的 AH、邮件、背包记录各自保留时间，汇总不声称是实时库存。
9. Core 的货币物品计数与 Vault 库存不能重复相加；Builds 的装备构筑快照及现有显示不因 Vault 扫描而改变。

## 6. 文档同步与阶段交付

- [Mail 产品方案](YiboMail-产品边界与开发路线图.md) 与 [API 与能力总览](Yibo插件API与能力总览.md) 已同步本计划的职责边界；阶段 0 冻结字段和方法名时继续更新两处接口细节。
- 每个公共 API 发布时提供独立接入说明：版本、能力、参数、结果示例、状态与错误语义、事件、兼容策略。内部 Lua 函数或全局命名空间不自动成为公共 API。
- 每阶段在目标客户端完成其产品方案列出的场景验证，再进入依赖它的下一阶段；客户端 API 未验证的字段不写成稳定保证。

## 7. 本轮完成定义

Vault 已能通过公共 API 查询自己采集的实体库存、AH 上架与精简邮箱附件，并把来源与小计分清；Mail 将可独立展示邮件并提供版本化只读附件来源，双插件共存时按角色择一；Core 提供一致的角色范围、入口和设置体验；至少一个实际消费者只通过 Vault 公共 API 读取已有物品缓存。主动收件与发送辅助仍按 Mail 后续阶段实施。
