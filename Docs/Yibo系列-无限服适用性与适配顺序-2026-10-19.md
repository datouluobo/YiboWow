# Yibo 系列：无限服适用性与适配顺序

2026-11-04 用户确认无限服11月5日上线后的发布节奏：第一批Core；第二批其它已完成适用验证的插件；第三批仍缺验证但低等级角色有用／可用的插件或功能，先补验证再发布；其余随等级与相关内容解锁逐步验证上线。已有六个业务目标均按实际证据进入相应批次，不因局部通过统一记为可发布。Core首批及四个取证探针的用途、批次准入与范围见[开服分批发布计划](无限服-开服分批发布计划-2026-11-04.md)。本次仅文档排期，不更改实现、验收结论或实际发布状态。

分析日期：2026-10-19（北京时间）。状态：**适配顺序与分阶段安排已获用户确认**；无限特有系统的具体契约与实现范围仍须按实机证据确定。依据当前源码、目标 TOC、探针样本、分插件实施记录、用户观察与官方产品资料；本轮未运行游戏、修改运行代码或执行发行。

## 结论

15 个插件中，12 个有明确的产品适用方向；YiboQuestBlocker 属于需求较窄的可选工具；YiboLegendary 等待本服路线证据；YiboBeastPaths 当前潘达利亚路线不适用。产品适用不等于当前包可用。

截至2026-10-20，Core、Builds、Crafting、Vault、Mail、Currency、Reputation存在Forever独立清单。Core0.2.0新增专业档案，Crafting0.1.1配方采集实机失败待诊断；Builds0.1.0装备最小版待实机；Currency金币正值与中文页面、Reputation0.1.1等级与进度条已获实机确认。各插件范围、剩余项及可发布状态统一见[无限服台账](无限服适配与发布验收台账.md)。本页维护适用性与顺序，不把窗口框架外推为跨角色或共享业务已完成。

已确认主线：**Core／Vault／Mail 现有范围验收 → Currency 最小版 → Reputation → Crafting → Builds 完整构筑 → AltoBoss → Todo → Mounts → TaskHub**。Builds装备最小版可在Crafting前插入；AutoOpen有真实容器样品后可以提前开发。基础功能优先，后三项业务随升级逐步取证，**以角色达到满级时完成AltoBoss、Todo、Mounts适配为交付目标**；低等级阶段不强行安排缺少业务对象的调试。

TaskHub等大部分业务插件的范围、数据模型与契约稳定后集中接入。QuestBlocker、Legendary待角色满级后，再根据实际用途决定是否适配。BeastPaths维持既有适用范围。

## 已确认实施顺序与进入条件

### 第一阶段：完成已有实现的验收

Core → Vault → Mail／Vault 联动。先验证原生清单选择、当前GUID、独立存档与重载／重登恢复，再逐来源验证银行、邮件、本人AH与可查看公会银行。真实系统暂不可访问时保留待验，不反复写实现，也不要求等待所有系统解锁才推进其它插件。

Mail这一轮只读；以后恢复收取、发送、规则寄件、收件人匹配与在途时，作为后续操作阶段逐项验收。Core和Vault的最小实现同样不能当作跨角色业务已完成。

### 第二阶段：低等级即可取得收益

1. **Currency最小版**：先金币、独立保存与当前角色展示，再按真实对象增加货币。物品代币若复用Vault，先提供并验证所需计数能力；Forever当前未支持 GetPersonalCounts，不能直接套用Mists调用。
2. **Reputation**：有正向阵营数据与变化后，优先适配已发现声望，不先复制整套MoP目录。
3. **Builds装备最小版（可插入）**：若当前需求是装备查看，可利用已有装备正向样本先交付；不为提前上线同时实现完整天赋／增强。

把Currency提前是基于最小版可验证性；完整账号货币与共享汇总不属于这个低成本范围。Reputation与装备最小版可按玩家当前需求互换。

### 第三阶段：专业与角色成长

**Crafting → Builds完整构筑**。先在Core补齐真实需要的通用专业档案采集，再由Crafting拥有配方、学习状态与制造业务。以一门已学专业和可核对配方开始，不把未知配方当未学。

Builds的完整适配须先核实无限天赋／专精模型，再接入装备增强判断与允许操作。不能把有 C_ClassTalents／C_Traits 候选接口视为已支持当前结构。商业技能差异、天赋树与传承的具体核验项见下节。

### 第四阶段：副本、周期与收藏

**AltoBoss → Todo → Mounts** 为默认后续顺序。真实副本与锁定出现后推进AltoBoss；有可观测冷却／活动并能跨周期验证时推进Todo；坐骑收藏和来源资料齐备时推进Mounts。任一项条件先满足都可提前，不以固定角色等级排死顺序。

三项均为明确要做的插件，低等级阶段用途和调试样本有限，随升级分批取得证据；完成节点为角色达到满级时。升级过程中需检查剩余目录、真实锁定／冷却／收藏样本及跨周期验收，提前安排取样，避免把全部工作留到满级后。若实际系统尚未开放或样本不足，明确记录受阻范围与补验条件，不能将未验收项记为完成。

### 第五阶段：业务稳定后的行动中心

TaskHub等大部分业务插件定下来后再接入。接入来源必须完成“目标添加、身份与范围、进度、完成、失效”契约验证；当前Forever的Vault只读库存契约和Mail只读收件箱并不自动满足目标条件。各业务开发时保留清晰所有权与公开注册边界，TaskHub阶段基于实际稳定契约实现，不预建空目标模块。复杂任务链仍是独立后续范围。

### 可提前项目与满级后决策

AutoOpen有真实容器样品后可提前开发：先确定允许目录、打开条件和失败行为，再实机验证操作，不必等其它业务插件完成。QuestBlocker、Legendary满级后评估实际意义再决定，不纳入满级前必须完成清单。BeastPaths不排入现有功能适配清单。

## 无限特有系统的适配要求

### 商业技能与Crafting

按无限自己的专业、配方和制作条件建立目标模型。官方介绍已明确新增配方、营地设施及专业制作场所；具体可用内容与接口以当前build实测为准。适配时至少核对专业身份／等级／上限、配方ID与学习判定、材料／产出、制作场所／设施要求及冷却。配方已学、当前满足制作条件、当前可制作数量分别表达，不能仅由已学状态推出可制造。

Crafting拥有配方与制造规则；Core只提供实际需要的通用专业档案。涉及营地设施的“共享冷却”还须核对共享发生在技能、设施、角色还是账号范围，不能从措辞直接推定所有角色共用冷却。Todo负责经核实的周期判断；Builds若展示专业增益影响，消费明确的公开契约。

### 职业天赋树与Builds

用户已观察：无限采用天赋树，与MoP不同；视觉样式部分接近正式服，实际结构看起来更接近60—80级版本。该观察作为适配方向，节点、等级、前置、点数、重置／切换等业务语义尚须目标样本核验。

Builds按无限实际节点和连接关系、节点等级、已投入／可用点数、前置与解锁条件保存和展示快照。界面相似不能作为套用正式服数据结构的依据，也不能只按旧版天赋API实现；树标识、节点标识和刷新事件应由实际接口确认。先做只读快照与变化验证，操作能力单独确认。

### 传承：账号共享成果与角色独立分配

官方深度解析明确：传承点数由账号下角色共享，但每个角色可在自己的传承树中独立分配。因此应拆成账号层面的点数／挑战与奖励进度，以及角色层面的传承天赋选择；各项实际范围、可读取性和重置行为继续实测。跨规则集共享存在专家模式边界。

传承后续纳入Builds属于已记录的候选方向，尚未确定实现范围。若其角色分配成为Builds构筑的一部分，可由Builds承担相应业务；账号挑战／奖励是否也归该插件，待真实需求确定。Core只承担通用身份、范围与连接，不因传承账号共享而接管其业务规则，也不提前创建占位服务。

### 共享能力与资源的逐项核验

用户观察到无限有更多账号共享能力／资源，将其列为每个业务适配的必查项。各类事实分别记录：权威所有者、共享主体、角色适用条件、规则集／阵营等边界、读取来源、观察时间、失效与重置方式。区分共享获得、角色独立分配、角色使用资格及实际可转移资源，不能用一个accountWide标记概括。

已确认共享的事实只保存和计数一次；角色视图可以显示该共享事实对本角色的适用情况，独立分配仍按角色保存。共享范围未确认时保留未知或当前角色范围，不把相同显示值自动合并。该核验随具体业务实施，不预先建立统一共享业务数据库。

## 所有阶段共同的边界

- 角色记录关联使用Core公开GUID；规则集未知不阻塞当前角色功能，但跨角色查询、可交易范围和账号共享须分别证明。离线可查看不等于可互寄、可合并或可共同完成。
- 官方规则说明收藏／传承存在跨规则集共享和专家模式单向边界；这不能推导库存、邮件、声望也共享。传承点数也不能未经业务核验直接归为可消费货币。
- 新目标继续使用独立存档与目标策略。Core能力最低版本、版本不足提示与停止行为、中英文资源、统一设置／入口和主窗／预览同源均按仓库约定实施。
- 每个插件逐项标注代码实现、离线验证、实机验收、发行状态；API存在、空结果或模拟通过均不能替代目标客户端业务验证。
- 每次业务适配固定当时满足验证要求的Core能力基线，审查实际触及范围并更新公共能力迁移台账。业务规则仍归业务插件，不借跨版本适配迁入Core。
