# Core 触及即迁移执行审查

日期：2026-10-08。范围：Core 1.8／1.9 合并更新及当前业务配套工作树；另列一项规则生效后的较早提交旁证。审查阶段只登记源码证据；后续用户确认保留触及即迁移，并已在 AGENTS 加入修改收尾时的 diff 核对。未改运行代码。

## 结论与计数口径

目前有多处按规则正确迁移的实例，不能因为台账尚有待迁移项就判定 AGENTS 没有生效。当前配套工作树发现 **1 处调用层触及后仍保留本地实现的漏迁项**，位于 Crafting 角色名称 Tooltip；另确认 **1 处较早的已提交漏迁**，位于 Crafting 搜索框，发生在规则加入之后、Core 1.8 之前，不混入本次 Core 1.8 后的统计。

严格按提交时间判断：当前 HEAD 为 1ef9ccf，Core 1.8／1.9 首次合并进入该提交；该提交仅改 Core，之后没有业务提交。业务配套改动仍未提交，因此不能宣称已经发现“1.8 发布后某个业务提交违规”，也无法用 Git 精确确定每个未提交 hunk 的实际编辑时间。下方 F01 是当前配套改动的源码执行缺口，F02 是具有明确提交时序的历史执行缺口。

这说明触及即迁移有实际执行效果，但执行存在遗漏。集中迁移可作为减少遗留范围的排期方式；不能把尚未触及的代码数量当作该规则失败率，也不因本次漏迁推导必须全仓库改造。

> Core 已提供满足需求的公共能力后，新增代码和本次修改涉及的同类逻辑必须复用该能力，迁移范围内的重复实现应同步收拢。

本轮采用以下边界：

- 以实际 diff 中的新增／修改调用和其直接承担的逻辑为触发，不以“文件名出现在 diff 中”或“插件有新版本”作为触发。
- 同一文件中没有修改的另一套名称函数、输入构造、设置壳或依赖声明不自动进入范围。忽略 CRLF／LF 和行尾空白差异，避免把换行转换当代码触及。
- 修改身份名称的 Tooltip 显示调用属于名称显示路径触及；即使只是修正 Tooltip API 参数，调用直接使用的本地名称组合仍在相关范围。F01 按这一调用层口径登记；没有要求顺带迁移整个 Crafting 页面。
- Core 未实现的语言服务、完整 Provider、通用调度或网络协议不触发运行时接入要求；内部函数不能假定为公开能力。
- 最低版本较低不自动违规；复用旧公开接口而没有新能力需求，不需要机械提高到 api10。只有实际新接入才检查相应最低版本／能力。

## F01：当前 Crafting 角色名称 Tooltip 调用触及后未迁移

关联 CAP-001。证据：[AccountPage.lua:630](../YiboCrafting/AccountPage.lua)，Page:RenderMatrix 中的角色列头 OnEnter。

当前 diff 的实际修改：

```lua
-- HEAD
GameTooltip:SetText(CharacterName(character, context), 1, 1, 1, true)
-- 工作树
GameTooltip:SetText(CharacterName(character, context), 1, 1, 1)
```

该调用直接生成角色名称提示，仍经过 [CharacterName:59](../YiboCrafting/AccountPage.lua) 自行按 context.scope 组合 name 与 realm。Core 在规则加入时已经提供 Characters:FormatName；[名称契约](../YiboCore/Docs/API-v8-公共名称格式化.md) 支持原名与服务器策略，能够覆盖当前显示需求。

本轮触及的是这条角色身份提示，不是只有同文件内的物品加载回调。仅移除原生 Tooltip 参数而保留本地名称组合，没有完成当前调用范围的收拢；[Bootstrap:9](../YiboCrafting/Bootstrap.lua) 也仍仅要求 API v7 / item-resolver:1，没有新名称能力检查。

处理范围应限于这个身份提示及其需要的公共调用：明确原名／短名和服务器显示策略、复用 FormatName，并声明／检查 API v8 / character-name-format:1 及升级停止行为；真实身份提示与显示文本不得变成业务 ID。其他未触及的列表、下拉、搜索框不因这项发现被自动认定本轮违规。

状态：**待修复，当前工作树调用层漏迁**。未宣称它已作为业务版本发布，也未把未提交编辑的精确时间当作已证实事实。

## F02：规则后已提交的 Crafting 搜索框漏迁（历史旁证）

关联 CAP-002。提交 a4c7944 时间晚于规则提交约 3 小时 12 分钟。该提交在 Page:Create 中新增：

```lua
Theme:AttachClearButton(ui.search, { OnClear = function()
    ui.state.search = ""
    ui.searchGeneration = (ui.searchGeneration or 0) + 1
    if ui.search:IsShown() then Page:RenderResults(parent) end
end })
```

搜索输入仍由 [AccountPage.lua:340](../YiboCrafting/AccountPage.lua) 本地 CreateFrame("EditBox", ..., "InputBoxTemplate") 创建，自己处理输入／焦点。Core 的 [Theme:CreateInput:46](../YiboCore/UI/Input.lua) 此时已提供搜索输入、清空和变化回调；未发现该搜索框继续保留本地实现的旧版兼容例外记录。

这里确实使用了 Core 的清空按钮工具，但只接入子操作，修改到同一个输入控件后仍未收拢其基础输入重复实现，也没有 API v7 输入能力要求。这是可由提交时序证明的触及漏迁，不是因为后来审查看见旧 EditBox 才追溯归责。

职责核对：清空按钮的实现已经在 Core [UI/Input.lua](../YiboCore/UI/Input.lua)，Crafting 调用的就是 Core.UITheme:AttachClearButton。标准 CreateInput 支持 clearable=true，内部复用相同实现；清空后的搜索状态、结果刷新等回调由 Crafting 提供。现有缺口是业务搜索框迁入标准输入，Core 无需为该搜索框再增加一套清空实现；将来真实需求超出公共契约时再优先扩展 Core。

状态：**待修复，规则后已提交历史漏迁**。发生于 Core 1.8 之前，单列作为规则执行效果的旁证。当前工作树对 Page:Create 的新增改动是物品加载回调，未再修改搜索输入，因此不将此历史事项重复计成当前第二处漏迁。

## 对规则有效性的判断与后续措施

保留触及即迁移规则是合理的：实际修改跨业务调用、物品加载、首次提示和页面刷新时，已经出现正确迁移实例。存在 F01/F02，说明单靠规则文字仍会漏掉小范围修复或“仅加一个清空按钮”的修改，不代表所有业务都没有遵守。

用户已确认保留触及即迁移，并持续观察执行效果。AGENTS 已加入每次业务修改收尾时的有边界 diff 检查：列出被修改的公共能力调用，逐项记录“已接入／不适用／有明确兼容例外／待修复”；未触及的旧实现只作为迁移库存。输入子交互和名称 Tooltip API 参数修复应覆盖其直接控制的输入／名称路径。集中追赶随无限服开服后的各插件大幅更新执行，届时固定当时 Core 能力基线并逐项验收。

本轮检查 Git 提交时序、忽略行尾差异后的全部业务运行 diff、相关公开契约及最低版本检查；未运行游戏、未新增测试、未改运行／测试代码。登记 F01/F02 到台账；更新迁移节奏审查，明确旧实现库存与规则执行结果是两种不同判断。
