# YiboMail 发件箱通讯录与快捷寄件栏完整方案

方案状态：已确认。

实施状态：代码已实施，2026-10-04 按游戏内反馈将来源菜单收窄为 200、名单为 200 UI 单位，来源名单改为悬停或点击后向右展开（右侧不足时向左）；自动验证通过；目标客户端游戏内验收待完成。详见 `YiboMail/_NonRelease/Docs/Recipients-Implementation-Check.md`。

日期：2026-10-04。

适用客户端：魔兽世界熊猫人之谜经典版，沿用当前 YiboMail 原生发件箱增强架构。

## 1. 目标与交付范围

本方案覆盖收件人通讯录、六类联系人来源、常用收件人增删、独立快捷寄件栏、角色好友采集、账号好友生成、最近邮寄、数据迁移和资源验收。

玩家应能在少量联系人时看到紧凑名单，在大量联系人时通过搜索和分页找到对象；通讯录用于选人，快捷寄件栏用于熟悉对象的快捷填写与寄件。各入口使用同一套候选查询、地址规范化和显示规则。

首版交付：

1. 通讯录首页及六类来源名单。
2. 当前收件人加入或移出常用名单。
3. 快捷寄件栏独立的 16 个槽位及右键选人菜单。
4. 按角色保存好友名单，生成排除当前角色来源的账号好友。
5. 成功发送后的最近邮寄记录。
6. 小名单收缩、大名单按安全空间分页及可复用结果缓存。
7. 管理入口灰态占位，后续接入 Core 邮件设置页。

当前发布代码以 `NativeUI.lua` 的基础发件箱为入口；收件人菜单已有服务器分组及每页 12 项分页，但联系人与辅助操作均为标准大按钮，满页高度仍然偏大。右侧现有两列八行快捷面板使用已保存联系人；本次实施将其数据与通讯录常用名单分别保存。

`Settings.lua`、`SettingsUI.lua` 当前未由发布 TOC 加载，`FEATURES.settings` 为 false。“管理”占位按第 9 节执行。正文、主题、金额、COD 和原生发送确认继续由现有发件流程承担。

## 2. 统一命名与职责

| 对象 | 面向玩家的名称 | 开发沟通简称 | 职责 |
|---|---|---|---|
| 收件人输入框右侧下拉及其名单 | 收件人通讯录 | 通讯录 | 浏览、搜索、筛选和选择收件人 |
| 通讯录内手动保存的地址分类 | 常用收件人 | 常用名单 | 保存用户主动加入的收件地址 |
| 发件箱右侧两列八行图标面板 | 快捷寄件栏 | 快捷栏 | 独立配置 16 个快捷格，提供快捷填写和寄件 |
| 当前角色游戏好友名单入口 | 角色好友 | 角色好友 | 使用当前登录角色 O 好友面板中的名单 |
| 其它角色游戏好友名单入口 | 账号好友 | 账号好友 | 使用其它角色已读取的名单并去重 |

入口悬停文案：“收件人通讯录”。快捷栏展开与收起文案：“展开快捷寄件栏”和“收起快捷寄件栏”。空格悬停文案：“右键添加快捷收件人”。

常用名单与快捷格分别持久保存。通讯录的加入或移出只修改常用名单；快捷栏的添加、更换或清空只修改目标快捷格。快捷栏复用通讯录的候选查询与名单组件，通过独立选择回调配置槽位。

## 3. 联系人来源与默认规则

来源顺序固定为：常用收件人、账号角色、最近邮寄、角色好友、账号好友、公会。六项默认显示，来源为空时显示禁用行和零人数，接口未就绪时显示相应状态。

| 来源 | 数据依据 | 顺序与范围 |
|---|---|---|
| 常用收件人 | `YiboMailDB.contacts` | 保持保存顺序，数量与快捷格容量独立 |
| 最近邮寄 | 已确认发送成功的收件地址 | 最近发送者在前，去重保留 20 位 |
| 账号角色 | Core 角色目录 | 排除当前角色，尊重 Core 隐藏、准入与角色顺序 |
| 角色好友 | 当前角色的游戏好友名单 | 当前角色范围，按规范完整地址稳定排序 |
| 账号好友 | 其它角色已读取的游戏好友名单 | 排除当前角色来源，地址去重后稳定排序 |
| 公会 | 当前角色客户端取得的公会角色名单 | 包含可解析的在线、离线成员，按完整地址稳定排序 |

账号角色默认显示全部服务器。服务器筛选使用 Core 服务器身份信息。角色隐藏只控制自动账号角色候选，已保存的常用地址和快捷地址仍以各自数据为依据。

候选必须能解析为明确的角色邮寄地址。战网身份与角色地址分别处理，以昵称、Real ID 或 BattleTag 代替角色地址的条目不能进入邮寄候选。

## 4. 地址规范化、显示与去重

### 4.1 地址规则

- 保存、匹配和填入原生收件人输入框时使用完整“角色名-服务器名”。
- 用户手工只填角色名时，在当前角色服务器已知的情况下补全；当前服务器未知时要求填写完整地址。
- 各角色好友接口只返回角色名时，使用来源角色的服务器补全。
- 去除首尾空白，使用统一地址键处理大小写和服务器规范形式；禁止控制字符、换行及颜色控制串。
- 服务器包含连字符时沿用完整服务器解析，不能按最后一个连字符随意截断。
- 同名不同服务器是不同对象；同一完整地址跨来源合并为一个搜索结果并保留来源标记。

### 4.2 显示规则

账号角色名单以当前登录角色服务器为基准：同服显示“角色名”，不同服显示“角色名-服务器名”。切换服务器筛选不改变这个比较基准。

其它来源沿用相同地址显示规则，常用名单可显示已保存的显示名；完整地址始终可悬停查看。跨服同名的可见文本必须保留足够的服务器区别，不能让两项只能通过相同的省略名字判断。

文本过长时省略并悬停全文，避免换行造成行高跳动。显示短名或显示名只改变标签，实际保存和操作目标仍为完整地址。

## 5. 通讯录结构与操作

### 5.1 来源首页

```text
搜索姓名 / 服务器
常用收件人       1  >
最近邮寄        20  >
账号角色        30  >
角色好友        18  >
账号好友        42  >
公会           126  >
─────────────────────
加入常用         管理（灰态）
```

示例人数仅表示布局，不作为容量限制。

- 点击来源，在同一浮层内进入名单；点击返回回到首页。
- 悬停来源不切换页面。
- 搜索始终覆盖全部六类有效来源，不受当前展开分类限制；合并同一完整地址并标记来源。切换分类保留搜索词，清空搜索后显示该分类名单。显式服务器筛选继续作用于全局结果。
- 搜索匹配显示名、实际角色名、服务器和完整地址。
- 先对全部候选搜索与筛选，再计算页数和当前页，不能只搜索可见页。
- 人数表示该来源去重后的候选数；搜索时另显示匹配数。
- 选择联系人填入原生收件人输入框并关闭通讯录。

### 5.2 来源名单

```text
< 返回     账号角色 · 30
搜索姓名 / 服务器
服务器：全部 v
天堂山狩
天堂双影
天堂暗影-莫格莱尼
……
───────────────────────────
上一页       1 / 3       下一页
加入常用             管理（灰态）
```

搜索、返回、服务器筛选和底部操作保持可见。服务器选择器同样受安全高度约束；来源页面和筛选页面均在同一浮层中切换，并提供返回操作。

首次打开进入来源首页；每次重新打开清空搜索并回第一页。来源内翻页保留搜索和筛选，筛选变化回第一页。菜单打开期间保存或移出常用后，保留来源和筛选，页码收敛到有效范围。

### 5.3 当前收件人加入或移出常用

动作依据原生收件人输入框中的当前地址判断，不以鼠标悬停项或名单选中项代替。

| 当前收件人状态 | 底部文案 | 操作 |
|---|---|---|
| 有效地址，未在常用名单中 | 加入常用 | 保存地址并更新常用人数，按钮转为“移出常用” |
| 有效地址，已在常用名单中 | 移出常用 | 确认明确对象后移除，按钮转为“加入常用” |
| 地址为空或无效 | 加入常用（禁用） | 提示“请先填写有效收件人” |

同服短地址与完整地址匹配到同一对象。输入变化时更新动作，点击动作时再次校验最新地址与名单状态。

移出确认示例：“将 天堂暗影-莫格莱尼 从常用收件人中移除？”操作仅修改常用名单；快捷格配置、当前收件人、邮件草稿、最近邮寄、规则地址及 Core 角色保留。此对象仍可能通过其它联系人来源出现。

失败时显示具体原因，保留原数据与输入内容。常用名单不沿用快捷栏的 16 格容量限制；使用搜索和分页组织。

## 6. 尺寸、定位与长名单

尺寸使用 WoW UI 逻辑单位，游戏内按目标客户端和 UI 缩放验收。

| 项目 | 初始规格与约束 |
|---|---|
| 浮层宽度 | 目标 300，受安全屏幕宽度限制 |
| 联系人行高 | 28，单行呈现 |
| 搜索高度 | 28 |
| 浮层最高高度 | 目标 360，同时受锚点可用安全高度限制 |
| 翻页 | 底部固定，仅多页时显示 |
| 联系人控件 | 按当前页容量创建并复用 |

计算方法：先扣除顶部返回、搜索、服务器筛选、底部操作和必要间距，再用剩余高度除以行高得到页容量；多页时扣除翻页行并再次计算。标准空间预计每页约 8–10 人，实际以可用尺寸为准。

小名单按实际内容收缩，不保留空白行；大名单在高度上限内分页。最后一页可保留稳定的名单区高度，避免翻页时控制位置跳动。

通讯录默认向下打开，下方不足且上方更充足时向上打开。快捷格右键菜单优先向右展开，右侧不足时向左避让。水平及垂直位置均限制在屏幕安全边界内，使用与所属窗口一致的 UI 缩放计算空间。

同一浮层内页面切换保持宽度稳定。窗口缩放或位置变化后重新计算布局，并保留当前筛选；必要时收敛页码。极低可用高度时减少页容量，保持搜索、选人、返回及分页可操作。

## 7. 快捷寄件栏

### 7.1 布局与槽位

沿用与邮箱等高的两列八行面板，16 个正方形快捷格完整显示。槽位编号固定为 1–16，顺序与当前布局一致；清空某格后该格显示“+”，其它格保持原位置。

每格独立保存收件地址及可选显示名。图标可复用 Core 已知角色的职业信息，悬停显示标签、完整地址、左键行为和右键配置提示。

### 7.2 右键添加与更换

右键空格或已配置格，在该格右侧打开：

```text
自定义…
────────────────
常用收件人 >
最近邮寄   >
账号角色   >
角色好友   >
账号好友   >
公会       >
────────────────
清空此快捷格     ← 仅已配置格显示
```

- 第一项“自定义…”打开一次性的地址输入流程，支持角色名或完整地址；已有格可预填原地址。
- 从第二项起复用通讯录的来源、名单、搜索、筛选、分页和地址显示规则。
- 右键时记录目标槽位；后续来源切换、搜索和返回均维持这个目标。
- 选人或确认自定义输入后，只保存到目标格并关闭配置菜单。当前原生收件人及草稿保持原状。
- 取消或 Esc 放弃本次配置；地址无效时显示错误并保留输入。
- 清空操作确认明确槽位和地址后执行，仅修改该格。
- 跨格打开右键菜单时关闭前一菜单，切换目标槽位。
- 同一地址可由用户配置到多个格，覆盖或清空始终按槽位执行。

自定义输入复用或改造现有输入流程，文案明确为“配置快捷收件人”；作为一次性操作输入，不承担常驻设置窗口职责。通讯录的常用增删及管理占位属于通讯录入口。

### 7.3 左键行为

已配置格左键沿用现有逻辑：先填入该格地址；主题或正文至少一项有内容，且附件非空时，触发现有原生发送按钮，继续使用游戏的确认和错误提示。其它情况只填写收件人。

空格显示“+”，右键配置；空格左键不发送、不修改当前收件人。自定义输入、名单选择和清空格子均为配置动作。

## 8. 好友名单、刷新与删除边界

### 8.1 两个入口

| 入口 | 数据来源 |
|---|---|
| 角色好友 | 当前登录角色好友，排除全部已知账号角色地址 |
| 账号好友 | 其它角色好友并集，排除全部已知账号角色地址与当前角色好友地址 |

账号好友提供“其它角色的其它好友”：从其它角色快照生成并集，排除当前角色好友完整名单，以及 Core 完整已知角色目录中的地址。角色好友同样排除完整账号角色地址。账号身份集合包含当前角色和隐藏角色，与 Core 的隐藏、展示准入、排序无关；账号角色分类的展示仍遵循 Core 规则。

例如当前 A 有甲，B 有甲、乙，C 有乙、丙，则角色好友为甲、账号好友为乙、丙。A 删除甲并完整刷新后，甲可由 B 进入账号好友。B 删除乙后，乙仍由 C 提供；C 也删除后，乙退出账号好友。好友快照保存原始完整成员关系，分类去重仅在候选查询时执行。

所有分类按完整地址去重；同名不同服分别保留。常用、最近、公会保留跨分类重叠；全局搜索合并同地址并标记来源。先完成分类去重，再计算人数、搜索、服务器筛选和分页。

### 8.2 采集状态

每个角色单独保存最新一次完整好友名单、读取状态和成功读取时间。成员状态区分未读取、完整名单可用、暂时不可用或读取失败。完整的零人名单与接口未就绪分别处理。

- 登录角色并成功取得完整名单后，替换该角色的原有快照。
- 好友更新事件触发当前角色重新读取；连续事件合并处理。
- 读取时确认各条地址有效及枚举完整；接口未就绪、返回不完整或失败时保留最后成功快照。
- 零人名单的可靠就绪条件在目标客户端验证，不能只凭人数为零清空旧数据。
- 临时读取状态与最后成功快照分别记录，使失败状态不会误删有效离线来源。

### 8.3 删除与离线

一个角色删除好友，只更新该角色的成员集合；账号好友从其它角色有效快照重新生成。只有某地址不再属于任何其它角色的有效已保存名单时，才退出账号好友。

离线角色使用最近成功快照；其游戏好友变化只能在该角色再次登录读取后确认。未读取过的角色不贡献候选，已确认空名单贡献零项。旧快照不因时间经过自动推断好友已删除。

悬停账号好友时，可按地址查询来源角色和各自成功读取时间。玩家删除 Core 角色缓存时，YiboMail 同步清理该角色好友快照并使账号好友结果失效；即使该角色没有邮件快照，好友缓存也纳入清理影响说明。

角色 ID 迁移时按 Core 的新旧标识处理关联快照：只有旧记录时迁移；新旧均存在时优先保留较新的完整快照，不能把两份历史好友名单简单取并集而恢复已删除的成员。

## 9. 最近邮寄与管理入口

### 9.1 最近邮寄

仅在 `MAIL_SEND_SUCCESS` 关联到明确的本次发送收件人后更新。发件调用时捕获地址，成功时使用该捕获值；不要读取发送成功后可能已被清空的收件人输入框。

同一规范地址再次成功发送时移到首位并更新最后发送时间。最多保留 20 位，超出时淘汰最旧一位。失败、取消、只填入地址和配置快捷格均不更新最近邮寄。

最近邮寄在当前客户端 SavedVariables 中账号共享，独立于长期邮件历史期限。可一次性从已有明确成功的发件历史初始化；仅接受已确认成功、具有有效地址的发件记录，不能使用待核实记录或收件记录。

### 9.2 管理占位与后续设置

通讯录底部“管理”灰显、不可点击，悬停提示“后续在 Core 邮件设置页提供”。首版直接使用本方案默认值：六类来源显示、首次打开来源首页、账号角色范围为全部服务器、最近邮寄保留 20 位、重新打开清空搜索和页码。

后续 Core 邮件设置页可提供来源开关、默认分类、默认服务器范围、近期记录容量和记住筛选。常用名单编辑、最近邮寄管理及清空等操作放在“数据与缓存”，破坏性操作位于分区末尾并确认。角色短名、隐藏和排序继续由 Core 的“角色与排序”承担。

## 10. 持久数据、运行时缓存与迁移

### 10.1 持久字段

联系人功能使用独立迁移标记，例如 `recipientSchemaVersion = 1`，与既有邮件快照的 `schemaVersion` 分别维护。

| 字段 | 内容 | 归属与约束 |
|---|---|---|
| `contacts` | 常用地址和可选显示名 | 现有数据保留，按保存顺序组织 |
| `quickRecipients` | 1–16 槽位的地址和可选显示名 | 固定槽位，可以有空位，独立于 `contacts` |
| `friendsByCharacter[characterID]` | 地址集合、读取状态、成功读取时间 | 每角色仅保留最新完整名单 |
| `recentRecipients` | 地址、最后成功发送时间 | 最多 20 位，最近者在前 |
| `recipientSchemaVersion` | 本功能迁移版本 | 幂等迁移，完成后不重复初始化 |

地址集合使用规范完整地址作为成员键，值为布尔成员标记；每个好友不建立含角色详情的独立记录。地址规范化和匹配统一走联系人模型，保留正确显示所需的规范拼写。角色身份由 Core 角色 ID 关联。

运行时维护来源版本、当前角色对应的账号好友缓存、有效排序结果和菜单状态。好友来源明细按悬停地址查询；账号好友结果不另作一份持久历史名单。

### 10.2 旧数据迁移

1. 保留现有 `contacts` 记录并沿用其显示名，不改动邮件、规则和历史数据。
2. `quickRecipients` 尚未初始化时，按当前快捷栏实际显示的有效、去重地址顺序填入最多 16 格，保持玩家原有对象与顺序。
3. 明确区分“未初始化”和“用户已清空”：字段已初始化，即使为空也不重新导入。
4. 初次好友缓存为空，角色实际登录读取后建立数据；不能从联系人或近期记录推测好友关系。
5. 最近邮寄可按第 9 节从明确成功的历史记录初始化，完成迁移后记录标记。
6. 地址规范化失败的旧常用记录保留原数据，跳过候选并提供明确数量或诊断；迁移不静默丢弃用户记录。
7. 新字段在完整初始化后写入迁移标记，再次加载保持结果一致。

快捷格中的记录与常用名单使用独立对象，不能通过 Lua 表引用让修改一份数据影响另一份。

### 10.3 清理与数据边界

Core 角色缓存清理只清除该角色所属的邮件、好友快照和相应运行时派生缓存。手动常用地址、快捷格和账号近期记录按各自生命周期保存，不能因为删了一个来源角色就推断用户也要移除保存地址。

YiboMail 的角色清理 `Inspect` 应识别邮件或好友数据；`Delete` 应处理角色标识及其别名，并保持 Core 未加载插件后的补清理流程可用。

## 11. 性能与复杂度约束

### 11.1 计算规模

设 N 为所有角色的好友成员关系总数，U 为去重地址数，F 为当前角色好友数，C 为来源角色数。

| 操作 | 计算规模 |
|---|---|
| 当前角色完整读取及集合比较 | O(F) |
| 账号好友哈希去重 | O(N) |
| 结果稳定排序 | O(U log U) |
| 搜索 | O(U)，检索有效缓存 |
| 来源悬停 | O(C)，逐角色集合查询该地址 |
| UI 行控件 | 按当前页容量，约 8–10 行随空间调整 |

示例工作量：假设 30 个角色，每角色 100 个好友，共 3000 条成员关系；100 个角色则为 10000 条。这是资源验收场景，不代表客户端实际好友容量。

实际内存还包含 Lua 字符串、表和哈希存储开销。实现前只评价数据规模，实际增量内存与耗时在目标客户端测量后填写，不把假设当作实测结果。

### 11.2 更新与缓存

- 登录就绪和好友更新事件触发当前角色采集，连续事件合并；不逐帧扫描，不持续轮询。
- 地址规范化在采集或保存时完成；合并直接使用统一成员键。
- 只有好友成员集合变化才递增版本、使账号好友缓存失效；在线状态、API 名单顺序或读取时间变化不触发重建。
- 缓存以当前角色 ID 和成员集合版本判定有效，切换角色后重新生成排除当前来源的结果。
- 需要好友候选、全局搜索或首页人数时，对失效结果重建一次。搜索、翻页和重复打开直接复用有效结果。
- 通讯录、快捷栏右键选人共用候选缓存；运行时仅保留当前角色所需的账号好友结果。
- 菜单更新保留用户来源与筛选；失效结果不得继续用于选人，选择回调重新核对对象和调用目标。
- 初版使用完整集合比较与按需重建。只有实测表明较大名单重建超过界面帧预算时，再分帧处理该步骤。
- 采集回调只更新数据和失效标记，不重复构造全部 UI；可见菜单按合并后的刷新执行。
- Core 角色职业图标、显示名等辅助信息按可见行需要查询，避免每次扫描复制整份角色业务数据。

## 12. 通用交互、异常和共存

| 情况 | 行为 |
|---|---|
| 下拉入口再次点击、点击浮层外、关闭邮箱或切换收件箱 | 关闭菜单和本次快捷格配置输入 |
| Esc | 搜索有内容时先清空；再次按下关闭当前菜单或配置流程 |
| 中文输入法组词 | Enter 不误选联系人、不触发快捷寄件 |
| 搜索无结果 | 显示“没有匹配的联系人”及清除搜索操作 |
| 来源未就绪 | 显示状态，可保留有来源时间的成功快照 |
| 来源确实为空 | 禁用来源或显示空名单提示 |
| 翻页首尾 | 禁用对应按钮 |
| 数据减少 | 收敛页码，重新填充可见行 |
| 校验或保存失败 | 保留草稿、目标槽位和输入，显示具体错误 |
| 战斗或原生界面不可操作 | 沿用现有受限处理，解除限制后再刷新 |

首版做菜单内搜索。原生收件人补全和 Postal 共存时，验证菜单层级、焦点和关闭行为；输入框自动补全功能后续单独规划。

候选地址仅表示已知对象，实际跨服或跨阵营可寄送性由目标客户端原生发件流程判断。邮寄成功表示原生发送成功，沿用已有在途记录语义。

## 13. 文件职责与实施步骤

建议增加 `Recipients.lua` 作为联系人业务模型，避免把采集、缓存和菜单回调全部堆到 `NativeUI.lua`。

| 文件 | 实施职责 |
|---|---|
| `Recipients.lua`（新增） | 地址规范化、常用增删、槽位保存、近期记录、六类候选、好友采集与账号派生缓存 |
| `Store.lua` | 新字段初始化、幂等迁移、好友角色清理及标识迁移配合 |
| `ViewModel.lua` | 转接现有联系人调用，统一名称和地址显示；常用保存容量与快捷格容量分别处理 |
| `NativeUI.lua` | 通讯录和右键浮层、动态底部动作、自定义输入、可见行布局及独立快捷格展示 |
| `Compose.lua` | 捕获发送收件地址，在确认成功后记录最近邮寄 |
| `Bootstrap.lua` | 联系人模型初始化、事件路由、Core 角色清理影响和 ID 迁移事件接入 |
| `YiboMail.toc` | 按模型依赖顺序加载新增文件 |
| `README.md` | 更新功能名称、操作说明和可核对的缓存边界 |
| `_NonRelease/Tests` | 地址、迁移、独立槽位、好友成员更新、失效缓存与成功发送等必要模型验证 |

本业务沿用 Core 的视觉主题、角色目录和服务器身份。若实现需要通用选择浮层，按明确复用需求提取；不能通过直接改变所有 `CreateDropdown` 的行高或高度影响其它插件。

实施顺序：

1. 核对目标客户端好友、公会接口及名单就绪条件；记录完整零人、未就绪和失败的区别。
2. 实现地址模型、新字段和幂等迁移，验证常用与槽位数据独立。
3. 接入按角色好友采集、账号好友查询、候选缓存及 Core 清理。
4. 实现通讯录来源首页、名单搜索筛选、动态常用动作和屏幕边界分页。
5. 实现快捷格右键自定义、候选选择组件复用、目标槽位回调和原有左键快捷行为。
6. 接入最近邮寄、公会来源及各入口一致性，完成异常状态。
7. 完成模型验证、游戏内操作验收和资源测量，更新 README。

如目标客户端验证需要新增非发布探针，目录与 TOC 名同名，统一放在仓库根 `_NonRelease/` 下，按项目约定联接到游戏客户端。

## 14. 验收清单

### 14.1 名单、地址和布局

- [ ] 六项顺序、名称及人数在通讯录和快捷栏选人菜单一致。
- [ ] 0 / 1 / 5 / 12 / 25 / 100 名候选均可正常浏览。
- [ ] 小名单自然收缩，大名单在安全边界内分页。
- [ ] 搜索全量数据后分页，未显示页中的目标也能查到。
- [ ] 同服与跨服显示符合规则，跨服同名分别保存和选择。
- [ ] 长名字、服务器连字符、大小写地址和未知服务器正确处理。
- [ ] 高 UI 缩放、小屏幕、贴近四边时菜单避让正确。
- [ ] 翻页、返回、筛选及数据减少时位置和页码稳定。

### 14.2 通讯录与快捷栏

- [ ] 当前地址变化时“加入常用/移出常用”及时切换。
- [ ] 常用名单增删与快捷格配置分别生效。
- [ ] 右键首项自定义，之后六类来源可用。
- [ ] 配置准确作用于目标槽位；取消保留原配置。
- [ ] 配置快捷格不改写当前邮件收件人，也不触发发送。
- [ ] 清空格子后其它格不移动，可配置重复地址。
- [ ] 已配置格左键在现有条件下发送，其它情况填入。
- [ ] 常用移出和快捷格清空均确认明确对象。
- [ ] 管理占位不可点击，悬停说明正确。

### 14.3 好友与近期记录

- [ ] 角色好友来自当前角色；账号好友排除当前角色来源。
- [ ] 多角色共同添加的好友只显示一次。
- [ ] 单一来源删除后保留其它来源；最后其它来源删除并刷新后才移出账号好友。
- [ ] 当前角色与其它角色共有的好友只在角色好友中展示；两个好友入口均排除完整账号角色地址。
- [ ] 未就绪、不完整、失败及确认空名单分别处理。
- [ ] 离线来源保留快照时间，切换角色后范围重算。
- [ ] 仅成功发送更新最近邮寄，失败、取消和配置动作不更新。
- [ ] 重复发送移到首位，超过 20 位淘汰最旧记录。

### 14.4 迁移、清理和资源

- [ ] 旧快捷对象与顺序保留，空字段与未初始化字段分别处理。
- [ ] 清空快捷格后重新登录，不再次导入常用名单。
- [ ] 两份保存数据的记录不共享 Lua 对象引用。
- [ ] 无效旧记录保留原数据，迁移重复执行结果一致。
- [ ] 只有好友缓存、没有邮件快照的角色也纳入 Core 清理。
- [ ] Core 角色 ID 迁移选择最新完整好友快照，清理后派生名单失效。
