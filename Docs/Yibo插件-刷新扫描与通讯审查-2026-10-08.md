# Yibo 插件刷新、扫描与通讯审查

审查日期：2026-10-08。状态：审查已完成，改造建议待实施。

## 范围与结论

覆盖根目录 YiboCore 及 13 个业务插件：YiboAltoBoss、YiboAutoOpen、YiboBeastPaths、YiboBuilds、YiboCrafting、YiboCurrency、YiboLegendary、YiboMail、YiboMounts、YiboQuestBlocker、YiboReputation、YiboTodo、YiboVault。以当前开发目录及其 toc 加载路径为依据；dist 历史发行副本、第三方 Libs、测试和非发布探针不作为当前业务问题计数。

存在明确的重复工作路径，最优先的是 AltoBoss 副本信息返回后再次发请求，以及 Reputation 监测预览的逐帧快照复制与 Tooltip 重建。其它主要问题集中在整份采集、无变化通知、重复邮箱扫描、规则循环读取整角色和公共刷新缺少合并。

可以复用公共调度、页面刷新合并、物品请求和轻量身份读取。库存、邮件、专业、锁定等业务采集与判断仍由业务所有者负责，通过 Core 公开契约提供结果。各插件监听同一个原生事件本身不构成性能问题；需要减少的是事件后的重复工作。

初次审查没有修改运行代码。后续按用户要求修复 F01～F10，实施状态见下表。未启动游戏采样；以下离线验证控制流和次数，不代表客户端耗时或卡顿归因。先前采样中嵌套耗时不能相加，不同角色和操作场景不能直接作为优化前后对照。

## 按优先级排列的问题

### F01 / P1：副本返回事件重新请求，形成反馈路径

位置：`YiboAltoBoss/InstanceLockouts.lua:450–469`，重点为 465–469；toc 当前加载该文件。

模块监听 `UPDATE_INSTANCE_INFO`，但没有单独消费返回事件，最终进入通用分支：延迟 1 秒调用 `RequestRaidInfo()`，再执行 `RefreshInstanceLockouts()` 和 `RecordNormalInstanceEntry()`。因此服务端返回信息后，会再次启动请求。在客户端继续产生返回事件的情况下，此链没有次数或在途请求限制，也不依赖窗口是否可见。

`RefreshInstanceLockouts()` 在 295–327 行遍历全部锁定和各副本遭遇，替换记录、更新时间并无条件 `Notify()`。Notify 又调用 PersistDB 和页面通知。因此反馈链同时放大通讯、扫描、维护与可见页面重绘。

额外触发放大：所有 `CHAT_MSG_SYSTEM` 都排队延迟扫描；登录、进世界、区域和副本欢迎事件分别安排请求，没有请求合并。

验证：抽取真实事件处理代码，模拟一次请求产生一次 `UPDATE_INSTANCE_INFO`；执行 20 个延迟回调后，请求 20 次、刷新 20 次、仍有 1 个回调待执行。证实代码在该响应条件下不能自行终止。游戏内实际响应频率与服务器限流尚未测量。

建议：把主动请求与返回消费分开。返回事件只采集，不发新请求；主动请求设置单一在途标记、最小间隔和有限超时。过滤系统消息，按业务字段变化决定通知，单独维护观测时间。先在 AltoBoss 修复；当前只有这一处使用 RequestRaidInfo，不需为此预建 Core 通讯层。

### F02 / P1：声望监测预览每帧复制完整声望域并重建 Tooltip

位置：`YiboReputation/MonitoredPreview.lua:8–28,104–107`。

悬停行的 OnUpdate 每帧调用 ShowMonitoredTooltip。函数没有“当前列/角色/声望/修订号未变”的短路，每次都会通过 Data → Snapshot → DataDomains:Get → DomainStore:Get 复制完整声望域，然后格式化、SetOwner、ClearLines、AddLine、Show。鼠标静止仍执行。

同文件渲染监测表时，在每个角色/声望单元多次调用 Snapshot/Data（87–99 行），每次都是完整域复制，也可改为单次渲染按角色预取。

对照：`AccountMatrixView.lua:42–58` 的普通矩阵 Tooltip 已按列和 Tooltip 所属行短路；`MonitoredPreview.lua` 未复用这一保护。

验证：抽取真实 ShowMonitoredTooltip，固定鼠标位置和数据，模拟 120 帧，得到域读取 120 次、ClearLines 120 次、Show 120 次。模拟替换了游戏 UI/API，不测实际时间。

建议：按角色、factionID 和数据修订号缓存显示文本；位置检测与内容重建分离，仅在列或数据变化时重建。一次表格渲染每角色只取一次快照。优先在业务插件修复，不把声望格式化迁入 Core。

### F03 / P2：Core 对旧兼容机制做无消费者的整角色读取

位置：`YiboCore/Data/Profile.lua:18–26,36–57`；`Data/Characters.lua:10–14,225–231`。

Profile:RefreshCurrent 在 DataDomains 分发后无条件调用 RunLegacyCollectors；后者即使 `_collectors` 为空，也先 GetCurrent、读取完整角色快照。当前工作区没有业务 RegisterCollector 调用。领域更新还通过 QueueLegacyUpdate 复制整记录并发送旧 CHARACTER_PROFILE_UPDATED；当前工作区没有该旧通知的消费方。

这不会导致其它业务插件必然重绘，但会在多个原生事件及领域变化后增加复制和垃圾分配。领域扫描本身正常，不应混记成重复整库扫描。

验证：真实 Profile.lua 在零旧采集器条件下处理 20 次 RefreshCurrent，仍读取当前角色 20 次。

建议：零旧采集器时立即返回；旧通知在没有订阅者时避免构造整记录。保持兼容 API 和已有消费者语义。仅需要当前角色 ID 的路径可直接复用已存在 `Characters:GetCurrentID()`，需要姓名/服务器/阵营时再评估最小身份投影。

### F04 / P2：构筑技能事件触发完整双专精与装备采集

位置：`YiboBuilds/Bootstrap.lua:116–125`；`Snapshot.lua:1064–1097,1117–1124`。

SPELLS_CHANGED、SKILL_LINES_CHANGED、TRADE_SKILL_LIST_UPDATE 与天赋、雕文事件共用 ScheduleCapture，最终采集当前专精、装备及另一专精，不按变化域区分。每次 Capture 完成无条件 NotifyChanged。已有 0.35 秒 token 合并，能抑制短突发；相隔更久的事件仍各做一次完整采集。

装备变化还主动安排 0.05 秒和 0.3 秒两次采集，这是明确的稳定性策略，不能直接删掉后一次。建议在第二次数据已完整且无变化时停止额外通知；按天赋/雕文/装备分别记录 dirty 状态，技能事件只更新确实依赖技能的部分。

以前客户端样本曾出现 Capture 158 次、累计约 3.55 秒，另一次只有 4 次；场景不同，说明需要原因计数，不能用这两份样本直接判定修复效果。

### F05 / P2：传说插件所有相关事件立即重建全部目标

位置：`YiboLegendary/Bootstrap.lua:69–87,145–169`；`Probe.lua:36` 起。

任务、声望、货币、背包、装备事件都先 Probe:Run，再 Refresh；Refresh 创建全部目标快照并无条件通知传说页面。没有突发合并或业务结果相等判断，后台窗口隐藏仍会采集。Probe 也在每次事件重建诊断结果并做业务查询。

当前 UI:Refresh 已使用 `NotifyPageChanged("legendary")`，此前“重绘其它业务页面”的问题已修复，本次不再作为开放问题。

建议：诊断中的固定 API 可用性仅初始化/显式诊断时检查；动态可读性保留必要事件。按目标依赖失效并合并快照重建，业务结果未变不通知。货币 quantityChange 等增量负载必须先按顺序应用或累积，不得用最后一个事件覆盖整批输入。

### F06 / P2：邮箱打开时，任意物品信息返回触发全背包规则匹配

位置：`YiboMail/RuleSendController.lua:36–40,196–201`；`SendRules.lua:203–220`；`Recipients.lua:33–40`；`RuleSendUI.lua:114–123`。

邮箱关闭时重匹配已被修复。但邮箱打开时，所有 GET_ITEM_INFO_RECEIVED 都立即 Scan，不检查 itemID 是否属于本次待加载物品，也没有合并。Scan 重新读全背包并匹配全部规则。Match 已读取一次当前角色，规则循环的 CanRuleSend 又各自读取；规则 UI 渲染循环也重复读取。只用姓名、服务器、阵营却复制整角色，规则数增加会放大开销。

Controller:OnEvent 最后还无条件 Changed；RuleSendUI 有 root/active/refreshing 防护，因此不将每个关闭邮箱事件判成实际全量绘制。

建议：跟踪待加载 itemID 集合；仅相关信息返回或背包变化时标脏并合并匹配。同一次匹配/渲染传入一份身份上下文。发送前的实时校验和装填前背包校验必须保留，不能直接使用延迟缓存执行操作。

### F07 / P2：邮箱复用的待就绪／错误路径与来源发现边界

位置：`YiboMail/Scanner.lua:129–187`；`YiboVault/MailItems.lua:35–56,89–154,158–168`；`YiboVault/MailProvider.lua:33–75`。

更正：两插件都监听 MAIL_SHOW/MAIL_INBOX_UPDATE，但原 Vault.MailItems:Scan 在 MailProvider:GetSnapshot 返回可用快照时已经提前返回，不是每次更新都双份读取。风险集中在提供方尚未完成扫描、返回错误或生命周期切换的本地回退；原错误状态还可能切回 Vault 更老缓存。Vault 本地扫描同步遍历附件，而 Mail 按每帧最多 5 封分块。初次双扫描结论范围过大，本轮以真实集成测试修正并覆盖上述边界。

建议：Mail 能力兼容且就绪时由 Mail 作为采集所有者，Vault 消费其快照；Mail 缺失/禁用/接口不兼容时保留 Vault 必要的独立基础扫描。切换必须处理晚注册、失效、关闭与错误状态，不能把未就绪数据当空邮箱。

架构约束：当前 MailProvider 直接 `_G.YiboMail.Items`，Currency 的 VaultIntegration 直接 `_G.YiboVault.Items`；这些是实际存在的旧公开 API 集成，但绕过 Core 发现边界。接入改造时应经 Core 公开能力契约发现，保持业务数据归属。当前 Registry/Capabilities 不等同于已经实现通用版本化 Service/Provider 生命周期，不得假定存在该 API。

### F08 / P2：公共页面通知没有突发合并

位置：`YiboCore/UI/AccountView.lua:1464–1487`；`YiboCurrency/CoreIntegration.lua:50–54`。

Core 已按页面和可见性过滤，并在战斗中延迟刷新，这些保护有效。但每个命中当前页面的通知立即调用 RefreshPage，再 ShowPage/ShowPreview；没有同帧 pageID 去重。一次动作使多个数据域/来源同时变化时，即使消费者都遵守页面定向通知，也可反复完整布局。

验证：真实 NotifyPageChanged 方法收到 10 次同页面通知，调用 RefreshPage 10 次。此处模拟验证合并缺失，不代替实际页面渲染测量。

建议：Core 提供统一的“标记页面变化并合并刷新”，累计原因，下一帧最多刷新一次可见目标。保留必须立即反馈的交互入口及战斗处理；执行前复核当前页面，避免旧定时器刷新新页面。Todo 现有预览 2 秒合并有业务策略含义，不应机械改成所有页面统一等待 2 秒。

### F09 / P2：装备变化重复扫描且未过滤单位

位置：`YiboVault/Collector.lua:207–221`。

UNIT_INVENTORY_CHANGED 未按单位筛选，两个 equipmentDirty 分支均立即 ScanEquipment，因此标志并未合并扫描。其它单位的事件也会扫描玩家装备；一次换装的 PLAYER_EQUIPMENT_CHANGED 和 UNIT_INVENTORY_CHANGED 可分别扫描。Builds 同类监听已限制 `name == "player"`。

建议：按目标客户端已验证的单位负载筛选，无法确认时使用保守校验；把装备事件合并到一次延迟扫描。不要要求 Vault 直接调用 Builds 内部装备对象；两者保存信息粒度和权威职责不同。

### F10 / P3：后台空轮询和无变化重绘机会

- `Core/Runtime/ItemResolver.lua:99–108`：常驻 OnUpdate 每帧建立 finished 表、遍历 pending；空 pending 时也运行。有请求去重与超时，属于可低成本优化的空转；请求存在时还逐帧 GetInfo，可改按需启停与适当轮询间隔。
- `AltoBoss/Core.lua:1377–1379,1186–1274`：PersistDB 不是即时磁盘写入，而是 EnsureDB；后者还重建目标缓存、迁移与清理。高调用次数不能描述成高频硬盘写入，优化应分离一次性初始化/迁移和增量维护。F01 会放大它。
- `AltoBoss/HolidayBoss.lua:432–454`：一次排队操作立即、0.05 秒、0.25 秒通知，加上 LFG 原生事件可能重复绘制；应按状态变更判断，保留必要稳定确认。
- `Crafting/Collector.lua:92–95`：成功扫描后即使新增数为 0 仍通知。不能仅以 added==0 跳过，因为输出物品、类别或时效可能变化；需要完整结果/修订号判断。现有自身窗口检查与 0.2/0.5 秒合并有效。
- `BeastPaths/MinimapRenderer.lua:675–683,710–743`：0.15 秒轮询有签名去重，但插件隐藏时仍反复进入隐藏路径。可按可见性暂停，再由设置/区域事件恢复。地图移动跟随仍需要周期更新，不能把整个轮询判断为异常。

## 通讯专项判断

当前业务 Lua 中未找到 SendAddonMessage、CHAT_MSG_ADDON、RegisterAddonMessagePrefix、AceComm 或 ChatThrottleLib 调用，暂无 Yibo 插件间网络消息广播风暴的代码证据。Core.Events 是本机 Lua 回调分发，不能按网络通讯次数统计。

真实服务端请求方面：AltoBoss 的 RequestRaidInfo 返回反馈路径需要优先修复；Vault 的 QueryGuildBankTab 按页串行、单页等待/超时，拍卖本人上架查询有在途保护和 3 秒超时；Mail 发送/收取有等待确认与超时停止。这些存在请求不等于异常频繁通讯。本次没有抓包或测请求限流。

## 多业务插件应如何复用

| 能力 | 当前基础 | 建议最小边界与所有权 |
| --- | --- | --- |
| 页面刷新合并 | AccountView.NotifyPageChanged 已定向 | Core 合并同页面通知、复核可见性；业务提供变化原因与修订号 |
| 调度/取消/去重 | 多插件各有 token 或 queued 实现 | 出现迁移需求时 Core 提供 owner+key 调度、取消、最大等待；业务选择延时和紧急策略，不合并不同业务键 |
| 身份读取 | Characters.GetCurrentID 已有，GetCurrent 复制整记录 | ID 查询直接复用；同一次操作共享一份身份投影；需要姓名/阵营时再按需扩展 Core |
| 物品信息加载 | ItemResolver 每 itemID 请求去重、取消、有限超时 | Crafting/Mail/Vault 的独立请求逐步接入；完成回调只更新待加载的项目，页面统一合并刷新 |
| 库存计数与快照 | Vault 查询、批量 PersonalCounts、dirty bag | Vault 保持业务所有者，经 Core 发现；AutoOpen/Mail 执行前仍实时检查锁定、位置、数量和安全状态 |
| 邮箱快照 | Mail 公共查询、Vault MailProvider 已有 | Mail 就绪时一次采集、多方消费；Vault 缺少 Mail 时保持独立基础能力 |
| 专业配方列表 | Crafting、Todo、Builds 各读部分原生列表 | 先量化重复遍历收益；确需共享时专业业务提供方发布列表快照，冷却、装备制作适用性仍由消费业务解释 |
| 数据变化通知 | Core.Events、DomainStore 相等判断/修订号 | 按真实业务变化发事实通知；订阅幂等、清理明确，消费方不过度扫描；不以广播代替查询结果 |
| 服务端请求调度 | 当前锁定/银行/拍卖各有专用路径 | 先修各自请求生命周期；仅有多个真实消费方时再增加最小去重机制 |

不要为了复用建立统一的每秒“刷新全部插件”Ticker；它会让无变化插件也工作，并丢失脏区域、时效和窗口可见性边界。也不要将所有原生事件转发到所有业务，现有原生监听继续保留。

Core 新机制按“先 Core 契约与验证，后本次业务接入”实施；新增最低能力版本检查，旧版本明确提示升级并停止依赖操作。相关实现及接入完成时更新公共能力迁移台账；本轮已实施项见修复状态表与台账；尚未实现的行动中心 Provider 等机制保持草案状态。
