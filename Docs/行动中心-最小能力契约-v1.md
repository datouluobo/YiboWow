## 0. 主动添加目标契约修订（已实现）

Core 1.11.0 / API v12、TaskHub 0.5.0。最小闭环采用 **Normalize → Add → Evaluate**，取代本节原草案 Describe／Submit／EvaluateBatch 命名；下文复杂需求契约继续是后续设计，不是现有公开方法。接口经 Core Contracts 隔离复制值表；没有业务强依赖。

### 0.1 Core 通用交互

`business-item-actions:1` 的 Bind／Handle／Invoke／Unbind、手势与冲突规则见 [API v12](../YiboCore/Docs/API-v12-业务项目主动添加.md)。复用现有 Register／Resolve／List／Call／NotifyChanged。Task 或来源缺失只停止增强；Core 不解释业务规则。

### 0.2 来源 Provider：action.targets v1.1

稳定 providerID 为来源注册身份；九个实现及各自业务限制见 [实施记录](行动中心-主动添加实施与验证.md)。

- `GetEntry({})`：v1.1 新增，返回 `{title,pageID}`，用于目标管理的添加来源导航；来源提供自己的已注册业务页面。Task 仅对 `major=1,minMinor=1` 调用本方法，按 Provider 技术标识排序。原 v1.0 Normalize／Evaluate 保持兼容，旧来源缺入口仅不出现在添加导航中；注册／注销随 Core 生命周期重新发现，不扫描来源目录或 SavedVariables。

- `Normalize({intent,restart?})`：验证意图，返回 `{intent,identity,title,fields}`；缺条件返回 `{needsConfiguration=true,fields,needsCharacter?}`；失败返回 nil,原因。intent 含 providerID、targetType、objectID（装备源以 conditions 装备引用为准）、scope、conditions、repeatPolicy。scope 是 character+characterID，或 account+固定 characterIDs；repeatPolicy 为 once／recurring／maintain。identity 区分对象、范围及语义模式，不包含周期或可编辑数量。restart 是明确重新执行；制造源据此重设计数起点。
- fields 为纯值 `{id,label,kind,options?,default?,scope?}` 数组；kind 为 select／number／text；select options 是 `{value,label}`。来源只定义业务参数；Task 用 Core 控件渲染角色及必要条件，来源在保存时再校验。每个目标只提交一份意图，不接受可执行表达式。
- `Evaluate({goals})`：一次评估本 Provider 的显式目标集合；每项至少有 id、intent、revision。返回 `{sourceEpoch,revision,sourceTitle,evaluations}`；evaluations 按目标 ID 索引 `{task?,reason?,invalid?}`。缺项或返回异常按未知处理。各来源当前无硬批次上限，20角色批次已自动化验证，客户端压力另验。
- task 复用 action.todo v1 的展示信封：title、state(active/completed)、readiness、execution、beneficiary、temporal、freshness、可选 progress/summary/item/nextAction；Task 重写 itemKey／businessRef 为稳定 goalID。invalid=true 只有新鲜已知证据才能暂停目标，例如同装备实例已更换。
- sourceEpoch 是业务数据连续性标识；revision 随事实变更推进。freshness.state=known 且未超过 validUntil 才可完成；partial、stale、unavailable 均不误判。周期来源必须给 cycleKey 和下一变化时间，Task 不另算重置；持久目标使用 persistent。

来源只解释自己权威数据。制造持有模式经 Core 调用 Vault 的同版本 Evaluate，Vault 缺失只影响该模式；不读取库存实现。所有 source registration／change／unregistration 复用 Core 通知，不以查询触发反向全账号刷新。

### 0.3 目标 Service：action.demands v1.1

Todo 的 action.targets v1.2 可选提供当前角色图标执行描述与点击后验证，Task 主表／悬停经 Core 消费；接口、缺失行为、安全限制与验证见 [目标图标执行契约](行动中心-目标图标执行契约-v1.2.md)。原 v1.0 评估与 v1.1 添加入口保持兼容。

TaskHub 所有，providerID=`YiboTaskHub:demands`。Resolve major1 后调用：

| 方法 | 输入与结果 |
| --- | --- |
| Add | `{intent}` → `{id,existing?}`；缺参直接返回 Normalize 的配置描述。来源先规范化，单目标事务写入；以持久规范化 identity 实现重复点击／重试幂等，不需要额外 requestID；数量不自动累加 |
| Lookup | `{intent}` → 可选 `{id,state,revision}`；先经来源 Normalize，以规范化 identity 精确匹配（含角色、难度、模式等）；缺参数／来源不可用返回 nil，不把同对象的其它目标误标为已添加 |
| LookupItems（minor1） | `{intents}` → `{revision,items}`；逐项返回独立 `{count,active,paused,completed}`。匹配 providerID 与类型敏感 objectID；输入含 characterID 时仅匹配该角色或包含该角色的账号目标，无角色时汇总该对象全部目标。排除 removed；只读持久库，不要求来源就绪或参数完整，不代表精确重复／完成判断 |
| Update | `{id,revision,patch}` → `{id}`；patch 可含 intent、state(active/paused/removed)、priority(-100..100整数)、reopen。revision 不匹配拒绝；已完成转 active 必须 reopen=true，来源重校验，追加历史 |
| Query | `{}` → `{revision,goals}`，返回独立值副本，默认不含 removed；保留完成／暂停目标及历史 |
| Configure | `{intent}` → 打开 Core 壳内必要参数编辑，未保存不创建目标 |
| Locate | `{id}` → 定位 Core 壳内目标管理行 |
| PreviewCopy | `{goalIDs,destinations}` → `{token,added,existing,destinations,revision}`；仅角色目标，来源重新校验；一个有效暂存预览 |
| ApplyCopy | `{token}` → true；检查库 revision 并重新规范化全部项，通过后一次提交；不复制完成证据／历史 |

来源缺失、异常、major 不兼容和 epoch 改变保留已保存意图，给待核实原因。再次明确编辑才确认新 epoch。角色缓存删除保留目标；稳定 ID 迁移更新 scope 与 revision。目标数据归 Task，来源事实仍归业务。

LookupItems 供 Core 项目折角标记批量查询，消费方检查 major1 / minMinor1；索引按目标库实例与 revision 失效，状态计数读取当前目标，关闭服务释放索引。目标变化复用既有 BUSINESS_CONTRACT_CHANGED 通知；旧方法保持兼容。标记含暂停／完成目标，表示“已加入”，与精确 Lookup 的菜单✓区分。

### 0.4 生命周期、缓存与迁移

单次完成历史持久化并退出默认待办，重复 Add 定位原完成记录；周期配置不随重置重新创建；maintain 在确认回落后恢复。暂停／移除不改来源监控。完成通知合并到查询之后，避免回环。

仅按已添加目标分来源查询；空库无 Evaluate。缓存使用注册句柄、目标 ID／revision 和展示范围，来源通知定向失效，最迟60秒或来源边界失效；每来源最多24个范围缓存，四面复用。sourceFilter／hiddenWork 仍只是显示选择。

schema4 只迁移用户明确旧 Boss 计划，暂存成功后提交，保留旧 ID 关联、暂停及备份；Todo／Mail 自动来源行不导入。`task.boss-targets` v1 保留同一库的公开只读投影，原编辑与复制是写适配；适用版本、移除条件和验证见 [实施记录](行动中心-主动添加实施与验证.md)。现有 action.todo 来源公开方法保持兼容，生产 Task 走目标路径。

## 2. 最小连接机制：Core.Contracts

### 2.1 版本与依赖

- 当前 Service 最低 **API v9 / business-services:1**；后续中心 demands 可复用。首阶段 Provider／List 最低 **API v11 / business-providers:1**，已有运行实现，业务接入时须检查实际方法与契约版本。
- 使用 Service 检查 business-services:1；首次提示另检查 API v10 / account-view:2；Provider 检查 API v11 / business-providers:1。草案 business-contracts:1 不写入初始化。插件已有更高要求不得降低；不足时提示升级并停止相应接入，不增加全局对象回退。
- 原插件独立业务功能继续按自身既有初始化要求运行；连接版本不足仅阻止新集成模块，不能因此破坏本来可独立工作的业务。
- 业务契约版本独立于 Core API。v1 表示 `major=1, minor=0`；消费者指定所需 major 和最低 minor。major 必须匹配，不能把不兼容的 v2 自动当作满足 v1。
- 同一 major 新增可选字段可增加 minor；改变必填字段、既有方法语义或状态意义须升级 major，并处理已知消费者。

### 2.2 注册、发现和调用

```lua
-- Service 已有；Provider 与 List 已在 API v11 工作树实现。
Core.Contracts:Register(ownerAddon, definition)  -- registrationRef 或 nil, code
Core.Contracts:Unregister(ownerAddon, registrationRef)
Core.Contracts:Resolve(name, requiredVersion)   -- 单 Service 的 descriptor
Core.Contracts:List(name, requiredVersion)      -- 多 Provider 的 descriptors，按 providerID 排序
Core.Contracts:Call(callerAddon, descriptor, method, request)
Core.Contracts:NotifyChanged(ownerAddon, registrationRef, change)
```

注册定义只含以下需要的内容：

```lua
definition = {
  name = "action.todo",
  kind = "provider",             -- Core 支持；Todo 两项业务 Query 已交付
  providerID = "owner-addon:local-source", -- 所有者命名空间内的稳定来源标识
  version = { major = 1, minor = 0 },
  methods = { Query = handler },
}
```

Core 保存连接定义和回调，返回不暴露回调或内部表的描述符：能力名、kind、owner、providerID、版本与本次 registrationRef。描述符只能交回 Core 调用，不作为业务全局对象使用。

providerID 必须处于 ownerAddon 的命名空间，由 Core 检查归属，防止不同所有者在不同能力中使用同一个无来源前缀的标识。`requiredVersion` 使用 `{ major = 1, minMinor = 0 }`。方法回调形状为 `handler(requestCopy, callContext)`，只返回新建值结构或 `nil, code, details`；details 是可空的错误说明值结构，Core 在边界再次复制结果和 details。

`Call` 在查验注册、兼容版本、声明方法和调用方登记后，复制请求，构造调用上下文，隔离提供方异常并返回结果副本。上下文包含 `callerAddon`、能力、providerID、注册引用；消费方不能用请求中的 owner 字段替换该上下文。此标识用于来源记录与契约校验，不宣称 Lua 插件之间存在安全沙箱。

Core 不解释物品、配方、需求或任务状态。输入必须是可复制的值结构；业务参数、返回 schema 与业务判断由提供者校验，公开值不得夹带函数、内部数据库引用或执行对象。

### 2.3 冲突与生命周期

- Service 在同一能力和 major 下只能有一个所有者；冲突明确拒绝，不由最后加载者覆盖。
- Provider 以能力、major 和 providerID 区分。重复注册同一所有者、同一标识与定义保持同一注册，不重复发通知；不同所有者冲突明确拒绝。
- 同一能力／major 混用 Service 和 Provider 返回 kind-conflict。Resolve 只发现 Service，List 只枚举 Provider；无符合者返回空数组，不代表业务数据已知为空。
- 变更回调或定义通过显式注销再注册处理，旧 registrationRef 立即失效。稳定 providerID 保持业务来源引用，本次注册引用不写入持久需求。
- 注册不等于数据已采集。提供方先完成自身基础初始化再注册；查询可返回 `pending` 或 `partial`。数据就绪变化用变更通知表达。
- 消费方先订阅生命周期，再发现当前注册；Service 用 Resolve，Provider 检查 API v11 / business-providers:1 后使用 List。用注册引用去重，处理晚注册和注销，不为加载顺序添加业务 OptionalDeps。
- 注销后旧句柄调用返回 `unregistered`，中心保留需求与历史，相关事实待确认。重新注册后重新发现，不继续调用旧句柄。
- 消费方订阅使用稳定 owner；现有 Core.Events:Register 对同 owner／callback 幂等。重初始化产生不同闭包时仍须注销旧订阅，避免重复监听。

### 2.4 通知

沿用 Core.Events 已提供的三个事件；Provider 扩展继续保持同一负载形状：

| 名称 | 负载 | 语义 |
| --- | --- | --- |
| `BUSINESS_CONTRACT_REGISTERED` | 描述符 | 新连接可发现 |
| `BUSINESS_CONTRACT_UNREGISTERED` | 描述符、reason | 该次注册已失效 |
| `BUSINESS_CONTRACT_CHANGED` | 描述符、change 值表；epoch、revision、失效范围和 reason 位于表内 | 所有者已提交数据变化或数据失效 |

提供方通过 `NotifyChanged` 提交最后一种通知，由 Core 校验注册归属并附加描述符；通知不携带全量业务数据库，不指定其它插件执行私有方法。

写入和 revision 提交先于通知。中心按来源、角色和对象合并刷新；重复通知允许出现，广播顺序不作为正确性条件。页面读取与缓存重算本身不广播数据变化；中心只有自身需求状态或设置确实改变时才发布中心变化，避免循环。

现有契约通知通过 Events:FireIsolated 分别提供负载副本并隔离回调异常，分发开始时取得订阅列表快照。一位消费者失败或修改负载不影响其余消费者；新增 Provider 通知复用该入口，旧 Events:Fire 的行为保持原状。

## 3. 公共查询规则

### 3.1 范围与角色身份

- 跨角色枚举和事实查询显式传 `scope = { characterIDs = { ... } }`，无默认的全账号查询；空数组表示空范围。调用方去重并保留 Core 提供的角色顺序。精确 demandID、goalRef 或单 characterID 的方法以该引用限定范围，不悄悄扩为全账号。
- 页面与悬停从同次 `context.characters` 构造范围；首阶段登录摘要／HUD 从 Core 当前角色构造显式范围，账号投影从 Core 当前有效目录构造范围。后续需求后台工作另使用已保存需求的角色引用，不读取其它页面暂存选择。
- 名称、短名、地址文本不是关联键。角色 ID 变更按 Core 的身份迁移通知处理，双方迁移各自引用；未知角色保持待确认。
- 需求和历史的保存范围与当前页面显示范围分开。隐藏或筛掉角色不会自动取消它的需求，也不会释放其在途预留；查询隐藏角色仅在有明确需求引用时显式进行。
- 最终需求角色、承接角色和本段接收角色分别传递。跨服务器或其它转交限制由相应业务提供者判断，不由中心按名字推断。

### 3.2 查询结果与失败

所有只读业务查询使用如下外壳：

```lua
{
  providerID = "stable-provider-id",
  sourceEpoch = "persisted-data-generation",
  revision = 12,
  generatedAt = 0,
  status = "ready",              -- ready | pending | partial | error
  coverage = {},                 -- 本次请求涉及对象的状态和时效
  data = {},                     -- 按能力定义
}
```

`sourceEpoch` 由数据所有者持久维护，数据库重建或历史身份不能连续时必须更换。`revision` 在同一能力名、providerID 与 epoch 内单调推进并持久保存；不同能力、不同来源、不同 epoch 的数值不能比较大小。注册引用只描述本次运行连接，不能代替持久的数据 epoch。

coverage 使用 `known`、`known-empty`、`partial`、`stale`、`not-yet-scanned`、`unavailable`、`error` 表达具体角色或来源范围，可包含 observedAt、clockSource、validUntil、nextChangeAt 与业务判定说明。

- `ready` 只说明查询已完成，不保证所有返回记录都可用于自动操作；每条记录仍须检查证据和时效。
- coverage 未覆盖的对象不能当成零。只有明确覆盖且已知为空的对应来源，才支持空结果判断。
- 已确认历史事件与当前快照的时效分开。后续来源变 stale 不会抹去已确认寄出历史，但不能肯定物品仍在原位置。
- 提供方给出快照是否足以支持正向资格、预留或完成判断。消费者不得自行统一设定某个天数就宣布业务事实有效。
- 离线快照的正向计划依据与当前执行依据分开。提供方可显式返回 `mayReserveFromSnapshot`、`canExecuteNow` 和理由；中心只在前者明确为 true 时建立计划预留，执行前仍须由当前角色的数据重新检查。旧 API 仅有 stale 数量时不能由适配器无依据地改为可执行。
- 能操作的准备步骤与最终动作分开。提供方可返回只读 `nextAction` 提示，例如先打开专业界面或前往邮箱；中心可以提醒已确认可推进的准备工作，但不能因此声明当前已可制作或发送。
- 周期待办由来源提供 cycleKey、快照时间、业务 nextChangeAt 和失效状态；中心只按来源声明刷新，不另算日常或周常重置。
- 查询只读已有快照和可用目录，不触发开专业窗口、打开邮箱、制作、寄送或扫描 UI。未准备好返回 pending，并通过变化通知提示可重试。
- 参数错误、未注册、版本不兼容、未声明方法或提供者异常返回 `nil, code`。主要代码为 `invalid-request`、`not-found`、`incompatible`、`unregistered`、`method-unavailable`、`provider-error`。业务未知状态通过 coverage 表达，不伪装成接口异常或已知空数据。

### 3.3 身份与引用

业务引用使用 `{ capability, providerID, sourceEpoch, key }`；capability 明确引用属于哪种契约，key 是所有者内稳定的不透明键，不能由中心按标签重造。方法所属能力已明确时允许省略重复的 capability 字段，保存为持久引用时必须补齐。

物品需求使用 `itemID` 及所有者要求的严格 variantKey／匹配条件。匹配策略由目标描述和提供者共同声明；中心不默认把所有同 ID 变体当作等价。

物理 `sourceID` 是快照位置引用，背包格、mailKey、附件序号和 itemLink 均不宣称为永久物品实例 ID。中心可有自己的 supplyRef 与数量预留记录，但这只是需求分配身份，不是业务物品身份。

没有足够证据把两个来源或操作关联为同一份数量时，保留待核实，不能通过时间相近、同名或同数量自动确认。

### 3.4 最小值结构

| 结构 | 必填内容 | 可空或按类型填写 |
| --- | --- | --- |
| BusinessRef | capability、providerID、sourceEpoch、key | 显示标签，仅供展示 |
| ItemSelector | 正整数 itemID、明确的 identityMode（item-id 或 strict） | strict 时提供 variantKey；无法提供则身份待确认 |
| GoalSpec | goalRef、intentKey、需求角色、目标引用、目标数量／业务目标、最终判断来源 | 物品目标含 ItemSelector；非物品目标以业务结果表达，数量不适用时省略 |
| Assignment | mode（open 或 assigned） | assigned 必须有 characterID 和适用 goal／任务类型；角色集合候选不是多份分派 |
| NextAction | kind、标题与提供者确认的可推进依据 | 对应业务引用和阻塞说明；不包含可执行函数 |

物品目标数量为正整数；非物品目标的进度单位由所有者定义。Plan 输入包含目标 ItemSelector、requestedQuantity、scope；CheckActor 引用 Plan 的 planRef。Inventory 输入的 items 是 ItemSelector 数组；物流请求的 item 同样使用 ItemSelector。

通用 scope 转为现有 Items v1 时，由 Vault 自身适配器使用 `{ mode = "characters", characterIDs = ... }`，保留显式顺序与状态语义；这项转换不由中心识别插件名称执行。

## 4. 能力总表

首阶段只实施 action.todo 及其实际所需的 Core Provider 机制。其余 action 能力保留为后续场景契约，按真实消费需求逐项交付；mail.items 是已经存在的附件协议。Core 使用同一个连接机制，不为每个业务插件建立专用目录。

| 能力名 / v1 | 机制 | 最小方法 | 权威所有者与消费方 |
| --- | --- | --- | --- |
| `action.demands` | Service | `Submit`、`Get` | 中心保存需求；来源业务下发并查询结果 |
| `action.todo` | Provider | `Query` | 各业务生成即时待办；中心枚举聚合 |
| `action.targets` | Provider | `Describe`、`Evaluate` | 目标来源拥有业务目标和完成判断；中心组织任务链 |
| `action.production` | Provider | `Plan`、`CheckActor` | 制造业务拥有配方、产出、材料和资格；中心选择及分派 |
| `action.inventory` | Service | `Query` | 库存聚合所有者提供统一物品位置投影；中心分配数量 |
| `action.logistics` | Provider | `CheckRoute` | 对应转交业务判断路线条件；中心安排具体转交工作 |
| `action.evidence` | Provider | `Query` | 每类操作事实由其所有者提供；中心关联历史与阶段 |
| `mail.items` | 已有 Service | `GetState`、`GetByCharacter`、`GetRevision` | 邮件附件所有者复用 Items v1；Vault 已通过 Core 发现来源 |

`action.inventory` 采用单 Service，是为了只选择一份账号库存聚合视图。Mail 当前附件供给通过 Vault 的来源选择进入库存，不再由中心额外叠加。Mail 的寄出／收取事件通过 evidence 提供，不算第二份库存。

所有方均只在有真实方法实现后登记能力。首阶段以 YiboTodo 输出说明 action.todo，后续以 Builds、Crafting、Vault、Mail 说明跨角色需求职责；中心依能力与来源引用发现，不能在运行时维护按技术名分支的适配表。

## 5. 后续契约 action.demands：用户需求写入

### 5.1 Submit

```lua
request = {
  requestID = "stable-retry-key",
  intentKey = "source-business-intent-key",
  source = { pageID = "...", businessRef = { providerID = "...", sourceEpoch = "...", key = "..." } },
  goals = { goalSpec },
  priority = "normal",
  assignment = { mode = "open" }, -- 或指定角色的明确约束
}
-- result = { demandID, demandRevision, outcome = "created" | "existing" }
```

goalSpec 来自目标来源的 Describe，含需求角色、目标引用、所选物品／业务目标、数量与目标能力引用。中心在写入前通过已发现的来源契约验证引用和参数；不接受另一业务伪造来源所有权。

- `requestID` 解决同次操作重试；来源必须复用该 ID，不能每次重试都产生新键。
- 同一来源 owner、intentKey、目标周期和目标身份形成持久去重依据。同目标再次点击返回已有需求，不自动加量。
- 去重命中但目标或数量不同，返回 `nil, "intent-conflict", { demandID, demandRevision }`，转主窗口编辑，不静默覆盖。
- 已完成或已取消需求的重试返回已有状态；明确新增目标或重新处理由主窗口操作表达，不靠重新 Submit 绕过去重。
- 写入为一次中心事务：验证、创建需求及初始任务、保存去重关系、提交 revision，再通知。失败不留下半份需求或预留。
- Service 缺失时来源业务只禁用需求下发入口，原候选、实时提升等基础功能继续运行。

中心自建需求直接使用同一内部事务和校验；手动目标以中心自己的规则管理，不伪造外部目标来源。

### 5.2 Get

请求 `{ demandID }`，返回状态、revision、目标摘要和关联任务的只读摘要。来源业务可用结果定位主窗口；不公开中心内部可修改对象。

主窗口的编辑草稿、影响预览、承接与人工校正属于中心内部功能，本轮没有跨业务消费者需要这些写操作，不提前扩展公开 API。

## 6. 首阶段契约 action.todo：来源任务聚合

### 6.1 所有权、输入与输出

2026-10-09 实现定稿：首项 Provider 为 YiboTodo:profession-cooldown v1.0；外壳可提供 `sourceTitle` 作为业务显示名称，缺失时中心使用登记 owner。`coverage` 为以 Core 角色 ID 为键的值表，每个请求角色均须明确返回覆盖状态。角色顺序由请求与 Core 决定；任务记录不携带内部函数或数据库引用。首项的数量／进度没有观察依据，省略。Source epoch／revision 与可再生指纹元数据由 Todo 自己保存，中心不持久化业务任务；具体版本与失败验证见 O2 记录。

提供方为生成该工作的业务插件，消费方为 TaskHub；来源保存自己的任务安排、判断、周期与完成状态。中心只读展示，保存自己的设置和可再生投影。TaskHub 不写来源数据库，也不提供来源任务的通用完成按钮。

`Query({ scope })` 使用 §3 的明确角色／账号范围及查询外壳，`data = { tasks = {...} }`。查询读已有快照，不触发扫描或游戏操作。coverage 须说明请求范围内哪些角色已知、已知无任务、未采集或过期；空数组只有对应范围明确 known-empty 时才说明无任务。不能直接使用来源页面当前可见角色作为查询范围。

最小记录为值表，实际编码在首个来源字段映射与实现验证时定稿：

```lua
task = {
  itemKey = "source-stable-task-key",
  businessRef = { capability = "action.todo", providerID = "...", sourceEpoch = "...", key = "..." },
  title = "...",
  summary = "...",
  execution = { mode = "self", characterID = "core-character-id" },
  -- mode: self | assigned | open | account
  -- open/account 按来源依据提供 candidateCharacterIDs；未知不等于所有角色都有资格。
  beneficiary = { mode = "character", characterID = "core-character-id" },
  -- mode: character | account | unknown；受益者不自动成为执行者。
  state = "active", -- active | completed | paused | cancelled
  readiness = "unknown", -- actionable | preparation | blocked | unknown | not-applicable
  reason = "...",
  temporal = { kind = "cooldown", cycleKey = "...", nextChangeAt = nil },
  -- kind: daily | weekly | cooldown | persistent | other；cycleKey 按业务是否有周期提供。
  freshness = { state = "known", observedAt = 0, validUntil = nil, clockSource = "server" },
  nextAction = { kind = "open-page", title = "查看业务页面", pageID = "..." },
  priority = nil,
  item = nil, quantity = nil, progress = nil,
}
```

execution、beneficiary、状态／就绪性、周期性质和 freshness 为每条记录明确声明。self/assigned 必须提供执行角色；self 表示来源确认该角色为自己做，受益者须一致。assigned 可以为其他角色做。open 表示未分派的同一工作；account 表示账号工作，其候选范围同样由来源解释。open/account 的候选集合不完整时在 coverage 或 reason 声明，中心不自行补齐角色。

nextAction、物品、数量与进度按来源实际能力填写；缺少动作入口时仍可展示任务。已有业务页面跳转复用 Core 注册页面，不返回函数或技术名分支。仅有 pageID 时打开页面；精确定位业务对象只在已有受控接口支持时使用。首阶段不新增无真实消费者的通用执行接口。

2026-10-09 显示增量：可选 `icon` 为正整数 WoW 纹理 ID 或不含 `|` 的非空纹理路径，属于来源拥有的显示元数据；缺失时消费方使用通用任务图标。已有 `item.itemID` 的图标由消费方复用 Core ItemResolver 加载，不触发业务查询或物品扫描。非法 icon 按 invalid-icon 拒绝该来源结果；这是 v1.0 向后兼容的可选字段，旧消费方可忽略。TASK 0.3.0 的待核实折叠仅改变投影，保留每项原始身份、数量与引用，见 [收拢记录](行动中心-概念图收拢与流程修正.md)。

state 与 readiness 分开：active 不等于可执行，preparation 只说明已确认可推进的准备动作，不承诺最终制作或寄送已可执行。未知 beneficiary 按 unknown 返回，不默认当前角色。物品数量和进度是来源当前快照，每次刷新替换，不累计叠加；非物品工作可省略数量。

### 6.2 身份、归属与去重

- 唯一任务身份由能力、providerID、sourceEpoch、itemKey 和适用 cycleKey 组成；来源保持 businessRef 与 itemKey 的关系稳定。持续工作跨日不换身份，周期任务由来源提供周期身份。
- 同一查询中一条开放／账号工作只返回一条记录，候选角色集合附在其上；当前角色和其他角色列表是这条记录的投影，不增加任务数量。
- 来源指定 C 后不再保留 D 为开放候选；来源完成后，中心同步更新两个视角并停止该项行动提醒。登录、查看、隐藏或排序不触发承接和完成。
- 已安排工作、候选机会和等待／未知分组展示。角色统计可包含候选数，账号唯一任务数不能把各角色候选数相加。
- 同标题、同物品或相近时间不足以合并不同来源任务。来源存在多个投影时须使用同一权威 businessRef；跨来源未明确关联的工作保持独立并显示来源。
- TaskHub 不从 Builds 的缺口与 Crafting 的资格自行组合出制作安排。跨角色工作须由来源真实提供；用合成输入测试归属只证明投影规则，不代表已交付跨角色下发能力。

### 6.3 今日、时效与两个角色视角

当前角色视角按 execution 匹配 Core 当前角色，展示自己的工作、为他人执行的工作和明确可承接候选。其他角色视角使用同一集合排除当前角色并按角色分组。账号工作保留一份身份，候选或账号区域可以引用它；受益者身份不改变执行者筛选。

“今日”按 temporal 和来源业务状态解释。日常、周常、冷却到期和长期工作可同时进入今日列表，分别标注周期；中心不统一按本地午夜清空或创建新任务。来源负责给出下一变化时间及失效语义，中心仅按声明重新读取／标记失效。

freshness 的 known、partial、stale、not-yet-scanned、unavailable、error 与外壳 coverage 保持一致。离线工作可以保留可信观察，但是否可行动取决于来源正向依据；过期或未知工作不产生肯定的可执行摘要。completed、paused、cancelled 默认退出行动提醒，来源没有覆盖的范围不能推断为这些状态。

### 6.4 更新、缓存与失败

来源先提交自身状态与 revision，再通过既有 CHANGED(descriptor,change) 通知；中心按来源和影响范围合并查询、重建投影与页面刷新。通知是失效信号，查询返回任务结果，不要求全量任务经广播往返。

中心先订阅再 List，按注册引用维护连接，持久任务引用使用来源 epoch。重复通知和重复记录不重复计量；查询及缓存重算不再发布同一业务变化。首次查询和晚注册返回数据后重新投影，注销、旧句柄或版本不兼容停止相应调用并使该来源缓存失效。单来源异常仅隔离其范围。

可再生缓存默认留内存，重载后重新查询；中心 settings 可持久化，运行描述符不持久化。首次来源接入时，来源自己的 epoch／revision 采用实际数据生命周期维护，不能用登录次数制造新任务身份。缺来源与已知无任务的提示分开，其他有效来源继续显示。

### 6.5 后续关联

后续需求能力交付后，同一业务引用和周期下的来源任务与持久需求可以建立显示关联；关联按稳定引用，不按标题猜测。goalRef 和“保存为需求”入口只在目标描述与需求消费者真实交付后增加，不构成首阶段的必填字段或初始化要求。

## 7. 后续契约 action.targets：目标描述和最终完成

### 7.1 Describe

输入来源 businessRef、用户选择和必要的目标 revision；输出 goalSpec：

- goalRef 与 intentKey，需求角色、目标对象引用与目标版本。
- 所选产物或业务结果、数量、匹配条件、业务能力需求。
- 来源校验过的最终完成条件，以及后续 Evaluate 使用的不透明参数。

Builds 必须区分装备身份与附魔／宝石字段的正常变化；不能把提升后 itemLink 变动直接判成换装，也不能用裸 itemID 确认是原来的那件装备。当前快照能否证明同一装备对象须验证，不能证明时返回 identity-ambiguous。

用户在中心改物品、配方、最终角色或目标后，由对应 Describe 重新验证目标规格；暂缺来源时保留编辑意图并标记待确认，不伪造来源批准。

### 7.2 Evaluate

输入 `{ goalRef, scope }`，输出：

```lua
data = {
  state = "active", -- active | satisfied | invalidated | unknown
  fulfilledQuantity = 0, -- 仅有足够完成依据时可用，否则为 nil
  targetRevision = 0,
  identityState = "confirmed", -- confirmed | ambiguous | unknown
  evidenceRefs = {},
  reason = nil,
}
```

这是目标当前状态快照，fulfilledQuantity 是该目标当前累计满足量，不能每次刷新都作为新完成数量相加。

- satisfied：确认最终目标满足；中心完成需求并处理未来预留，保留已寄出物流。
- invalidated：来源确认原目标已失效；中心暂停。
- unknown／ambiguous／stale：等待核实，不能当成 invalidated 或完成量零。
- 成品已制作或已收取，只推进相应步骤，不能代替最终 Evaluate。
- 来源更换业务目标时返回新的目标引用与去重身份，不修改已有需求引用的历史。

## 8. 后续契约 action.production：计划与制造资格

### 8.1 Plan

输入目标产物及需求数量、严格匹配条件、显式角色范围；返回候选计划：

- planRef、配方／能力引用、产物及适用匹配条件。
- 本次 requestedQuantity 对应的计划制作次数、预期产量范围及材料需求。
- 材料数组各项的物品条件、数量和所需阶段，及材料／产出数据覆盖状态。
- 角色候选和其正向已学证据状态；缺少完整学习扫描时其它角色是 unknown，不是明确未学。
- 可分批处理的数量边界和产出条件。来源负责制作批量、产率、随机产出与材料规则，中心不另算配方业务。

产物对应多配方时返回候选，中心保留用户选择；缺配方或材料证据不自动选择一份虚构方案。附魔的直接施加与卷轴产物不能混为一个物品计划；卷轴身份、材料和产出关系未确认时不自动生成邮寄卷轴工作。

### 8.2 CheckActor

输入 `{ planRef, characterID, requestedQuantity }`，返回正向资格、当前是否可处理、阻塞原因、就绪数量、材料需求与时效。

`eligible` 表示确认具备业务资格，`actionable` 表示按已确认条件当前能操作；未知为 nil。中心还要检查承接、预留和任务前置，因此 CheckActor 的 actionable 不会单独覆盖中心分派。

离线角色只返回快照能够支持的结论。库存材料和已学配方各有覆盖状态；确认已学不能自动推断材料充足或不存在其它业务限制。

制作实际发生由制造所有者的 evidence 提供。仅背包增加不能证明该任务发生制作；关联不足时显示待核实或由用户确认。当前 Crafting 尚无这项公开证据能力，集成阶段须明确补充与客户端验证。

## 9. 后续契约 action.inventory：统一供给查询

`Query({ scope, items, purpose, destinationCharacterID })` 使用多个物品／严格匹配条件一次查询，返回：

- 现有 Items v1 的物品身份、数量、characterID／guildKey、source、sourceClass、sourceID、位置、coverage 和快照时间。
- 原始所有者引用 originRef，用于 Vault 采用 Mail 来源时识别出处；聚合来源改变不能让同批附件成为新供给。
- 正向使用资格：是否匹配目标、是否可访问、绑定／限制是否已知，以及数据是否足以支持预留；unknown 不当成 true。
- 在途／附件与实体库存分别表达，AH 不作为可立即交付库存。

中心在可信数量上施加自己的需求预留，不能要求 Vault 维护中心的预留数据库。新库存查询发现已预留物品的来源失效时保留核实量，不立即给其它需求重复分配。

现有 Items v1 没有足够字段时，由 Vault 提供方明确返回未知并按新契约补充必要字段。不得让中心扫描其它插件私有 DB 或只凭 GetPersonalCounts 的汇总值完成位置关联。

公会银行是共享库存，不能重复计入多个访问角色。仅看见数量不能确认有权取用，权限不足或未知时提供位置线索。

### 9.1 既有附件 Service 与元数据扩展

当前 mail.items v1.0 已注册，方法为 GetState({characterID})、GetByCharacter({characterID,options})、GetRevision()，准确签名以 [Core API v9](../YiboCore/Docs/API-v9-业务服务与刷新.md) 为准；业务返回语义沿用 [附件 API v1 契约](YiboVault-Mail-API-v1-契约.md)。该 Service 没有 Query 方法，也不套用 action 查询外壳或提供完整物流证据。

Vault 已通过 Core Resolve／Call 获取附件并监听生命周期。providerID 从描述符获得；持久 sourceEpoch、originRef 等新增元数据须由 Mail 所有者维护，在真实来源关联需求出现时按兼容版本扩充副本结果，不能假定当前返回已含这些字段，也不能改写旧 Items API v1 的既有语义。

每个角色只选择一份邮箱投影。Mail 缺失／禁用／注销／不兼容时，Vault 独立采集继续可用；Mail 已注册但尚未完成扫描时等待其采集，不能认定邮箱为空或重复开始采集。partial、stale、error 和可信历史快照沿用现有服务链的覆盖语义，不因结果不完整静默切换为更旧缓存。originRef 标明所选来源，来源更换时重新核对关联而不叠加数量。

现有 MailProvider 边界和 TOC 的邮件加载顺序依赖迁移已完成；本轮只补需求级元数据与关联，未涉及的其它旧 Items 消费者不要求一次性修改。

## 10. 后续契约 action.logistics：转交路线资格

`CheckRoute({ fromCharacterID, toCharacterID, item, quantity, mode })` 返回：

- 路线是否具备业务资格、当前是否可操作，分别允许 true、false、unknown。
- 可支持的数量、阻塞原因与有效性状态，及物流能力的来源引用。
- 邮寄／交易等方式由对应提供方解释。Mail 首批只判断自己的邮寄方式，不替其它运输业务推导规则。

成功寄出后的事实目的地不可编辑。中心修改意图时保留原段，再根据路线检查安排未来转交；不把新收件人替换进已发生记录。

Query 类方法不打开邮箱、不填入收件人、不发邮件。业务页面跳转和操作预填如有实际需求，后续另立最小操作契约；本轮只定义计划与证据连接。

## 11. 后续契约 action.evidence：可关联事实

### 11.1 Query 请求与覆盖

请求含 scope、事实类型、业务／操作引用，以及分页 cursor 和 limit。提供方可按其声明的限制分批返回；中心不可因拿到第一页就推断历史完整。

返回外壳的 data 含 facts、nextCursor、complete；coverage 另说明证据时间覆盖、历史是否因清理截断、可关联性及版本连续性。cursor 不透明，并绑定 providerID、epoch、过滤条件及查询边界；无法继续一致查询时返回 snapshot-changed，中心重新查询而非拼接不一致页。

事实类型首批只覆盖真实流程：production-confirmed、send-confirmed、receive-confirmed、return-confirmed、external-transfer-confirmed 和 target-satisfied。提供者仅返回自己确实采集并解释的类型；AH 上架不等同于售出，库存消失不等同于 external-transfer-confirmed。

### 11.2 单条事实

```lua
fact = {
  factID = "owner-stable-fact-id",
  subjectRef = { providerID = "...", sourceEpoch = "...", key = "..." },
  factVersion = 1,
  type = "send-confirmed",
  occurredAt = nil,
  observedAt = 0,
  clockSource = "server",
  fromCharacterID = "...",
  toCharacterID = "...",
  recipientScope = "account", -- account | external | unknown
  items = { { itemID = 12345, quantity = 1 } },
  operationRef = nil,
  originRefs = {},
  resultRefs = {},
  correlation = "ambiguous", -- confirmed | ambiguous | unlinked
  basis = "observed",       -- 提供者说明观察或确认依据
}
```

- 事实身份是 evidence 能力的 providerID、sourceEpoch、factID；同一事实重放只处理一次。factVersion 更新的是同一事实说明，不能作为又发生一次操作。不同能力的快照 revision 不作为证据事件 ID。
- occurredAt 无法确定时为 nil，observedAt 不冒充实际发生时间。只有契约能比较的同一主体／版本才用于先后判断，不能按跨插件时钟全局排序。
- 明确的起止角色、数量和 origin／result 引用用于同批物品转移；角色地址不能解析时保留 unknown，不按短名认定是自己的角色。
- 无法在当前目录中找到收件人不代表已确认外部角色。recipientScope=external 须有业务依据；缺证据时保持 unknown，不能据此宣布供给已售出或流失。
- correlation=confirmed 要有提供者可说明的业务关联依据；同物品、同数量、时间接近只够产生候选，不能确认属于需求。
- 中心保存采用的最小事实投影与引用，用于自身工作流审计；不复制完整邮件历史或库存数据库。
- 对已知事实的撤销、修正或失效要关联原 factID 并说明依据，不能删除查询结果就让中心推断发生反向操作。

### 11.3 当前能复用的证据与限制

Mail 内部成功发送记录与 `collected-archived` 记录具有 eventID，可作为公开投影的基础；必须加上稳定 epoch、准确数量、角色及操作关联。内部记录不能由中心直接读取。

当前业务库尚未提供本契约的持久 epoch 时，必须在提供者自己的数据生命周期中补充；不能用登录时间或重新注册次数伪装成连续的数据版本。对旧数据关联无法证明连续的范围，应声明新 epoch 和覆盖限制。

Mail 现有历史会按设置清理，公开查询须报告 retention 截断。查不到历史不是“从未寄出”，不能取消已保留的中心事实或生成重复制作。

当前接口没有通用的跨角色永久物品身份。完全相同的多份邮件、堆叠变化、原生 UI 外部操作等场景可能不能确认关联；此时按已确认的待核实和人工校正流程处理，不能承诺所有交易／售出都能全自动识别。

如未来要把任务引用带入业务操作，需先定义真实的用户操作预填和作用范围，再由业务产出 operationRef。本轮不创建无使用者的操作绑定 API，不把缺少 operationRef 的事实一律视为已关联。

### 11.4 合并与冲突

中心先按事实身份去重，再核对供给引用与阶段；寄出、在途、收取是位置或阶段迁移，不能叠加为三份供给。

较早、可比较的快照不倒退较新的已确认进度。真正的自动事实与人工校正冲突时保留双方，隔离受影响任务和数量，由用户核实；其它独立工作继续运行。提供方不能用通知要求中心清除人工记录。

## 12. 后续跨角色需求闭环的调用顺序

1. Builds 通过自己的 targets 描述用户选定提升，使用发现的 demands Service 提交需求；缺中心时基础提升仍正常。
2. 中心读取目标规格；向 inventory 查询成品并施加自身数量预留，已有可信成品就进入交付／使用阶段。
3. 仍有缺口时查询 production 的计划和候选。中心自由承接或用户指定制造者后，再确定材料转交目的地。
4. 查询材料位置及 logistics 路线；能确认条件时生成转交工作，不能确认时显示线索或待核实。
5. 数据所有者在真实操作发生后提交 evidence，并发轻量变化通知。中心按影响范围读取、去重和推进数量，部分已完成数量可先流转。
6. 中心查询 targets Evaluate；最终目标满足才完成需求，目标失效则暂停。售出等确认供给流失后先寻找替代成品，再为剩余缺口新增补做。
7. 页面编辑数量、角色或目标在中心执行影响预览和事务保存；已发生的证据保持原记录。主窗口、只读悬停、常驻面板和提醒读同一工作投影。

同账号切换角色依靠各所有者和中心的持久记录继续查询，不在本轮增加在线消息传输。来源读取缺口和时效仍必须如实显示。

## 13. 缺失、注销与数据重建

| 情况 | 中心与来源的行为 |
| --- | --- |
| 中心 Service 不存在 | 来源禁用下发增强，原业务继续工作 |
| 业务契约缺失或版本不兼容 | 需求保留，相关资格或事实未知；能人工管理的功能继续可用 |
| 晚注册 | 生命周期通知后重新发现并查询，避免重复来源、订阅和 UI |
| 单提供者异常 | 标记来源错误，只隔离相关工作，不影响其它来源 |
| 来源注销 | 旧句柄停止调用，派生缓存失效；保留需求与已采用历史事实 |
| sourceEpoch 改变 | 旧新修订不比较大小；重新核对引用，不能把新库的同编号当成旧事实 |
| 删除角色或业务数据 | 由各所有者处理自身数据；中心保留受影响需求并显式标记失去角色／来源，等待用户处理，不自动删除用户目标 |
| 清理业务历史 | 查询报告截断；中心既有审计仍在，未关联旧事实不被猜测成零 |

## 14. 验证门槛与实施边界

### 14.1 Core 连接验证

- 同 owner 重复注册不重复通知；不同 owner 的 Service／Provider 冲突明确失败。
- major 不兼容不发现；注销旧句柄不能调用；晚注册和重注册可恢复。
- 输入与输出副本隔离，未声明方法被拒绝，业务异常不污染其它提供者。
- 订阅可清理，不依赖广播顺序；提供方写入先于变更通知。
- 现有账号页面、设置、入口和 API v8 既有调用保持行为兼容。

### 14.2 首阶段任务总览验证

- 首项专业冷却输出与来源 Model/Snapshot 一致；已知无任务、未采集、部分、过期与异常分开。
- 当前角色为自己／他人执行、开放候选、账号工作与其他角色分组；受益角色不被当成执行角色。
- 同一工作多候选仍一份身份；指定后退出其他角色候选；完成后两个视角同步停止行动提醒。
- 周期更新由来源解释，长期工作跨日保持身份；离线未知不产生肯定的可执行摘要。
- 来源 Query 不修改来源页面范围，中心字段／排序设置不修改来源业务状态；重载后由查询重建缓存。
- 正常、缺失／禁用、异常、不兼容、晚注册、注销、重注册和 epoch 更换；重复通知不重复任务或订阅。
- 第二个真实来源通过同契约接入，中心无技术名分支；合成跨角色输入与真实来源验收分别记录。
- 主页面、账号悬停、当前角色 HUD 和登录摘要同一投影，登录提醒只发一次，未知／过期不计为可做。

### 14.3 后续需求与业务契约验证

- Submit 重试、重复点击和修改数量冲突；不能产生两份需求或半份任务链。
- 配方正向已学与未知区分，材料和产出关系必须有依据；角色有资格但缺材料不能显示当前可制作。
- 目标装备正常提升与真正换装、身份不明分别处理；最终累计完成不能重复加量。
- 明确范围、隐藏角色、账号级待办及 cycleKey，页面与后台范围不会相互覆盖。
- 成品、材料、邮件、AH 和公会库存不重复计数；未知权限或不可转交不能自动预留。
- 制作／寄送／收取证据重放、截断历史、跨 epoch、同内容邮件、多来源重叠和人工冲突。
- [模型审查](行动中心-详细模型审查.md) 的部分流转、补做、改派及在途编辑全部成为后续实际测试和游戏验收用例。
