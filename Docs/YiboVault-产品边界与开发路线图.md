# YiboVault 产品边界与开发路线图

> 状态：正式产品方案，作为 YiboVault 后续设计与实施的范围基准。
>
> 关联讨论稿：[Yibo 系列业务插件方向头脑风暴（临时）](Yibo系列业务插件方向头脑风暴-临时.md)

> 实施状态：背包/装备、Core 查询页、个人银行、公会银行和 AH 已完成主要客户端检查；角色仓储/容量视图已获用户确认，物品 Tooltip 的基本显示与数量汇总已获截图验证。Vault 独立邮箱附件采集已通过基础客户端验证，部分可见邮件仍待边界验收；`storage.summary` 已开放，YiboCurrency 已可选接入物品代币来源明细。

## 一、产品定位

YiboVault 是 Yibo 系列的账号物品缓存与查询服务。它回答：

> 账号当前已记录了什么物品、各有多少、分布在哪里？

YiboVault 的核心价值是让 Core 和其它 Yibo 子插件能够查询角色已缓存的物品数据。物品主窗口和 Tooltip 是这些数据面向玩家的查询界面；自动采集是数据进入缓存的方式。

YiboVault 不要求用户逐个登录角色来响应每一种新查询。其它插件可直接读取已有缓存；如果某角色或容器从未被采集，Vault 不会编造数据，也不显示缺失提示。用户通过登录角色、打开背包或访问银行等正常行为控制数据何时进入或刷新缓存。

## 二、产品原则

1. **只呈现有依据的数据。** 物品、容量和位置均来自成功采集的快照；未采集的位置不生成零库存或缺失警告。当前角色的已知来源可提示待刷新；其它角色的数据作为各自最近一次记录展示，不附加“陈旧”标签。
2. **按位置逐步积累。** 每次访问某个物品位置时，采集并更新该位置的缓存；其它角色或位置的数据不因此被判定为缺失或过期。
3. **一份缓存，多处查询。** 主窗口、物品 Tooltip、Core 与子插件使用同一物品身份、数量汇总和位置分布逻辑。
4. **Vault 提供事实数据。** “需要哪些材料”“哪个角色适合使用物品”等业务判断由调用方负责。
5. **邮件附件可独立采集。** Vault 保存满足物品统计所需的精简附件快照；Mail 未来维护完整邮件生命周期。两者共存时 Vault 对每个角色只选一份附件来源。

## 三、数据来源与责任边界

| 数据来源 | 采集责任 | Vault 展示与查询范围 |
|---|---|---|
| 角色背包 | YiboVault | 角色、服务器、容器及物品数量 |
| 角色装备栏 | YiboVault | 已装备物品及数量/槽位信息 |
| 角色个人银行 | YiboVault | 角色、服务器、银行容器及物品数量 |
| 公会银行 | YiboVault | 公会及可确认的页签/位置、物品数量 |
| 邮件及附件 | Vault 当前采集精简附件；Mail 将来独立管理完整邮件 | 待取附件进入 Vault 外部来源小计；共存时优先 Mail 公共来源，避免重复计数 |
| 拍卖行上架商品 | YiboVault | 玩家当前角色在 AH 上架且可读取的商品、数量及上架信息 |

Vault 只保存当前可见收件箱附件的精简物品快照；YiboMail 将独立负责完整邮件快照和生命周期。Vault 的物品总量可聚合邮箱附件，但查询结果必须区分背包/银行实体库存与待领取附件。双插件共存时，按角色选取一份来源，不叠加两个快照。

YiboVault 负责缓存与展示角色当前在拍卖行（AH）上架的商品，因为 Yibo 系列目前没有专用 AH 插件。Vault 不因此扩展为完整拍卖行经济插件；货币、配方、任务需求和邮件处理操作仍不属于 Vault 的数据所有权。

## 四、玩家界面

### 主窗口

- 通过 YiboCore 的统一账号工作台进入，不另建独立窗口壳或第二套设置入口。
- 全量呈现当前已采集、可查询的物品数据，支持按物品名称/ID搜索，并按 Core 当前服务器和角色范围筛选。
- 物品格显示图标与堆叠数量，悬停通过原生物品 Tooltip 查看账号范围内的角色、来源和数量分布。
- 邮件来源数据归入相同物品查询，但在明细中标注邮件/附件来源，并提供 YiboMail 可用的来源信息。
- AH 上架商品纳入物品查询和角色分布；明细标记为“拍卖行上架”，可展示可读取的上架数量、堆叠数、价格及剩余时间等上架信息。物品总汇总包含 AH 上架数量，并同时单列 AH 上架小计；实体库存小计仍只统计背包、装备、个人银行和公会银行，避免把上架中的物品误认为仍在这些容器中。
- 使用单一仓储页面承载跨角色物品搜索与按持有者/储存区浏览。Core 继续提供账号页面壳、当前服务器/角色范围和角色顺序；YiboVault 提供角色物品、储存区聚合、容量摘要和来源数据，不把 Vault 的物品持久化或来源规则移入 Core。
- 仓储视图按“角色 → 储存区”组织：角色随身背包、装备、个人银行分别浏览；公会银行按公会和页签单独浏览，不归属到某个角色。
- 背包区将角色已装备的包整合为一个物品区；个人银行区将银行物品整合为一个物品区。角色摘要分别显示随身背包和个人银行的空位/总格数，并可显示可识别的包类型组成与容量信息；物品详情不依赖单包、单格位置。
- 容量仅由最近一次成功扫描得到的真实总格数和空槽数计算；不从非空物品记录反推容量。未采集或不可访问的储存区不伪造容量或空位。公会银行仅汇总已成功读取的页签，标明统计范围，不推断未访问页签。
- “空槽数”与可继续堆叠到现有物品的剩余堆叠量是不同指标；首版容量以明确的空槽/总格数为准，只有客户端数据可可靠计算时，才另外呈现堆叠余量。
- 不为从未采集的位置生成空行、零库存行或缺失警告。

### 角色仓储与容量视图

- 固定采用占满内容高度的左侧持有者列表、右侧身份摘要与物品格；唯一的物品名称/ID 搜索框位于右侧顶部。搜索同时筛选持有者、储存区与格子，清空后恢复此前浏览位置。
- 信息结构采用“持有者列表 + 仓储详情”：左栏沿用 Core 的角色范围与排序，每个公会只显示一个公会名条目；角色详情固定显示背包、邮件、个人银行、拍卖、装备五个来源标签，公会详情固定显示八个银行页签。未扫描标签置灰且不可点击，所有可见按钮等宽平分同一行；背包、个人银行空位摘要放在右侧详情。
- 背包与个人银行各以一个整合物品网格呈现图标和堆叠数量；可在区域摘要显示空位/总格数及可识别的包类型、容量组成。角色总览不把角色个人仓储与公会共享容量合并。
- 角色摘要分开展示背包区和个人银行区的总容量与空位。容量字段绑定到具体角色和储存区；可识别的背包类型/大小作为组成摘要呈现，不作为物品浏览层级。
- 公会银行按共享公会数据呈现各已扫描页签及其格数/空位，不放入访问角色的个人空间汇总。
- 页面始终使用 Core 传入的 `context.characters`、服务器范围和排序。搜索结果与角色浏览复用 Vault 的同一查询/身份匹配/数量汇总逻辑；物品位置明细仍保留真实来源所需的信息，仓储浏览按区域整合展示。
- 容量是缓存快照，不承诺远程角色此刻的实时空位。跨角色数据不附加“陈旧”标签；当前角色尚未刷新的来源仍遵循当前角色状态提示规则。非当前角色的历史内容由其最近一次成功记录代表。
- 上线前需验证目标客户端对背包/个人银行总格数、空槽数、可识别包类型及大小、公会页签格数的读取覆盖；不支持读取的属性应省略，而不是猜测或显示为零。

### 物品 Tooltip

- 玩家查看某一物品 Tooltip 时，展示该物品在已缓存数据中的汇总及分布。
- 分布与主窗口使用同一物品匹配和只读查询；Tooltip 的服务器范围由 Vault 业务设置选择，角色准入和排序沿用 Core。
- 可按服务器、角色、背包/装备/个人银行/公会银行/邮件附件分组；没有已采集记录的分组不出现。
- Tooltip 的可显示总数包含已扫描的 AH 上架数量；当前角色未扫描来源显示`~`，其缓存数量暂不计入显示合计。公会只统计成功扫描且有数量的页签，无法扫描的页签不显示。来源图标和公会页签提供分布明细；上架价格、堆叠及可读取的剩余时间仍保留在查询数据中，不将上架物品归入实体容器。
- Tooltip 负责单件物品的上下文查询，不承担账号全量物品浏览。
- Tooltip 的正式样式与展示规则见 [仓储视图与物品悬停规则](../YiboVault/Docs/仓储视图与物品悬停规则.md)。
- Tooltip 使用原生物品 Tooltip 的扩展内容，消费 Vault 同一只读查询结果；显示总数只累计已扫描来源的可见数字，未扫描来源按规则标示，不创建第二套缓存或独立窗口。

### Broker/小地图入口悬停

YiboVault 提供 Broker/小地图入口图标。点击图标打开主窗口；入口悬停不展示库存摘要或物品列表。物品数量和种类不适合在入口悬停中展开，用户通过主窗口搜索，通过物品 Tooltip 查询单件物品。

## 五、跨插件 API 产品契约

YiboVault 必须向 YiboCore 和其它 Yibo 子插件提供稳定、只读的物品查询接口。Public API v1 的冻结候选命名、Lua 表结构、状态和版本见 [联合 API 契约](YiboVault-Mail-API-v1-契约.md)；产品契约如下：

### 查询能力

- 按物品 ID/物品身份查询缓存记录。
- 返回包含实体库存与 AH 上架数量的物品总数，以及可展开的位置明细；位置明细至少包含服务器、角色、容器/来源和数量，实体库存与 AH 上架小计可分别取得。
- 支持调用方传入服务器/角色范围；不传时固定查询 Core 当前登录角色。账号页面使用 Core 页面范围，物品 Tooltip 使用 Vault 的服务器范围选项；两者均遵循 Core 的角色准入。
- 允许调用方区分实体库存（背包、装备栏、银行、公会银行）与邮件附件等外部来源。
- 对存在物品变体的物品，身份字段须足以避免将不等价的物品错误合并；具体身份规则由实现阶段验证游戏 API 后确定。

### 数据更新

- 角色或容器采集完成后，更新对应缓存并通知已注册的调用方，或提供等价的缓存变更检测机制。
- Vault 自有邮箱快照更新时刷新附件汇总。Mail 上线后，通过其公开接口更新附件来源；Vault 不读取 Mail 私有 SavedVariables。
- 查询只读取现有缓存，不要求强制登录其它角色或打开其它容器。
- 空结果仅表示“当前可查询缓存中没有匹配记录”，不得由 Vault 推断该账号所有角色和位置都没有此物品。

### 一致性与兼容

- 主窗口、Tooltip、Core 与第三方 Yibo 子插件共用同一查询结果；Tooltip 对未扫描来源使用未知标记，并以可显示数字计算悬停合计。
- API 返回的数据须可识别实体位置和来源，调用方不得将邮件附件混同为背包库存。
- 后续 API 演进应保持向后兼容；无法兼容时通过接口版本或能力协商处理，不要求用户为新消费者重新扫描所有角色。

## 六、明确不做

- 不显示未登录角色、未打开容器或未采集位置的列表、状态或提醒。
- 不因其它插件新增查询，就要求用户重新登录所有角色；已有缓存直接可查。尚无缓存的数据只会在用户正常访问相应角色/位置后产生。
- 只采集当前可见邮件附件的物品统计；不收取、转发、删除或发送邮件，也不管理邮件生命周期。
- 不提供自动整理、自动移动、自动存取、自动邮寄或自动售卖。
- 不提供通用经济系统或利润计算。
- 不负责专业配方、制造建议、待办决策或自动采购；这些插件可消费 Vault API。
- 不制作入口悬停库存摘要或物品清单；Broker/小地图图标只负责打开主窗口。
- 不提供拍卖价格走势、竞拍、自动上架/下架、利润计算或完整 AH 经济分析；仅缓存并展示玩家已上架商品及客户端可读取的相关信息。

## 七、开发路线图

### 阶段 0：游戏 API 与数据模型验证

**目标：** 确认目标客户端中各容器的读取、事件与权限边界，为统一缓存模型定稿。

- 验证背包、装备栏、个人银行、公会银行可读取的数据与刷新时机。
- 验证 AH 当前角色上架列表的读取方式、分页/条目限制、价格字段和刷新时机；记录客户端对已结束或已撤销上架的可见性边界。
- 验证物品 ID、链接及可能影响堆叠/区分的变体信息。
- 定义角色、服务器、公会、容器、槽位、物品身份、数量和采集时间的数据模型。
- 定义 AH 上架记录模型及其与实体库存的分离规则。
- 与 YiboMail 约定只读附件数据接口及来源字段。
- 产出 API 草案与缓存迁移/清理策略。

**阶段交付：** 数据模型说明、客户端 API 验证记录、跨插件接口草案。完成后评审再进入采集实现。

### 阶段 1：核心缓存与背包/装备采集

**目标：** 建立可复用的基础物品缓存。

- 创建 YiboVault 插件骨架并按项目约定注册 Core 页面及设置分区。
- 实现背包与装备栏采集、角色身份关联和局部位置更新。
- 实现缓存结构、数据校验、旧数据兼容及角色清理接入。
- 建立统一的物品身份、数量汇总和位置查询内部服务。
- 发布只覆盖已完成采集来源的首版只读查询 API，并以来源能力标记后续银行、AH、邮件尚不可查询；接口形状在阶段 0 冻结，后续来源按能力增量扩展。
- 玩家只看到已经写入缓存的物品，不展示采集缺口。

**阶段交付：** 稳定的本地库存缓存、可供 UI/Tooltip 复用的查询服务及背包/装备来源的首版公共 API。

### 阶段 2：银行与公会银行采集

**目标：** 扩展容器覆盖，同时保持逐位置采集语义。

- 玩家打开个人银行时更新该角色的银行缓存。
- 玩家访问可读取的公会银行时更新相应 `guildKey + tabID` 快照；同一公会的其它角色再次访问时替换该公会页签数据，不按角色重复累计。
- 更新单个容器不得清空或标记其它角色、容器数据缺失。
- 将所有实体容器纳入同一物品汇总与位置明细。

**阶段交付：** 背包、装备、个人银行、公会银行统一资产数据。

### 阶段 2A：拍卖行上架缓存

**目标：** 在无独立 Yibo AH 插件的前提下，记录并展示玩家已上架商品。

- 玩家打开 AH 后立即主动查询当前角色的上架记录，不依赖进入“取消”页或其它特定页签；只在对应更新事件完成后替换缓存。
- 保留物品身份、上架数量/堆叠、价格及可读取的持续时间等信息，并关联角色与服务器。
- 上架记录作为独立来源提供给主窗口、Tooltip 和查询 API；不计入背包/装备/银行实体库存合计。
- 不显示未采集角色或不可读取上架列表的缺失提示。
- 上架缓存随玩家再次访问 AH 更新；按客户端实际提供的数据能力定义记录替换与过期清理规则。

**阶段交付：** 可查询的角色 AH 上架商品缓存，与物品实体持有量明确区分。

### 阶段 3：Core 页面与搜索体验

**目标：** 让玩家可以按物品检索，也可以按角色和储存位置查看缓存物品及空间余量。

- 接入 Core 统一账号页面、范围筛选、角色排序和显示设置。
- 注册 Broker/小地图入口图标，点击打开 Vault 主窗口；不提供入口悬停摘要。
- 在固定仓储页中提供一个全局物品搜索入口；沿角色 → 整合背包/装备/整合个人银行/AH 上架浏览，公会银行另按公会/页签组织。
- 为成功扫描的储存区保存容量元数据：总格数、空槽数，以及客户端可读取时的背包类型/专用类别与大小组成。容量与物品记录分开建模，空储存区也能表达；不从非空物品记录推算容量。
- 角色空间摘要分别呈现整合背包区和个人银行区的空位/总格数；包类别与大小作为组成摘要。公会银行以公会和页签为单位单独展示，不归属到访问角色的容量总计。
- 在 Vault 查询契约中补充储存区容量摘要能力；展示仅覆盖实际成功扫描且客户端可确认的容量范围。
- 随物品规模采用筛选、分页或其他有界列表组织方式。
- 遵循 Core 设置工作台与插件顺序约定，不创建独立窗口壳。

**阶段交付：** Core 统一账号工作台中的单一物品仓储页，支持全局物品搜索与按持有者/储存区查看库存和容量。

### 阶段 4：公开 API 稳定化与 Tooltip

**目标：** 启用 Vault 的主要差异化能力。

- 物品 Tooltip 的展示层级、服务器范围、角色与公会行、来源顺序、数量与状态、长度控制及设置入口，按已确认的 [仓储视图与物品悬停规则](../YiboVault/Docs/仓储视图与物品悬停规则.md) 实现并复核。
- 核对只读查询 API 的范围参数、来源标记和兼容策略，补齐已实现来源及容量数据的能力声明与接入文档。
- 提供缓存变更通知/检测能力，供调用方刷新视图。
- 按已评审的视觉/信息规则，将物品 Tooltip 接入统一查询服务，显示合计和已知分布。
- 验证仓储页搜索与浏览、Tooltip、API 的数量与位置语义一致。
- Vault 已独立采集邮箱附件；YiboMail 尚未上线。待 Mail 提供稳定只读附件 API 后再实现双插件来源切换与集成验收。

**阶段交付：** 其它 Yibo 插件可直接查询库存的正式接口；无需为了新查询重新登录已有缓存角色。

### 阶段 5：调用方接入与稳定化

**目标：** 证明 API 可支持实际业务，并处理长期使用问题。

- 首个实际消费者确定为 YiboCurrency；从其物品管理场景接入 Vault 公共 API，明确物品库存与货币计数的分工并避免重复累计。后续再评估 YiboReputation 或 YiboTodo。
- 检查角色删除、服务器变更、插件升级、数据规模与 SavedVariables 负担。
- 根据实际数据量优化搜索和渲染；避免保存可从基础记录重建的重复汇总。
- 完成发布说明、缓存影响说明和用户可控的清理入口接入 Core。

**阶段交付：** YiboCurrency 通过 Vault 公共 API 查询已有物品缓存，数据生命周期与升级行为清晰。

## 八、路线图验收原则

- 已采集到的来源能在主窗口与 Tooltip 中显示正确物品、数量和来源明细。
- 角色仓储页能逐角色查看整合背包、装备及整合个人银行，明确显示可确认的包类型/容量组成和各储存区空位/总格数；公会银行按共享公会页签独立浏览。
- 储存区容量严格来自成功扫描的真实容量快照；空储存区容量正确，未采集或不可访问的储存区不会伪装成零库存或已知空位。
- 只访问一个角色或容器时，只更新相应缓存，不改写其它位置的记录。
- 未采集位置不会生成零数量记录；物品 Tooltip 对已有匹配记录的当前角色以`~`标示未扫描来源，无法扫描的公会页签省略。
- 同一角色范围及扫描覆盖下，主窗口和 API 的缓存数量可逐来源核对；Tooltip 的数字与其显示的已扫描来源相符，未知来源不冒充为零。
- Vault 当前自行提供邮箱附件统计；Mail 上线后可通过其公共接口提供更完整的来源，Vault 对同一角色只采用一份。
- AH 上架商品可在主窗口、Tooltip 和 API 中查询，并与实体库存分开展示和统计。
- Broker/小地图入口可打开主窗口，悬停不出现库存摘要。
- 调用方读取已有缓存不触发全角色重新扫描，也不要求逐个登录角色。
- 调用方无法从空结果推断从未采集的位置库存为零。

## 九、产品总结

YiboVault 不承诺知道账号所有角色和位置的完整现状。它可靠地告诉用户和其它插件：**当前已经记录了哪些物品、数量是多少、记录来自哪里。** 缓存随着用户正常访问角色与容器逐步增长；Vault 不把尚未记录的内容说成“没有”。
