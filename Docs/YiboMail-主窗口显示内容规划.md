# YiboMail 主窗口完整方案

> 更新日期：2026-10-05。
> 文档状态：已按方案实施，代码版本 `0.8-api1`；自动验证已接入，游戏内布局和交互待客户端验收。
> 适用范围：YiboCore 承载的 YiboMail 主窗口、账号总览悬停投影，以及相关查询和历史记录。
> 目标客户端：仓库当前基线为熊猫人之谜经典版，Interface 50504；发布时以客户端实测为准。

## 1. 目标与确认基线

主窗口帮助玩家查看其它角色的收件箱、比较各角色的邮件状态，以及追溯一定时间内的收发记录。信息必须能支持找邮件、找物品、判断优先处理的角色，且说明数据来自哪次扫描。

### 1.1 已确认要求

| 要求 | 实施约束 |
| --- | --- |
| 三个主要页面 | 收件箱、账号总览、历史记录；收件箱是最主要的内容 |
| 收件箱搜索 | 全局搜索当前 Core 范围内全部有效角色的邮件，不受左侧选中角色限制 |
| 浏览状态 | 同一次打开窗口期间，切换标签保留各页状态；保存上限为本次登录，RL 后不保留 |
| 主窗口业务范围 | 浏览邮件快照、账号状态及历史；实际邮件操作沿用游戏邮箱场景 |

### 1.2 用户提出的 UI 方向

- 三个主要页面采用 AltoBoss 风格的标签页。
- 收件箱采用物品仓库风格的左侧角色列，右侧查看邮件。
- 账号总览与悬停使用相同表格样式，可按实际需要显示更多列。
- 历史记录逐行显示，顶部提供搜索和筛选控件。

本方案沿上述方向细化。2026-10-05 用户要求按方案实施，本轮采用第 13 节列出的默认值。

## 2. 总体结构与职责

### 2.1 主窗口结构

```text
Core 窗口壳、业务导航与服务器范围
└─ 收件箱 | 账号总览 | 历史记录
   ├─ 收件箱：左侧角色列 | 右侧身份/扫描说明、搜索筛选、纵向滚动邮件列表
   ├─ 账号总览：角色摘要表、必要的覆盖说明、分页
   └─ 历史记录：搜索筛选、纵向滚动记录表、详情
```

三标签固定顺序为收件箱、账号总览、历史记录。Core 范围栏和标签条位置固定，角色列只占收件箱内容区；其它两页使用内容区全宽。

### 2.2 Core 与 Mail 的分工

| 归属 | 职责 |
| --- | --- |
| YiboCore | 角色目录、短名、当前角色标识、隐藏与等级过滤、服务器范围、角色排序、窗口壳、通用主题和表格/滚动控件、入口生命周期、字段与预览配置、设置工作台 |
| YiboMail | 邮件与历史数据、角色业务准入、快照/风险/金额口径、全局搜索、来源追溯、三个标签的业务布局与临时浏览状态 |
| 游戏邮箱场景 | 实际收取、付款、退回、删除、装填和发送；现有原生增强按其独立流程工作 |

Mail 只依赖 Core。AltoBoss 与 Vault 提供样式参考，不增加对它们的业务或代码加载依赖。需要提取可复用标签控件时，应放在 Core 的通用 UI 层。

## 3. 现有代码与本轮改造范围

实施前基线为 `0.7-api1`，本轮完成后的版本为 `0.8-api1`，账号功能开启。

| 文件/模块 | 当前情况 | 本方案中的用途 |
| --- | --- | --- |
| `AccountPage.lua` | 注册 `mail-inbox`；普通页面挂载 CacheUI，悬停挂载角色摘要 | 保持稳定入口 ID，承载三标签主页面与同源预览 |
| `CacheUI.lua` | 邮件列表/附件集中、角色选择、最新/待核实范围、搜索、排序、分页与来源展开 | 复用业务浏览能力，重组为收件箱布局 |
| `CacheModel.lua` | 查询当前可见或待核实记录，按完整物品身份聚合 | 统一准入、收空隐藏、搜索范围与排序；提供稳定来源定位 |
| `MailUI.lua` | 四标签旧工作区源码仍在，当前只复用输入框方法 | 参考已有历史与来源交互；本轮采用本方案三标签结构 |
| `ViewModel.lua` | 邮件查询、格式化、收空隐藏、部分历史查询 | 整理为主窗口/悬停/历史共用的状态与格式化能力 |
| `Store.lua` / `Scanner.lua` | 持久快照、可见投影、待核实状态、历史保留 | 保持事实归属，按历史需求补充关联及首次发现信息 |
| `Queue.lua` / `Compose.lua` | 实际收取结果和发送结果记录 | 提供有证据的历史事件 |

主页面已由 `CacheUI.lua` 实现三标签工作区与角色侧栏。`WorkspaceState.lua` 维护登录内状态，`HistoryModel.lua` 提供事件及待核实扫描投影；正式 TOC 已加载这两个模块。历史记录新增稳定事件 ID、来源 mailKey 与首次发现信息，旧事件在初始化时补充稳定 ID。

**实际悬停基线：** 已核对最新代码，默认六列为角色、邮件数、附件数、可收金币、最早到期、更新状态。账号总览复用这六列及同一个摘要渲染器，附加到期提醒、COD 邮件数和可选待核实缓存数。

## 4. 共用布局、主题与尺寸策略

### 4.1 标签及主题

参考 `YiboAltoBoss/LockoutsPage.lua` 的 `CreateBusinessTabs`，沿用标签填色、边框、文字及选中标签与内容区的衔接。参考标签高度为 34 个 WoW 逻辑 UI 单位，最终由 Core 通用样式管理。

字号、色彩、表头、行色、边线与间距读取 `Core.UITheme`。角色职业色和当前角色标识沿用 Core，不使用颜色独自表达风险。所有图标使用已有资源和实际物品纹理。

### 4.2 宽高与长列表

- 按实际文本、列宽、工具栏和角色列计算自然尺寸，由 Core 调整到安全屏幕边界；不用固定角色数或初始视口提前截断内容。
- 共用标签及 Core 控件保持位置稳定，切标签不主动重置窗口位置或尺寸。Mail 报告内容尺寸，不自行维护第二套窗口尺寸设置。
- 收件箱角色列采用单行角色项，约 230 逻辑单位宽、32 逻辑单位行高、34 单位行距；同行显示职业图标、职业色名称、数量及紧凑风险提示，服务器和扫描说明在悬停及右侧头部显示。长名称须测量。
- 账号总览沿用当前悬停摘要渲染器的文字、内边距、行高语义和角色样式；主表扩展列由同一字段定义提供。
- 历史一条事件对应一行。主题与附件过长时先显示摘要，展开详情或进入同一内容区的详情态。
- 表头及工具栏固定。邮件明细、附件图标网格与历史记录使用 Core 纵向滚动控件，并复用可见行/图标控件；角色摘要按安全高度分页。
- 角色列可独立纵向滚动；长详情使用 Core 通用纵向浏览。任何页面不得依靠横向滚动完成阅读和操作。
- 搜索使用 Core `CreateInput` 的 `OnChanged` 回调，等待输入法组字结束后更新查询；输入及数据刷新期间保留原生组字文本和光标，仅在切标签或外部条件变化时同步查询。筛选与查看方式保持在同一行，通过缩短标签及紧凑宽度适配。主窗口最小内容宽度为 1000、自然宽度至少 1154 逻辑单位，最终服从 Core 的屏幕安全边界；补充信息可展开。

## 5. 收件箱

### 5.1 左侧角色列

只显示 Core 当前范围内具备成功收件箱扫描依据的角色，包括已知空邮箱。使用 Core 顺序、短名、职业图标/颜色及服务器信息。

每角色仅占一行，显示职业色名称、邮件数和必要的紧凑风险提示；服务器在角色悬停及右侧身份信息中完整显示。当前登录角色与当前选中角色使用不同标识；查看其它角色时当前角色标记仍留在其自身行上。

提供“全部角色”项，用于普通跨角色浏览。搜索不要求先选择该项。角色很多时列内滚动，不隐藏到固定角色数。

首次选择：当前角色有合格快照时选当前角色，否则选 Core 顺序中的首个有快照角色。范围内无快照时显示首次扫描提示。

### 5.2 右侧头部及工具栏

单角色浏览显示角色/服务器、最后成功扫描时间、完整/部分扫描及本轮未扫描数量。全角色浏览和搜索结果显示 Core 范围与参与角色数，提示各角色时间不同。

工具栏提供：全局搜索、最新快照/待核实缓存、类别、风险和排序。默认为最新快照、全部类别、全部风险、估算临期优先。

| 控件 | 候选内容 |
| --- | --- |
| 类别 | 全部、含物品附件、含金币、付款取信、退回、无附件及金币 |
| 风险 | 全部、紧急、临期、三天内到期、七天内到期、到期提醒全部、到期待核实、期限未知 |
| 排序 | 估算临期优先、Core 角色/扫描时邮件顺序 |
| 查看方式 | 按邮件、按附件汇总；右侧采用紧凑切换 |

筛选条件取交集，类别允许业务语义重叠；筛选不修改邮件事实。“三天内到期”合并紧急与临期，不包含已到估算期限记录。

### 5.3 邮件列表及详情

| 字段 | 内容 |
| --- | --- |
| 所属角色 | 全角色浏览及搜索结果必须显示；单角色普通浏览由头部说明 |
| 发件人/主题 | 显示必要文本，长文本省略并可查看完整内容 |
| 附件 | 实际物品图标、名称和数量；主行摘要，展开完整清单 |
| 金币/COD | 明确命名待取金币或整封付款金额 |
| 期限/类型 | 约 N小时/天、风险或期限未知；退回等必要标记 |
| 数据状态 | 旧快照、部分或读取失败的醒目标识；完整时间在头部/详情中可见 |

邮件为顶层记录，同签名邮件逐封保留。邮件序号只表示扫描当时的位置，不作为当前操作身份。

点击邮件展开：完整发件人/主题、每个物品链接与数量、金币/COD、退回标记、最后可见时间、覆盖说明，以及附件槽位等来源信息。详情过长时进入同一内容区，返回恢复原滚动锚点和阅读位置。

账号收件箱用于查看已缓存内容；正文不进入长期存档。显示内容与原生收件箱共用快照及收空隐藏规则。

### 5.4 全局搜索交互

全局定义为 **当前 Core 范围内全部具备收件箱业务依据的有效角色**。角色隐藏、过滤和服务器范围继续生效；选择所有服务器后可跨服务器查询。Mail 不从 Core context 之外重新扩张角色范围。

- 搜索字段：角色、服务器、发件人、主题、物品名或物品 ID；WoW 文字需安全转义，匹配按普通文本处理。
- 非空关键词进入“全局搜索结果”，不受搜索前选中角色限制；保持当前记录范围、类别与风险过滤，并显示有效条件。
- 每条结果显示所属角色与服务器；单角色查看的选中状态不能让其它角色的命中被静默隐藏。
- 左侧展示角色命中邮件数并保留 Core 顺序；点击角色定位并高亮该角色的命中结果，查询范围仍为全局。命中数按邮件计，不按包含该物品的附件槽重复计数。
- 清除关键词恢复搜索前的角色、滚动锚点及阅读位置；原选择失效时采用有效回退值。
- 改变关键词或过滤条件后结果滚回顶部；普通数据刷新保留查询、稳定记录锚点和行内偏移，并修正超出范围的滚动位置。
- 全局无匹配时说明当前 Core 范围、有效筛选与结果为空，提供清除条件入口。

### 5.5 附件汇总

附件汇总属于收件箱内的查看方式。按完整链接/变体身份汇总，相同 itemID 的不同属性变体可区分；ID 搜索可查到这些变体。

使用与原生邮箱附件视图一致的图标网格：42×42 图标、46 单位格距、右下角汇总数量，品质边框在 24 小时内变红、1–3 天变橙；不设置文本列或表头。普通/COD 数量、来源角色、邮件数及估算期限在悬停和来源详情中区分，COD 不混作免费待取附件。

悬停每个附件来源占一行，格式为“邮箱：角色 · 服务器 · 发件人：名字 · ×数量 · 期限”；关闭来源行的自动换行，保持紧凑高度。来源顺序与附件槽明细一致，跨服同名角色保留服务器信息。完整来源详情显示角色/服务器、发件人、主题、该槽数量、期限、最后可见时间及 COD 标记。点击来源进入对应邮件详情，返回时恢复查询与原位置。

同封 COD 的付款金额不得逐槽累加或按物品数量拆分。未知期限与有期限来源分别说明；最新快照与待核实范围分别聚合，后者使用“曾扫描数量，待确认”文案。

### 5.6 摘要与数量口径

摘要对应当前表格结果集：邮件数、含附件邮件数、待取金币、COD 邮件数和风险数量。附件模式另显示物品组数及来源数量。

扫描覆盖属于查询范围说明，和筛选结果数量区分。已知附件数量只汇总有明细的记录，不推测未暴露邮件。无临期时写“已扫描邮件无临期记录”，部分扫描仍提示未知覆盖。

## 6. 账号总览

### 6.1 同源表格及字段

账号总览为角色行表格，使用内容区全宽。悬停是其预览字段投影：共用角色摘要、准入、状态、格式化和表格渲染，预览不跟随主窗口当前搜索或单角色选择变窄。

共同字段为角色、邮件数、附件数、可收金币、最早到期、更新状态。字段顺序保持一致，主窗口附加字段排在共同字段后。

| 主表扩展候选 | 口径与意义 |
| --- | --- |
| 到期提醒 | 紧急、临期、到期待核实的邮件封数，便于决定处理量 |
| 附件数（共同列） | 按物品附件格计数，每格计 1、不累加格内堆叠数量；含附件邮件封数显示在收件箱结果摘要 |
| 可收金币（共同列） | 最新快照中非 COD 邮件金币总额 |
| COD 邮件数 | 需要付款的邮件封数；必要时展开整封付款明细 |
| 待核实缓存数 | 独立统计，不加到确定的当前数量 |

默认扩展列为到期提醒与 COD 邮件数；待核实缓存数默认隐藏。支持经 Core 主表字段配置显示/隐藏。预览默认仍为六列，扩展列可由 `settings.previewColumns` 和 Core“显示与入口”开启。

### 6.2 行为与覆盖

- 角色顺序沿用 Core，不因风险自动重排；风险排序用于邮件记录。
- 点击角色进入其收件箱；点击风险数量进入该角色对应条件，并显示有效筛选。跳转前挂起原搜索，返回时恢复原状态。
- 账号总览可访问全部有效角色，按安全高度分页；悬停最多 20 名，超过时保留覆盖提示。
- 空邮箱显示零封及扫描时间；无成功收件箱扫描的角色不生成零值行。
- 最后成功扫描时间按角色分别显示，不用一个时间冒充全账号更新时间。

## 7. 历史记录

### 7.1 布局与工具栏

顶部固定搜索框、时间范围、角色、方向/事件类型、结果及清除条件；默认时间倒序。时间选项为近7天、近30天、近90天和保留范围内全部，默认近30天。角色选择菜单使用 Core 分页控件，长角色列表可访问全部结果。

搜索支持角色、对方、主题、物品名/ID；与时间、角色、事件及结果筛选取交集。历史角色筛选独立保存，不继承收件箱的单角色选择。

一条事件一行，列顺序：时间、角色、事件、对方、主题、附件/金币摘要、结果。长内容以摘要显示，点击展开原邮件来源及具体数量。表头及工具栏保持可见，记录表连续纵向滚动，顶部摘要显示结果总数。角色列与角色筛选选项中的名称使用职业色。

### 7.2 事件与证据

| 事件 | 时间/内容依据 | 显示原则 |
| --- | --- | --- |
| 扫描发现收件 | 实际可见且读取成功的邮件、首次发现时间 | 只能称首次发现；既有旧信不标为此刻新到达 |
| 实际收取 | 客户端确认成功的附件/金币操作 | 按本次实际取得内容记录，支持部分收取 |
| 成功发送 | 客户端发送成功事件及原邮件摘要 | 显示已发送/在途，不直接称已送达 |
| 确认收到 | 目标角色实际扫描、唯一匹配 | 匹配能力接入并验证后显示 |
| 确认退回 | 明确退回标记和可匹配来源 | 有证据后显示，邮件消失不作退回依据 |
| 待核实 | 结果不明确或匹配有歧义 | 保留事实和疑点，不推断最终去向 |

客户端/插件未捕获的往来不能补造。首次升级只能从已有历史和可识别的快照事实生成投影；缺少原始发送/到达时间时明确未知或扫描时间。

### 7.3 归一、关联与保留

历史查询统一适配 `snapshot.history` 与需要追溯的扫描记录，但不把最新快照重复列成多条操作历史。

已归一字段：稳定事件 ID、角色 ID、事件类型、方向、对方、主题、实际附件/金币、时间及其依据、结果状态、来源 mailKey。持久操作事件来自 `snapshot.history`，扫描待核实记录来自 `snapshot.records` 的独立查询投影，不另存第二份业务事实。

重复扫描不新增发现事件。歧义 mailKey 关联不能冒充新的到达或成功操作；多个部分收取分别保留实际结果，并通过同一来源关联。已确认结果优先使用队列成功证据，不根据邮件从列表消失推断收取。

已确认历史默认保留90天，待核实默认30天，期限由 Core 承载的 Mail“数据与缓存”设置管理。登录时清理超期数据；缩短期限需要游戏内确认，确认后立即按新期限清理。展示时间范围不改变保留期限，查询独立排除超期数据；历史页提示两种保留期限。历史不进入当前持有量和最新快照风险。

### 7.4 角色准入

历史允许显示只有发件历史、没有成功收件箱扫描的角色，仍遵守 Core 隐藏、范围和角色排序。收件箱/账号总览/悬停只采用各自有效收件箱快照，不能因历史准入而生成无数据摘要行。

## 8. 临时浏览状态与交互状态机

### 8.1 保存内容及生命周期

| 状态组 | 临时保存内容 |
| --- | --- |
| 主工作区 | 当前标签 |
| 收件箱 | 角色选择、邮件/附件模式、查询、记录范围、类别、风险、排序、滚动锚点及偏移、展开项、阅读位置、搜索前浏览位置 |
| 账号总览 | 页码、展开详情及返回锚点 |
| 历史 | 时间范围、角色、方向/事件/结果条件、查询、滚动锚点及偏移、展开项、阅读位置 |

这些状态只存在 Mail 的内存状态对象中，不写入 SavedVariables；重新登录或 RL 后恢复默认。字段显隐、入口、窗口设置、邮件缓存、历史和业务规则仍按其自身设置/数据契约保存。

同一次打开窗口期间切标签保留状态，关闭再打开在同次登录内继续复用内存状态。RL 或重新登录清空浏览状态，业务缓存遵循自己的保存规则。

悬停开启/关闭不修改主工作区状态。Core 对同一宿主进行主窗口/预览切换时，主状态存放在宿主帧之外，避免重建导致意外丢失。

### 8.2 状态转换

| 触发 | 结果 |
| --- | --- |
| 切标签 | 保存当前页锚点，恢复目标页状态 |
| 输入关键词 | 收件箱进入全局结果，结果列表滚回顶部，保存搜索前位置 |
| 清除关键词 | 恢复搜索前普通浏览位置；失效选择回退 |
| 改变筛选 | 结果列表滚回顶部，保留其它可用条件 |
| Core 范围变化 | 重新计算有效角色；旧选择失效才回退，明确新范围 |
| 邮件/历史变化 | 更新投影，保留条件与稳定锚点，修正失效滚动位置 |
| 从总览定位邮件 | 暂存来源页，建立目标角色与风险条件；返回恢复来源 |
| 从附件定位邮件 | 按角色 ID+mailKey定位，不依靠可能变化的邮箱序号；返回恢复附件结果 |
| 目标记录失效 | 提示已变化/待核实，刷新结果并提供返回，不跳到相邻邮件 |
| 重新登录或 RL | 清空浏览状态，保留业务数据与正式设置 |

## 9. 快照、风险与格式化规则

### 9.1 三类记录边界

| 记录范围 | 数据 | 数量意义 |
| --- | --- | --- |
| 最新快照 | 最近有效扫描的 `visibleKeys`，应用统一收空隐藏 | 已扫描且当时可见的邮件/附件 |
| 待核实缓存 | 曾经可见、本轮无法确认的记录 | 曾扫描数量，待重新核对 |
| 历史 | 有证据的发现、操作与往来事件 | 事件记录，按事实追溯 |

三者分别统计。积压旧缓存不能叠加成当前持有量或进入收取队列；Vault 当前邮件来源继续只消费最新有效可见投影。

部分扫描示例：已扫描100/总计148，另48封本轮未扫描。“本轮未扫描”不等于从未缓存；此前缓存仍可在待核实范围追溯。

### 9.2 风险与视觉状态

| 估算剩余时间 | 风险分桶 |
| --- | --- |
| 大于72小时 | 普通 |
| 大于24且不超过72小时 | 临期 |
| 大于0且不超过24小时 | 紧急 |
| 小于等于0 | 到期待核实 |
| 缺少有效期限 | 期限未知 |

风险按邮件封数计，桶间不重叠。到期后保留缓存，不宣称邮件已丢失、删除或退回。空信、COD和退回邮件按同一规则检查。

风险桶与倒计时颜色是不同展示维度，颜色与悬停保持同一来源。当前摘要源码的最早到期颜色为不超过3天红色、3至7天警示色，其余普通色；不要因24/72小时桶另写一份不同的主窗口倒计时着色。实施时核对最新批准的颜色基线并同步文档。

倒计时在打开时及定时刷新时重新计算，跨阈值刷新状态；离线、关闭邮箱和读取失败不更新真实扫描时间，不把旧值当作实时邮箱。

### 9.3 金额与格式

金额按铜币原值保存，展示沿用统一格式化函数，准确区分待取金币、寄送金币与 COD。物品显示实际链接/图标，未缓存名称时使用可辨认的物品 ID 回退，不制造不存在的名称。

所有用户/游戏文本按 WoW 转义规则安全处理；长名称、重复角色名、跨服地址均须可辨认。混合扫描时间与缺失期限分别说明。

## 11. Core 接入与模块改造

### 11.1 页面和角色上下文

保持现有 `mail-inbox` 页面 ID 及 Core 业务入口注册关系，三个标签是一个业务工作区。入口左键打开该工作区，右键由 Core 提供入口设置；预览始终显示账号总览投影。

Core 的 `GetEligibleCharacters(characters, baseContext)` 已提供 `baseContext.preview`。主窗口准入可包含具备有效收件箱快照或实际历史的角色；预览仅纳入成功收件箱快照角色。三个主标签在 Core 提供的角色列表内应用各自业务准入，不重新取全账号名单或改变 Core 顺序。

范围、角色过滤和清理继续采用已有 Core 注册接口。历史-only 角色必须有实际记录，不能仅凭初始化空表准入。

### 11.2 查询与渲染

- 统一有效邮件迭代、收空隐藏、期限分桶、金额与时间格式化，供主页面、悬停和已有消费接口使用。
- 收件箱查询从 `context.characters` 构造明确角色范围。普通单角色浏览与全局搜索采用不同查询参数，但相同准入和状态口径。
- 历史归一与物品来源保持稳定 ID；滚动列表按可见范围复用控件，展开内容不改变结果总数。
- 保留 `AccountPage:GetSummary` 一类摘要入口并扩展必要计数，预览不读主窗口临时查询状态。
- 将主工作区状态与帧渲染分离，帧可重建，浏览状态只留在本次登录内存。
- 事件更新先完成数据/投影，再通知页面，遵循现有 revision/通知契约。倒计时变化只刷新展示，不伪造业务数据变更。

### 11.3 字段配置与设置

页面、入口、主表字段、悬停字段、角色排序仍由 Core 保存和渲染。Mail 注册各视图字段及适用范围，不另做业务字段设置窗口。

若现有 Core 字段面板只支持平铺列表，需要补充通用视图字段分组/适用性展示；这是实施时检查的通用 UI 适配项，不能假定现有注册接口已自动支持。字段稳定 ID 保留已有配置，新增字段按默认值初始化。

Mail 业务设置保留登录提醒、历史保留及缓存维护。自动发件规则归属见第 13 节；联系人与规则共用既有数据，不建立第二套来源。

### 11.4 数据迁移

优先采用查询适配，使现有快照和历史可读。新增事件关联/首次发现字段时采用向后兼容迁移，未知时间明确标记。

现有 `cacheBrowserMode` 等历史浏览偏好不再作为本方案的跨登录恢复来源；新浏览状态不持续写入此类字段。正式预览列、规则与数据保留配置继续按各自契约工作。

本轮不以迁移为由批量清理已有业务记录。确需用户缓存删除时走统一数据与缓存入口及明确确认流程。

## 12. 实施顺序与验收

### 12.1 实施步骤

1. 核对悬停最新字段/颜色、Core字段适用性及历史事实来源，冻结共同口径。
2. 建立内存浏览状态、三标签工作区及既有页面ID接入，复用Core样式。
3. 完成单行收件箱角色列、邮件详情、全局搜索、单行风险筛选和纵向滚动列表。
4. 接入附件汇总与稳定来源定位，核对COD和待核实数量。
5. 将账号总览和悬停接入同一摘要表格，添加获批的主表扩展列及跳转。
6. 统一历史事件投影、时间筛选、角色准入、职业色、详情和纵向滚动；缺乏匹配证据的状态保留待核实。
7. 完成适当的自动验证与游戏内布局/交互验收，同步README和悬停等相关文档。

### 12.2 自动验证重点

- 单角色选择不缩小全局搜索；Core范围/隐藏规则仍生效，结果标明来源角色。
- 同签名重复邮件逐封保留；收空隐藏在主窗口、总览和悬停一致。
- 物品变体不错误合并；COD金额不逐槽重复统计。
- 待核实/历史不增加当前持有量；部分覆盖不伪造明细。
- 0、24、72小时及期限缺失边界；打开状态跨阈值刷新。
- 切标签恢复各自状态；RL初始化恢复默认；正式设置/缓存继续可读。
- 只有发件历史的角色能进入历史，不污染总览/悬停准入。
- 重复扫描不增伪事件，部分收取按实际量，发送成功不直接标送达。
- 扩展/来源返回保持稳定记录 ID、滚动锚点及阅读位置。

根据改造范围复用现有正式TOC加载、运行流程、公开API及收件回归检查，并补充验证上述业务边界的主窗口测试。自动检查使用模拟游戏API，不替代客户端功能和外观验收。
