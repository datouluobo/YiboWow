# Mail 真实历史与回调分配峰值（2026-10-29）

本轮实机反馈：登录26.2MB，打开邮箱41.2MB；附件箱Alt＋左键仅收一份后增长至305MB，邮箱保持打开时自动降至41.6MB，后维持54MB左右；再次打开规则寄信后约67MB；收件箱批量收两封约110MB、三封约150MB。上述是用户观察值，不能由此前无寄信历史的合成测试替代。本轮新代码尚待相同场景实机复测，不能宣称305MB已解决。

## 已确认的遗漏与修复

### 在途证据重复解析

此前合成收件场景没有在途寄信，提前跳过了收件证据构建。只读回放实际较大存档，含31角色、1990条记录、7786条历史，其中683条在途寄信、4545条收件归档；真实数据变化后，按角色查询在途会反复解析全账号历史。

Items现按角色保存派生证据，Store发布同时给出实际变化角色ID。真实内容发布立即释放该角色旧证据及全局结果／合并索引，未变化角色复用；下次查询重新合并并按既有时间、身份、多重性与消费顺序匹配。没有丢弃寄信、收件、退回、重复观察或历史事件，没有改变业务判断。

- 只有有效版本化owner快照可跨数据代次复用；检查源快照、coverage/revision、records/history引用和history长度。缺版本不持久缓存。无角色ID的手动失效清空所有证据，保持原有强制重建语义。
- 身份目录按id/name/realm的排序指纹失效。Core无关域更新虽会重新分配只读身份数组，值不变时仍可复用；改名／删除／范围变化会重新解析地址。
- 每次构建只为同一地址＋realm规范化一次，失败解析同样局部复用；相同不可变附件数组的签名在本次构建复用。局部memo构建后释放，完整历史仍由Mail唯一权威持有。
- 关闭邮箱、显式释放和来源失效清理全部owner证据。公开GetTransfers仍隔离，Core.Contracts仍执行既有单次隔离；新增缓存不暴露给其它插件。

### 收件带来的寄信规则重匹配

收取改变背包，每个BAG_UPDATE_DELAYED原本都能重新读取全部背包并匹配寄信规则。现在收件运行中／仍有待确认动作时只记录失效，不抢占收件；完成或没有未决动作的暂停后合并读取一次。已排队回调执行前再检查队列，关闭清除待刷新状态。规则寄信的Guard、阵营／服务器、规则版本、草稿指纹、附件校验与显式发送步骤保留，不自动发送。

### 物品回调与悬停

每个物品信息成功回调原本都直接请求整箱界面重绘。现在同一帧合并为一次，失败和无关ID不触发；隐藏、关闭、释放及旧会话回调不重绘新会话。没有延迟扫描、收件确认或物品真实数据的校验。

附件收取后原逻辑会程序调用当前物品格的OnEnter，再次SetHyperlink，重复执行原生Tooltip及其挂钩路径。现在收取确认使当前悬停来源失效时关闭旧悬停；下一次正常移入仍显示完整原生物品与剩余来源，格子和收取点击保持。没有证据把305MB归因于某个外部插件；本轮仅确认并移除Mail主动重复调用的链路。

## 实际存档只读回放

TransitRealDataProbe在空环境和指令预算内加载两份磁盘SavedVariables，只在独立Lua进程修改内存副本。当前客户端文件SHA前后相同；不写WTF，不操作游戏，不输出账号／角色名称。对比冻结本轮前Items，使用同一当前Store与数据，以最新观察角色的内容发布触发每轮失效，再逐角色公开查询。

| 31角色、同一数据 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 首次构建累计分配 | 5.512MB | 4.659MB |
| 随后10次失效＋全角色查询累计分配 | 41.390MB | 13.355MB |
| 10轮离线耗时（单次样本） | 1.359s | 0.200s |
| 回收后派生数据保留增量 | 1.037MB | 1.217MB |

累计分配减少约68%；耗时是一次离线样本，非客户端帧耗时。代价是打开会话中额外保留约0.18MB的有界owner索引，关闭全部释放，不新增登录预加载。前后全部公开结果字段的确定性指纹均为964c785a；首轮输出121行。没有以减少历史或省略真实核实换取指标。以上不能直接推算305MB峰值会下降多少，真实悬停挂钩、物品事件时序和其它消费者仍需客户端证据。

## 后续实机反馈（2026-10-29）

用户随后报告：登录26.2MB，打开邮箱41.2MB，等待后回收一部分；附件箱Alt收一份后约40MB，普通左键批量收件后73MB；随后正常批量收取多封、多附件，最终约170MB。按用户反馈登记Alt单份异常增长已明显改善，登录与首次打开占用基本持平；本次未独立核对实际加载字节，不据此重新定位此前305MB的全部归因。

大批170MB时的邮件／附件数量及数分钟自然回收后的保留量尚未提供，不能与此前两三封的110／150MB直接比较，也不能判断为持续泄漏或已解决。已向用户询问批量规模及保持邮箱打开后的自然回落值；完整历史、在途、寄信与暂停等功能验收不由内存反馈推定通过。该反馈只覆盖用户当前客户端，不扩大Forever或发布就绪范围。
