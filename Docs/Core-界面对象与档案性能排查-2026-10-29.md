## 确认的问题与修复

### 设置工作台隐藏控件持续累积

`UI/AccountPages/SettingsWorkbench.lua` 原来只用 `parent.rows[index]` 记录每个位置最后使用的控件。如果下一页同位置需要另一种控件，就隐藏旧控件并创建新控件，再覆盖唯一复用引用。旧 Frame 仍属于原父级，返回原页时也不能再复用。反复切页会持续创建同类对象，正常 GC 不能销毁 WoW UI 对象。

现改为在每个行位置按控件类型保留复用池；`parent.rows` 仍表示本次布局使用的控件，切换类型仍隐藏上一控件。重复进入已使用过的页面／行类型不再创建控件。池规模取决于实际访问过的行位置与类型组合，而不是切页次数；首次进入新页面或显示更多行时仍可按需扩展。

真实 Core 清单及真实设置渲染器，模拟原生 Frame，依次访问常规／窗口／信息条／显示入口／角色排序五页一次，再重复相同顺序 20 轮（100 次切页）：

| 目标 | 本轮修复前 Frame 数 | 修复后 Frame 数 |
| --- | ---: | ---: |
| Mists | 157 → 2,877 | 147 → 147 |
| Retail | 125 → 2,205 | 115 → 115 |
| Forever | 153 → 2,793 | 143 → 143 |

zhCN／enUS 两种客户端语言分别得到相同计数。初始计数不同是因为一轮内的控件也开始复用。计数只包括夹具记录的 Frame，不包含 FontString／Texture，不是游戏 MB 或 FPS。没有对既有会话中的旧 Frame 做运行时删除；加载修复并 reload 会重建 UI 对象。

### 档案筛选重复发现字段／调用提供者

`UI/AccountPages/CharacterArchive.lua` 原来无论选“全部”“有档案”或“无档案”，都逐角色调用 `Fields:GetByConsumer`。其中会通过 Core.Contracts 枚举并调用业务字段提供者的 GetFields。因此随着角色数量增加，同一轮筛选会重复获取、隔离复制和排序相同字段定义。

现“全部”模式跳过无用的档案有无判断，其余模式只在本次筛选开始读取一次定义；不建立跨刷新缓存，下一轮仍重新发现提供者。保留既有档案判断规则、角色排序、等级及隐藏角色过滤。当前角色高亮仅比较 GUID，改用现有 GetCurrentID，不再读取整份当前角色。

30 名角色的单次页面尺寸计算，字段定义读取从三种模式均为 31 次，降为“全部”1 次、“有档案／无档案”2 次（含取得可显示列的独立读取）。这是调用次数对照；多个渲染／测量阶段仍各有必要工作，没有换算为游戏帧耗时。

## 职责、能力与发布收尾

生产改动仅为两个共享 UI 文件，完整职责单元是设置行控件生命周期和档案角色筛选／高亮读取。适用 Core Mists／Retail／Forever；无新增客户端专用 API、事件、静态目录，保持共享位置。设置仍由 Core 统一托管；业务提供者仍通过 Core.Contracts 发现，不按业务插件技术名分支，不接触其内部对象或 SavedVariables。

Core 自身复用现有角色 GUID 查询及公共字段／服务接口；API13、能力版本、业务最低 Core 要求和接入状态不变，没有新增公共能力或业务接入变化，因此公共能力迁移台账无需新增条目。没有新增玩家可见文案或修改语言区域，无需语言资源迁移；现有中英文渲染专项通过不替代实机语言验收。

源码清单保持 `YiboCore_Mists.toc`、`YiboCore_Mainline.toc`、`YiboCore_Forever.toc`，玩家包实际清单仍为 `YiboCore.toc`；无 TOC、XML、间接引用、加载或初始化入口改动。误目标写库保护、Core 就绪／版本检查及单次初始化沿用原实现，未把模拟 UI 结果登记为新实机保护验收。技术名、安装目录、各目标 SavedVariables 身份和 schema 均不变。

同路径覆盖，无新增旧文件参与运行链；三个目标的目标／Interface／引用／包内容静态校验通过。已有相同机制证据可复用，本轮新字节的干净／保留旧文件覆盖后实际界面、切页焦点、下拉菜单、短名编辑、档案提供者、reload／完整退出恢复及 CPU／回收后占用仍待实机。Forever不外推Mists／Retail或离线结论，尚不宣告整插件可发布。
