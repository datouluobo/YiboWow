# YiboMail 产品边界与开发路线图

> 文档状态：正式产品方案，作为立项与分阶段实施的范围基线。
>
> 适用游戏：魔兽世界熊猫人之谜经典版（当前项目目标客户端）。
>
> 方案范围：YiboMail 产品职责、数据契约、客户端限制与分阶段交付条件。

## 1. 产品身份

- 技术名：`YiboMail`
- 中文产品名：邮件管家（暂定，可在产品命名评审时调整）
- 产品类型：YiboCore 业务插件
- 核心依赖：`YiboCore`
- 正式 Slash 命令：`/yma`（2026-09-24 已完成整个工作区 `SLASH_*` 占用检查）
- 数据归属：邮件业务快照、历史和规则由 `YiboMailDB` 保存
- 产品状态：`0.5.0-api1` 已接入原生收发件增强、三标签设置与 Core 邮箱缓存浏览；正式版游戏内验收、Vault 切换适配及在途匹配确认待完成

邮件是独立业务域。YiboMail 管理邮件快照、生命周期、收件和发送辅助；YiboVault 管理全账号物品资产视图。邮件附件通过 YiboMail 的只读物品来源接口供 Vault 等插件消费，Vault 不重复扫描邮箱。

## 2. 面向玩家的产品承诺

YiboMail 帮助使用多个角色的玩家在一个地方回答：

1. 哪些角色的邮箱有邮件，分别有什么附件和金币？
2. 哪些已扫描邮件最接近到期，数据最后何时更新？
3. 同一种待取物品分布在哪些角色、邮件和数量中？
4. 哪些附件可以安全地一键收取？收取后原邮件内容是什么？
5. 物品应该寄给哪个角色，最近与谁有过邮件往来？

主窗口用于邮件附件的跨角色完整浏览和汇总；悬停用于快速查看邮箱数量、临期风险和数据新鲜度；玩家打开游戏邮箱时执行收件和发件操作。

“完整”指完整展示已经扫描并保存在本地的邮件及历史记录。游戏接口未暴露的邮件不能被插件读取；过期提醒也基于最近一次实际扫描，不代表邮箱实时状态。

## 3. 产品边界

### 3.1 包含范围

- 按角色保存已扫描的收件箱快照和最后扫描状态。
- 展示邮件发件人、主题、邮件类别、附件物品与数量、金币、剩余时间、退回状态及扫描时间。
- 主窗口跨符合 Core 范围与角色准入条件的角色展示邮件明细、附件来源和相同物品汇总。
- Broker／小地图悬停展示有效快照角色的邮件数、附件/金币提示、最近到期时间和扫描时间。
- 提供可由其它插件读取的只读邮件物品来源接口。
- 提供玩家主动触发的一键收取、收件规则、附件合并视图、联系人和发送规则。
- 保存已收取邮件的必要摘要及简明收发记录。
- 按 Core 的角色目录、服务器范围、统一页面、悬停入口、统一设置工作台和缓存清理机制运行。

### 3.2 明确不包含

- 独立维护角色目录、服务器选择、窗口壳、入口位置、角色排序或第二套设置窗口。
- 离线扫描、后台自动收取、后台自动删除或退件。
- 未经玩家逐次确认的自动发件、无人值守批量发件、自动转寄或规则链式转发。
- 邮件正文/信件内容的长期存档，除非未来有明确且独立评审的需求。
- 全量聊天、交易、拍卖行、经济分析或复杂关系图谱。
- 对未扫描邮件、跨电脑 SavedVariables 或离线期间的服务器状态作实时保证。
- 用主题、发件人或猜测数据推断 AH 买家；无法由游戏发票确认时标记为未知。

### 3.3 与相邻插件的职责

| 能力 | 责任方 |
|---|---|
| 角色目录、账号范围、统一主页面与入口、悬停外壳、设置工作台 | YiboCore |
| 邮件扫描、邮件生命周期、业务快照、收件/发件规则、邮件历史 | YiboMail |
| 邮件附件作为待取物品的搜索、跨容器物品总览 | YiboVault 消费 YiboMail 的来源接口 |
| 货币余额和上限 | YiboCurrency；不接管邮件金币流水 |
| 周期待办和任务状态 | YiboTodo；可读取邮件物品来源，不复制邮箱采集器 |

### 3.4 在 Yibo 系列中的位置

YiboVault 是当前优先建设的账号物品基础设施；YiboMail 排在其后，作为独立邮件业务插件推进。两者通过稳定的邮件物品来源接口集成，不形成插件间的硬性业务依赖：YiboMail 可先完成自身快照和页面，Vault 在具备消费条件时接入邮件来源。

YiboMail 延续 Yibo 系列“一个业务插件解决一类明确需求”的结构，不将邮件收发、背包管理、拍卖行分析和交易流水合成大型插件。其独立价值是邮件期限与生命周期追踪、邮箱到物品库的数据连接，以及之后的收件/发送工作流。

## 4. 数据与状态模型

### 4.1 邮件快照

每封扫描到的邮件至少记录：

```text
characterID
mailKey
sender
subject
mailType
items[]: itemID / itemLinkIdentity / name / count
money
CODAmount
daysLeftAtScan
scannedAt
returnedFlag
readState（如客户端可读取）
recordState
```

`mailKey` 是 YiboMail 分配的本地 opaque ID，不宣称是暴雪提供的永久邮件 ID，也不允许消费者解析。内部匹配签名优先综合角色、发件人、主题、邮件类型、附件、金币/COD 与退回标记；相似或重复邮件不能静默合并。物品变体应尽可能保留完整 itemLink 身份，同时以稳定 itemID 支持常规汇总。完整匹配与歧义规则见 [Public API v1 契约](YiboVault-Mail-API-v1-契约.md)。

默认不保存正文。AH 邮件通过游戏发票接口读取类别、物品、金额和可用的交易方；如接口返回单一买家/卖家姓名则记录，否则记录交易方未知。

### 4.2 邮件记录状态

| 状态 | 含义 |
|---|---|
| `observed` | 邮件在最近一次邮箱扫描中可见 |
| `stale` | 有缓存，但扫描时间已久，当前邮箱状态未知 |
| `in-transit` | 本账号角色发件成功后建立的待确认记录 |
| `received-confirmed` | 目标角色后续扫描到匹配邮件 |
| `collected-archived` | 玩家收取后保存了来源邮件摘要 |
| `return-confirmed` | 扫描到明确的退回邮件并完成匹配 |
| `unverified` | 邮件未再次出现，但无法确定其收取、退回或删除原因 |

发件成功只代表发送操作成功，不代表目标邮箱已收到。邮件不见了不能自动解释成已退回。只有目标角色实际扫描确认后才能标记收到；只有匹配到退回邮件后才能标记退回。

### 4.3 数据新鲜度和提醒

- 根据最后扫描时的剩余天数与扫描时间估算到期时刻；悬停和主窗口同时显示扫描时间或过期状态。
- 暴雪支持资料说明邮件通常在邮箱保留 30 天；运行时仍以客户端对单封邮件返回的剩余时间为准，不用固定 30 天替代实际读数。[Expired Mail - Blizzard Support](https://us.support.blizzard.com/article/8893)
- 角色离线、邮箱关闭或长时间未扫描时，提醒标为“按上次扫描估算”。
- 没有缓存、接口不可用、扫描未完成、数据过期和已知无邮件必须分别表达，不得将缺数据显示为零。
- 临期排序优先考虑有附件或金币的邮件，再考虑空信；展示期限阈值由设置确定，默认阈值在阶段一设计评审时冻结。

## 5. 100 封可见上限与积压邮件

游戏邮箱接口存在单次最多可见 100 封的限制。邮箱总数超过当前可见数时，YiboMail 必须展示可见数、游戏返回的总数、未扫描数量和上次扫描时间。

### 可以保证的行为

- 主窗口可以展示所有本地已缓存的邮件和归档记录，不受当前原生邮箱只显示最近一批的限制。
- 重复扫描时尽量去重并更新快照；已收取记录继续保留在历史列表。
- 通过游戏返回的 `current` 与 `total` 数量差识别存在尚未扫描的邮件，并发出积压提示。
- 阶段二可在邮箱内逐批处理当前可见邮件；游戏暴露下一批后继续扫描，并把处理前的邮件摘要归档。
- 每次邮箱刷新时把新显现且读取成功的邮件写入本地持久缓存；同一封已缓存邮件复现时更新最近可见时间。此前批次的缓存可在 Mail 历史／待核实视图追溯，但当前待取附件以最新可见扫描为准。

### 不能保证的行为

- 阶段一只读扫描无法读取当前游戏接口尚未暴露的旧邮件，也不能展示这些邮件的具体发件人、附件或到期时间。
- 插件不能在角色离线时阻止邮件到期，也不能保证服务器一定会继续保留邮件。
- 只有在游戏暴露下一批邮件之后，YiboMail 才能缓存该批内容。阶段二的逐批处理需要玩家在邮箱在线操作，并依赖游戏实际刷新行为、背包空间和受保护操作限制。
- `total - current` 是本轮未显示的邮件数；其中可能有先前扫描过的旧缓存，也可能有从未读取过的邮件，不能单凭这个差值判断具体身份。
- 提醒不能替代及时登录处理邮件；若邮箱超过可见上限，提示应明确写出“仍有邮件未扫描”，而不是“邮箱已完整扫描”。

阶段二的逐批收取须先预览当前批次、检查背包容量、标明 COD/特殊邮件，并在批次之间等待游戏刷新。背包空间不足时停止并报告，不能跳过后误报完成。用户可选择仅扫描/归档流程能读到的批次，或确认收取附件以释放邮箱位置；产品文案必须区分这两种结果。

## 6. 页面与交互

### 6.1 YiboCore 主页面

页面名称暂定“邮件”。主表使用邮件为行、邮件来源角色为主要识别字段；过滤和组织优先采用状态、到期时间、邮件类别及物品搜索。相同物品汇总作为可切换视图或明确分区，点击汇总必须能回到来源邮件列表。

主窗口需覆盖 Core 允许显示的所有有效角色及其已缓存邮件，不设置固定角色数截断。邮件较多时使用搜索、筛选、分页或分组，不能无限延长页面或使用横纵双滚动。表格布局在实现阶段按邮件字段密度与 Core 能力评审后确定。

### 6.2 悬停预览

- 复用 YiboCore 的统一入口、窗口与快照，不创建独立文本摘要窗。
- 默认显示有有效邮件快照的角色及邮件数量、最早到期项和数据更新时间。
- 有临期附件/金币时显示精简风险信息；不包含无数据角色、调试信息或装饰文本。
- 角色准入、过滤、范围和状态判断必须与主页面一致；受 Core 悬停角色数量上限约束时明确显示覆盖状态。

### 6.3 邮箱内操作区

收件与发件辅助附着于原生邮箱操作场景。YiboCore 仍管理其统一账号窗口和设置；邮箱内面板由 YiboMail 提供业务控件，不另造全局设置工作台或入口系统。

原生收件箱保留窗口标题、关闭与收发标签，内容区提供邮件／附件切换、附件聚合来源、逐槽与金币勾选及批次预览。原生发件箱沿用收件人、主题、正文、附件、金额/COD 与最终发送控件，增设联系人和规则装填条。Core 业务面板用于各角色邮箱缓存浏览，提供邮件列表与附件集中模式，搜索、角色筛选、分页及来源展开均基于同一快照；最新快照与待核实缓存分别浏览。联系人、规则与缓存管理位于 Core 三标签设置。

## 7. 插件接口与数据所有权

### 7.1 所有权原则

- `YiboMailDB` 保存邮件快照、归档、联系人和业务规则。
- Core 不接管邮件业务 SavedVariables，也不把邮件内容写入 `YiboCoreDB`。
- Core 管理账号页面、范围、入口、统一设置和跨插件角色清理注册。
- 邮件附件作为 `mail` 容器来源参与 Vault 搜索，但仍保留“待取邮件”来源与到期信息。

### 7.2 对外只读接口

阶段一提供版本化公共接口。阶段 0 冻结候选签名如下，完整参数、结果、状态与兼容规则见 [Public API v1 契约](YiboVault-Mail-API-v1-契约.md)：

```lua
YiboMail.Items:GetByCharacter(characterID, options)
YiboMail.Items:Query(query)
YiboMail.Items:GetState(characterID)
YiboMail.Items:GetRevision()
YiboMail.Items.Events:Register(callbackOwner, callback)
YiboMail.Items.Events:Unregister(callbackOwner, callback)
```

查询结果至少含有 `itemID`、可用时的完整物品链接、数量、`characterID`、来源邮件匹配键、剩余时间估算、快照时间、待取状态和数据有效性。调用方不得修改返回值或依赖私有 SavedVariables 结构。

接口应返回副本或不可变投影；在邮件扫描、收取、归档和状态迁移后，通过 YiboMail 版本化事件通知订阅者刷新。相同内容不重复广播，事件需携带角色、变更范围和 revision。

### 7.3 与 Vault、Core 的协作

YiboMail 作为邮件来源的所有者，提供稳定的 `mail` 来源 ID、只读查询、状态、接口版本/能力和变更事件。Vault 在 Mail 可用时通过其公开接口读取附件，并在自己的物品查询中保留邮件来源与到期信息：

- Mail 不依赖 Vault；Vault 的 Mail 适配是可选能力，缺少或不兼容 Mail 时其它容器查询仍可工作。
- Mail 返回明确的数据新鲜度、完整性和不可用状态；Vault 不把缺失邮件来源当作空库存。
- Core 管理两插件共用的角色目录、账号范围、页面、入口、设置和角色缓存清理注册，不持久化邮件或库存业务数据。

本轮不在 Core 增加物品专用来源注册表。Mail 与 Vault 各自提供版本化业务接口和接入文档；Vault 不直接读取 `YiboMailDB`。联合开发顺序见 [Core、Vault、Mail 实施计划](YiboCore-Vault-Mail-实施计划.md)。

### 7.4 清理、容量与隐私

- 注册 Core 角色缓存清理回调；删除角色时移除该角色的邮件快照，保留账号级联系人和规则。
- 已收取邮件历史设置可配置保留期限/容量；默认策略在阶段一数据设计评审时冻结，任何清理只针对业务历史，不影响当前邮箱。
- 邮件正文默认不采集；调试输出不记录正文、收件人完整历史或敏感用户内容。

## 8. 竞品与开发理由

已有插件可覆盖局部功能，下载页未见单独收费说明；仍需 WoW 游戏客户端及适用游戏授权。它们可以与 YiboMail 并行使用，也说明邮箱交互必须兼容原生 UI、避免重复扫描和按钮冲突。

| 插件 | 已有能力 | 对本项目的限制/差异 |
|---|---|---|
| [Postal](https://www.curseforge.com/wow/addons/postal) | MoP Classic；联系人、快速附件、批量收取与部分收件筛选 | 功能按邮箱操作设计，不提供 YiboCore 多角色邮件历史、YiboVault 物品来源接口和统一状态视图 |
| [Favorite Contacts](https://www.curseforge.com/wow/addons/favorite-contacts) | 收藏联系人并快速填写原生发件人 | 主要解决快速选联系人，没有跨角色邮件库存、到期/收件状态和规则化物品来源 |
| [Inbox Mailbag](https://www.curseforge.com/wow/addons/inbox-mailbag) | 将可见收件箱附件聚合成可搜索物品格 | 上游原版多年未更新；聚合主要面向当前可见收件箱，不能替代账号级持久缓存和 Core 集成 |
| [MailLogger](https://www.curseforge.com/wow/addons/maillogger) | 记录邮件/交易往来 | 目标是广泛日志；YiboMail 只需邮件收发对象、附件/金币和 AH 可确认交易方的简明业务记录 |
| [BagSync](https://www.curseforge.com/wow/addons/bagsync) | MoP Classic；追踪角色物品、邮件、货币和金币，提供跨角色搜索 | 覆盖面广，适合直接满足通用库存查询；YiboMail 的建设重点是 YiboCore 工作台、过期/在途邮件状态、收发规则和供 Vault 消费的稳定来源契约 |

开发 YiboMail 的理由是形成统一的邮件快照与物品来源，让 Vault 与账号工作台能回答多角色“有什么、在哪里、多久到期”，再逐步把高频收件和发送操作放进同一条工作流。实现时只借鉴公开可观察的交互，不复制第三方插件源码或资源；各插件具体授权按本仓库项目合规流程核验。

## 9. 三阶段开发路线图

各阶段按顺序推进。每阶段完成编码、验证和文档后再进入下一阶段；阶段二依赖阶段一稳定的数据模型，阶段三依赖收件箱数据与规则接口稳定。

### 阶段一：邮件信息缓存与物品来源接口

**目标**：建立可信的邮件快照与跨角色读取基础。

**交付物**

1. `YiboMail` 插件目录、TOC、SavedVariables、Core 注册、唯一三字母 Slash 命令和基础配置。
2. 邮件采集、去重/匹配、快照时间、期限估算、状态和归档数据模型。
3. YiboMail 只读邮件物品来源查询、状态、版本能力与变更通知 API 及对应文档。
4. YiboMail 邮件账号页：跨角色邮件明细、附件来源、物品合计、筛选/分页、空状态与过期状态。
5. Core 悬停预览：邮件数、临期摘要、扫描时间与数据覆盖状态。
6. YiboVault 可选消费 `mail` 来源的契约和示例；实际适配由联合实施计划中的 Vault 集成阶段交付。
7. 角色删除清理、缓存保留策略和中文文案。

**阶段验收**

- 访问邮箱后能采集全部当前可见邮件及附件、金币、类型和剩余时间；再次扫描不会产生重复邮件。
- 主窗口显示 Core 范围内所有角色的已缓存邮件，允许按角色/范围/状态筛选；重复物品能合计并追溯每条来源。
- 悬停和主页面使用同一快照与状态逻辑，最多角色限制按 Core 契约执行，不静默截断。
- 超出当前可见邮件数时明确显示未扫描数量和扫描时间；不把未暴露邮件显示成已扫描。
- 公共只读接口能返回待取物品和来源状态，供 Vault 接入；调用方不直接访问业务私有 SavedVariables。
- 目标客户端验证邮箱打开、分页/刷新、空信、金币信、附件信、AH 邮件、重复主题邮件、退回邮件及邮件消失后的状态迁移。

**不在本阶段**：自动/一键收取、按物品规则发件、批量发送。

### 阶段二：收件辅助与附件聚合

**目标**：把查看到的邮件安全转换为可处理的收件队列和持久归档。

**交付物**

1. 邮箱内聚合视图：同物品合并计数、搜索/筛选、最早到期标识、来源邮件跳转。
2. 玩家主动触发的一键收取与规则筛选，包括附件/金币、邮件类型、发件人等。
3. 收取预览、背包空间检查、COD/特殊邮件处理、逐封节流、停止/恢复和结果报告。
4. 收取后归档来源邮件摘要，并通过 YiboMail 事件通知 Vault 等已订阅消费者刷新。
5. 面向大于 100 封邮箱的逐批处理：识别 `current/total` 差异、在可见批次收取/归档后等待邮箱刷新、重复至用户停止或安全条件不满足。

**阶段验收**

- 只执行玩家明确触发的操作；开始前显示范围和预计收件内容。
- 背包空间不足、COD、不可收取邮件、游戏刷新变化和操作失败均能安全停止并解释，不误报完成。
- 邮件列表更新/重排期间不会把附件取自相邻邮件；每次只在游戏 API 允许的安全上下文调用动作。
- 合并物品可逐一定位来源；收取后历史仍可看见原始附件和角色、时间。
- 邮箱总数超过当前可见数时，能逐批获取后续由游戏暴露的邮件，并在每批前保持可见预览/进度；无法暴露或无空间时明确停止。
- 不承诺离线防退件；临期和未扫描状态在操作界面清晰区分。

### 阶段三：发送辅助、联系人与发送规则

**目标**：缩短常用邮件操作，同时让玩家保有最终发送控制。

**交付物**

1. 联系人清单：账号角色、手动常用联系人、最近收件人；避免重复造好友/公会通讯录管理。
2. 邮箱原生发件界面的快速选人和玩家配置的物品/类别到收件人规则。
3. 装填前预览：收件人、物品、数量、邮件格占用；支持本次修改、撤销尚未发送的装填。
4. 发件成功后的 `in-transit` 快照、目标角色确认、未确认/待核实状态和去重策略。
5. 简明往来记录：方向、收发双方、附件/金币摘要、时间、状态；AH 买家只在游戏发票明确返回时记录。

**阶段验收**

- 联系人和规则跨符合设计范围的角色共享并可删除/编辑；不会覆盖原生收件人或附件输入而无提示。
- 规则只辅助选择和装填；发送必须由玩家明确点击确认，不执行无人值守批量发送。
- 同账号角色发件成功后，工作台立即显示在途；目标角色扫描匹配邮件后再确认送达。
- 邮箱未开、超时、重复物品/主题或扫描缺失时显示待核实，不错误推断退回或已收到。
- 往来记录范围保持简洁，无交易面板、利润统计、正文存档或关系图谱扩张。

## 10. 质量、兼容与发布约定

- 目标客户端版本与 `.toc` Interface 按每次发布时的项目基线确认；当前项目多个插件使用 `50504`，实现前仍需核对客户端实际构建。
- 插件 `.toc` 使用统一 `[Yibo]` 青绿色标题前缀，声明 `## RequiredDeps: YiboCore` 和独立 `YiboMailDB` SavedVariables。
- 所有正式 Slash 注册必须工作区全局唯一，恰好三个英文字母，不能保留旧命令别名。
- 设置只注册到 Core 统一设置工作台，插件页只呈现邮件业务规则与数据/缓存，不重复 Core 的角色、页面、入口或字段设置。
- YiboMail 与 YiboVault 的公开接口采用能力版本检查和明确的数据状态；缺插件、旧版本、不可用来源均可降级显示。
- 收件和发件 UI 兼容原生邮箱及目标客户端受保护操作约束；具体事件/API 必须在目标客户端验证，不能仅按 Retail 代码推断。
- 缓存删除、历史容量、事件订阅注销和角色清理纳入每阶段验收。

## 11. 路线图依赖与决策门

```text
阶段一：采集与缓存
        ├── YiboMail 只读查询/事件接口
        ├── Vault 可选来源适配契约
        └── 邮件账号页与悬停
                 ↓
阶段二：收件辅助
        ├── 附件聚合与规则
        ├── 安全队列与归档
        └── 100 封积压邮件逐批处理
                 ↓
阶段三：发送辅助
        ├── 联系人和发件规则
        ├── 在途/确认状态
        └── 简明往来记录
```

进入每阶段前必须冻结其数据契约、游戏客户端限制和验收场景；阶段验收通过后才开始下一阶段。Mail API 必须维持邮件快照由 Mail 拥有，不通过让 Vault 读取 YiboMail 内部表来绕过。

## 12. 后续需求变更门槛

新增需求进入路线图前回答：

1. 是否直接帮助玩家查看、收取、发送或追踪游戏邮件？
2. 是否能复用 YiboCore 角色/页面/入口，以及 YiboMail 的邮件来源接口和 YiboVault 的物品查询接口？
3. 数据是否有明确来源、时间和已知/过期/未知状态？
4. 是否会造成未经玩家确认的收取、删除或发送？
5. 是否会把插件扩张成拍卖行、经济日志或通用库存管理器？

若与邮件工作流无直接关系，或需要伪造服务器状态、无人确认的破坏性动作，应拒绝纳入 YiboMail，转交对应业务插件或单独评审。
