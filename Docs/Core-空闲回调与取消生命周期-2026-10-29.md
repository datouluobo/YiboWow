## 已确认并修复

| 范围 | 原因与处理 |
| --- | --- |
| `UI/Input.lua` | 每个共享输入框创建后即保留 OnUpdate，即使没有 OnChanged 或待提交文本。现仅在存在输入法组合文本待提交时安装，提交、静默替换或隐藏取消待提交状态时卸载；保留客户端标志晚清除、userInput、预编辑文本及光标语义。 |
| `Runtime/ItemResolver.lua` | Cancel 原先只置 cancelled 标记，等待数组和句柄继续保存回调闭包。现取消时移除等待者并释放回调；同步／异步完成也释放句柄回调引用。完成分发前先解除等待列表关联，避免一个回调取消另一等待者时移动数组并跳过其它回调。 |
| `UI/BusinessItemActions.lua` | 有菜单项目全部解绑后，仅剩 menu=false 绑定时，原先以“还有任意绑定”为由保留 20Hz 鼠标焦点监视器；同一控件改绑 menu=false 也会留下监视器。现统计有菜单的有效绑定，最后一个菜单移除时隐藏监视器，再绑定菜单时恢复；重复绑定不重复计数。 |

物品取消仍只影响自己的回调；已发出的原生请求继续按原事件／超时收敛，其他消费者可加入同一请求，不重复发请求，不重置原超时。失败必须显式 retry 的策略保持。此处减少的是取消后的短期引用滞留；旧实现通常在事件或默认8秒超时后释放等待数组，不能把该现象描述为永久泄漏。完成后仍持有句柄的调用方，现也不再通过句柄保留回调数据。

## 修改前后证据

真实 Core Mists／Retail／Forever 清单和共享实现，模拟原生 UI／物品接口：

- 100 个空闲输入框、600 帧：每个目标 OnUpdate 调用均从 **60,000 → 0**。这不是实际游戏输入框数量或 FPS 测量。
- 对同一未就绪物品连续请求并取消1,000次，保留句柄后主动 GC：闭包捕获的弱引用探针从 **1,000 → 0**，等待数组长度从 **1,000 → 0**；原生请求次数始终为1。
- 只有 menu=false 绑定时：三个目标的 hoverFrame 从仍显示改为隐藏。并覆盖菜单开／关、双绑定、重复绑定、逐个解绑和重新启动。

输入／取消的编辑前实际输出为 `_NonRelease/CorePerformance20261029/deferred-baseline.txt`；监视器单独的编辑前输出为 `hover-baseline.txt`（后者采集时输入／取消修复已经生效）。baseline参数只允许旧源码执行同一夹具，不自动重建旧源码。
