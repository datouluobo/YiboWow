# YiboAutoOpen 队列与失败恢复规则

## 目标

任何一个白名单物品开启失败，都不能占住 `pending` 或反复抢占扫描，使背包中的其它白名单物品得不到处理。自动失败隔离只针对单个物品；背包扫描、世界状态和人工取消等暂停/隔离原因必须分开处理。

## 队列模型

- 每次处理前根据最新背包状态重建候选集合；仅包含目录白名单中、非手动专用、未锁定、冷却完成且未隔离的物品。背包数据未就绪、锁定和冷却物品不算失败候选。
- 队列调度单位是物品 ID（而非槽位）。同 ID 多个槽位不制造重复队列项；每次实际开启前仍重新定位该 ID 的当前槽位，避免背包移动后使用陈旧槽位。
- 同时只允许一个 `pending` 开启操作。扫描事件不得取消或覆盖正在等待结果的操作。
- 成功：清零该 ID 的失败计数；重新读取背包并继续处理仍存在的候选。
- 失败或有界观察后仍无法确定结果：释放该操作的 `pending`，立即把失败 ID 移到队尾。只要队列还有其它不同 ID，就先尝试其它 ID，不因单个失败而隔离它。
- 为避免多个坏物品在队列中无限轮转：某 ID 达到单项重试上限，且队列中其它候选也都已达到各自上限时，才允许隔离当前 ID；随后继续处理剩余队列。队列只剩一个失败 ID 时，对该 ID 做有界重试，达到上限后隔离。
- 每次出队前都重新核验物品仍在背包、仍符合目录与安全条件；不存在或已不符合条件的队列项直接丢弃，不计失败。新出现的物品由背包/拾取事件加入候选。
- 隔离是每物品独立状态，不是全局队列暂停。隔离期间其它候选照常处理。

## 结果判定与 pending 生命周期

- 物品总数减少或对应堆叠减少，判为成功。
- 槽位变化、暂时读不到槽位/物品信息、物品锁定等属于未知结果；有限次、有限时间复查后仍未知，转为一次失败。
- 失败、超时、API 调用异常、未知结果终结、玩家明确取消确认框，以及队列清空/插件停用等所有终结路径，都必须释放或使旧 `pending` 令牌失效。
- `pending` 只表示当前正在判定的一次使用操作，不能兼作候选队列或失败隔离状态。

## 隔离类型和清除规则

- `retry-backoff`：自动失败隔离，触发原因与失败计数按物品记录。世界恢复事件清除此类隔离；若设置了退避计时，计时到期也清除。清除后重新扫描并加入仍符合条件的物品。
- `bind-cancelled`：玩家主动取消拾取后绑定确认，是显式人工决定；换地图、读条、进出副本、拾取事件和普通自动恢复均不得清除此隔离。仅手动“重新尝试”、用户重新加入目录等明确操作可以清除。
- 恢复信号包括登录、`PLAYER_ENTERING_WORLD`、读条结束、区域/地图/副本变更、传送后的世界恢复以及拾取关闭等。触发时先清理自动失败隔离，再在短恢复窗口内重扫；必要时延迟重扫以等待背包数据稳定。
- 世界恢复和设置页“刷新/重新尝试”会按游戏当前可见的商人、银行、邮箱、交易、拍卖、公会银行和虚空仓库界面重建敏感界面状态，纠正丢失关闭事件造成的陈旧暂停标记；仍实际打开的敏感界面继续暂停。
- 战斗、施法、读条、死亡/未登录、敏感界面打开、拾取界面打开、背包数据未就绪、冷却、锁定和空位不足都是安全暂停/延迟条件，不增加失败次数、不进入自动失败隔离。条件解除后恢复扫描。
- `ITEM_PUSH` 或背包更新只表示重新检查背包；不得清除玩家主动取消的隔离。新物品 ID 正常入队。

## 状态与诊断

- `pending`：当前单次使用尚未判定。
- 候选队列：尚待尝试的不同物品 ID。
- 失败计数：当前登录内每个物品 ID 独立累计；成功或自动隔离解除后清零。
- 隔离列表：按物品 ID 区分自动失败与玩家取消原因。
- 当队列为空且无延迟候选时进入 `IDLE`；因安全条件无法处理时显示对应 `PAUSED`/`WAITING_READY`，不能伪装成开启失败。

## 验收场景

1. A 失败、B 可开：释放 A 的 pending，先开 B；不能立刻再次开 A。
2. A、B 都失败：按队尾轮转且每个 ID 独立计数；达到边界后隔离单项并继续处理队列，不能无限轮转。
3. 只有 A 且始终失败：有限次尝试后隔离 A，队列归空且状态恢复为可等待/空闲。
4. A 失败等待期间发生读条或进出副本：不把临时安全暂停记作新失败；世界恢复清除自动隔离并重扫。
5. 玩家取消绑定确认：该 ID 保留人工隔离，世界恢复不清除；显式手动重试才清除。
6. 等待期间槽位移动、物品离包或 ID 变化：按最新背包重定位/丢弃过期候选，不误用旧槽位。
