# 多版本目标与发行标识规范

状态：已确认。建立日期：2026-10-13；最近修订：2026-10-27。

本规范统一产品目标、源码目录与加载清单、客户端实际 TOC、安装包名和 CurseForge 标签。它是这些标识的唯一命名来源；架构与分包原则见 [多版本开发规则](多版本开发规则.md)，渠道内容和归档生命周期见 [发布包约定](../发布包约定.md)。机器配置位于 `Tools/ReleaseProfiles.psd1`，必须与本规范同步维护。

## 1. 产品目标

| 游戏产品 | 稳定目标 ID / 源码目录名 | 安装包目标 slug | 标准源码 TOC 清单 |
|---|---|---|---|
| 正式服 | `Retail` | `retail` | `<Addon>_Mainline.toc`（已实测识别） |
| 熊猫人怀旧服 | `Mists` | `mists` | `<Addon>_Mists.toc` |
| 燃烧的远征周年纪念服 | `TBC` | `tbc` | `<Addon>_TBC.toc` |
| 经典怀旧服60 | `ClassicEra` | `classic-era` | `<Addon>_ClassicEra.toc` |
| 泰坦重铸「时光」 | `Titan` | `titan` | `<Addon>_Titan.toc` |
| 无限 | `Forever` | `forever` | `<Addon>_Forever.toc` |

`<Addon>` 是插件技术名，例如 `YiboVault`。目标 ID 和目录使用表中大小写，包 slug 使用表中小写；命令接受不区分大小写的输入，输出统一为规范名称。目标命名不代表已经适配或可以构建。新增产品先更新本表与机器目标目录，再为实际接入插件登记构建配置。

本表是 Yibo 的产品简称，不要求与所有外部系统使用同一字符串。TBC 在本仓库明确指燃烧的远征周年纪念服，完整产品名称保留在说明中；Titan 对应时光产品，本机暴雪安装目录为 `_classic_titan_`。打包工具也使用简短映射，例如 [BigWigs Packager 源码](https://github.com/BigWigsMods/packager/blob/master/release.sh)接受 `tbc` 并映射为 `bcc`，时光使用 `titan`。这些外部别名分别登记和验证，不反向决定仓库目录名或兼容范围。

`Common/` 保存共享实现，不是产品目标。`universal` 仅为已获准单包兼容方式的产物标识，实际支持范围必须列为明确目标集合；它不表示所有已知或未来客户端均兼容。

## 2. 三种标识分别管理

| 层次 | 用途 | 规则 |
|---|---|---|
| 产品目标 ID | 源码、规则、数据、构建选择 | 使用上表；不以客户端内部分类代替产品名称 |
| 源码 TOC 清单 | 确定版本与加载文件 | 默认按上表命名；迁移中的现有清单通过配置明确映射 |
| 客户端加载 TOC | 游戏实际读取 | 独立安装包统一输出 `<Addon>/<Addon>.toc`；源码内容及引用路径保持有效 |
| CF flavor / 游戏版本 | 平台匹配与上传 | 显式配置并核验；不由产品名称、TOC 后缀或 Interface 整数猜测 |

源码目标清单优先直接使用已实测可识别的后缀。Retail 目标 ID、目录和包 slug 保持 Retail／retail，源码唯一清单采用 `<Addon>_Mainline.toc`；不得另建内容相同的 `_Retail.toc` 或开发别名。构建时将选定清单输出为默认 TOC，包内仅有该目标的加载 TOC。其它新客户端先实测再确定清单后缀，不以产品简称猜测。

`## Interface` 是客户端兼容声明，必须与构建配置中的 Interface 集合一致；它不是 CF 上传 API 的 `gameVersions` 数字 ID。CF 游戏版本名称、flavor 与平台数字 ID 均属于发布元数据。平台数字 ID 在准备上传时从当前平台版本列表解析，并与包内清单核对后使用。

现有共享构建的 Mists 基线为 Interface `50504`、CF flavor `mists`、游戏版本名称 `5.5.4`。尚未迁移的插件继续以原 `<Addon>.toc` 为源清单；`existing-mists-baseline` 不替代最新工作树实机验收。

2026-10-26 Core 已接入 Mists 与 Forever 两个构建配置，分别从 `YiboCore_Mists.toc`、`YiboCore_Forever.toc` 输出单目标默认 `YiboCore.toc`。仓库默认 TOC 只加载预启动提示，该提示不进入单目标安装包运行链。Forever 配置为 Interface `16001`、flavor `forever`、游戏版本名称 `1.60.1`，状态为开发入口已验、发行未就绪；flavor 映射见上述 BigWigs 一手源码，平台数字 ID 仍须上传前查询。其它插件的开发 Forever 清单不因此获得发行配置。

Core 全目标源码归档统一采用 `Bootstrap.lua` 的主版本及 API，R2前目标标签为 `forever-mists`，不随所选构建目标改变；安装包使用对应目标版本（当前 Mists `1.12.9`、Forever `0.2.0`，API 均为 `13`）。R2新增Retail0.1.0后，全目标源码标签为forever-mists-retail，主版本／API仍从Bootstrap读取；各玩家包按目标独立版本。正式发行检查另行完成。

## 2.1 多目标 TOC 与运行入口规则（2026-10-26）

适用于本次已验证的 MoP／Forever 环境，以及后续触及的多目标入口迁移；未迁移插件和已声明维护例外保持各自现状。机制探针与Core实现均已有实机证据，但不代表所有业务插件已完成迁移。新增客户端须重新验证其识别后缀、选择优先级与加载保护。

| 层次 | 统一规则 |
| --- | --- |
| 源码默认清单 | `<Addon>.toc` 是缺目标时的最小提示入口，不再承载旧版默认业务；不声明业务SavedVariables，不创建就绪API，不初始化业务或注册采集事件 |
| 源码目标清单 | `<Addon>_Mists.toc`、`<Addon>_Forever.toc` 分别列出该目标共享文件与适配文件，可声明 `X-Yibo-Target` 供诊断；该元数据本身不实现路由 |
| 单目标安装包 | 构建器选中目标清单，输出 `<Addon>/<Addon>.toc`，包内只保留本目标加载TOC及所需文件；不附带开发默认Hint或其它目标清单 |
| 全目标源码归档 | 保留默认提示及已有各目标清单、实现和公开文档，用于开发查阅；不作为默认玩家安装包 |
| Interface | 使用该目标实测值并与构建配置一致；Interface不是运行时产品身份校验，也不是平台上传数字ID；正常验收不依赖加载过期插件 |

2026-10-27 Retail实测：本机12.1.5.70575／Interface120105，WOW_PROJECT_ID与WOW_PROJECT_MAINLINE均为1；仅_Retail候选不会被识别，_Mainline被识别，候选同存仍选_Mainline，缺目标只执行默认Hint且消费者不就绪。2026-10-28按用户确认收敛：Core源码与构建统一只用YiboCore_Mainline.toc，删除冗余YiboCore_Retail.toc，取消DevelopmentToc映射；玩家包仍只含默认YiboCore.toc。统一构建器拒绝Retail配置使用其它源清单、DevelopmentToc别名或残留_Retail.toc。后续插件新增Retail目标遵守同一规则。原始探针证据保留，见[Retail接入验收](../YiboCore/Docs/R2-01-02-Retail目标与构建实施验收.md)。

源码目录以目标清单选择运行链；已验证环境中正确目标清单优先于默认提示，缺目标时只走提示，不运行其它目标业务。不得依赖故意Lua错误触发清单重选。空TOC或提示TOC可能仍被客户端记作已加载，因此“已加载”不等于业务API就绪。

每个目标在适配入口校验实际产品身份，并在业务数据库初始化或写入、角色采集及对外注册前停止误目标业务。依赖Core的业务目标清单声明 `RequiredDeps: YiboCore`，运行时仍须检查Core就绪状态、最低API及所需能力版本；Core不就绪／版本不足应给出升级或不可用提示并停止依赖功能。跨业务插件按Core公开能力发现，不以堆叠业务TOC依赖替代能力就绪判断。

初始化必须幂等：重复就绪通知和晚到依赖不重复注册事件、入口、页面或提供者；代码错误不发布成功就绪标记。客户端专用API、事件、规则与静态目录归入Mists／Forever；共享代码消费稳定契约，不复制整套共用实现。目录加载顺序由真实依赖确定，目标身份／策略必须早于依赖它的业务初始化。

保持技术名、安装目录与各目标SavedVariables身份稳定；MoP与Forever分别使用已约定的存档，不因文件迁移重置、互相导入或切换存档。版本按目标独立维护；公共API只从显式契约声明读取，不能由插件版本或最低Core要求推算。

覆盖更新必须替换旧默认TOC，保留旧文件时只让新适用加载链执行。除Lua外还需审查历史目标TOC、XML和间接引用；旧客户端认可的目标清单残留可能影响选择，不能只验证旧Lua残留。安装目录由一个更新来源管理，源码联接目录不得直接当作解压覆盖目录。需要临时测试时保留原联接与测试目录，切换前退出客户端，存档另行备份。

验证按证据去重：通用机制用例已在同客户端确认后可复用；每插件仍需检查实际加载图、一次初始化、误目标写库前停止、依赖未就绪，以及适用版本的干净安装／保留文件覆盖。TOC增删或变更后的重新发现须完整退出启动；reload只验证已发现加载链的重载。相同版本和加载字节可复用已有实机证据；离线、客户端和更新工具结果分别记录，不能互相替代。

这里的“运行入口”指加载与初始化。玩家可见入口继续遵守Core统一入口规范：由Core管理小地图、Broker、内置条及账号页面生命周期；探针／诊断走三字母Slash命令，不占用常规入口交互。

## 3. 包名与版本

| 产物 | 文件名格式 |
|---|---|
| 独立目标 CF 安装包 | `<Addon>-<slug>-v<Version>-curseforge.zip` |
| Core CF 安装包 | `YiboCore-<slug>-v<Version>-api<API>-curseforge.zip` |
| 已带 API 的业务版本 | 保留完整版本，如 `YiboVault-mists-v1.2.3-api1-curseforge.zip` |
| 单包兼容例外 | `<Addon>-universal-v<Version>-curseforge.zip` |
| 每插件全目标 GitHub 源码归档 | `<Addon>-<完整游戏目标slug集合>-v<插件版本>-src.<SourceSHA256前12位>-github.zip` |

文件名顺序固定为“插件 → 目标 → 目标版本 → 公开 API（适用时）→ 渠道”。slug 在版本号之前，使同一目标的文件归为一组；此顺序是 Yibo 的发行约定，与 CF 版本选择机制分开管理。

每个目标是独立发布流，版本号独立递增，源常量与该目标 TOC 版本必须一致；带 API 的版本只附加一次 API 标识。Core、Mail、Vault 的公开 API 从自身实现读取；Reputation 等插件的最低 Core API 不作为自身 API 后缀。未声明自身公开 API 的业务包仅带目标与插件版本。目标专属修复只提升并发布该目标版本，其它目标保持现有版本。共享改动核对并回归受影响目标，分别决定是否发布；共同发布时可以使用相同版本号，也可以沿用各自版本序列，不要求齐步递增。

例如 Mists 已为 `1.2.3`，新目标可以从 `0.1.0` 起步；Mists 修复后升为 `1.2.4`，新目标仍可保持 `0.1.0`。不同目标的版本号不用于直接比较功能是否相同；以各目标变更说明与能力契约为准。API 版本描述公开契约，不能由资料片名称或插件版本号自动推导。上述版本仅为规则示例，不增加目标兼容声明。

GitHub 归档以源码及构建配置的 SHA256 标识快照，名称不随本次选中的目标或渠道变化。哈希由按路径排序的公开源码文件摘要与 `ReleaseProfiles.psd1` 摘要计算，包内记录完整值；此哈希标识构建输入，不是 zip 文件自身摘要。

每个 zip 保留一层 `<Addon>/`。源码目录迁移不改变插件技术名、玩家安装目录或各目标既有 SavedVariables 身份；目标间保持存档隔离。独立目标包只保留该目标实际使用的加载清单，单包兼容例外按已声明集合验证。目录迁移遵循 [触及即迁移规则](多版本开发规则.md#触及即迁移)，新旧包差异、旧入口残留与覆盖更新按 [发布验收要求](../发布包约定.md#覆盖更新与升级验收)核对，不能仅凭新包清单正确判定升级安全。

包内新增 `YiboReleaseManifest.json`，不在 TOC 中加载：

- 共通信息：schema、插件名、完整源码及配置哈希、已配置目标的版本/API/最低 Core API/源与加载清单/Interface/验证状态。
- CF：本包目标 ID、slug、CF flavor、游戏版本名称与包内文件清单。当前构建不上传，平台数字 ID 尚待发布时解析。
- GitHub：全目标源码用途、构建配置快照和文件清单；保留各源清单，不注入面向单一目标的运行时改写。

清单中的文件列表列出载荷文件，清单自身单独生成。归档包含某目标源码不意味着该目标已通过实机验证或已正式发布。

## 4. 统一构建入口

使用 PowerShell 7.2 或更高版本。全部 15 个插件入口复用统一命名与归档；14 个单目标插件接入共享构建器。BeastPaths 通过独立维护包构建器保留原有多 TOC/XML 内容，包名使用 universal；AutoOpen 当前只登记现有 Mists，未新增多目标声明。

```powershell
# 默认同时生成目标安装包和一份 GitHub 源码归档
.\Tools\Build-ReleasePackages.ps1 -Addon YiboVault -Target Mists

# 只构建/归档本目标的 CF 产物，保留现有 GitHub 归档
.\Tools\Build-ReleasePackages.ps1 -Addon YiboCore -Target Mists -Channel CurseForge

# 只生成全目标源码归档，保留各目标的 CF 产物
.\Tools\Build-ReleasePackages.ps1 -Addon YiboVault -Target Mists -Channel GitHub

# 校验源清单、版本、引用与 Lua 语法并返回计划，不创建安装包或移动旧包
.\Tools\Build-ReleasePackages.ps1 -Addon YiboCore -Target Mists -ValidateOnly
```

各单目标插件原 `_NonRelease/Tools/Build-*.ps1` 作为兼容入口，转调统一脚本；默认目标 Mists、渠道 Both，原 ProjectRoot/OutputRoot 参数继续可用。KeepStaging 参数保留以兼容旧命令；新版直接写入 zip，无复制式暂存目录。失败的 `.building-<运行ID>` 文件保留供诊断，成功时移为最终 zip。

单目标构建器校验静态 Lua TOC 引用，遇到 XML、条件或变量路径会明确停止，待真实目标需要时再扩展解析；Lua 编译器版本由目标配置指定。动态 TGA 和第三方通知通过显式资源配置补充。越界路径、其它产品目录、非发布内容、重复包条目、版本或 Interface 不一致均阻止出包。

Core CF 包继续生成目标对应的 `Data/PackagedAddonVersions.lua` 并插入加载位置；不要求不同目标 TOC 使用相同版本。Core 实际构建继续生成本地化候选报告，报告及客户端语言验收要求保持有效。ValidateOnly 不生成本地化报告，也不表示已完成游戏验收。

## 5. 产物发布与归档

先完成本次所有请求 zip，再复核源码及配置未在构建中变化、检查旧包归档目的地是否冲突，随后按插件、渠道和目标移动旧包并落地新包；移动失败尝试回滚本次所有已移动文件，若回滚也受限则列出未恢复路径。目标包和 GitHub 归档是独立产物流。

已存在同名最终产物或旧包归档目的地冲突时停止，不覆盖、不删除、不添加日期后缀。能匹配旧版稳定或 test/alpha/beta/rc 命名的无目标后缀 CF 包按历史 MoP 基线归档；其它已命名目标和 universal 包分别保留，无法分类的文件保持原位。旧包位于 `Builds/Archive/<Addon>/`，原文件名保持不变。

归档识别同时支持已生成的版本号在目标 slug 前的文件与当前目标在前的格式。新产物统一使用本规范第三节顺序；已有文件不批量改名，归档时保留其原始文件名。

## 6. 新目标接入检查

1. 检查目标实际客户端、TOC 加载方式、Interface、API 与内容范围。
2. 为对应插件登记 SourceToc、LoadToc、版本常量位置、Interface、CF flavor/版本名称、Lua 语法版本、资源与验证状态；版本文件可按目标单独指定。
3. 运行 ValidateOnly、目标构建与包内检查，确认源码清单映射、代码/数据隔离和版本信息。
4. 完成实机验收，再按实际状态发布；准备上传时解析并校验当前 CF 数字版本 ID。
5. 同步插件说明与本规范中的实施状态；命名或映射规则变化须同步修改配置、文档和相关测试。

本规范及构建支持不自动增加插件的运行时兼容范围，也不改变 Core 与业务插件的数据所有权。
