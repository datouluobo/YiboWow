# Yibo 系列业务插件方向头脑风暴（临时）

> 状态：系列方向仍为临时讨论稿；YiboMail 已另行形成正式产品边界与开发路线图。
>
> 目的：根据 Yibo 与 Altoholic 的功能差异，寻找适合 Yibo 架构的业务插件方向。
>
> YiboMail 正式方案：[产品边界与开发路线图](YiboMail-产品边界与开发路线图.md)。

## 一、总体判断

Altoholic 的核心是“账号资料库”：集中查看角色、背包、银行、邮件、配方、任务、拍卖和物品搜索。

Yibo 的核心是“账号业务工作台”：通过 YiboCore 统一角色目录、服务器范围、账号页面、入口、悬停摘要和设置，再由业务插件处理某一类明确业务。

因此，Yibo 不应重新制作一个包含所有功能的 Altoholic 巨型插件，而应坚持：

> 一个业务插件覆盖一类用户需求，并通过 YiboCore 共享角色、范围、状态和视图能力。

## 二、现有基础需要校正的认识

### 货币不是当前缺口

Yibo 已具备以下货币能力：

- 通过服务器页面切换查看服务器范围的数据；
- 系统货币目录的全量扫描；
- 自定义货币 ID；
- 将物品按货币方式登记、统计和显示；
- 货币页面、入口悬停和角色范围由 YiboCore 统一承载。

因此，货币不应列为“需要从目录制升级为全量扫描”的新方向。后续若继续增强，重点应放在：

- 货币分类和检索体验；
- 服务器合计与账号合计的展示；
- 角色绑定、服务器共享、账号共享的状态标识；
- 周上限、持有上限和数据有效性；
- 自定义物品货币的维护和导入体验。

这些属于 YiboCurrency 的增强，不必新建货币插件。

## 三、最值得考虑的新方向

### 1. YiboVault：背包、银行、公会银行与物品搜索

这是 Altoholic 对 Yibo 最明显的功能领先项，也是最适合优先立项的方向。

#### 用户需求

> 我有什么物品？在哪个角色？哪个服务器？哪个容器？总共有多少？

#### 建议范围

- 所有角色背包；
- 所有角色个人银行；
- 公会银行；
- 装备栏；
- 邮箱中可确认的待取物品；
- 服务器、角色、容器和账号合计；
- 物品名称、ID、品质、类型、装等搜索；
- 物品 Tooltip 显示拥有角色、服务器和容器；
- 材料总量和角色分布；
- 最后扫描时间和数据状态。

#### 明确不做

- 钥匙栏；
- 自动整理背包；
- 自动移动物品；
- 自动邮寄；
- 自动银行存取；
- 拍卖价格和利润计算。

背包、银行、公会银行应作为一套统一的物品资产模型实现，而不是拆成三个互不相通的插件。

#### 与现成插件的关系

BagSync 已经覆盖背包、银行、公会银行、邮件、货币和物品搜索；因此 YiboVault 的价值不应只是重复扫描物品，而应体现为：

- 接入 YiboCore 的服务器切换和角色范围；
- 使用统一账号矩阵和悬停预览；
- 为 YiboTodo、YiboCrafting 等插件提供物品查询 API；
- 统一数据状态、缓存删除和角色清理；
- 面向 MoP Classic 的稳定数据模型。

### 2. YiboMail：多角色邮件工作台

邮件保持为独立业务插件。YiboMail 负责邮箱快照、邮件生命周期和收发辅助；YiboVault 继续负责全账号物品资产查询。邮件附件是可通过接口提供给 Core 和其它子插件的物品来源之一，不应由 Vault 再实现一套邮箱扫描。

#### 用户需求

> 哪个角色收到什么邮件和物品？邮件何时到期？我如何安全地收取、转寄给需要的角色？

#### 阶段一：邮件信息缓存与物品查询接口

- 玩家访问角色邮箱时，缓存邮件发件人、主题、邮件类型、附件物品与数量、金币、剩余时间、退回标记和采集时间；邮件正文默认不保存。
- 主窗口展示已缓存邮件的完整角色列表、邮件明细和附件物品；同一物品可以跨邮件、角色汇总，但必须能展开看到每封来源邮件及其角色和时间。
- 悬停摘要展示有邮件的角色数、邮件数和最近到期时间；临期摘要优先显示有附件或金币的邮件。
- 对外注册只读邮件物品查询接口，返回物品身份、数量、角色、来源邮件、时间和数据状态；供 YiboCore 账号视图及 YiboVault 等插件查询。Core 仍不接管 YiboMail 的业务 SavedVariables。
- 记录每个角色最后扫描时间、可见邮件数与游戏返回的邮件总数；旧快照标为过期/待刷新，不得伪装成实时邮箱。

#### 阶段二：收件辅助

- 在原生邮箱界面提供玩家主动点击的一键收取和收件规则，可按附件、金币、发件类型或来源筛选。
- 提供邮箱附件聚合视图：相同物品合并显示总数，点击后可定位到来源邮件；剩余时间按最早到期来源显示。
- 收取前检查背包空间；显示将处理的邮件数、物品和金币。COD、退回/删除等特殊邮件默认跳过或单独确认，并逐项报告成功、跳过和失败原因。
- 玩家打开邮箱并触发处理后，按受保护操作允许的节奏逐封执行；不做无人值守的后台收取或删除。
- 收件过程中记录附件已收取的原始邮件摘要，使邮件从游戏收件箱移除后仍能在历史视图中查到。

#### 阶段三：发送辅助

- 联系人清单支持账号角色、常用联系人和最近收件人，并能在原生发件界面快速选人。
- 玩家可保存物品/类别到默认收件人的发送规则；装填前显示目标、物品与数量，允许逐次调整。
- 规则仅辅助选人、选物和装填；发送按钮仍由玩家确认，不执行无人确认的批量发件。
- 发件成功后立即建立账号内“在途”记录；目标角色扫描到对应邮件后再标记“已确认收到”。超时或目标邮箱不可访问时显示“待核实”，不推断已退回。
- 保存简明往来记录：发送给谁、收到谁的邮件、物品/金币摘要；AH 发票能返回单一买家时记录买家，否则标为未知，不根据主题或发件人猜测。

#### 全量展示与 100 封边界

- YiboMail 主窗口可以全量展示**已扫描并缓存**的邮件历史，不受原生收件箱当前显示条数影响。
- 当前邮箱 API 暴露的邮件有限；已安装的 Postal 也按最多 100 封可见邮件分批刷新/处理。因此，插件无法在只读扫描时读取尚未暴露的旧邮件。`GetInboxNumItems()` 返回的总数高于可见数时，必须显示“还有 N 封未扫描”及最后扫描时间。
- 被遮蔽的旧邮件要先由玩家在邮箱主动处理可见批次、腾出邮箱位置后，游戏才可能暴露下一批。阶段二可提供带预览、空间检查和逐批进度的“处理下一批”流程，并把已处理邮件归档到阶段一的历史视图。
- 单靠提醒无法阻止角色离线期间邮件到期或服务器退回/删除邮件。临期提醒以最近扫描快照为准，并明确提示快照时间；对未扫描邮件不得声称已保护。

#### 数据边界与状态

- 在途邮件、已扫描邮件和历史归档是不同状态；只有目标角色扫描确认后才记为收到。
- 邮件没有可供子插件长期依赖的稳定跨角色唯一 ID 时，以角色、发件人、主题、时间和附件组成匹配线索，并保留匹配置信度；重复或不确定的记录不得静默合并。
- 悬停和共享查询只返回满足角色准入且有有效邮件快照的角色；显示数据状态与扫描时间。
- 邮件附件查询由 YiboMail 提供，Vault 可将其作为“邮箱”容器并入全账号物品搜索，但仍标明待取状态和最早到期时间；附件被收取后由 YiboMail 发出更新，Vault 再刷新来源状态。

### 3. YiboCrafting：专业、配方、材料与可制造角色

YiboTodo 解决“现在有哪些周期待办”，YiboCrafting 可以解决“哪个角色能制造什么”。两者应保持边界。

#### YiboTodo 继续负责

- 专业冷却；
- 每日、周常和周期活动；
- 农场、诺米、烹饪等业务待办；
- 可执行状态和下一次恢复时间。

#### YiboCrafting 负责

- 角色专业和等级；
- 已知和未知配方；
- 哪个角色能够制作某件物品；
- 配方材料需求；
- 与 YiboVault 联动查询材料库存；
- 按服务器筛选可制造角色。
- 向 YiboBuilds 装备提升面板提供角色专业、已学配方、配方产物和材料需求查询 API；Builds 继续校验当前装备目标并执行原生施加流程。

#### 不做范围

- 拍卖利润；
- 制造成本估算；
- 自动生产；
- 自动采购；
- 完整拍卖行经济系统。

### 4. YiboLockouts：副本、周常与锁定进度

YiboAltoBoss 负责世界 Boss；YiboLockouts 可以负责副本和周常锁定，避免重复实现。

#### 用户需求

> 这个角色本周还剩哪些副本、Boss 或周常没有完成？

#### 建议范围

- 副本锁定；
- Boss 击杀状态；
- 每周次数；
- 团队副本、地下城和场景战役分类；
- 角色和服务器筛选；
- 账号级未完成列表；
- 与 YiboTodo 联动生成待办。

#### 与 YiboAltoBoss 的边界

- YiboAltoBoss：世界 Boss、特殊区域 Boss、Warbringer 观察；
- YiboLockouts：副本、团队副本、周常锁定和可重复次数。

### 5. YiboAchievements：账号进度与收藏目标

该方向适合在资料库基础稳定后考虑，不建议作为第一批开发。

第一阶段可以只覆盖：

- 成就完成角色；
- 哪个角色最接近成就目标；
- 成就关联的声望、Boss 和任务；
- 坐骑目标和来源；
- 自定义收藏目标。

不建议第一版同时覆盖坐骑、宠物、玩具、幻化、头衔和全部收藏系统，否则会迅速变成新的巨型插件。

## 四、不建议优先做的方向

### 通用拍卖行插件

TradeSkillMaster、Auctionator 等插件已经覆盖拍卖、制造、材料、邮寄和经济分析。Yibo 如果进入该领域，开发量和维护成本会显著扩大，也会偏离“账号业务工作台”的定位。

### 完整背包管理器

YiboVault 可以查看和搜索物品，但不建议承担背包整理、自动移动、自动售卖、自动邮寄和自动银行存取。

### 将所有功能继续堆入 YiboTodo

以下需求应保持独立：

| 用户问题 | 对应插件 |
|---|---|
| 我有什么物品、在哪个容器 | YiboVault |
| 哪个角色有邮件 | YiboMail |
| 哪个角色能制作某物品 | YiboCrafting |
| 本周还剩哪些副本 | YiboLockouts |
| 今天该做什么 | YiboTodo |
| 货币有多少、上限多少 | YiboCurrency |

## 五、建议开发顺序

| 顺序 | 方向 | 价值 | 难度 | 建议 |
|---:|---|---:|---:|---|
| 1 | YiboVault | 极高 | 高 | 首要立项 |
| 2 | YiboMail | 高 | 中高 | 独立插件，按“缓存与接口 → 收件辅助 → 发送辅助”三阶段交付 |
| 3 | YiboCrafting | 高 | 高 | 先明确与 YiboTodo 的边界 |
| 4 | YiboLockouts | 高 | 中高 | 与 YiboAltoBoss 分工开发 |
| 5 | YiboAchievements | 中 | 高 | 等资料库基础稳定后开发 |
| 6 | YiboCurrency 增强 | 中 | 中 | 属于现有插件迭代，不新建插件 |
| 7 | YiboAuction | 中 | 很高 | 暂不建议 |

## 六、推荐的目标结构

```text
YiboCore
├── YiboCurrency       货币、服务器切换与货币统计
├── YiboVault          背包、银行、公会银行与物品搜索
├── YiboMail           邮件缓存、物品接口、收件与发送辅助
├── YiboCrafting       专业、配方、材料与可制造角色
├── YiboTodo           周期待办与专业冷却
├── YiboLockouts       副本、周常与锁定进度
├── YiboReputation     声望
├── YiboBuilds         装备、天赋、雕文与构筑
├── YiboLegendary      传说任务线
├── YiboAltoBoss       世界 Boss
└── YiboQuestBlocker   任务拦截
```

## 七、暂定结论

最应该立项的是 YiboVault，但它的目标不是复制 BagSync 的全部功能，而是建立 Yibo 的账号物品基础设施：

1. 统一记录角色、服务器、容器和物品数量；
2. 为其它 Yibo 业务插件提供物品查询 API；
3. 复用 YiboCore 的服务器范围、角色筛选、排序、缓存和页面框架；
4. 用统一数据状态表达“已扫描、未扫描、过期和不完整”；
5. 将背包、银行、公会银行和物品搜索作为一个完整需求交付。

Yibo 的长期差异化不应是“也能查看背包”，而应是：

> 物品资料库负责回答“有什么”，业务插件负责回答“应该用哪个角色做什么”。
