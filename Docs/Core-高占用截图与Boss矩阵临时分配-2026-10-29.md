## 用户实机证据

截图为AltoBoss2.8.4的Boss行／角色列主页面，内存面板显示Core约192.7 MB。用户明确确认已更新并reload；随后提供同次场景回收后的Core值：主窗口打开 **12.4 MB**、关闭 **12.2 MB**，相差约0.2 MB。

这说明截图中的192.7 MB不能视为主窗口持有的同等规模常驻数据，主要差额在回收后释放。该组数据不能证明CPU没有问题，也不能证明所有会话均无泄漏。前几轮切页次数优化没有直接量化这个页面的分配速度，本轮改按真实业务调用链定位。

只读核对当前Mists客户端的Core和AltoBoss安装目录，均为指向当前仓库的目录联接；没有更改联接、客户端文件或WTF。仅查看Core存档文件元数据，没有执行或改写实际存档内容。用户上述实测属于本轮AltoBoss修复前字节，不能当作修复后验收。

## 根因和修复范围

`YiboAltoBoss/AccountPage.lua`的SetStatus包装器，在每个角色×Boss单元格的目标绑定阶段调用：

```lua
for _, entry in ipairs(YAB.TargetCatalog:Query().targets) do
    if entry.bossKey == boss.key then definition = entry; break end
end
```

Query通过Core.Defaults:Copy返回完整隔离目录。目录包含所有副本、难度、首领及别名，不只是当前Boss；一次矩阵渲染因此按单元格数重复深复制全目录。分配经过Core提供的通用复制函数，排行榜归属不能替代对业务调用链的定位。

现目录所有者在Build完成排序后生成按bossKey的索引，单元格用内部GetByBossKey读取一个定义。相同bossKey继续采用原排序结果中第一个条目；Invalidate同时清理索引，客户端目录重建、名称变化或移除后不保留旧结果。该索引复用所有者已有定义，不复制业务数据库。

对外Query仍返回完整隔离副本；跨插件服务继续经过Core.Contracts，GoalTargets绑定及Core.BusinessItemActions调用保持。没有修改Core复制函数或隔离契约，没有新增强制GC、修改GC参数、清理业务存档或限制玩家数据量。

生产仅改AltoBoss的 `AccountPage.lua`、`Common/TargetCatalog.lua`。本轮未再修改Core生产代码。
