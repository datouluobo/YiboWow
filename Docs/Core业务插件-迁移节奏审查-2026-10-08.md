## 已确认的实施节奏

保留“先 Core、后业务”和触及即迁移。每次后续业务修改收尾时按实际 diff 核对对应能力的接入情况，并通过台账持续观察规则执行效果；未触及的旧实现作为后续迁移库存。

用户计划在无限服开服后对所有插件进行大幅更新，集中追赶随各插件对应更新一起实施。每个插件开始更新时固定当时已实现且满足验证要求的 Core 能力基线，覆盖该插件全部适用调用；当前 api9／api10 合并增量及当时其它可用能力均须分别审查。开服日期与客户端差异尚未确定，按实际更新任务启动。

实施单位分两种：普通显示、输入、设置和语言适配按单个插件验收；跨业务 Service 按提供方与消费方的一条链验收。业务数据与策略仍由业务所有者负责；Core 尚未实现的规划保留为观察项，待实际提供后接入。双语方案继续按既有阶段准备 Core 服务与检查工具，业务收尾结合实际大幅更新安排。

Core 本身也应控制接入成本：API 数字用于标记契约代际，能力版本用于判断某一功能是否可用；保持新增可选字段和旧调用兼容。当前 v10 首次提示已有明确的强版本要求，本轮按现契约登记；今后类似可选显示增强，应在 Core 契约设计时评估是否能由 Core 内部兼容并自动提供，而不是每次让整插件抬高最低 Core 版本。业务代码不能自行绕过已明确的版本要求。

## 当前证据

本轮以 main 工作树、根目录 TOC 加载源码、初始化检查、能力注册和迁移台账为依据，排除第三方 Libs、历史包、探针和测试夹具。覆盖 13 个现有业务插件及 YiboTaskHub 项目基础；没有游戏内采样、英文客户端回归或发布渠道核查。

| 事实 | 依据与影响 |
| --- | --- |
| API 增长明显，但主要是增量扩展 | HEAD Core 1.7.1 / API v8；工作树 1.9.0 / v10。v7 输入／物品、v8 名称／批量控件、v9 服务、v10 首次提示均保留旧调用契约。数字差距不直接等于运行故障 |
| 接入存在多处未收尾 | CAP-001 多个插件仍本地组合角色／服务器；CAP-002 多个搜索或业务设置输入仍本地创建。仅 Mail 部分显式调用 FormatName，共享表头内部迁移不能证明业务标签全部完成 |
| 存在应尽早关闭的具体缺口 | Mounts 调用 v6 RegisterSettingsPanel，却声明／检查 v5；已有方法存在检查，所以不能说它必然崩溃。AltoBoss 强依赖 Core，却保留独立设置壳回退 |
| 服务链已向前推进 | Mail 注册 mail.items，Vault 消费并注册 vault.items，Currency 消费。三者工作树最低 v9；Currency TOC 仍 OptionalDeps: YiboVault，需要核实并收拢加载顺序依赖 |
| UI 版本门槛已经提高 | Builds、Reputation、Todo 检查 v10 / account-view:2 并注册 firstUseTip，但名称／输入或其它历史接入仍未收尾。声明 v10 不表示“已完成 v10 全部迁移” |
| 台账与实现脱节 | 原台账总表还写 v8 和 CAP-005 待实现，能力索引误称全部为版本 1；旧 API 总览仍将 Mail 记阶段 0，并要求直接调用业务提供方。已在本轮文档中修正 |
| 验证维护开始落后 | CharacterNamesSpec:26 将 v10 当未来版本拒绝，当前源码已接受 v10，测试失败。首次提示只有静态证据，尚不能作为完成验收的基线 |

仅“遇到对应代码再迁移”没有主动关闭剩余范围的期限；对长期少改的插件，输入、名称和设置壳会一直留下两套维护路径。逐插件收尾能减少这种技术债，也能把中文／英文布局、主视图／预览和旧 Core 停止行为放在同一次完整验收中。

## 后续 Core 演进分别怎么处理

| 方向 | 当前状态 | 是否值得推动逐插件集中收尾 |
| --- | --- | --- |
| 名称、基础输入、物品控件 | 已实现，剩余范围已登记 | 是，按插件实际需要一次覆盖对应显示／控件；名称仅替换显示，身份键、地址与业务校验保留 |
| 双语化 | 已确认方案，公共语言运行时和检查工具待实施 | 影响页面、设置、状态、Tooltip、错误和静态目录。继续按既有阶段准备 Core 服务与工具，日常按触及区域迁移，结合各插件大幅更新安排适用语言范围与集中收尾 |
| 内置 LDB／信息条 | 方案待实施 | 主要是 Core 阶段。方案明确保留 RegisterBusinessEntry、defaultMode、legacyIDs 兼容；已注册业务入口原则上直接受益，仅不兼容或自行维护入口的调用需要改 |
| 最小 Service／完整 Provider | 单一 Service 已实现；完整 Provider／List 待实施 | 对真实协作链集中接入，不强迫无业务协作的插件注册服务；行动中心依赖的能力需先完成契约与所有权验证 |
| 网络通讯协议 | 当前业务运行 Lua 未找到 addon-message 发送／接收／前缀注册，尚无明确契约 | 不作为本次追赶目标。Core.Events／Contracts 是本机连接；若用户所指是跨插件本机协议，则属于上一行，若是跨玩家同步，另立真实需求与契约 |

不能把所有规划捆绑成一个“Core 最终版本”后才开始业务迁移；也不能为暂未实现的能力提前复制一套本地回退。新能力落地后，先判断已有插件是否自动获得行为、是否真正需要改调用，再安排下一轮。

## 大幅更新时的实施与验收参考

### 开始更新前：固定并验证 Core 基线

1. 修正名称测试的版本断言并重跑相关名称契约、旧调用兼容验证。
2. 补 v10 首次提示的成功记录、只显示一次、预览不触发、缺少 Tooltip／数据库、关闭计时验证；验证 Builds／Reputation／Todo 的旧 Core 升级提示与停止。
3. 单独关闭 Mounts 的 v6 门槛／可选加载定位，AltoBoss 的设置壳遗留，以及 Currency 的业务 OptionalDeps 审查项。
4. 完成当前 v9 Mail→Vault→Currency 服务链游戏内验收：提供方可用、缺失、晚注册、注销、不兼容；扫描未就绪、error、partial、关闭邮箱后的 stale 保真。

上述事项作为大幅更新开始时的基线核对清单；日常修改仍按实际触及范围执行。运行／测试修改按对应实施任务推进，当前仅登记问题。

### 对应插件大幅更新：集中收尾

无限服开服后的插件更新按实际客户端适配、正在开发的页面与真实协作影响安排。以下分组是依赖与验收参考；具体执行顺序随实际更新任务确定。产品列表／设置导航继续按技术名排序。

| 批次 | 插件 / 链路 | 集中范围与理由 |
| --- | --- | --- |
| 1 | Mail→Vault→Currency | 现有服务链已经涉及，先整体验收。三个插件分别补齐名称、适用输入和语言文本，链路联合验证；不把业务数据库迁入 Core |
| 2 | YiboAltoBoss、YiboQuestBlocker | 都有明确名称与输入缺口；AltoBoss 还需设置壳收口。适合做第一次逐插件完整清单验收 |
| 3 | YiboBuilds、YiboCrafting | 有目标／制作的真实产品计划；当前名称、Crafting 搜索输入与语言一起收尾。新跨业务能力等契约实现后再接，不能以草案 API 作为完成条件 |
| 4 | YiboLegendary、YiboReputation、YiboTodo | 分别核对名称、Reputation 搜索、已有首次提示、主视图与预览；保留业务状态与采集所有权 |
| 独立范围 | YiboAutoOpen、YiboBeastPaths、YiboMounts | 仅迁移可选 Core 托管范围；保持独立基础功能。BeastPaths 的双客户端和已有独立校准界面按专门方案验收，不为一致性强制 Core 依赖 |
| 新插件 | YiboTaskHub | 从第一段实际功能起直接使用当时已验证的适用接口；目前只建立项目基础，没有旧调用可追赶 |

Mail／Vault／Currency 的服务链需要联合验收；涉及 Builds 或 Crafting 时按真实目标／制作需求确定协作范围。各插件日常业务开发继续按触及即迁移执行。

### 每个插件的完成口径

- 开始时记录 Core 基线、实际所需 API／能力版本、适用能力、全部调用路径及明确不适用项；追赶 v1.9.0-api10 必须同时覆盖 api9 与 api10 的适用项，分别登记完成证据；过程中 Core 再新增能力不自动扩大该批范围。
- 把基线内适用的重复实现收拢到公共 API；保留业务策略、动态 WoW 名称、身份键、地址与用户文本。移除源文件仍须遵循仓库删除确认策略。
- 初始化和操作检查真实最低版本，旧 Core 提示升级并停止依赖路径；独立插件缺少 Core 的基础功能继续可用。可选业务提供方缺失仅影响增强。
- 验证完整页面、悬停、设置、角色范围／筛选、短名／完整身份、缓存和保存数据，以及语言相关的中文回归与英文布局。
- 存在服务时覆盖缺失、晚注册、注销、契约不兼容和状态时效。记录自动化与游戏内证据；只有调用完成而验证未完成仍记“部分接入”。
- 更新现有 CAP 条目，并增加插件收尾记录：固定基线、范围、尚余事项和验收证据。按能力台账继续保留，不用“一次追完”掩盖单项缺口。

## 执行与持续观察

AGENTS 保留先 Core、兼容旧调用、按真实能力检查版本、业务数据所有权和可选集成规则，并加入每次业务修改收尾时的 diff 核对。观察按后续实际修改触发，有接入变化或遗漏时更新台账；没有触及相关能力的改动不计规则未执行。

集中追赶随已确认的无限服大幅更新计划执行。语言适配继续遵循已确认双语方案，实际更新时按当时 Core 能力与工具覆盖情况安排本插件适用范围和收尾验证。当前观察结论不能把尚未触及的历史代码当作规则未生效的证据。
