## 1. 目标与归属

将多个业务插件重复实现的局部交互逐步收归 Core，业务插件通过配置和回调调用公共能力。Core 负责控件、通用解析、交互与生命周期；业务插件负责业务准入、目录与规则、风险文案、校验和保存。

业务数据继续保存在各插件的 SavedVariables 中。首轮保持既有存档结构，不要求用户重新添加目录，也不迁移业务数据到 Core。

所有控件接入已有统一设置工作台或账号页面，遵循仓库的布局、入口与设置归属规则。

## 4. 首轮成品需求

### 4.1 基础输入框

由 Core 创建和管理，供物品选择器及后续普通输入场景复用。

- 统一字体、颜色、边框、内边距、尺寸档位与禁用状态。
- 支持提示文字、长度限制与按用途配置输入约束。
- 默认不自动抢焦点，管理获得／失去焦点和隐藏后的焦点清理。
- 支持回车提交、Esc 退出焦点；业务可声明需要恢复原值等行为。
- 区分用户输入和程序赋值，调用方可控制程序赋值是否触发回调。
- 业务校验由调用方提供；物品 ID 的通用格式校验由物品解析服务负责。
- 独立搜索框的延迟搜索、页码重置和浏览状态恢复在后续搜索框项目中细化。

### 4.2 物品解析服务

由 Core 提供可脱离 UI 调用的服务，供选择器和后续命令接入使用。

- 解析正整数物品 ID、物品链接及业务启用的名称输入。
- 名称搜索使用当前背包与调用方提供的已知候选；候选来源、范围和匹配方式显式配置。
- 按物品 ID 去重；同名或多候选时要求用户明确选择，不能静默选择第一项。
- 返回统一物品信息：ID、名称、链接、图标及信息加载状态。
- 区分输入格式合法、物品信息可确认、业务允许保存三个层次。
- 统一异步信息请求、同 ID 请求合并、成功／失败状态及可控重试。
- 未缓存物品展示加载状态；加载失败给出可操作反馈，不能无限等待或重复请求。
- 回调关联当前请求和所属组件；输入改变、页面隐藏或组件解绑后，旧结果不得执行过期操作。
- Core 只维护通用物品信息与请求状态，不写入业务目录或规则。

### 4.3 可配置的物品选择与操作栏

以 Currency 当前的“自定义输入框＋添加按钮＋删除按钮＋拖放区域”为成品基线。Core 统一创建和布局，按业务配置显示以下功能。

| 功能 | Core 职责 | 业务提供 |
| --- | --- | --- |
| 输入框 | 控件与键盘交互，调用解析服务 | 输入方式、提示、用途 |
| 添加按钮 | 解析、提交回调、反馈与操作状态 | 校验、确认文案、保存 |
| 删除按钮 | 提交回调与确认交互 | 可删除范围、风险文案、删除操作 |
| 拖放区域 | 读取物品，展示信息，分派指定操作 | 拖放模式、是否已存在及可删除性 |
| 候选下拉 | 候选显示、明确选择与分页 | 候选数据与匹配要求 |
| 选中预览 | 名称、ID、图标、加载或失败状态 | 业务补充状态 |
| 扩展操作按钮 | 可选显示、调用回调、展示结果 | 文案、可用条件、动作 |

业务插件声明启用的输入方式、按钮、候选来源、拖放模式和动作回调。未启用控件隐藏且不占位。宽度不足时完整控件或语义组换行，不裁切、不依赖横向滚动完成操作。

拖放模式明确支持：

1. 仅选择：填入业务草稿，后续由业务提交。
2. 仅添加：进入添加流程，已有项目反馈由业务决定。
3. 根据是否存在执行添加／删除：使用业务存在性与删除资格检查分派。

读取拖放信息不执行物品移动、邮寄、使用或装备增强。清除鼠标物品的时机应作为组件交互契约明确；无效拖放和解析失败不得误触发业务动作。

### 4.4 Currency 行为

| 操作 | 预期结果 |
| --- | --- |
| 输入后点击添加 | 解析物品，确认客户端信息，经添加确认后加入自定义目录 |
| 输入后点击删除 | 仅对自定义目录项目进入删除确认 |
| 拖入尚未加入目录的物品 | 进入添加确认 |
| 拖入已有自定义物品 | 进入删除确认 |
| 输入或拖入内置目录项目 | 反馈已存在；不进入自定义删除流程 |
| 回车 | 执行添加流程 |
| 添加或删除成功 | 清空输入并刷新相关目录与页面 |
| 操作失败 | 保留输入，展示具体原因 |
| 取消确认 | 不修改目录；输入清理时机在实施时统一明确 |

ID、物品名称、链接、拖放和候选下拉属于公共选择器能力；Currency 的具体默认输入方式和候选来源在实施前完成最后一次规格核对。

Currency 保留 `AddCustomItem`、`RemoveCustomItem` 等业务入口。`ConfirmRemoveCustomItem` 还被主账号页面调用，迁移后必须保持该调用有效，并复用同一确认流程。

删除确认使用明确风险文案；涉及删除的入口布局须遵循统一设置工作台关于 `数据与缓存` 末尾放置破坏性动作的约定。图中的操作能力是行为基线，实际位置以该约定为准，实施时明确布局。

### 4.5 添加当前目标

首轮提供可选扩展操作接口，后续目标插件可以显示“添加当前目标”。该按钮复用操作栏的布局、可用状态和结果反馈。

AltoBoss 当前目标为 NPC，目标读取、GUID 解析、NPC 准入和添加仍由 AltoBoss 的回调完成。物品解析器处理物品身份；目标插件显式传递 NPC 身份，任务插件显式传递任务身份，避免不同类型的数字 ID 混用。

首轮只验证扩展接口，不迁移 AltoBoss。NPC 解析是否进一步成为公共服务，在实际复用需求出现时单独评估。

## 5. API、依赖与发布顺序

### 5.1 首批 Core＋Currency

1. Core 新增公共能力，公共 API 从 v6 升至 v7，并保持 v5／v6 接口兼容。
2. Currency 改为调用公共能力，移除被替代的通用 UI 和解析实现，保留业务校验与存档。
3. Currency 在注册与初始化时要求 API v7；`.toc` 继续声明 `RequiredDeps: YiboCore`。
4. 检查新版 Currency 遇到旧 Core 的初始化路径，给出明确升级提示并安全停止，避免提前访问新接口导致 Lua 错误。
5. 同批发布两个插件，发布说明写明 Currency 所需的最低 Core 发布版本与 API v7。

具体发布版本号在实施时确定。`.toc` 加载依赖与运行时 API 检查同时具备。可按 Core 现有机制声明版本化能力，用于精确能力检查。

### 5.2 后续三个业务插件

AutoOpen、Mail、Vault 逐个迁移、验证与发布，每个接入版本均要求 API v7。

- AutoOpen 将 Core 从可选依赖改为必需依赖；设置与命令共用公共解析服务，确保 `Commands.lua` 调用链同步迁移。
- Mail 替换规则编辑中的物品选择与通用解析，保留收件人、规则和保存校验。
- Vault 替换过滤项的输入与选择交互，保留过滤配置和悬停失效通知。
- 各插件在 `.toc` 和运行时检查中声明必需依赖；完成接入后清理被替代的实现。
- 各业务插件发布顺序根据单项验收结果确定。

## 6. 影响范围与验收

首批预计涉及 Core＋Currency 两个插件、约 5–7 个功能文件；三个业务插件全部接入后，总体约 10–14 个功能文件。以上为估算，测试、文档、版本记录及打包文件另计。

具体文件划分在实施时确定，公共模块按基础输入、解析、选择交互分层组织，避免继续堆入设置工作台渲染函数。

### 6.1 首批验收

- ID、链接、名称、拖放与候选选择按启用配置工作。
- 空输入、非法 ID、无候选、同名多候选、未缓存与加载失败均有明确反馈。
- 添加、重复添加、按 ID 删除、拖放删除、内置项目保护与取消确认符合 Currency 行为表。
- 主账号页面右键删除与设置页删除使用同一业务入口。
- 异步结果不会覆盖新输入、触发重复确认，或在离开页面后保存数据。
- 程序回填不产生非预期提交或刷新循环。
- 业务存档、目录顺序、货币统计与页面通知保持兼容。
- 宽窄窗口、插件页面切换和关闭后的控件生命周期正确。
- 基础输入、解析与操作回调使用有意义的自动化检查；客户端验证拖放、确认框、异步加载和布局。

### 6.2 版本组合

| 组合 | 预期 |
| --- | --- |
| 新 Core＋新 Currency | 使用统一公共功能 |
| 新 Core＋尚未迁移的业务插件 | 保持已有功能正常运行 |
| 旧 Core＋新 Currency／已迁移业务插件 | 明确提示升级要求，安全停止初始化相关功能 |
| 已迁移业务插件缺少 Core | 按必需依赖处理，避免产生运行时接口错误 |

后续接入分别验证 AutoOpen 命令和目录运行、Mail 规则保存、Vault 过滤效果。邮件附件装填和装备增强等实际游戏操作保留原业务执行链路。

## 7. 后续通用重构项目

以下按建议顺序逐项开展。每项实施前确认需求、接入插件和发布范围，首轮完成不代表后续项目已自动进入实施。

### 7.1 独立搜索框

优先级：高。建立在首轮基础输入框上。

已有使用者：Mail 的设置、缓存与收件界面，Vault 仓储页，Crafting 配方页，Reputation 矩阵。

Core 提供提示、清空、焦点、用户输入／程序赋值区分、可选延迟搜索、回车立即搜索和过期回调取消。插件负责搜索字段、匹配规则、范围、保存策略与搜索后的页面动作。

接入时覆盖实际差异：Vault 清空后恢复浏览位置；Crafting 延迟约 150ms 并支持回车立即执行；Mail 搜索变化重置页码；Reputation 保存搜索状态。

### 7.2 列表分页与分页下拉

优先级：高。已有使用者：Mail 多处列表和候选下拉、Vault 公会列表、Core 自身角色设置页。

Core 提供页码边界、上一页／下一页、跳页、结果数量、数据或容量变化后的页码修正、分页下拉。插件负责筛选、排序、每页容量及业务列表绘制。

须区分业务列表分页与 Core 已有账号矩阵角色分页，保留矩阵按自然宽度和屏幕安全边界确定分页的契约。

### 7.3 通用确认框

优先级：高。首轮先服务物品操作，后续完善独立公共接口。

已有使用者：Currency、Mail、AutoOpen、Vault、Builds。Core 提供弹窗创建、确认／取消、独立请求数据和回调生命周期；插件提供风险文案、是否需要确认及具体动作。

需要验证多个插件连续请求、取消、页面切换及当前数据变化时的正确性。涉及实际游戏操作的确认仍由业务保留最终资格检查和执行流程。

### 7.4 筛选工具栏布局

优先级：中。已有使用者：Crafting、Mail、Reputation。

Core 提供搜索与筛选控件的间距、宽度分配和窄窗口换行。插件提供控件、选项和筛选关联。布局以完整语义组为单位，遵循安全屏幕边界，无横向滚动。

### 7.5 空状态与加载状态展示

优先级：中。已有使用者：Crafting、Vault、Mail。

Core 提供状态文案与操作按钮的样式、布局和切换接口；插件判断无数据、无匹配、加载中或失败，并提供引导文案及动作。

### 7.6 进一步评估项目

通用大表格／列表引擎、业务排序、状态判断与重试队列需单独论证。仓库格子、配方列表与账号矩阵的结构差异，以及业务重试的副作用，均应以实际共同契约作为抽取依据。
