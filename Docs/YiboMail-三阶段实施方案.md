# YiboMail 三阶段实施方案

> 状态：2026-10-01，`0.5.0-api1` 已接入原生邮箱增强与 Core 邮箱缓存浏览（邮件列表／附件集中、角色筛选、搜索、分页及来源展开），并按确认设计实施发件、收件、缓存管理三标签设置。发件规则支持 ID、名字、背包及拖放，收件人支持角色／规则地址／同服补全；收件偏好接入原生邮箱。UI 与操作的游戏内验收待完成。Vault 提供者切换与在途唯一匹配送达/退回确认待实施。
>
> 目标客户端：魔兽世界熊猫人之谜经典版，当前 Interface 基线 `50504`。产品技术名 `YiboMail`，依赖 `YiboCore`，正式命令 `/yma`。

## 1. 产品目标与边界

YiboMail 在统一账号视图中展示各角色的邮件、附件、金币、期限和数据更新时间，并在玩家打开邮箱时提供可预览、可停止的收件与发件辅助。邮件快照、状态、规则和历史由 `YiboMailDB` 拥有；`YiboMail.Items` 将待取附件作为只读来源提供给 YiboVault 等消费者。Core 负责角色目录、范围、页面壳、入口、悬停投影、统一设置和角色清理。

三个阶段均交付可查看的信息与可由玩家触发的操作：

| 阶段 | 查看与追踪 | 邮箱内操作 |
|---|---|---|
| 一 | 可信扫描、跨角色邮件页、附件来源、到期与待核实状态 | 当前可见邮箱中跨邮件勾选附件/金币，整批预览确认后依次收取 |
| 二 | 附件聚合、收件归档与队列结果追踪 | 完善收件筛选/恢复；账号角色和手动收藏联系人、基础发件辅助 |
| 三 | 在途、送达确认与简明往来记录 | 物品到收件人的规则推荐、预览与附件装填 |

邮件正文不进入长期存档。邮件发送始终需要玩家对每封邮件明确点击最终发送。客户端未暴露的邮件不展示虚构明细；离线角色的邮件状态和到期提示基于最后扫描估算。

## 2. 可用产品与建设理由

Postal 已覆盖邮箱快速操作与联系人；BagSync 已覆盖跨角色物品搜索；Favorite Contacts 已覆盖常用收件人选择。这些插件的 CurseForge 下载页未列单独购买价格，使用仍取决于玩家的游戏客户端和相应游戏资格。Postal 不提供本方案所需的 Core 多角色邮件生命周期视图和 Vault 来源契约；BagSync 的广泛库存搜索不承担 YiboMail 的收件队列、待核实状态和发件规则；Favorite Contacts 的能力聚焦联系人。YiboMail 的独立价值是把邮件快照、到期、操作结果与 Yibo 系列物品来源连接为同一条可追溯工作流。

参考页：[Postal](https://www.curseforge.com/wow/addons/postal)、[BagSync](https://www.curseforge.com/wow/addons/bagsync)、[Favorite Contacts](https://www.curseforge.com/wow/addons/favorite-contacts)。第三方插件可以并存；邮箱按钮和界面挂载须验证冲突。

## 3. 数据事实与状态

### 3.1 扫描边界

- 只有 `MAIL_SHOW` 或可见邮箱框体提供开放证据时，才采集正式快照。打开瞬间的 `0/0` 可能在同秒 `MAIL_INBOX_UPDATE` 后变成非空；真实 `known-empty` 须等待本次打开后的收件箱更新或经客户端验证的稳定读取边界。关闭后 API 残留可读数据不刷新时间、覆盖状态或 revision；不依赖 `MAIL_CLOSED` 单独判定关闭。
- 每次 `MAIL_INBOX_UPDATE` 后整体重扫当前可见列表。记录 `currentCount`、`totalCount`、`unscannedCount`、`scannedAt` 与 `known`、`known-empty`、`partial` 或不可用状态。`totalCount > currentCount` 时只声明未扫描数量。
- 积压邮箱每次刷新都将**新显现**且成功读取的邮件逐封合入该角色的持久缓存，记录首次及最近可见时间；先前已扫描而当前未显示的邮件保留缓存与待核实状态。`unscannedCount = totalCount - currentCount` 表示本轮未暴露的数量，不等于这些邮件从未进入过本地缓存。只有确实显现并读取后，才为它们建立发件人、附件和期限明细；主窗口须能追溯此前批次的缓存记录及其最后可见时间。
- 邮件记录保留 `characterID`、本地 opaque `mailKey`、发件人、主题、类型、附件及槽位、金币、COD、扫描时剩余天数、退回标记、可读状态与来源时间。物品尽可能保留完整链接身份，同时支持 itemID 汇总。
- 同签名重复邮件逐封保留。匹配歧义时建立新 key，旧候选转为 `unverified`。只读扫描发现邮件消失，不推断收取、删除或退回。
- AH 发票只记录客户端实测可确认的字段；交易方无法确认时为未知。

### 3.2 当前、待核实与历史

Core 主页面分为“当前邮箱”和“历史／待核实”视图。当前邮箱展示最后一次有效扫描中可见的邮件，并标注扫描时间及覆盖范围；历史／待核实展示已确认收取、退回、在途关联和 `unverified` 记录。相同物品汇总可回溯至角色、邮件和附件槽位。

已确认历史默认保留 90 天，在 Core 统一设置工作台的 Mail“数据与缓存”分区调整。`unverified` 默认满 30 天自动清理；清理期限以转入该状态的时间起算，清理时更新查询投影与事件。当前可见邮件不受历史期限清理。

**积压缓存收敛规则：** 当邮箱开放状态持续有效、`currentCount = totalCount <= 100`，且至少间隔 60 秒的两次完整扫描在数量与邮件签名多重集合上稳定后，清理此前积压快照中未再出现在当前完整投影的旧邮件缓存记录。`100/100` 已满足完整覆盖条件，不要求额外减少到 99 封。相同签名的多封邮件若在两次扫描中数量保持稳定，不单独阻止收敛；当前投影仍须逐封保留，无法唯一关联的旧 `mailKey` 不得被指认为某一封现存邮件。此清理只针对旧积压缓存，不触及已确认收取的归档历史；清理事件须带 `reason = "cleanup"`。若计数或签名多重集合变化、扫描失败、邮箱关闭，或无法建立稳定当前投影，则重置观察并保留待核实记录。60 秒是待客户端验证的最低观察窗；若实测延迟更长，应提高窗口并更新验收记录。

上述清理只表示本地缓存整理，不宣称已知邮件的服务器最终去向。Vault 的当前邮件附件来源始终只取最近一次有效可见扫描的投影；旧积压缓存可供 Mail 页面追溯，但不得叠加成当前持有量或直接进入收件队列。

## 4. 阶段一：邮件事实与选择式收件

### 4.1 交付范围

1. 建立可安装插件、`YiboMailDB`、扫描器、匹配与状态迁移、到期估算和必要迁移机制。
2. 经 Core 注册账号邮件页、主入口与悬停预览、统一设置业务分区、角色缓存清理；独立入口按 Core 的“不显示／Broker／小地图／两者”设置提供。主页面和预览复用同一份快照与数值格式化。
3. 主页面以邮件为行，按 Core 角色/服务器范围查看；支持邮件类别、状态、到期时间和物品搜索。附件汇总点击后可定位来源邮件。邮件较多时分页或分组，所有当前有效角色都可访问。
4. 发布契约所列 `YiboMail.Items` v1 能力、查询、状态、revision 与 `MAIL_ITEMS_CHANGED` 事件。返回副本，不暴露私有 DB；相同内容重扫不重复广播。
5. 在打开的邮箱中提供跨多封邮件的附件槽位和金币勾选。仅当前可见、可唯一复核且非 COD 的邮件进入队列；空信不产生收取动作。
6. 确认页逐封列出所选附件、数量、金币、当前角色、预期操作数与风险状态。玩家整批确认一次后顺序执行；每一步执行前重新核对邮件身份、当前索引和所选槽位，成功后等候邮箱更新并重扫，再处理下一项。
7. 内容改变、身份歧义、背包容量不足、API 失败、超时、邮箱关闭或受保护操作限制时立即暂停，保留未执行项与逐项结果。再次开始前重新预览并由玩家确认。已确认收取的来源摘要进入历史。
8. 每轮队列仅覆盖玩家确认时已可见且已勾选的邮件。出现下一批邮件后重新展示、重新勾选并再次确认。

### 4.2 客户端验证门槛

阶段 0 现有样本已覆盖开放/关闭后的 API 残留、空邮箱、基础附件、刷新事件和 AH 发票。进入阶段一编码前，继续用 `_NonRelease/YiboMailStage0Probe` 验证重复邮件、退回、邮件消失、99/100 与 `total > current`、剩余时间、附件槽位和重载后的匹配结果，并将记录状态改为“已验证”。

操作队列在正式接入前另设原型验证：所选附件/金币的目标客户端 API 行为、操作所需玩家交互、邮件索引重排、部分收取后的同封身份、背包容量、刷新等待与失败恢复。任何不允许连续执行的受保护操作，都必须在队列中暂停并请求下一次玩家操作；不得以模拟点击或旧索引绕过限制。未经该门槛验证的操作能力不得标为阶段一已交付。

### 4.3 阶段验收

- 可见邮箱扫描与空邮箱状态准确，重复扫描不重复邮件、不无故提高 revision；关闭后残留 API 不续期快照。
- 同签名邮件不合并，歧义邮件不会被队列误选；超出可见范围的邮件只计数量，不伪造附件。
- 主页面、悬停与公开 API 对同一角色的当前邮件、附件和状态一致；Vault 只消费当前已确认扫描投影。
- 多封邮件的选择、一次确认、逐项核对、暂停和重新预览在目标客户端可复现；COD 不进入队列。
- 所有已执行项、失败项、未执行项可区分；邮件重排后无相邻邮件误取。

## 5. 阶段二：聚合处理与基础发件

### 5.1 交付范围

1. 邮箱内按物品汇总当前可见附件，支持物品搜索、来源邮件跳转、临期排序和收件规则筛选；规则只预选候选，不绕过最终批次预览与确认。
2. 收件队列提供暂停状态、结果报告及重新扫描后的恢复入口。跨 100 封积压邮箱仍逐轮选择和确认，不自动接收未预览的新批次。
3. 联系人仅包含 Core 账号角色与玩家手动收藏，提供去重、编辑和删除；不得把扫描到的发件人或最近发件对象自动加入联系人。
4. 在原生发件界面提供联系人选择、收件人核对和单封邮件装填前预览。玩家最终点击原生发送；发送成功才建立 `in-transit` 记录，失败保留待核实而不写成已送达。
5. 归档展示收件来源摘要和队列操作时间；不保存正文。对外事件在收件状态或附件投影实际变化后发送，供 Vault 刷新。

### 5.2 验收

- 聚合数量与来源邮件逐项可核对；筛选不会使未勾选邮件进入队列。
- 暂停后不重复执行已确认成功的项目；恢复前必须重新扫描、预览和确认剩余选择。
- 联系人只出现账号角色和手动收藏；发件人和附件均可在发送前核对与修改。
- 只有客户端确认发送成功才写入在途；目标角色未扫描到对应邮件前不宣称送达。

## 6. 阶段三：规则装填与往来追踪

### 6.1 交付范围

1. 玩家为具体物品配置目标收件人规则；规则建议收件人、附件和数量，显示邮件格占用。冲突规则需要玩家选择；任何装填前均显示单封预览。
2. 玩家确认装填后，逐个核对背包物品与目标邮件格；允许撤销尚未发送的本次装填。最终发送仍须玩家对每封邮件明确点击。
3. 发送成功记录 `in-transit`；目标角色后续扫描到唯一匹配邮件后转为 `received-confirmed`。明确退回且可匹配时转为 `return-confirmed`；匹配歧义或扫描缺失保持待核实。
4. 简明往来记录包含方向、双方、附件/金币摘要、时间和确认状态。AH 交易方仅采用发票明确给出的姓名。

### 6.2 验收

- 规则装填与最终发送分离；背包变化、邮件格不足和规则冲突都能停止并保留可修改预览。
- 同账号角色的在途、确认收到、明确退回与待核实状态有各自可复现的客户端证据。
- 简明往来记录遵守 90 天已确认历史与 30 天待核实清理策略，不读取或长期保存正文。

## 7. 跨插件契约与交付顺序

`YiboMail.Items` 沿用 [Public API v1 契约](YiboVault-Mail-API-v1-契约.md) 中的 `GetAPIVersion`、能力检查、`Query`、`GetByCharacter`、`GetState`、`GetRevision` 和事件。收件、归档或清理导致来源变化时，先提交 DB 与查询投影，再增加 revision 并通知；消费者收到事件后可立即读到对应状态。API 的当前附件数量只包含最新有效扫描中可见且仍待取的内容，不混入旧积压缓存或已确认历史。

Vault 可选接入 Mail 公共接口；两插件共存时每个角色只选择一份邮件附件来源，Mail 兼容且状态可用时优先使用 Mail，否则回退 Vault 自有精简快照。Mail 本身不依赖 Vault，Core 不保存邮件业务数据。联合集成按 [Core、Vault、Mail 实施计划](YiboCore-Vault-Mail-实施计划.md) 单独验收。

## 8. Core 页面、悬停与设置

- `.toc` 标题使用统一 `|cff20e070[Yibo]|r` 前缀，声明 `## RequiredDeps: YiboCore`；正式 Slash `/yma` 在编码前再次全工作区核对 `SLASH_*` 占用。
- 邮件页由 Core 承载；悬停是同一账号视图的预览列投影，默认覆盖全部有效且有邮件快照的角色（最多 20 名），显示邮件数、最早到期和扫描时间。预览列由 `settings.previewColumns` 保存，并由 Core 统一设置页呈现。
- 主表字段、预览字段、页面与入口显示、角色排序由 Core 统一管理。Mail 设置页只呈现适用的业务规则及数据与缓存；清理动作放在“数据与缓存”末尾并使用明确确认框。
- Mail 的角色删除回调仅删除对应角色快照和历史；账号级联系人与规则按其自身管理入口维护。

## 9. 实施与发布检查

1. 完成阶段 0 探针记录，冻结扫描、身份匹配和操作安全边界。
2. 按“数据模型 → 扫描/匹配 → 公共 API → Core 页面/悬停 → 收件队列 → Vault 可选适配”顺序交付阶段一；每一层使用同一快照与状态判断。
3. 阶段二、三各自先验证目标客户端的发件、装填与状态确认行为，再完成对应代码和游戏内验收。
4. 每阶段核对独立安装、与 Postal 等邮箱插件并存、Core 角色范围、空状态、部分可见、重载、断线重连、缓存清理与事件注销。
5. 发布前同步产品路线图、联合计划、API 契约、插件 README 与测试清单中的阶段范围和实际验证状态；未通过门槛的能力保持草案状态。
