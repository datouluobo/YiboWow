# YiboCurrency - 货币管家

## Register

product

## 产品身份

- 技术名：`YiboCurrency`
- 中文产品名：`货币管家`
- Core 页面名：`货币总览`
- 正式 Slash 命令：`/ycu`
- 核心依赖：`YiboCore`

“货币管家”负责形成独立插件的传播身份；“货币总览”只描述玩家当前打开的功能表面，两者不得混用。

## Users

使用多个《魔兽世界：熊猫人之谜》经典版角色，并希望在游戏内直接比较各角色金币、标准货币、系统虚拟货币和物品代币余额的玩家。

这些玩家可能保留从经典旧世、燃烧的远征、巫妖王之怒、大地的裂变到熊猫人之谜的资源，也可能需要追踪客户端默认货币面板没有展示的历史或特殊货币。

## Product Purpose

在 YiboCore 统一账号框架中提供一份完整、稳定、可比较的多角色货币视图，让玩家不必逐个登录角色、翻找货币面板、专业系统、背包和银行，就能回答：

1. 每个角色分别持有哪些货币，数量是多少？
2. 同一种货币主要集中在哪些角色？
3. 哪些余额接近总上限或周上限？
4. 从当前版本到 60 年代还有哪些历史货币或物品代币？
5. 哪些货币需要长期放在悬停窗口中快速查看？

本插件展示余额事实，不指导玩家如何赚钱，也不分析物品或账号的经济价值。

## Product Promise

1. **直接展示完整目录。** 主窗口不依赖搜索，不先要求用户选择“常用”或“已拥有”。
2. **来源不同，阅读一致。** 金币、标准货币、考古碎片和物品代币进入同一比较模型，但保留来源与数据状态。
3. **没有数据不等于零。** 未扫描、银行未知、接口不可用、不适用和已知为零必须分别表达。
4. **内置目录允许补漏。** 插件维护跨资料片目录，同时允许用户用 itemID 添加遗漏的物品代币。
5. **主窗口与悬停各司其职。** 主窗口显示全部未隐藏项目；悬停只显示用户监控项目且不设人为数量上限。
6. **业务目的允许重叠。** 其它子插件可以为了任务或进度目的再次展示相同货币事实，不建立业务插件之间的依赖。

## Scope

### Included

- 金、银、铜。
- Blizzard 标准 currencyID 货币，包括货币面板当前未列出但可按稳定 ID 读取的货币。
- 考古碎片等独立系统持有的虚拟余额。
- 内置目录中的历史与当前物品代币。
- 用户按 itemID 添加的自定义物品代币。
- 当前余额、周获取量、周上限、总上限和数据状态。
- Core 角色范围、角色排序、统一窗口、设置工作台和可选独立入口。

### Permanently Out of Scope

以下功能与本插件目的不符，后续完善时也不得因为“经济”或“资产”相关而自然扩张进来：

- 收入与支出流水。
- 拍卖行情和价格历史。
- 物品、角色或账号资产估值。
- 金币获取路线、搬砖建议和交易策略。
- 自动购买、兑换、转移或花费货币。
- 邮件、拍卖行、 guild bank 或交易记录管理。
- 普通背包管理和全物品搜索。
- 将普通制造材料、装备、钥匙或一次性任务物品泛化为货币。

如未来确实需要上述能力，应建立职责独立的新插件，而不是扩大 YiboCurrency。

## Information Architecture

主页面使用“货币为行、角色为列”的账号矩阵。

固定资料片顺序：

1. 熊猫人之谜
2. 大地的裂变
3. 巫妖王之怒
4. 燃烧的远征
5. 经典旧世（60 年代）
6. 自定义货币
7. 考古
8. 其它与未归类

每个资料片按“常规货币 / 专业与系统货币 / 物品代币”分组。所有资料片默认展开；顶部资料片按钮只滚动定位，不过滤或搜索。

考古碎片在独立的“考古”分组中按种族汇总，避免按资料片分散。

左侧货币列固定，角色列遵循 Core 顺序并在宽度不足时分页。货币数据区允许纵向滚动，不默认使用横向滚动。

## Display and Monitoring

每项资源具有两个独立偏好：

- `主窗口显示`
- `悬停监控`

主窗口默认显示完整目录，用户可以隐藏单项、分类或资料片。悬停只显示监控资源，数量不设上限；内容超出安全高度时使用纵向滚动。

隐藏主窗口项目不会自动取消监控，取消监控也不会隐藏主窗口项目。两种偏好不得合并为“收藏”或“常用”这一含义不清的单一状态。

## Currency Sources

统一资源键按来源区分：

- `money`
- `currency:<currencyID>`
- `archaeology:<raceKey>`
- `item:<itemID>`

目录条目必须声明稳定键、资料片、分类、来源、数值范围、刷新来源、能否合计及客户端验证状态。客户端临时列表索引、本地化名称和界面折叠状态不得作为存储主键。

## Built-in and Custom Item Tokens

内置目录负责收录已经确认的历史与当前物品代币，但产品不假设内置目录永远不会遗漏。

用户可以添加自定义 itemID。添加时必须读取并展示客户端物品名称和图标、检查重复与合法性，并在确认后纳入与内置资源相同的矩阵和悬停流程。

自定义 itemID 默认归入“自定义货币”，允许指定资料片与分类。用户删除定义只停止其展示和后续采集，不影响其它货币数据。

插件不能通过扫描全部背包物品并猜测用途来自动认定货币；货币身份来自内置目录或用户明确添加。

## Data Ownership

YiboCore 负责：

- 稳定角色目录。
- 中性余额事实、快照状态、更新时间和 revision。
- 账号窗口、范围、角色排序、分页、滚动和入口生命周期。

YiboCurrency 负责：

- 内置资源目录和资料片分类。
- 主窗口显示与悬停监控偏好。
- 自定义 itemID 定义。
- 货币页面、格式化、状态解释和业务设置。

YiboCurrency 不建立第二套角色目录、独立窗口壳、入口位置或角色排序。

## Cross-plugin Policy

中性事实集中存储不等于业务页面只能显示一次。

其它子插件可以为自己的目标再次展示相同货币，并保存与任务生命周期绑定的派生状态。例如 Legendary 可以在相关任务进行期间统计并显示累计勇气；任务完成并交付后停止累计并退出该任务展示。YiboCurrency 则继续长期显示当前勇气余额和上限。

业务子插件不得依赖另一个业务子插件才能完成核心展示；它们只共享 Core 提供的中性事实。

## Brand Personality

完整、可信赖、高密度、克制。它应像一份经过整理的账号货币档案，而不是金融软件、拍卖工具或网页数据大屏。

## Anti-references

- 不做搜索驱动的资源浏览器。
- 不只展示当前角色。
- 不把所有缺失值都显示为零。
- 不把历史货币藏在需要逐层寻找的深菜单里。
- 不因为资源很多而缩小字体、静默截断或默认隐藏旧资料片。
- 不使用夸张财富、交易、股票或金融视觉语言。
- 不以功能完善为理由加入永久排除项。

## Design Principles

1. 先比较同一种货币在不同角色上的差异，再查看单元格详情。
2. 所有目录默认可见，隐藏必须是用户明确选择。
3. 资料片和来源层级承担查找职责，不依赖搜索框。
4. 主窗口负责完整，悬停负责监控；两者复用同一事实和状态判断。
5. 数值、文字和状态图标共同表达结果，颜色只作辅助。
6. 数据来源和可用范围必须可解释，尤其是银行及历史快照。
7. 新增来源必须先进入数据基线，再进入正式目录和 UI。

## Success Criteria

- 玩家无需搜索即可从熊猫人之谜定位到 60 年代任一目录资源。
- 同一货币能稳定比较所有符合范围的角色，不遗漏超过 20 名的角色。
- 标准货币、系统虚拟货币和物品代币在同一页面可辨认但不混淆来源。
- 用户可以隐藏不需要的资源，并能在统一设置中完整恢复。
- 用户可以监控任意数量的资源，悬停不会静默截断。
- 用户可以用 itemID 补充遗漏物品代币，且行为与内置条目一致。
- 银行未知、未扫描、不可用、不适用、零值和真实余额具有不同表达。
- 其它业务插件重复显示同一货币时，不改变 YiboCurrency 的数据与职责边界。

## Change Gate

后续新增需求进入实施前必须回答：

1. 它是否仍然是“可持有并用于兑换、购买或推进系统的余额”？
2. 它是否服务跨角色货币比较，而不是交易、估值或攻略？
3. 它的数据是否能以稳定 ID 和明确来源采集？
4. 它是否可以复用 Core，而不创建第二套角色或窗口体系？
5. 它是否会破坏主窗口完整展示、悬停监控和数据状态语义？

任一答案为否时，应拒绝加入或拆分为新的独立插件。
