# 货币数据归属迁移方案

日期：2026-10-15。状态：**已确认并实施（代码与离线验证完成，客户端待验收）**。版本为Currency0.9.1工作树 / Core1.12.4工作树。本文保留已确认的职责与执行顺序；实际接口、存储字段及验证证据见[实施与验收记录](货币数据归属迁移-实施与验收记录.md)。尚未操作玩家实际SavedVariables。

版本安排：按用户要求，TOC与运行时版本保持Currency0.9.1、Core1.12.4，当前为未发布工作树。实机测试通过后再更新正式版本、提交、推送及打包；不能仅按相同版本号判断兼容，必须同时满足新增能力版本与停采集检查。

## 目标与选定边界

1. Currency 唯一拥有金币、原生货币、上限／周进度、目录和目标判断；新权威快照保存到 YiboCurrencyDB。
2. Vault 拥有通用物品库存和容器覆盖；Currency 经 `vault.items` 读取个人背包、银行、装备，不复制完整库存，不加入邮件、拍卖和公会共享数量。
3. 保留无 Vault 的基础代币功能：Currency 只采集所选代币的随身计数，保存最小业务观察值，不实现银行、装备或完整库存系统。每角色一次读取只选一个来源，禁止以 Core 或本地旧银行数补齐 Vault 的缺失来源。
4. Core 保留角色身份、目录、公共 UI、能力连接、清理协调和历史快照读取；停止货币业务采集。Core 档案需要金币时，改为消费通用业务字段 Provider，不按 Currency 技术名分支。

## 新存储与快照规则

YiboCurrencyDB插件存档version5、业务dataSchemaVersion1；快照使用data子表，以下结构为执行边界示意，完整字段见Store.lua及实施记录：

```lua
characters[coreCharacterID] = {
    native = {
        state = "known", observedAt = 0, revision = 1,
        data = { moneyCopper = 0, moneyState = "known", currencies = { [currencyID] = {
            quantity = 0, maxQuantity = nil,
            weeklyQuantity = nil, maxWeeklyQuantity = nil,
            weeklyResetAt = nil, weeklyState = "unknown", state = "known",
        } } },
        provenance = { kind = "client" },
    },
    carriedTokens = {
        state = "partial", observedAt = 0, revision = 1,
        data = { items = { [itemID] = { carried = 0 } } },
        provenance = { kind = "client-carried" },
    },
}
migration = { version = 1, byCharacter = {} }
```

不保存角色显示名作为键，不将 Vault 返回表原样写入DB。显示缓存只保留当前来源ID、registrationRef、revision与生成时间；来源注销或变化立即失效，下次读按来源策略重建。

`observedAt` 是实际成功采集时间，即使数量不变也更新；`revision` 仅随事实／状态变化增加。保留 balanceState 与 weeklyState 的区别：跨周只使周进度失效，不将未采集的新周值写成0。周重置沿用仓库已使用的客户端重置时间接口，来源缺失或返回异常时标unknown，不写死星期／时区。离线余额作为带时间的历史值呈现，不承诺实时库存；过期或不确定周进度不得令目标变成已完成。

## 公开契约与 Core 档案金币

已核对：Core 有 Contracts Service / Provider / List，但当前 Fields / Resources 必须绑定已注册的 Core domain。不能给 Currency 新建一个假 Core domain 来保存业务数据，也不能让 Core 直接访问 YiboCurrencyDB。

已为真实档案需求实现通用 Provider 契约 **`character-archive.fields` v1.0**（Core1.12.4工作树 / character-archive-providers:1）：

- 提供方 Currency：providerID=`YiboCurrency:archive-currency`，数据所有者Currency。
- 消费方 Core 角色档案：经 Contracts:List 枚举所有兼容提供者，不按插件名适配；按稳定 fieldID 组织字段。首次只交付金币字段 `character.money`，保留现有用户显示选择的ID。
- `GetFields({})` 返回 `{id,title,order,width,formatKind}` 的副本数组；title来自提供方会话语言。首版 formatKind 只采用已有金币显示格式，不建立通用业务规则引擎。
- `Read({characterIDs={...},fieldIDs={...}})` 批量返回 `{sourceID,revision,generatedAt,characters={[id]={fields={[fieldID]={value,state,observedAt}}}}}`；金币 value 单位铜币，缺失值为nil，state区分known／stale／unknown／unavailable。
- 就绪：注册表示可查询，不表示各角色已有快照。缺失／不兼容时只缺金币增强，档案的身份、等级和其它字段可用；晚注册和注销更新字段及显示。冲突字段ID应明确报错并隔离冲突，不由最后加载者覆盖。
- 通知沿用 BUSINESS_CONTRACT_REGISTERED / UNREGISTERED / CHANGED，Payload按现有Core契约；Currency更新时调用 Contracts:NotifyChanged，Core合并刷新，读取不回发通知。
- Core1.12.4工作树已正式登记character-archive-providers:1和character-cleanup:2，Currency检查能力与实际方法；契约见Core/Docs/API-v13-档案业务字段与清理所有者.md。本轮新增的account-dynamic-fields仅处理页面选择，不能替代外部业务数据读取。

其它业务未来首次需要货币查询时再明确独立 Service，本阶段不预建无消费者的查询目录或空接口。

## 代币来源选择

| 情况 | 选择与显示 |
| --- | --- |
| Vault缺失、禁用、未注册或契约不兼容 | 使用Currency随身代币观察，显示partial／`~`；无当前或离线观察时unknown |
| Vault有兼容服务，但该角色无个人来源快照或查询失败 | 暂用Currency随身观察，保留其来源和时间，不补银行 |
| Vault有该角色可用个人来源快照 | 整个代币读模型选择Vault；背包／银行／装备缺项保持未知，使用已确认来源总量，不拼接Currency或Core旧值 |
| Vault注销或来源失效 | 清空相关派生缓存，重新按上述顺序读取；不回写Vault、不保存其第二份权威数据 |

由Currency负责“这些已确认来源如何构成代币余额”，由Vault负责库存事实与覆盖。来源标签、覆盖、时间在主表、悬停、提示和目标视图中一致。当前物品目标仍归Vault，不将随身代币部分观察用于证明完整库存目标。

## 旧数据导入与执行顺序

**阶段A：先完成Core最小通用能力。** 实现并测试档案业务字段Provider消费，保留其它档案字段行为；契约和最低能力写入API文档与台账。复用现有 CharacterCleanup:RegisterOwner / IsLegacyImportBlocked / RetryPending，核对离线未加载所有者的清理记录保留；如现有100条历史裁剪不足，只扩展通用所有者登记／清理留存机制，不在Core增加Currency技术名分支。

**阶段B：Currency本地所有权与导入。** 新增 Store.lua、Scanner.lua、Migration.lua，Data.lua／Projection.lua／GoalTargets改读自有快照或经Core发现的Vault能力。使用已存在的 Characters:GetAll({identityOnly=true}) 枚举目录，DataDomains:Get(id,"economy") / Get(id,"economy-items") 只读旧快照；不直接读取Core SavedVariables。

- 逐角色暂存、校验、提交后才写迁移完成标记；单角色失败保留原因并可重试，不阻止其它角色导入。
- native.money 和 currencies复制入Currency。旧updatedAt保留为来源时间，不能改成“刚刚采集”；该值可能是最后变更时间，因此导入值标记legacy历史，周进度先unknown，登录后重采确认。
- economy-items只导入可靠carried，旧bank/total不作为新库存权威。原快照由Core保留，不删除；无carried但只有total时保持unknown。
- Currency已有本地成功采集值优先；重复导入不覆盖新值。缺失／error／不支持的旧数据不转成0。
- 角色身份沿用Core唯一ID、别名与CHARACTER_ID_CHANGED；处理晚加载错过通知，禁止以同名重绑两个GUID。迁移前检查Core清理墓碑，避免恢复用户已删除缓存。
- 注册CharacterCleanup owner，由Currency实现Inspect／Delete；确认框说明影响native和carriedTokens，不清除目录、偏好、Vault数据或其它角色。清理失败可重试，禁用后重启仍处理pending，不能重新导入旧Core快照使删除复活。

**阶段C：配套切换与停止Core采集。** Currency采集、查询、档案Provider与回归通过后，再在同一配套版本取消Core TOC中Economy.lua、EconomyItems.lua、Resources/Economy.lua和Runtime/CurrencyCatalog.lua的运行加载；撤下静态character.money字段，改由通用Provider提供。Core仍保留其它业务所需通用事件机制；移除专用货币监听前全仓核对真正消费者，不能误删业务事件传递。旧profile.money／profile.currencies和domains保持冻结，停止新投影，不双写。

阶段C开始前再全仓搜索 economy / economy-items / CurrencyCatalog / profile.money / profile.currencies，固定实际消费者清单；本次已确认主要消费者为Currency及Core角色档案。发现新消费者时先迁移其公开读取路径，再停对应采集器。原Lua文件可保留停用说明；物理删除文件和用户存档清理不属于迁移默认动作，需另列精确路径并确认。

## 验证与回退

- 合成存档覆盖首次／重复／失败重试导入、旧字段缺失、确认零、跨周、缺重置API、角色ID晋升与冲突；确保源Core快照未改、新值优先、删除不复活。
- Vault正常／缺失／晚注册／注销／不兼容／异常／部分覆盖、每角色切换来源一致性；主表、悬停和来源明细总量一致，查询不触发扫描或循环通知。
- 档案Provider枚举、字段冲突、缺失与恢复；Currency被禁用时Core基础档案仍可用，金币不会静默显示旧值为实时值。
- 中英文、手动语言、离线角色、银行和装备变化、账户总量及目标的一致性，最后进行真实客户端验收。
- 发布前保留已验证配套Core/Currency包和正常备份。回退需恢复配套版本；新Currency数据保留，不反向双写Core，不自动将新旧快照合并。冻结旧Core记录只保证历史数据仍在，不保证旧插件能读取迁移后的实时值。

完成标准：新余额只由Currency采集保存；库存只经单一选定来源消费；Core无货币采集业务和Currency技术名分支；旧数据可追溯、可重试、不会被误清理；上述离线与客户端矩阵通过后，台账才可记为验收完成。
