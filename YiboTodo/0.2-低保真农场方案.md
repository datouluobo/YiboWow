# YiboTodo 0.2：农场操作低保真方案

## 1. 决策与边界

本方案是完整农场状态方案的受控降级，而不是替代品。阶段 0 已验证：当前 5.5.4 客户端没有可枚举的农场状态 API、等价全局任务信号或跨状态稳定的 16 地块槽位。只有在完整方案保持不可用时，才可实施本方案。

它只回答：**“本服务器日内，是否已观察到该角色进行过任一已验证的农场操作？”**

它绝不回答或推断：

- 是否已经收菜、全部处理完毕或完成任一每日目标；
- 可收获、可播种、成长、异常、未解锁或未知的地块数量；
- `生长 16/16`、`收获 N`、`播种 N`；
- 背包、种子、订单、收益、利润或任何自动化操作。

## 2. 可信度模型

完整地块状态仍不可得；但 v0.2.0 按用户明确选择采用“单次操作代表整轮流程”的乐观投影：

|条件|统一状态|玩家文字|待办统计|
|---|---|---|---|
|当前服务器日观察到收获|`completed`（乐观投影）|`已收菜`|不计入|
|当前服务器日观察到开垦或播种|`completed`（乐观投影）|`已种菜`|不计入|
|当前服务器日目视到“生长中的”作物|`completed`（乐观投影）|`已收菜并种菜`|不计入|
|前一服务器日观察到开垦或播种、今日尚无操作|`actionable`（乐观投影）|`可收菜`|不计入|
|无可投影记录、Provider 不可用、位置不符或规则未验证|`unknown`|`农场操作未确认：<原因>`|不计入|

这里的 `completed` 与 `actionable` 仅用于用户选择的乐观显示，绝不表示插件发现了完整地块状态；不使用数量、`16/16`、背包或订单事实。

v0.2.0 的“农场操作”作为页面第二个独立列默认显示，但只采用 `display` 语义，不能设为 `required`；用户可在设置中隐藏该列。若通用设置模型技术上不能限制该选项，则保存层应拒绝/归一化 `required -> display`。

## 3. 准入与法术规则

每个可记录操作必须满足全部条件：

1. 当前角色触发 `UNIT_SPELLCAST_SUCCEEDED`；
2. 角色处于经实机确认的半山地图范围；当前候选地图 ID 为 `376`，实施前需复验；
3. spell ID、`GetSpellInfo` 原值、事件参数、操作类型和客户端构建均已写入 `MoP每日经济活动基线.md`；
4. v0.2.0 中规则明确标记 `user-observed`，且通过目录校验；它们仅可写入低保真操作事实，不代表完整农场状态；
5. 事件发生时间属于当前 07:00 server-day。

低保真规则集应由多个经实机观察的法术组成，按**并集**聚合：收获、开垦、播种、除草、除虫或其它合法农场操作中的任一条 `user-observed` 规则命中，即设置 `operationObserved=true`。不设“操作次数达到 N 次即完成”的阈值；多种操作或多次操作只增加诊断事实，不提高状态等级。

任何法术事件都不依赖当时目标的 GUID、名称或实体条目作业务键：对象会在状态转换后被替换，且没有稳定地块槽位。

## 4. Provider 与数据模型

Provider ID 为 `farm-operation-observation`，与将来可能恢复的 `farm-observation` 独立，不能复用或伪装为后者。

仅保存角色级、原子提交的观察事实：

```lua
providers["farm-operation-observation"] = {
  providerVersion = 1,
  rulesetID = "mop-classic-50504",
  catalogVersion = <number>,
  state = "available" | "unavailable" | "unknown",
  reason = <string>,
  lastAttemptAt = <unix>,
  lastSuccessAt = <unix>,
  revision = <number>,
  days = {
    [serverDay] = {
      observedAt = <unix>,
      nextResetAt = <unix>,
      operations = {
        { spellID = <number>, kind = "harvest", at = <unix>, castGUID = <string>, source = "UNIT_SPELLCAST_SUCCEEDED" },
      },
    },
  },
}
```

`serverDay` 必须以 07:00 切分。操作按 `castGUID` 去重；缺少 cast GUID 时以 `spellID + at` 做仅本次会话的短窗口去重。当前日投影只计算 active spell 的并集命中，不计算次数、种类数或覆盖率。只保留当前日和最近 7 个历史日的诊断操作记录；清理只移除该 Provider 的可再生历史，不触及 0.1 冷却或其它 Provider。

事件处理只做以下事情：验证角色、地图和已激活规则；写入操作事实；通知快照失效。它不读取背包、订单、作物、目标对象或其它角色，也不调用任何受保护/自动化 API。

## 5. 快照、页面与悬停

投影为一个独立项目 `mop.farm.operation-observed`，名称固定为“农场操作（低保真）”。

- 没有当前日观察：默认不投影；若用户启用诊断显示，则显示 `未知`。
- 有观察：以 `unknown` 的中性样式显示“已记录操作”标记和文字“农场状态未确认；已观察到操作”，不显示对勾、收获篮、数量或完成色。
- 悬停必须同时显示：低保真说明、已观察到的操作类型集合、最近观察时间、服务器日截止时间、Provider 版本/可用性和“并不代表全部地块已处理”。
- Broker、小地图和主页面只能复用这一快照投影；预览中同样不得出现完成或数量措辞。
- 账号共享行永远不显示该项目；角色待办、行动摘要和 `GetActions` 永远不计入它。

## 6. 设置、诊断与迁移

YiboTodo 业务设置提供“农场低保真操作记录”分区，顺序在完整农场设置之后；只有完整农场项目不可用时才显示启用开关。启用前的确认文案必须说明：它不能判断收菜、播种、生长或 `16/16`。

`/ytd status` 输出：规则版本、当前地图门控、当前 server-day、最近观察、已记录操作数、未验证规则数和不可用原因。`/ytd validate` 校验 spell ID 不重复、操作类型存在、地图范围和验证记录齐全。`/ytd probe` 继续输出所有未知法术，不自动提升它们。

数据库迁移必须保留全部既有 0.1 数据与设置。新 Provider 缺失时视为 `unknown`；旧低保真记录不可升级为完整农场状态。

## 7. 验收与发布门槛

最低验收：

1. 验证每个 active spell 的名称、事件参数、地图门控和 07:00 行为；
2. 同一 cast 重复事件只记一次；任一 active spell 命中后只有一个低保真投影，多次不同操作可记录多条事实但不能升级为完成；
3. 角色重载、离线跨日和 07:00 后均不把旧操作显示为当前日事实；
4. 非半山地图、非玩家单位、未知 spell、未验证 spell 和 Provider 不可用时均不写业务事实；
5. 2/10/20/21 角色下不跨角色复制、不进入账号共享、不增加待做数；
6. 页面、Broker、小地图、悬停和行动摘要均使用同一 `unknown + operationObserved` 语义；
7. 启用/禁用、删除该 Provider 缓存、目录升级和 schema 迁移不影响 0.1 冷却。

任何出现“收菜完成”“全部处理”“收获数量”或 `completed` 的投影均阻断发布。若未来找到全量状态 API 或等价信号，完整 `farm-observation` 以新项目替换本方案；历史低保真操作仅保留为诊断，不参与状态迁移。
