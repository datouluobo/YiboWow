# YiboTodo：暗月马戏团、纳特·帕格与布林顿 4000 实施计划

## 目标

在 YiboTodo 的账号矩阵现有“钓鱼日常”列之后，加入以下三个独立活动列：

1. **纳特·帕格**：角色级；每个角色格直接显示三枚任务鱼图标，三项分别表达可交、进行中、已交或未知状态。
2. **暗月马戏团**：角色级、日历事件窗口；活动开放时直接显示该角色已启用且具备资格的专业任务图标。非开放期不显示图标，只显示“还有 X 天 X 小时”。
3. **布林顿 4000**：账号级每日；每日初始时全部有效角色显示可完成图标。任一角色完成后，完成者显示已完成图标，其余角色显示 `—`。

正式接入前，所有任务、日历和账号锁定行为必须在 MoP Classic 5.5.4 完整实机验收。候选期间只提供 `/ytd` 探针，不进入正式目录、账号快照、设置页或普通矩阵。

## 已确认的业务契约

### 矩阵与设置

- 三项均为独立顶层监控组和独立列，顺序固定为：`钓鱼日常 → 纳特·帕格 → 暗月马戏团 → 布林顿 4000`。
- 每个监控组只由 YiboTodo 的“活动监控”设置控制。父组和子项沿用现有三态父复选框逻辑；所有子项关闭时对应列自动隐藏。
- 纳特·帕格的三个子项对应三条任务鱼；暗月马戏团的子项对应各专业任务；布林顿 4000 保留一个活动开关，除非实机验证证明存在可独立监控的多个子项。
- 正式验证通过后，三组及其已验证子项默认启用；已有用户的显式监控设置优先于目录默认值。
- 角色资格只读取 Core 的专业数据，Todo 不采集或保存第二份角色资格记录。具备 Core 专业资格但尚无当前任务观察的角色，在活动窗口的当前周常周期默认显示可做；角色上线后以任务状态校正。无资格或不适用的角色显示 `—`。
- 布林顿账号记录只保存一次；角色行的不同显示是基于该账号记录和完成角色的投影，不复制多份完成记录。

### 状态与时间

- 每日任务必须区分 `actionable`、`in-progress`、`completed` 与 `unknown`；目标完成但未交付仍是待办。
- 暗月活动窗口以本次客户端从服务器同步的日历事件为唯一时间来源。日历未同步时显示“日历同步中”，不使用公式或历史缓存推定时间。
- 日历日期定义暗月活动窗口：周日 `00:00` 开始，随后首个周六 `23:59` 结束。窗口经过周四周常重置；重置后至周六结束为第二个任务周期，任务默认恢复为可做并在角色上线后由实际任务状态校正。
- 暗月非开放期的倒计时不计入待办数；悬停显示下一次开放的精确服务器时间。
- 布林顿的每日边界、完成信号和账号作用域在实机验收前均保持候选，不以历史资料推断。

实机验收清单：

1. **暗月马戏团**：验证日历同步事件、稳定日历事件识别、实际开启/关闭时刻、下一次开启时间、角色专业资格、任务接取、目标完成、交付、完成标记、登出/重载和关闭后状态。
2. **纳特·帕格**：分别验证三条任务鱼的任务/物品身份、接取或交付条件、每天每条只能交一次、单条交付后其它两条不受影响、交付事件、完成标记与 07:00 后恢复。
3. **布林顿 4000**：验证可操作对象身份、可完成与已完成的原始信号、任一角色完成后的账号锁定、完成者与其它角色显示差异、跨角色登录、重载、登出和 07:00 后重新可完成。

完成条件：三项均有稳定身份、资格、可做/进行/已交状态、作用域和重置结论；任何一个缺失时，保留在候选阶段。

数据约束：

- 纳特三项分别保存当前服务器日的状态；同一角色的任一条记录都不得改写其它两条。
- 暗月日历状态保存本次同步时间和事件窗口；窗口按周日 `00:00` 至周六 `23:59` 计算，周四重置切换到第二个任务周期。窗口外只生成文本倒计时投影，不生成可做图标。
- 布林顿保存 `{ serverDay, state, completedByCharacterID, completedAt, observedAt, nextResetAt }` 一份账号记录；矩阵根据当前行角色生成完成图标或 `—`。
