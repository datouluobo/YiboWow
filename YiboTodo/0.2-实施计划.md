# YiboTodo 0.2 实施计划：MoP 每日经济活动

## 1. 执行原则

- 本计划实施 [0.2 实施方案](0.2-实施方案.md)，不扩大其产品范围。
- `MoP冷却基线.md` 继续只维护 0.1 冷却；新建 `MoP每日经济活动基线.md` 作为 0.2 活动的唯一目录输入。
- 所有任务 ID、农场 API、成长规则、奖励和账号范围先以 5.5.4 实机记录确认，再把候选标为 `active`。
- 每个阶段完成时均运行目录/纯 Lua 冒烟测试；涉及游戏 API 的结论必须有游戏内记录，不能用网上资料代替。
- 不实现农场订单、背包/种子库存、自动操作、具体声望追踪或普通声望日常。

## 2. 任务拆分

### 阶段 0：基线台账与探针

**目标**：取得可发布活动的真实输入，不改正式页面和目录。

1. 新建 `MoP每日经济活动基线.md`，按候选记录稳定 ID、活动组、成员任务 ID、收益、前置、作用域、完成信号、跨 07:00 行为、验证状态与排除理由。
2. 在 `Probe.lua` 增加只读诊断：农场相关 API/事件原值、任务日志状态、`IsQuestFlaggedCompleted` 等完成查询结果和服务器日边界。探针输出不写业务快照。
3. 用农场空地、部分播种、全 16 块生长、成熟待收、部分未解锁五种状态完成实机记录。
4. 记录诺米五个阶段任务及满阶段固定日常的任务 ID、接受/完成/跨日行为；建立“首个未完成阶段”的确认表。
5. 记录半山烹饪六个随机日常的任务 ID 与奖励；验证任意一个完成后其余成员在当天的 API 表现。
6. 验证布林顿候选的账号共享完成信号；若不能可靠证实账号范围，则保持候选且不进入本版。

**退出条件**：每个计划接入项都有稳定身份、直接收益、可解释完成信号和 5.5.4 实机记录；未通过的候选明确标为排除或待验证。

### 阶段 1：通用每日活动模型

**目标**：让任务和农场可以在不影响 0.1 冷却的前提下进入统一快照。

1. 扩展 `ActivityCatalog` 与校验器，支持 `farm-plot`、`daily-quest`、`account-daily`，以及 `first-incomplete-member`、`any-member-completes-group` 两种任务组聚合方式。
2. 增加 `DailyActivityCatalog_MoP.lua`，但初始仅登记经阶段 0 验证的 `active` 项；未验证项留在基线而不写正式 Lua 目录。
3. 扩展 Database schema：保存 Provider 的版本、目录版本、`observedAt`、server-day、完成事实、来源与 revision；迁移必须保留全部 0.1 冷却观察和设置。
4. 抽出通用活动状态评估器：角色活动、账号活动、任务组及 07:00 转换均不进入 `ProfessionCooldown`。
5. 扩展 Snapshot：生成 `dailyProjects`，按 scope 聚合到 `accountActivities`，并保证一个活动组只计一次。
6. 为新 schema、目录校验、迁移幂等、账号不复制到角色、隐藏/仅显示/必做统计写纯 Lua 冒烟测试。

**退出条件**：无活动目录时页面和 0.1 冷却完全保持原行为；有模拟观察时状态、统计和账号聚合正确。

### 阶段 2：农场观察与投影

**目标**：让玩家清楚看到当前应收获、应播种，或是否 `生长 16/16`。

1. 新建 `Providers/FarmObservation.lua`，只在已确认的农场场景/API/事件触发后节流扫描；不得扫描订单、背包或种子。
2. 保存逐地块观察：稳定地块键、已解锁、空地、成长、成熟、未知、观察时间和下一次 07:00 转换时间。
3. 实现单一 `farm-project` 聚合：成熟优先为 `收获 N`；其次空地为 `播种 N`；所有已解锁地块成长为 `生长 G/T`；关键观察缺失为 `unknown`。
4. 实现确认成长地块在下一次 07:00 转成熟待收的状态转换。`生长 16/16` 必须自动变为 `收获 16`；空地与未解锁地块不被转换。
5. 将农场图标加入“每日经济”列，悬停显示成熟/空地/成长/未解锁/未知/最后观察，不为每块地创建单独图标。
6. 做 0、部分、16 块已解锁，空地、成长、成熟、重载、离线跨日和重复事件的游戏内验收。
7. 已证明无法取得稳定地块/状态信号；v0.2.0 按 [0.2-低保真农场方案](0.2-低保真农场方案.md) 实施 `farm-operation-observation`。它作为第二个独立列默认显示，但不得称为收菜完成、不得计入收获/播种数量或待办。

**退出条件**：所有农场状态在页面、Broker 与小地图预览中使用同一快照；不会把未解锁当空地、把旧成长误报为未知，或重复统计地块。

### 阶段 3：任务 Provider 与诺米

**目标**：按任务事实表示诺米阶段，不接管声望业务。

1. 新建 `Providers/DailyQuest.lua`，响应已验证的任务日志、接受、完成和交付事件；仅保存目录任务的事实。
2. 实现诺米 `first-incomplete-member`：按五个永久完成记录定位首个未完成阶段，页面只投影一个当前阶段任务。
3. 当阶段任务当天完成，组显示当天完成；下一阶段在下一个 07:00 后进入待确认/可接状态，只有任务 API 证实后才成为可做。
4. 五阶段完成后，切换到固定日常组；每日完成记录按 07:00 结算。YiboTodo 不读取、保存或显示声望数值。
5. 覆盖五阶段分别完成、当天完成后重载、跨日解锁、五阶段均完成、固定日常完成和任务 API 不可用的测试。

**退出条件**：任何时候最多一个诺米阶段任务进入当天待办；满阶段判断仅来自任务完成事实。

### 阶段 4：半山烹饪日常任务组

**目标**：六个随机任务对玩家表现为一个每日待办。

1. 将六个已验证任务作为同一 `any-member-completes-group` 目录组的成员，且共享角色作用域、每日 07:00 计划和显示策略。
2. 当任意成员出现当天完成事实，整个组为 `completed`；未完成成员不能再生成额外待办或重复计数。
3. 任务尚未被 API 确认可接时，使用 `unknown`/待确认，不凭“今天通常随机一个”虚构 `actionable`。
4. 悬停列出当前可用成员或实际完成成员；主表只保留一个烹饪图标。
5. 分别完成六个成员，验证跨日、多个任务事件、重载、预览投影和设置继承。

**退出条件**：任一成员完成后，主页面、悬停、Broker、小地图和行动摘要都只显示一次“半山烹饪日常已完成”。

### 阶段 5：账号级每日、设置与发布准备

**目标**：完成经基线批准的布林顿等项目，并保证统一工作台与交付质量。

1. 仅为已确认账号共享范围的候选实现 `account-daily`；按稳定账号键和 server-day 保存一次性完成事实。
2. 将每日经济列、悬停预览字段、独立入口交由 Core 设置工作台管理；YiboTodo 业务页只提供活动组/单项模式与数据缓存操作。
3. 完善 `/ytd status`、`/ytd validate` 和探针输出，标明 Provider 可用性、最后观察和未知原因。
4. 运行完整回归：0.1 专业冷却、2/10/20/21 角色、账号/角色作用域、07:00、离线、重载、目录升级、删除单角色缓存和页面/预览一致性。
5. 更新版本号、发布说明、测试清单和已知限制；本次随农场功能一同发布专业 CD 的 `skill-insufficient` 状态：基于 Core 缓存专业等级与各冷却组目录维护的精确门槛判断，图标右下角显示小型禁用标记，并在悬停中显示当前/所需技能等级。发布包不得包含探针输出、临时文档或未验证候选。

**退出条件**：所有 active 项有基线记录；无阻断级回归；账号级活动不重复计数；页面和两个入口的一致性测试通过。

## 3. 建议实施顺序

阶段 0 是唯一前置。阶段 1 完成后，阶段 2（农场）优先交付；阶段 3 和阶段 4 共享任务 Provider，可在同一分支连续完成。阶段 5 最后接入账号级每日，因为它依赖最严格的作用域验证。

每个阶段单独形成可验收提交：先代码和测试，再游戏内记录，最后更新基线与本计划的实施状态。发现 API、成长或任务范围与计划不符时，先修订 `0.2-实施方案.md` 与基线，再改代码。

## 4. 当前开工点

从阶段 0 的农场 API/事件实机探针开始。只有取得农场地块稳定身份和 07:00 成长转换的原始记录后，才创建 `FarmObservation` Provider 与正式农场目录。
