# YiboTodo - 账号待办

## Register

product

## 产品身份

- 技术名：`YiboTodo`
- 中文产品名：`账号待办`
- Core 页面名：`账号待办`
- 正式 Slash 命令：`/ytd`
- 核心依赖：`YiboCore`
- 首个目标客户端：熊猫人之谜经典版 `5.5.4`（Interface `50504`）

正式插件列表标题使用 `|cff20e070[Yibo]|r YiboTodo - 账号待办`。

“账号待办”表示账号各角色需要周期检查和处理的专业与经济项目，不表示通用任务清单。产品可以容纳每日、周常、月度、固定时长冷却和事件窗口，但必须遵守本文的准入规则。

## Users

使用多个《魔兽世界》角色，并通过专业制造、农场、烹饪或其它周期性经济活动维护角色产出的玩家。

这些玩家通常在每天上线时需要快速回答：

1. 哪些角色现在有可制作项目？
2. 哪些角色的项目仍在冷却，最早何时恢复？
3. 每个角色今天还有哪些已启用待办没有处理？
4. 哪些项目属于账号共享，只需要完成一次？
5. 哪些状态已经确认，哪些只是历史记录或预计结果？

## Product Purpose

在 YiboCore 统一账号框架中提供一份高密度、可比较、可配置的周期待办视图，让玩家不用逐个登录角色、打开专业窗口或回忆每日活动，也能选择下一名需要处理的角色。

产品首先帮助玩家作出行动决策，而不是展示尽可能多的任务：

- 当前可做什么；
- 哪些项目已经完成；
- 哪些项目还在等待；
- 下一项何时恢复；
- 数据是否足以支持这个结论。

## Product Promise

1. **先告诉玩家该登录谁。** 账号摘要优先展示可执行项目和未完成待办，而不是先展开完整配方库。
2. **共享冷却只算一次。** 多个配方共用同一冷却时，以公共冷却组聚合，不制造虚假的可制作数量。
3. **账号项目不复制到角色。** 布林顿等账号共享项目只显示和统计一次。
4. **没有数据不等于没有待办。** 未扫描、未确认、未学习、不适用和已完成必须分别表达。
5. **目录可以持续维护。** 项目使用稳定 ID、版本规则和验证状态，能够随游戏版本更新而修正，不依赖本地化名称。
6. **玩家决定什么算必做。** 设置可以按活动类型、资料片、专业、公共冷却组和单项控制待办意义与可见性。
7. **主窗口和悬停结果一致。** 两者复用同一账号快照、状态判断、角色准入和格式化逻辑。

## Scope

### Included Product Areas

产品允许逐版本加入以下类型，但所有具体项目必须先通过数据基线和准入检查。

#### 专业制造冷却

- 熊猫人之谜及后续补充的 1.x–4.x 商业技能冷却；
- 炼金转化、裁缝布料、制皮材料、锻造材料、工程零件、铭文研究、珠宝研究、附魔转化等；
- 固定时长、服务器日重置和由客户端 API 决定的冷却；
- 跨配方公共冷却组；
- 配方已学习、未学习、当前可制作、冷却中及预计恢复状态。

#### MoP 每日经济活动

- 半山农场收获、播种、生长和空地状态；
- 农场工作订单；
- 诺米日常；
- 烹饪日常及铁掌相关奖励；
- 直接提供专业材料、专业货币、配方、技能或专业系统进度的日常。

#### 账号级特殊项目

- 布林顿 4000 每日礼物；
- 后续能够可靠识别、具有明确经济价值且按账号共享完成的周期项目。

#### 周期与事件项目

- 暗月马戏团专业任务；
- 未来验证通过的专业周常；
- 只在特定日历事件期间开放的专业或经济活动；
- 非每日重置的固定多日项目。

### Candidate, Not Promised

以下项目可以进入候选基线，但在验证收益、完成范围和长期价值前不构成产品承诺：

- 纳特·帕格稀有鱼交付及其它钓鱼日常；
- 阡陌客好友食物或礼物；
- 其它资料片的专业日常；
- 新版本增加的账号级经济奖励。

候选项目默认不应作为必做项发布。只有通过 Change Gate 后，才能进入正式目录。

### Permanently Out of Scope

以下内容不因“每天可以做”“能获得金币”或“任务使用了专业能力”而进入本插件：

- 普通阵营声望日常；
- 只以声望为主要目的的专业主题任务；
- 世界 Boss、副本、稀有、拾取和团队锁定；
- 每日地下城、场景战役和战场首胜；
- 宠物对战日常；
- 职业专属训练日常；
- 通用任务清单、任务路线和自动接交任务；
- 材料库存管理、背包搜索和银行管理；
- 拍卖价格、利润估算、制造成本和赚钱建议；
- 自动制造、自动领取、自动完成或代替玩家操作；
- 公会专业查询、订单撮合和跨账号通信；
- 世界 Boss 或周常业务与 YiboAltoBoss 的重复实现。

云端翔龙提供烹饪、钓鱼、考古和急救主题日常，但这些任务主要服务阵营声望。除非数据基线证明其提供值得独立追踪的专业奖励，否则不得因为任务主题与专业有关就收入目录。

后续版本范围与实施顺序见：[版本规划](版本规划.md)；0.1 的工程结构、数据契约和验收门槛见：[实施方案](IMPLEMENTATION.md)。

## Inclusion Policy

一个活动必须同时满足以下基础条件：

1. 有稳定的活动 ID、配方 ID、任务 ID、物品 ID 或其它可验证身份；
2. 有明确的角色级或账号级完成范围；
3. 有可解释的开始、完成、冷却或重置语义；
4. 插件能够可靠采集，或能够诚实显示“未确认”；
5. 适合通过账号视图帮助玩家选择下一步行动。

在此基础上，还必须至少满足一项价值条件：

- 存在真实专业制造冷却；
- 直接奖励专业材料、专业货币、配方、技能或专业系统进度；
- 属于产品明确收录的农场、烹饪或其它经济系统；
- 是具有明确经济奖励的账号共享周期项目。

仅提供普通声望、经验、勇气、金币或通用任务奖励，不足以自动进入目录。

## Activity and Cooldown Catalogs

产品维护两层目录：

- `ActivityCatalog`：描述用户可以配置和处理的周期活动；
- `CooldownCatalog` 与 `CooldownGroupCatalog`：描述配方身份、公共冷却关系和客户端规则。

每项使用稳定 ID，不使用本地化名称作为存储键。项目来源资料片与当前客户端规则必须分开记录：一项 1.x 配方在 5.5.4 中可能仍存在，但其冷却已经取消或改变。

目录必须支持：

- 新项目追加；
- 项目 inactive 而不删除历史身份；
- 公共冷却关系变更；
- 重置方式随客户端规则集修正；
- 验证状态和验证版本；
- 设置继承和目录升级；
- 重复 ID、缺失组和冲突规则校验。

公共冷却组是正式业务实体。多个成员配方只能生成一个可制作、冷却中或最近恢复结果；具体成员可在详情中展示，但不能重复进入账号统计。

## State Model

所有采集来源映射到统一业务状态：

|状态|含义|
|---|---|
|`actionable`|当前可以制作、领取、完成或处理|
|`completed`|本周期已经完成|
|`cooldown`|已确认仍在冷却或生长|
|`estimated`|根据历史绝对时间推定已经恢复或进入下一状态，尚未重新确认|
|`in-progress`|已开始但尚未达到完成条件|
|`locked`|未学习、未解锁或尚不具备资格|
|`unknown`|尚未扫描、无法确认或数据来源不可用|
|`not-applicable`|该活动不适用于这个角色|

状态文字、颜色和图标必须同时表达语义。未知不得显示为零、完成或可执行。

## Account and Character Scope

活动必须声明作用域：

- `character`：每个角色独立完成和重置；
- `account`：整个账号共享完成状态，只统计一次。

角色级项目进入角色行和角色详情。账号级项目进入固定账号摘要，不复制到每个角色，不要求任意指定角色承担重复待办。

未来若出现其它共享范围，必须先扩展统一作用域模型，不得通过复制记录模拟。

## Information Architecture

主页面采用角色为行的稳定摘要表：

|角色|待做|可制作|冷却中|最近恢复|待做项目|
|---|---:|---:|---:|---|---|

- `待做`：被用户设为必做且当前尚未完成的活动数；
- `可制作`：当前可执行的公共冷却组数；
- `冷却中`：仍在等待的公共冷却组数；
- `最近恢复`：被监控项目中最早的恢复时间；
- `待做项目`：按行动优先级显示的简短项目清单。

一次只内联展开一名角色的详情。详情按活动类型、资料片、专业和公共冷却组组织，不通过持续新增主表列容纳新资料片。

账号级项目显示在角色表上方的固定账号摘要中。没有账号级项目时不保留空白区域。

Broker 和小地图预览是同一账号摘要的字段投影，默认展示所有符合准入条件且有业务快照的角色，最多 20 名时优先完整显示。

## Settings

最终设置语义为：

- `必做`：显示并计入待做、可制作、冷却和行动摘要；
- `仅显示`：显示状态，但不计入待办统计；
- `隐藏`：不显示，也不参与统计。

设置层级包括：

1. 活动类型；
2. 资料片；
3. 专业或业务分组；
4. 公共冷却组；
5. 单项活动或配方。

子项默认继承父组。用户只保存必要的覆盖值，不能为整个目录复制一份布尔表。新增项目自动继承所属分组策略，目录升级不得重置用户选择。

`0.1` 可以先提供显示/隐藏；三态设置可以后续完善，但数据结构不得阻止升级为三态继承。

页面显示、独立入口、主表字段、悬停字段和角色排序由 YiboCore 的统一设置工作台管理。业务设置不得创建第二套设置窗口壳。

## Data Ownership

YiboCore 负责：

- 角色目录、角色范围与账号身份；
- 可复用的中性角色或账号事实及其状态、更新时间和 revision；
- 账号窗口、导航、范围切换、排序、分页、滚动和入口生命周期；
- 统一主题、控件和状态语义。

YiboTodo 负责：

- 活动目录、冷却目录、公共冷却组和客户端规则；
- 活动准入和待办业务判断；
- 分组和单项设置；
- 账号摘要、角色详情、字段内容和业务格式化；
- 数据基线、探针和目录维护。

YiboTodo 不建立第二套角色目录、独立窗口壳、Broker、小地图拖拽、入口位置或角色排序。

## Data Freshness and Limitations

WoW 插件无法实时查询所有离线角色。产品必须清楚表达：

- 角色至少需要登录并完成相应扫描，插件才能建立快照；
- 某些专业冷却只有在打开自己的专业窗口后才能完整确认；
- 插件关闭、换电脑或 SavedVariables 未同步期间发生的动作可能无法观察；
- 绝对恢复时间到达后可以显示“预计可用”，但不能伪装成重新扫描确认；
- 查看他人、链接或公会专业窗口不得覆盖当前角色数据；
- 农场等观察型活动若无法确认全部动作，应显示“未确认”或“部分完成”。

产品宁可承认未知，也不得用推测生成确定结论。

## Cross-plugin Policy

- YiboTodo 只负责专业与经济周期待办，不接管 YiboAltoBoss 的 Boss 和锁定业务。
- 其它业务插件可以展示相同的 Core 中性事实，但不得依赖 YiboTodo 才能工作。
- 同一任务若属于另一个插件的核心目标，不因它也有每日或周期属性而重复收入 YiboTodo。
- 业务重叠无法避免时，以“玩家在本页面需要作出的决策”决定是否展示，并复用 Core 中性事实。

## Brand Personality

清晰、克制、可信赖、高密度、行动导向。它应像一份可靠的账号操作清单，而不是任务日志、日历软件或金币分析工具。

## Anti-references

- 不做所有日常和周常的杂项收集器。
- 不只展示当前角色。
- 不把公共冷却拆成多个虚假待办。
- 不把未扫描显示成已完成或可制作。
- 不用横向无限增加专业列承载新资料片。
- 不用搜索框替代稳定分组和目录。
- 不因功能扩展加入拍卖、利润、材料库存或自动化操作。
- 不建立独立入口、窗口壳或角色排序。

## Design Principles

1. 先比较角色待办，再展开具体项目。
2. 当前可行动状态优先于完整历史记录。
3. 摘要字段长期稳定，新增目录项进入详情而不是扩张主表宽度。
4. 状态同时使用文字、图标或形状与颜色，不只依赖红绿。
5. 账号级与角色级项目分开表达，统计范围必须可解释。
6. 主窗口、悬停和设置使用同一目录、快照和格式化逻辑。
7. 每个正式项目先建立数据基线，再进入目录、统计和 UI。

## Success Criteria

- 玩家打开页面后能立即判断下一名应登录的角色。
- 公共冷却不会重复增加可制作或冷却数量。
- 2、10、20 名角色可以稳定比较，超过 20 名不静默截断。
- 主窗口和悬停对角色、项目、状态和数量给出一致结果。
- 账号级项目只显示和统计一次。
- 用户可以按分组或单项决定必做、仅显示或隐藏，并能恢复继承默认值。
- 新增 1.x–4.x 冷却时不需要重做状态模型、数据库或主表结构。
- 日重置、固定时长、月度事件和观察型活动可以使用同一活动框架表达。
- 未扫描、预计状态和已确认状态清楚可辨。
- 任何新增项目都能说明为何符合产品准入标准。

## Change Gate

任何新增活动进入实施前必须回答：

1. 它是否具有明确的专业或经济价值，而不是普通任务价值？
2. 它是否有稳定身份、完成范围和重置语义？
3. 它能否被可靠采集，或诚实地表达未知？
4. 它是否帮助玩家在账号角色之间选择下一步行动？
5. 它是否已经由其它 Yibo 业务插件负责？
6. 它能否通过现有目录、作用域、计划和状态模型表达？
7. 它是否会把 YiboTodo 推向通用任务、拍卖、库存或自动化工具？

第 1–4 项任一答案为否时不得纳入；第 5 或第 7 项为是时应拒绝或拆分；第 6 项为否时必须先更新产品和数据契约，不能添加临时特例。
