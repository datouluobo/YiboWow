# YiboTodo 0.2 实施方案：MoP 每日经济活动

## 1. 版本目标

`0.2` 在现有 MoP 专业冷却之外，提供可比较、可确认的每日经济活动账号视图。首要问题仍是“现在该登录哪个角色处理什么”，而不是做一个完整任务清单。

本版仅收录具有稳定身份、完成信号和专业或经济收益的 MoP 日常活动：农场收获/播种/生长、诺米及半山烹饪日常、以及布林顿等账号级每日。农场工作订单不在本版范围。每一项都必须先经过第 5 节的基线确认；不能可靠判断的项目不进入正式目录，也不伪造成已完成或可做。

## 2. 范围与非范围

### 纳入范围

|活动域|待确认的正式能力|作用域|完成语义|
|---|---|---|---|
|半山农场|已成熟可收、已播种生长、空地可播、未解锁地块；是否全部 16 块地均在生长|角色|按地块计数；收获和播种分别是可执行行动|
|诺米|声望未满阶段的任务状态；声望满后当天日常是否完成|角色|按任务 ID 与“已满/未满”阶段完成；不保存或展示具体声望数值|
|半山烹饪日常|直接奖励烹饪材料、铁掌货币、配方、技能或明确专业进度的日常|角色|按任务 ID 完成|
|账号级特殊每日|布林顿及后续通过准入审核的每日经济奖励|账号|同一账号每天最多计一次|

### 明确不纳入

- 仅奖励普通声望、经验、金币或通用任务奖励的日常；
- 农场工作订单、投料、交付与领取状态；
- 云端翔龙等“专业主题”但主要服务声望的任务，除非基线证明其有独立、持续的专业/经济收益；
- 自动接任务、交任务、收菜、播种、制造或领取礼物；
- 物品库存、作物收益估价、拍卖价格或利润计算；
- 无稳定任务 ID、地块状态或完成信号的候选活动。

## 3. 信息架构与玩家体验

账号页继续以角色为行。现有“专业 CD”列保持不变，新增可由 Core 管理显示/隐藏的“每日经济”列；该列以紧凑行动图标投影角色级活动，按“可处理、进行中/等待、已完成、待确认”排序。图标悬停显示活动名、当前状态、完成条件、有效期和最近确认时间；不得仅靠颜色区分。

农场在此列是一个聚合项目而不是 16 个图标。行内图标优先表达下一步行动：`收获 N`、`播种 N` 或`生长 G/T`；其中 `G` 是确认生长的地块数，`T` 是已解锁地块数。角色已完整解锁时，`生长 16/16` 是明确的无操作、全部生长状态；跨过下一次 07:00 后，它确定转换为 `收获 16`。未完整解锁时显示真实的 `G/T` 并将未解锁数列入悬停。悬停固定给出成熟、空地、生长、未解锁、未知及最后观察时间。

账号级每日固定显示在角色表上方的“账号共享”行，只显示一次，绝不复制进任何角色行或角色待做数。默认预览是正式表格的字段投影：展示相同角色准入、相同账号活动和相同状态。角色数、表头、分页与悬停继续由 YiboCore 的统一框架决定。

活动状态复用现有统一模型，但含义固定如下：

- `actionable`：当前确认可以收获、播种、接取、交付或领取；也包括已确认生长作物跨过其下一次 07:00 后确定转化的待收获状态；
- `in-progress`：作物已开始生长，尚未达到下一操作条件；
- `completed`：本服务器日已确认完成；
- `cooldown`：已确认存在的等待时间；
- `estimated`：已跨过 07:00 或根据上次绝对时间推定，尚未重新确认；
- `locked`：农场、地块或任务前置尚未解锁；
- `unknown`：没有足够可靠信号；不参与“可做”计数。

## 4. 技术设计

### 4.1 活动目录

保留 `ActivityCatalog` 为所有待办的唯一目录，新增 `kind`：`farm-plot`、`daily-quest`、`account-daily`。每个活动必须含有稳定 `id`、`provider`、`scope`、`scheduleKind`、`completionMode`、`groupPath`、`defaultMode`、`active` 与 `verificationStatus`。任务和账号每日使用 `scheduleKind = "daily-07"`；农场使用 `scheduleKind = "observed-continuous"`，因为作物成长不应被伪装成服务器日重置。

任务型活动另建 `DailyActivityCatalog_MoP.lua`，以稳定任务 ID 而不是本地化标题作为键，并记录奖励类型、收益说明、前置条件、角色/账号范围、重复任务关系和验证构建。任务组额外声明聚合方式：诺米五阶段组使用 `first-incomplete-member`，半山烹饪组六项随机日常使用 `any-member-completes-group`。农场目录只保存可配置活动定义；逐地块作物等动态事实由 Provider 观察记录保存，不能写回目录。

目录校验扩展为：活动 ID、任务 ID、账号每日键不得重复；角色/账号作用域与 Provider 必须匹配；每日活动必须声明 07:00 重置策略；`active` 项不得缺少验证状态、完成信号或收益说明。

### 4.2 独立 Provider

|Provider|输入与触发|输出观察|不允许的推断|
|---|---|---|---|
|`farm-observation`|进入/离开半山、打开农场相关界面、可用农场 API 变化；节流后扫描|农场解锁、可用地块、每块作物/成熟/空置/待确认状态、观察时间|未到农场时不得根据昨天数据断言可收或已播种；不得读取或追踪订单|
|`daily-quest`|任务日志刷新、任务接受/完成/交付事件、登录后的已完成任务查询|任务 ID、可接/进行/可交/已完成、最后确认时间|任务未出现在可用 API 中时不得显示为完成；不得以声望数值替代任务信号|
|`account-daily`|已确认的每日完成任务或奖励领取信号|按稳定账号身份与服务器日保存的一次性完成事实|不得把某角色的“未观察到”当作账号未完成|

Provider 只写自己的 `byCharacter[characterID].providers[providerID]` 或 `byAccount[accountKey].providers[providerID]` 观察。每次收集必须先在内存中完成、校验通过后原子提交 revision，并在成功、不可用和未知状态之间保留可解释的原因。`profession-cooldown` 不读取任何任务或农场 API。

### 4.2.1 农场低保真降级（仅最后选择）

若且仅若阶段 0 的 5.5.4 实机探针确认不存在稳定地块身份、可用地块状态 API、可解释任务信号或可靠对象事件，才可采用“本日已发生农场操作”的低保真降级。完整的数据所有权、状态语义、spell 准入、设置、投影、诊断和验收门槛见 [0.2-低保真农场方案](0.2-低保真农场方案.md)。

### 4.3 快照、统计与重置

`Snapshot` 新增 `dailyProjects` 与 `accountActivities` 投影，并按活动作用域分别聚合。农场原始观察保留为每块地的事实，但页面只得到一个 `farm-project` 聚合：若成熟数大于零则为 `actionable`（收获优先）；否则若空地数大于零则为 `actionable`（播种）；否则若全部已解锁地块均确认生长则为 `in-progress`；任一关键地块未确认时为 `unknown`。已确认生长的地块在其后第一个 07:00 确定转为成熟待收；例如 `生长 16/16` 会转为 `收获 16`，无需再次到农场观察。播种只表示存在可播空地，不检查种子库存或替玩家选择作物。不把未解锁地块误计为空地，也不硬编码所有角色都有 16 块地。

其余聚合规则如下：

- 角色级每日只进入所属角色的 `dailyProjects`；
- 同一任务或地块不会因多个观察路径重复计数；
- 账号级活动按 `accountKey + serverDay` 合并，完成事实优先于任何单角色的缺失观察；
- 07:00 后旧的任务 `completed` 变为 `estimated` 或待确认，不能直接翻转成已确认 `actionable`；农场使用已验证的成长规则：已确认生长地块在下一次 07:00 转为成熟待收，空地和未解锁地块保持原状；仅原始观察中已为 `unknown` 的地块继续保持 `unknown`；
- `required` 模式才计入待做；`display` 仅显示；`hidden` 不投影也不统计。

数据库迁移提高 schema 版本，保留 0.1 冷却观察与现有显示偏好。新增 Provider 记录须带 schema、catalog、ruleset、`observedAt`、来源与 revision；移除目录项时标记 inactive，不删除用户覆盖或历史观察。

### 4.4 设置与诊断

遵循 Core 统一设置工作台：页面与入口、主表字段、悬停字段及角色排序继续由 Core 管理；YiboTodo 仅在其业务页提供适用的“业务设置”和“数据与缓存”分区。活动可按活动域、农场/烹饪分组和单项继承 `必做 / 仅显示 / 隐藏`，新目录项继承父级策略。

`/ytd status` 需要按 Provider 报告本次观察时间、服务器日、可用性和已确认/预计/未知数量；`/ytd validate` 输出目录、作用域和任务 ID 冲突。探针仅记录 API 原值和观察，不创建正式活动，也不占用 Broker 或小地图常规交互。

## 5. 先行数据基线与 Change Gate

在编写正式目录或 UI 前，为每个候选活动建立 `MoP每日经济活动基线.md`。每行至少记录：稳定 ID、候选名称、活动域、任务/地块身份、收益、角色或账号作用域、前置/解锁条件、可用 API 与事件、完成信号、07:00 后行为、测试角色、5.5.4 实机结果、验证状态与排除理由。

基线按以下次序执行：

1. 用空白农场、已播种、成长中、成熟待收、已收获及地块未解锁角色，探测农场 API、事件和重载后的状态。对每次观察同时记录总地块、已解锁、成熟、空地、生长和未知数，确认满级农场的 `16/16` 语义。
2. 枚举诺米与半山烹饪候选任务，逐项核对任务 ID、奖励、可重复性、前置和完成 API；无明确专业/经济收益的标为排除。诺米有连续五个声望阶段任务：每阶段一个任务，不是日常但每天最多完成一次；YiboTodo 以五个稳定任务 ID 的完成记录找出当前首个未完成阶段。五项都完成即视为已满，转而追踪固定日常的当天完成情况。该推断只保存任务完成事实，不保存、展示或读取具体声望值。半山烹饪则建立一个含六个随机日常任务 ID 的任务组。
3. 为布林顿候选验证每日边界、账号共享范围和领取完成信号；无法可靠确认账号范围则不发布为账号级项目。
4. 每项只有在身份、收益、范围、完成信号和跨日行为均已确认后，才能从 `candidate` 变为 `active`。

## 6. 实施阶段与验收门槛

### A. 基线与探针

交付候选台账、只读探针、API/事件记录和明确排除清单。退出条件是没有候选直接进入 `active` 目录。

### B. 通用每日基础设施

交付活动目录 schema、每日/账号观察记录、07:00 状态转换、作用域校验、三态设置迁移和纯数据冒烟测试。退出条件是账户活动不会被复制给角色，跨日旧状态不会伪造确认结果。

### C. 农场观察

按已确认基线交付 `farm-observation` 与农场聚合投影。退出条件是 0/已解锁/部分解锁地块，空地/成长/成熟，特别是 `生长 16/16`，在登录、离开区域、重载和跨日后均不重复计数或错误乐观。

### D. 诺米与烹饪日常

交付经审核的 `daily-quest` 目录和采集器。诺米只显示当前首个未完成的阶段任务，或五阶段均完成后的固定日常当天完成情况；阶段由五个任务完成记录推断，不记录具体声望。阶段任务当天完成后，诺米组显示当天已完成；下一个阶段只在下一次 07:00 后进入待确认/可接状态，待任务 API 证实后才标为可做，绝不把多个阶段并列为当天待办。半山烹饪的六个随机日常以单一任务组投影，采用 `completionMode = "any-member-completes-group"`：当天完成任意一个成员，整个“半山烹饪日常”组即显示完成；悬停显示实际完成的成员。退出条件是任务接受、进行、可交、完成、未解锁与不可用均可解释；普通声望任务不被收入目录。

### E. 账号级每日、页面和设置

交付布林顿等已验证账号活动、正式表格/预览投影、统一设置和诊断。退出条件是主窗口、Broker、小地图和 `GetActions` 在同一快照下给出完全一致的活动与数量。

### F. 发布验收

至少覆盖：2、10、20、21 名角色；同账号多角色；服务器 07:00 前后；离线跨日；农场 0/部分/16 块已解锁、空地/成长/成熟、`生长 16/16` 跨日转为 `收获 16`；诺米五阶段任务与已满后的固定日常；半山烹饪六个成员分别完成且任一完成即完成全组；任务未解锁/完成；账号每日由不同角色确认；目录升级；删除单角色缓存；以及无 API、冲突 API 和旧观察降级为 `unknown` 的情形。任何 active 项缺少实机验证、账号级重复计数、预览与页面不一致、越权保存或展示诺米具体声望、或普通声望任务误收录，均阻断 0.2 发布。

## 8. 0.1 文档保留决定

`MoP冷却基线.md` 是 0.1 目录的可维护根文档，继续作为每次 MoP 冷却修正的唯一输入，不能清理。`IMPLEMENTATION.md` 仍保留三类后续版本可复用内容：统一状态/快照/数据库/Core 接入契约、目录与迁移规则、以及跨角色、跨日、预览一致性等回归验收。它的 0.1 专属目录、专业窗口实现细节、阶段记录和发布门槛则已由实现与本方案替代。

因此目前不删除 `IMPLEMENTATION.md`，但将它定位为“0.1 实施与验收记录”；0.2 开工时只引用其通用契约和回归用例，新增实现决策全部写入本文及后续的 0.2 实施记录。待 0.2 发布后，再评估是否把可复用章节拆入独立架构契约文档、把其余内容归档。

## 7. 发布边界

0.2 不承诺一次收完所有 MoP 日常。发布物只包含已通过 Change Gate 的活动；其余候选留在基线中并标注原因。这样可以先稳定交付农场和少量可验证的经济日常，而不以错误待办换取目录数量。
