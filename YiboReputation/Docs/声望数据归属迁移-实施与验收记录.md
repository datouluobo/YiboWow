## 版本与职责

交付版本为 YiboCore 1.12.4 / API13、YiboReputation 1.7.1。沿用 API13 通用能力，没有新增公共数据后端或业务查询服务。

Core 停止 TOC 加载 `Data/Domains/Reputation.lua` 并撤下专用 `UPDATE_FACTION` 生命周期监听。运行时不再创建 ReputationRegistry、RegisterReputationFactions、RegisterReputationFactionIDs、GetReputationFactionMetadata 或 reputation 采集域。原始源文件保留为标注停用的审查参考；不在运行 TOC 中，不执行源文件删除。DomainStore 和其它业务域的实现不变。

Reputation 通过 Store／Scanner／Migration 接管目录、好友度兼容、采集与权威保存。账号矩阵、监控预览、当前角色遗留视图、资格筛选和 action.targets 全部读取 `Addon:GetSnapshot`。Core 旧声望快照仅在 Migration 通过公开 `DataDomains:Get` 导入，展示层没有旧来源回退，采集不写 Core。

初始化除原有能力外检查 `character-identity:1`、`character-cleanup:1`、GetDefinitions、GetAliases、ResolveLegacyKey、Events.FireIsolated 等实际方法。要求 Core 版本至少 1.12.4，并拒绝仍注册 reputation 采集域的 Core。缺失能力或交接未完成时提示升级并停止页面、导入和采集初始化。

## 实际数据与生命周期契约

`YiboReputationDB.dataSchemaVersion=1`；角色记录保存在 `characters[Core characterID]`。记录含 snapshot、lastScanAt、origin、identityAliases、lastError。snapshot 保留 schemaVersion、state、updatedAt、revision、data；首版业务负载继续使用 v5／contractVersion1。settings、nomi、矩阵展开状态与目标 sourceEpoch 保留原位置。

`migrations.coreReputationV1.characters` 保存逐角色 imported／existing／failed 结果、导入时间和来源版本／revision／时间；`blocked` 阻止已删除或已合并旧 ID 再导入；`remapped` 记录已处理的 ID 转换，重复事件不传播阻断或重复刷新。无源数据的角色不会被全局完成标记永久跳过。`identityConflicts` 只保留无法裁定的旧快照证据，不参与正常读取。

导入填充空缺记录或未成功采集且无业务负载的失败占位记录，已有有效新库记录优先。导入标记本身不能代替快照：快照缺失且没有删除阻断时可恢复；已有快照时不覆盖。写新角色记录后才记录导入成功，中断重试不会覆盖已写记录。v1～v4 原样保留版本并标记需重扫；未知版本、结构不合法或错误字段逐角色记录失败；原始 Core 记录保持不变。导入不修改历史动态名称，不把导入时间当作扫描时间。

Scanner 自行监听 PLAYER_LOGIN／PLAYER_ENTERING_WORLD／UPDATE_FACTION，以 0.15 秒合并扫描；失败最多追加 3 次、间隔 1 秒的重试，后续原生事件可以重新触发。Core 就绪后可先初始化存储和 UI，首次采集必须取得当前玩家 GUID；晚加载且已登录时主动安排首次扫描。

成功提交先校验结构并复制负载，只有数据／状态变化才增加 revision 和刷新页面。内容不变时仅更新 lastScanAt；updatedAt 保留最近一次快照变更时间。无 API、异常、空扫描或结构校验失败保留上次负载并标记失败／未就绪，目标不能完成，提示不展开成有效进度。没有声望条目的角色不进入页面／悬停资格范围。

保留稳定 ID 补采、真实主声望 header、目录外发现、普通声望满值与满友谊兼容。friendship ranks 使用 API 返回的 friendship ID；不能解释的好友度等级不会回退成普通 standingID。原有可识别原生关系名称的兼容解释保持。

数据事实事件为 `YIBO_REPUTATION_SNAPSHOT_CHANGED`，由 Core.Events:FireIsolated 分发，payload 为 source、characterID、revision、state、updatedAt、reason。来源 `YiboReputation`，删除时快照字段可缺失；每个监听器得到隔离负载。Store 本地失效矩阵缓存并通知页面和已有 action.targets；不发 DATA_DOMAIN_UPDATED，也不在通知接收端触发反向扫描。

通过 CharacterCleanup:RegisterOwner 提供 Inspect／Delete。先执行 pending 删除再导入；Core 未加载时积累的删除在插件启用后补处理。监听 CHARACTER_ID_CHANGED 迁移快照、导入状态及阻断；晚加载漏过事件时，只通过 Core 的 aliases／ResolveLegacyKey 修复 legacy ID，不把一个 GUID 按同名映射到另一 GUID。冲突优先本地采集、再比较有效性和观察时间；无法区分时保留冲突并要求重扫。

## 恢复与诊断

Core 旧快照冻结保留，无自动清除。恢复旧组合只能看到冻结时点，新声望数据仍保存在 ReputationDB；不提供反向双写或自动降级迁移。Core 与 Reputation 必须配套升级；旧 Reputation 与新 Core 的冻结显示不视为兼容通过。

沿用唯一 `/yrp`，工作区 SLASH 注册已核对；没有新增主命令或旧别名。`status` 查看快照／失败导入计数与当前状态，`scan` 采集当前角色，`migrate` 重试导入。迁移失败不会阻止其它角色导入，现有本地快照不会被重试覆盖。删除操作仍从 Core 统一角色缓存管理执行。

## 2026-10-15 二次复查

按用户指定重点再次审查历史数据保留、重复导入与缓存删除，代码审查与补充回归确认以下遗漏，现已修复：

- 首次扫描失败写入空占位记录后，原先的“记录存在即跳过”会阻断之后的合法历史恢复；现在仅允许无来源、无成功扫描时间、无声望负载且符合已知 v5／contractVersion1 的失败占位被导入替换；未知版本空记录也保持原样。
- imported 标记存在而快照缺失时，原实现永久跳过；现在以实际快照和删除阻断为准，安全恢复缺失快照。用户通过统一缓存删除产生的 blocked 标记仍优先。
- 重复 ID 变更事件会把已合并旧 ID 的 blocked 传给新 ID；新增 remapped 记录，重复事件不改阻断或数据版本。
- 历史导入失败后本地已有有效快照时，旧失败标记会继续显示在 status；重试确认本地记录优先后标为 existing，保留 previousFailure 作为诊断证据。
