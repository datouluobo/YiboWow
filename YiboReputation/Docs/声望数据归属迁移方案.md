# 声望数据从 YiboCore 迁入 YiboReputation 的改造方案

状态：方案已确认；运行代码与离线验证已完成，真实客户端验收待完成。审查与实施日期：2026-10-15。最终接口、版本与证据见[实施与验收记录](声望数据归属迁移-实施与验收记录.md)。

基线：当前工作树 YiboCore 1.12.3 / API13、YiboReputation 1.6.0；此前 API13 接入改动继续保留。本方案以仓库实际实现为依据，实施前重新核对版本与调用处。

## 1. 目标与边界

YiboReputation 成为声望业务数据的唯一权威所有者，负责目录、游戏 API 采集、好友度兼容、快照保存、迁移、时效、失效及目标判断。Core 继续负责角色身份与目录、账号范围、名称格式化、统一页面与入口、设置工作台、公共事件和缓存删除协调。

本次保持账号矩阵、监控预览和已有行动目标的业务表现，优先迁移数据链路。声望规则不放入 Core 的新服务；不为尚无消费者的查询预建 Provider。已有 `action.targets` Provider 继续由 Reputation 注册，行动中心通过 Core 契约调用。

旧 Core 声望快照在切换后仅作为冻结的迁移来源，不能继续采集，也不能作为页面或目标的实时回退。保留旧来源用于恢复不等于继续维护第二份权威数据。

## 2. 已核实的现状

| 位置 | 当前职责 | 改造方向 |
| --- | --- | --- |
| `YiboCore/Data/Domains/Reputation.lua` | 注册 `reputation` 域 v5；监听登录、进世界、声望变化；管理 faction 注册表与好友度 API 兼容 | 采集与目录行为迁入 Reputation；Core 停止加载该业务域 |
| `YiboCore/Runtime/DataDomains.lua` | 通用采集域注册／派发、读取快照 | 保留通用实现；不把 Reputation 的新采集器注册回此域 |
| `YiboCore/Data/DomainStore.lua` | 保存 `schemaVersion/state/updatedAt/revision/data`，拷贝读取，触发 `DATA_DOMAIN_UPDATED` | 其它域不变；旧声望记录只用于一次性读取 |
| `YiboCoreDB.characters.byID[characterID].domains.reputation` | 声望权威快照 | 切换后冻结；成功导入后由 Reputation 新存储接管 |
| `YiboReputation/ReputationCatalog.lua` | 声望目录、显示分类、给 Core 注册 faction IDs／主声望头；调用 Core 元数据查询 | 在本插件建立目录索引与发现表，不再向 Core 注册业务元数据 |
| Reputation 展示／目标模块 | 直接读 `Core.DataDomains:Get(id, "reputation")` | 统一改为插件自身快照读取接口 |
| `YiboCore/Data/CharacterCleanup.lua` | 统一删除协调，支持已加载 owner 与未加载 owner 的延后清理 | Reputation 接入现有 owner 协议；登记未加载时应提示的声望缓存影响 |

直接读取范围已发现：`AccountMatrixView.lua`、`MonitoredPreview.lua`、`CurrentCharacterPreview.lua`、`PreviewController.lua`、`CoreIntegration.lua`、`GoalTargets.lua`。旧视图路径即使当前默认不展示，也需改为同一来源。

仓库搜索未发现其它业务插件通过 Core 声望域读取快照。Legendary 的 `Probe.lua` 直接调用游戏声望 API，是原生能力探测，不依赖该域，保持自身业务采集。现有 `RuntimePerformanceSpec.lua` 含声望悬停复用场景，实施时更新其来源模拟并保留验收意义。

## 3. 推荐结构与数据契约

建议新增 `Store.lua`、`Scanner.lua`、`Migration.lua`；目录索引保留在现有 Catalog 模块。初始化由现有 Bootstrap／CoreIntegration 调度。均为 Reputation 内部模块，不新增跨业务实现对象。

建议存储结构（字段名在实施时固定）：

```lua
YiboReputationDB.dataSchemaVersion = 1
YiboReputationDB.characters[characterID] = {
    snapshot = {
        schemaVersion = 5,
        state = "known",
        updatedAt = legacyUpdatedAt,
        revision = 1,
        data = {
            contractVersion = 1,
            coverage = "registered-and-enumerated",
            factions = {}, statuses = {},
            enumeratedCount = 0, registeredCount = 0,
        },
    },
    lastScanAt = nil,
    origin = { kind = "core-import", importedAt = importTime },
}
YiboReputationDB.migrations.coreReputationV1 = { characters = {} }
```

顶层存储版本与声望快照版本分开。迁移首版保留 v5／contractVersion1 的业务负载，避免同时改变好友度解释。已有 settings、matrixExpanded、nomi、goalSourceEpoch 原位保留。来源 revision 仅存于迁移记录，不与新存储 revision 混算。

角色键必须使用 Core characterID；只通过 Core 公开身份接口关联，不用显示名或短名推断角色。静态 factionID、资料片 ID、分类 ID 保持稳定；角色身份与排序不复制成第二份权威目录。

插件内部最小方法：

| 方法 | 约定 |
| --- | --- |
| `GetSnapshot(characterID)` | 返回防御性拷贝；无数据返回 nil；不临时回读旧 Core 域 |
| `CommitSnapshot(characterID, data, state, context)` | 校验角色和结构；业务数据／状态变化时增加 revision 并失效派生缓存 |
| `ScanCurrent(reason)` | 只采集当前角色；读游戏 API，不读取其它业务插件数据 |
| `ImportLegacySnapshots()` | Core 就绪后通过公开接口读取旧快照；逐角色幂等导入并记录结果 |
| `InspectCharacter`／`DeleteCharacter` | 供现有 CharacterCleanup owner 回调使用；清除本插件角色业务数据并阻止重新导入 |

`updatedAt` 保持原有快照提交时间语义；新增 `lastScanAt` 表示最近一次成功完整扫描，内容不变时也可更新。导入时间不能冒充采集时间，历史快照原文不能因语言切换被改写。

## 4. 初始化、采集与通知

推荐顺序：检查 Core → 注册插件 → 订阅角色身份变化 → 注册 CharacterCleanup owner 并处理待清理记录 → 建立本地目录 → 导入旧快照 → 注册页面／入口及目标 Provider → 安排当前角色扫描。

Core 目前在自身 `ADDON_LOADED` 初始化，之后的登录事件会刷新角色身份。不能把 `CORE_READY` 等同于游戏声望 API 已就绪。Reputation 在 PLAYER_LOGIN 后确认当前身份，才做首次扫描；处理正常启动和晚加载两种路径，重复初始化不重复订阅或注册。

Scanner 自行监听 `PLAYER_LOGIN`、`PLAYER_ENTERING_WORLD`、`UPDATE_FACTION`；短时间多个事件合并为一次扫描。保留当前已解决的行为：折叠目录下按稳定 ID 补采、主声望同时为 header 时保留真实值、发现目录外 faction、友谊使用 friendship ID 查询 ranks、满友谊缺普通 standingID 时保留数据。

一次扫描先构建临时结果，完成校验再整体提交。API 不可用或抛错时保留旧负载并标记 unavailable／error，不用空表覆盖有效历史；短暂未就绪的空列表不得立即被当成成功清空。重试有界，诊断原因可通过现有三字母命令输出，普通入口不承载诊断。

声望是持久进度，本轮不引入日／周重置或任意 TTL。known 表示采集时已知，不承诺离线期间实时更新；缺数据、状态异常、好友度 rank 缺失或旧 schema 不满足展示要求时，继续显示未知／需重扫，目标不能因此判定完成。

数据变更后的业务事实通知建议为 `YIBO_REPUTATION_SNAPSHOT_CHANGED`，由 Core.Events 承载，来源固定 `YiboReputation`，负载为 characterID、revision、state、updatedAt、reason；不传内部表引用。订阅用稳定 owner，关闭或重建时通过 Events:Unregister 清理。页面刷新和 `action.targets` NotifyChanged 复用现有合并机制；接收方不反向触发扫描形成循环。不再伪造 `DATA_DOMAIN_UPDATED`。

## 5. 历史数据导入与冲突规则

1. 只枚举 Core 目录中的角色，再用 `DataDomains:Get(characterID, "reputation")` 读取公开拷贝。迁移模块不访问 `YiboCoreDB`，不写入或清空 Core 数据。
2. 先校验角色、快照结构、schema 和状态，再在临时表完成转换。首版原样保留可解释的 v5 数据及原始时间；v1～v4 保留旧版本标识并标为需重扫，不提升为 v5，不按名称猜测稳定 ID，不让旧好友度充当普通声望。
3. 首次导入只填充不存在的新记录。已有 Reputation 成功采集记录始终优先；已导入角色默认不再次覆盖，失败角色可重试。源快照版本未知或结构损坏时记录隔离原因，继续处理其它角色。
4. 成功顺序为准备副本 → 写新记录 → 标记角色导入成功。记录迁移来源 schema／revision／updatedAt 和 importedAt。迁移状态逐角色维护，不能用单一全局 done 跳过失败或后续新增角色。
5. 当前角色导入后由本地扫描替换；离线角色立即可浏览合法旧快照并保留时间。无快照角色不创建伪零值，也不因此加入业务预览。
6. 缓存删除与 ID 重映射同步处理快照、迁移记录、派生缓存；若新旧 ID 同时有记录，优先本地成功采集，再比较可用性和采集时间。无法确定时保留冲突证据并提示重扫，不按 revision 跨来源比大小。
7. 删除记录须先阻断旧数据导入；复用 CharacterCleanup 的删除历史与 `IsLegacyImportBlocked`，并保留本地迁移阻断状态。插件稍后启用时先执行 pending cleanup，避免被删角色复活。用户重新登录同一角色后允许产生新的现场快照。

旧 Core 数据首阶段保留为冻结来源，不自动清除，不在每次登录建立重复备份。清除旧来源属于后续明确操作：核对迁移结果与恢复窗口后，通过统一设置的风险说明和确认执行；本方案不授权删除源文件或历史数据。

## 6. Core 改动与版本混用

Core 最小改动是停止 TOC 加载声望业务域，撤下它独占的三项公开方法和注册表；若仍有引用，先完成引用迁移。Core 的 Profile 和 DataDomains 继续服务其它域。`UPDATE_FACTION` 若仅为声望使用，可撤下该监听；若发现其它消费者则保留通用转发。

保留 `DataDomains:Get`／DomainStore 的历史读取能力：现实现读取旧记录不要求该域仍在注册表中，因此无需为迁移新增 Service、Provider 或存储后端。已有 `GetDefinitions()` 可核对是否仍有 `reputation` 采集域，消费方只检查 id／owner，不能修改其返回的定义对象。

推荐继续使用 API13 既有通用接口，迁移版 Reputation 额外检查 `GetDefinitions`、`character-identity:1`、`character-cleanup:1` 及实际所需方法；发布时记录停采集 Core 的真实最低发布版本。Core 业务专用接口撤下属于兼容变化，须在发行说明明确列出；API13 是通用能力级别，不能只用 API13 数字推断声望已交接。

| 组合 | 预期行为 |
| --- | --- |
| 迁移版 Core + 迁移版 Reputation | 旧快照导入一次，新采集只写 Reputation |
| 旧 Core + 迁移版 Reputation | 发现 reputation 域仍有采集器后提示升级 Core，停止新扫描／迁移／依赖页面初始化，避免两个采集权威并存 |
| 迁移版 Core + Reputation 未安装／禁用 | Core 不扫描声望；冻结来源保留，未来安装时仍可迁移 |
| 迁移版 Core + 旧 Reputation | 旧版可能仍读到冻结数据但不会刷新，不能视为受支持组合；配套发行说明明确要求同步升级 |
| 降级到旧版本组合 | 只能恢复旧 Core 冻结时的数据，无法自动带回切换后的新采集；保留新 ReputationDB，避免破坏以后恢复升级 |

不建议为了旧版展示再让 Core 镜像新数据，那会再次形成双份业务数据。若需要自动拦截旧 Reputation，须先设计通用插件兼容性声明；当前没有这种机制，方案不宣称已实现。

## 7. 实施步骤与交付物

1. 固定迁移基线与真实数据样本，确认 v5、旧版本、友谊、公会和离线角色的负载；补齐本方案中的最终字段和失败规则。
2. 实现 Reputation Store／Scanner／Migration、目录索引和角色生命周期，先完成针对迁移边界的离线验证；不启用双写作为过渡。
3. 将六处读取模块统一迁入新 Store，移除 Core 声望注册／元数据调用，接通页面失效、目标通知和 CharacterCleanup。
4. 在同一交付批次停用 Core 声望域。新增升级、迁移失败、重扫与缓存影响文本全部走 owner 中英文资源。更新 API13 接入检查与本插件说明。
5. 核对实际 diff 的公共能力接入，更新 CAP-004／005／008／009 等实际相关台账状态，区分代码完成与客户端验收。新增迁移记录文档，不把方案写成已迁移。
6. 完成客户端验收与配套发布；记录 Core／Reputation 的实际版本、历史数据保留政策和恢复步骤。源文件删除若作为最终清理，另列精确路径按仓库删除规则办理。

## 8. 验收条件

| 范围 | 必须验证 |
| --- | --- |
| 数据完整性 | 各角色／faction 值、min/max、好友度、status、原始时间与导入前一致；v1～v4／未知版本不误升级 |
| 幂等与恢复 | 重载、重复迁移、部分失败重试不会覆盖新采集；模拟中断后可继续，源数据不变 |
| 采集 | 折叠／展开声望列表、主声望 header、目录外 faction、满普通声望、满友谊、纳特、API 暂不可用与空列表 |
| 身份与删除 | legacy ID 转 GUID、新旧 ID 冲突；已删除角色不导回；插件禁用期间删除后再启用能补清理 |
| 显示与目标 | 主矩阵、入口预览、单元格提示和 action.targets 使用同一快照，未知不算零或完成；分页角色一致 |
| 性能 | 无变化事件不导致重复复制／刷新；悬停复用同一轮快照，不逐格扫描；扫描事件合并有效 |
| 组合与语言 | 四种升级／缺失组合、晚加载、重复注册、低版本停止行为；zhCN／enUS 和 Core 手动语言模式 |
| Core 边界 | 无声望业务采集、规则、元数据注册表或新权威副本；其它域及公共角色目录照常工作 |

方案阶段仅交付设计；实施阶段已完成迁移、采集和生命周期的离线验证。真实客户端存档尚未在本会话读取或迁移；首次加载配套版本时才执行导入。静态语法／语言报告和离线检查不能替代游戏客户端验收。

## 9. 确认点

用户已确认实施：既有 API13 通用接口、一轮配套切换、旧来源冻结保留、逐角色一次性导入、新库唯一权威。实际工作树版本为 Core 1.12.4／Reputation 1.7.1；旧版 Reputation 与停采集 Core 不作为受支持组合。旧数据最终清理时间另行确定。
