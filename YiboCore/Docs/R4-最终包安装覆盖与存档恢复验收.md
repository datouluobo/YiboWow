- Core Retail0.1.0／Mists1.12.9／Forever0.2.0，API13／schema11。R3生产字节不变，R4按实际构建输入冻结源码和产物摘要。
- 三目标使用统一构建器；每个玩家包只含默认YiboCore.toc及本目标运行文件，含生成版本索引。三目标源码归档保留标准清单与Retail开发Mainline别名。
- 实际客户端以各次报告GetBuildInfo／Interface／产品ID为准，不能用离线模拟代替。已验开发源码基本启动、旧TOC机制不重复；本阶段核验实际单目标包及保留旧文件覆盖。
- Retail与Forever无旧正式发行包，干净安装为起点，既有本地验收包仅作开发载荷更新样本。Mists覆盖声明包括真实1.12.9和迁移前1.12.7包。精确旧包路径及摘要登记在动态记录。

## 安全安装与返回路径

先检查无WoW进程。不能向源码Junction解压：完整保留原联接，测试使用普通独立目录。所有递归移动或目录操作先校验绝对路径位于明确客户端根内；只操作YiboCore与本阶段同名探针，不改其它业务插件联接。无删除、自动退出游戏或自动操作游戏窗口。

各目标先备份现有YiboCore.lua及bak，逐文件核对SHA256。恢复验收使用该备份的工作副本；游戏按正常机制写回当前测试副本，原始字节备份保持不变。不导入其它目标存档，不执行真实存档内容为脚本。阶段结束时先保留测试期间的代码目录与存档，再恢复原联接与原始存档，结果逐文件登记。恢复前仍要求退出客户端。

旧文件覆盖在隔离目录先铺旧包，再直接铺新包；保留所有新包未包含的旧文件，并逐项验证旧文件哈希不变、当前加载链每一项来自新包。源清单归档／源码目录不是玩家包升级起点；残留客户端可识别目标TOC会优先于新默认TOC，不能将源码归档直接当玩家旧包覆盖。发现此类冲突记录精确路径与选择证据，部署脚本拒绝混用，不用运行时删文件解决。

## 实机步骤与判定

按Retail→Mists→Forever逐端引导，不要求同时登录。新增／变更TOC后完整退出启动，不能只reload。每端先验证干净包，再切换保留旧文件的覆盖目录；有多个同目标升级起点时逐一覆盖核对。

非发布诊断探针放根目录_NonRelease，以同名目录联接，按目标独立单TOC。探针校验实际产品及Core就绪、API和所需方法后才登记命令或修改测试设置。它读取公开状态，使用公开设置接口建立可辨认的恢复标记；只输出角色数量和身份是否可用，不输出角色名或GUID。不得用“插件已加载”代替Core就绪。

1. 登录后输出实际build／Interface、Core版本／API／目标、schema／独立存档归属、生成索引、角色数与幂等检查；打开/yco确认页面与既有角色／设置可见。
2. 用诊断命令标记测试副本中的公开排序偏好，然后/reload；报告标记仍匹配、角色目录与独立存档正常。
3. 完整退出客户端，离线记录测试存档新文件摘要与原备份保护，再重新启动。报告标记匹配、角色目录存在及界面正常，证明设置由磁盘恢复，不能仅以重采角色通过替代恢复证据。
4. 退出后切换旧包覆盖场景，核对旧文件仍在、新默认TOC与生成索引实际生效、初始化一次、标记与旧设置保留；需要时沿用前阶段相同字节通用恢复证据，仅补安装差异。
5. 结束该端后退出，保留测试结果并恢复原联接／原始存档；原始数据恢复不计为测试新包读取通过，二者分开登记。

若UI／语言／战斗／宿主／IME等R1～R3未验范围影响本阶段判定，按实际需要补验并记录；本阶段只完成安装／覆盖／恢复也不能宣称整插件全部客户端验收通过。第三方错误应按来源区分，不能笼统记为Core错误或无错。
