# Core 跨插件账号行动项与角色匹配方案

> 状态：**待实现方案**。当前 Core 尚未提供跨插件账号行动项的创建、持久化、聚合或角色匹配提醒能力；本文描述的是后续设计方向，不是现有功能说明。

## 一、目标

为 Yibo 插件建立一种可选、可组合的账号行动项协作能力：玩家可以从一个业务候选中保存一项跨角色目标，在账号范围中持续查看；当当前角色具备完成该行动的业务能力时，界面会将这项行动显著呈现。

以装备提升为例：玩家在 Builds 中看到当前背包没有、但适用于装备孔位的宝石，可以查看其它角色是否学会对应制作配方；玩家也可以把“为目标角色准备一颗宝石”保存为账号行动项。行动在账号范围内可见；当玩家切换到确认具备专业与配方的角色时，该行动显示为当前角色可处理。

这项能力面向不同业务域，不绑定特定插件名称或单一物品类型。

## 二、与现有 Core 概览行动的关系

Core 现有 `AccountView:RegisterPage()` 中的 `GetActions(characters)` 用于提供概览页即时行动建议。它按当前业务快照生成，供 Core 排序、限量展示和跳转，本身不是用户保存的跨角色请求记录。

拟议的账号行动项用于承载用户主动保存、可跨角色持续查看的目标。后续设计应将两种用途区分清楚：

- **即时行动建议**：由业务页面根据当前快照计算；用户不保存时可随状态变化消失。
- **账号行动项**：由用户明确保存；跨角色持续展示，并引用业务域提供的目标与适格角色信息。

## 三、职责边界

| 能力 | 责任方 | 边界 |
|---|---|---|
| 提供候选目标和来源上下文 | 发起业务插件，例如 Builds | 给出物品/目标、数量、目标角色及来源页面等可验证信息。 |
| 专业、配方、材料或库存能力查询 | 对应业务数据提供者 | 各自返回只读事实、数据状态与能力匹配结果。 |
| 统一角色目录、范围、角色切换上下文、页面和提醒呈现 | YiboCore | 提供通用平台能力，不推导配方、材料或任务完成等业务结论。 |
| 行动项持久化与业务完成状态 | 后续确定的行动项所有者 | 由独立设计决定归属；不在本方案中预设已有插件负责。 |

行动项记录应保存用户意图和稳定来源引用，不复制专业配方表、Vault 库存快照或业务插件的完整 SavedVariables。适格性与完成状态应由拥有相应业务事实的提供者重新查询，不能使用创建时的临时快照永久推断。

## 四、可选协作原则

- Builds 的候选列表、背包即时使用流程和既有装备提升能力不依赖 Vault、Crafting 或行动项能力。
- 如果业务提供者注册了匹配能力，消费者才显示相应的扩展动作，例如“查看制造者”或“保存账号行动项”。
- 提供者缺席、版本不兼容或暂时不可用时，仅隐藏或禁用对应扩展动作并说明状态；不能影响宿主插件原有页面和操作。
- 消费者通过业务 API 与 capability 协商查询能力，不把某个业务插件写为强制依赖，也不由 Core 按插件显示名称推测能力。
- 行动项发起者、信息提供者和最终执行者可以是不同插件/角色；通过稳定的 owner、provider、page、character 和 business-key 引用关联。

## 五、概念交互流程

1. Builds 过滤当前装备可用的宝石候选；背包有货时可直接走原有镶嵌流程，没有时仍展示灰色候选。
2. 若 Vault 能力存在，候选可展开账号已扫描库存的位置；若 Crafting 能力存在，候选旁可查看已学配方与可制作角色。
3. 玩家选择“保存为账号行动项”后，行动项中心保存目标物品、数量、目标装备角色/槽位、来源页面以及可选制造者范围。
4. 行动项在账号范围内持续可查；当某角色被确认具备相应制作能力时，Core 或行动项中心将记录提升到“当前角色可处理”的视觉优先级。
5. 宝石进入目标角色库存、行动完成或用户取消后，由对应数据所有者更新状态；完成判定的具体依据由后续业务契约确定。

上述流程不自动制作、采购、邮寄或镶嵌物品。玩家仍在对应业务界面完成操作。

## 六、建议的数据契约方向

以下仅是概念字段，API 名称、持久化结构和版本需在正式实施前另行冻结：

```lua
AccountAction = {
  id = "stable-user-action-id",
  ownerAddon = "future-action-owner",
  sourceAddon = "YiboBuilds",
  sourcePageID = "builds",
  businessKey = "gem-item-and-target-slot",
  target = {
    characterID = "target-character-id",
    itemID = 0,
    quantity = 1,
    slotID = 0,
  },
  eligibleCharacterIDs = {}, -- 来自业务提供者查询的候选执行角色
  status = "open",
  createdAt = 0,
}
```

契约设计应覆盖：

- 稳定去重键，避免重复点击生成大量相同行动；
- 目标角色与执行角色分离，支持 A 角色需要、B 角色制作；
- 多个合格执行角色、专业变化、配方状态失效和提供者不可用；
- 用户取消、完成、部分完成与重新打开；
- 数据删除、角色删除、服务器范围变化和来源插件卸载；
- action owner 缺席时的展示/处理边界；
- 状态变更通知及消费者刷新；
- 所有跨插件数据查询只返回明确范围、来源与有效性状态。

`eligibleCharacterIDs` 应按当前业务事实重算或由提供者通知更新，不能作为永久有效的能力证明。角色当前能力未被确认时，不显示“当前角色可制作”的肯定状态。

## 七、提醒行为

当当前角色属于经业务提供者确认的合格执行角色时，行动项在账号行动列表中应有明显的“当前角色可处理”状态，并允许跳转到提供者页面或对应配方。

角色切换时的提醒要与通用列表状态共用同一资格判断，避免页面显示可制作而提醒不出现，或相反。默认优先采用行动列表中的状态强调与排序；是否提供弹出通知、通知频率、静默时段和逐项关闭偏好，留待提醒交互方案单独定稿。

## 八、后续实施阶段建议

### 阶段 0：能力与所有权定案

- 梳理现有 `GetActions`、页面跳转、Core 范围和角色变更事件；确定即时建议与持久行动项的契约差异。
- 决定持久化所有者是 Core 新增通用用户意图存储，还是独立行动项插件；冻结用户数据生命周期、owner 卸载和迁移规则。
- 定义发起者、业务提供者、执行角色、目标角色、当前角色资格和完成状态接口。

**阶段门：** 所有权、可选依赖和缺失能力时的降级策略未定前，不新增持久化 API 或 `YiboCoreDB` 业务字段。

### 阶段 1：通用行动项基础服务

- 实现用户主动创建、查看、取消和完成的最小闭环。
- 接入统一账号范围、角色排序、页面导航和缓存/数据清理规则。
- 接受可选提供者的资格查询和变化通知；确保无提供者时行动仍可作为用户意图查看，但不声称当前角色可执行。

### 阶段 2：角色资格联动

- 接入一个真实业务场景验证跨角色创建、候选执行角色、切换角色后可处理状态及过期资格刷新。
- 根据试点反馈确定行动项显示预算、提醒优先级和低打扰通知设置。

### 阶段 3：跨业务扩展

- 评估更多业务插件是否能复用相同契约；仅在存在真实第二/第三消费者且语义一致时扩展公共能力。
- 不将业务特有流程强行抽象为 Core 规则；特殊状态由对应业务提供者解释。

## 九、待定事项

1. 持久化行动项由 Core 通用存储负责，还是由独立行动项插件负责；插件名称与产品归属随后确定。
2. 行动项可见位置：Core 概览、单独账号页面，或两者兼有。
3. 完成状态由用户手动确认，还是由库存/业务事件自动确认；可能按行动类型分别处理。
4. 当前角色匹配提醒采用页面排序、入口提示或可配置通知，以及通知频率。
5. 行动项是否需要依赖目标装备快照、角色槽位等易变来源上下文；来源实体变化后的继续/撤销行为。

## 十、验收方向

- 没有可选业务提供者时，Builds 的候选和当前操作仍可用。
- 安装业务提供者后，相关查询和按钮出现；卸载或能力降级后不产生插件加载错误。
- 用户保存的行动能在账号范围内持续查到，并能区分目标角色与执行角色。
- 切换到经当前业务事实确认的合格角色时，行动显示“当前角色可处理”；资格未知或失效时不误报。
- 业务库存、配方和完成状态仍归各自数据所有者；Core 不复制业务快照。
- 来源页面可打开；取消、完成、角色删除及 owner 缺席等生命周期规则有明确结果。
