## 已确认产品方向

### 数据与范围

- 首轮目标客户端为 MoP Classic，Interface `50504`；数据结构可预留扩展，但不承诺其它客户端版本的全量目录。
- 覆盖目标客户端可识别且可读取配方的所有专业，配方目录包括客户端可识别的历史配方。
- Core 的 `professions` 领域继续作为角色专业与技能等级的权威来源；Crafting 保存角色已学配方缓存和目录业务数据。
- Core 确认角色不再拥有某专业后，删除其该专业配方缓存。Core 数据不可用或读取失败时保留原缓存。

### 扫描与状态

- 采用混合采集：登录时尝试采集可用数据；玩家打开专业界面时补全或刷新对应专业。
- 不强制登录其它角色，不自动打开专业界面。
- 部分扫描只追加正向确认的已学配方，不推断未学；完整扫描成功才替换该专业完整基线。
- 扫描失败保留最后成功基线，并独立记录最近一次尝试状态。
- “未学”仅在配方目录覆盖完整、角色该专业存在匹配目录版本的完整扫描基线且配方不在学习记录中时成立。
- 配方取得状态与学习状态分开：客户端数据为基础，人工补充已核实例外；无法确认时标“未知”。全量目录不因配方可能已不可取得而隐藏历史配方。

图标语义：

- 已学：正常图标。
- 确认未学：灰色图标。
- 未扫描、部分扫描、目录覆盖不完整或状态无法确认：`?`。

## Core 账号页

- 在 YiboCore 统一业务面板注册一个 YiboCrafting 页面；Core 管页面壳、角色/服务器范围、统一设置与角色缓存清理。
- 同页提供“配方 / 专业”两种模式，切换按钮在两种模式下固定于内容区右上角；专业模式保留左侧“专业”和右侧“配方详情”标题，中间配方列表直接从搜索与筛选控件开始，不另设标题行。两种模式共用搜索与 Core 范围。
- 首次打开默认为“配方”，随后记住玩家上次模式。
- 默认遵循 Core 当前角色/服务器范围；查看全账号时由 Core 切换至所有服务器。
- 专业模式：先选专业，再浏览该专业的全量配方；选中配方后查看已核实详情及当前范围内各角色的学习状态与扫描证据。
- 配方模式：以目标客户端完整配方目录为行、当前范围内角色为列，逐格显示已学、确认未学或 `?`；取得状态作为次级信息展示。
- 配方是否出现在目录中不依赖账号角色、角色快照或已学记录。当前范围角色为空、或没有已确认掌握者时，配方仍显示；前者显示角色区域空状态，后者不得推断账号无人会做。
- 列表支持按角色、专业、名称和学习状态筛选；使用分组、搜索和分页/有界列表，不使用横向滚动或固定角色数截断。

## 插件分工与依赖

- YiboCrafting 依赖 YiboCore；业务数据存 `YiboCraftingDB`。
- YiboBuilds 可选读取配方/制造者查询。Crafting 不成为 Builds 强制依赖；Crafting 不可用时 Builds 现有装备提升能力继续工作。
- YiboTodo 继续独立负责商业冷却、周期任务和状态数据；Crafting 不参与 Todo 运行时或数据维护。
- YiboVault 负责已采集材料库存，Crafting 负责配方需求；以后通过只读 API 联动。
- YiboMail、YiboMounts 等消费者属于后续评估范围，不是首版要求。

## 后续从阶段 0 继续

非发布探针已安装并取得多轮目标客户端样本；正式插件的正向缓存底座已开始。继续核查候选目录和完整扫描能力，结果确认后再冻结对外 API、完整扫描基线和“确认未学”能力：

1. 找出 MoP Classic 客户端中可识别的全部专业配方来源，并按专业核实目录覆盖完整度及目录版本标识。

4. 核实配方与产物、材料的客户端事实，以及可取得状态能否可靠推导；无证据项保留未知。
