## 验证原则

- 目标为实际 MoP Classic、Interface `50504`。每份样本以 `GetBuildInfo()` 的版本、构建号、Interface 和采样时间标识。
- `GetAllRecipeIDs` 若存在，仅作为当前专业窗口的目录候选；不能由某个角色的列表直接推出目标客户端全部专业及历史配方已覆盖。
- 旧版 `GetNumTradeSkills` 所见行可能受筛选和折叠影响；无完整性证明时只能作正向证据。
- 即便有 `learned == false`，在专业目录覆盖和扫描完整性均未验证前也不生成“确认未学”。
- 取得状态、产物关系与材料数量分别记录证据。缺失字段保持“未知”，不根据名称猜测。
- 首版目录不要求在游戏内逐个取得未学配方。目录身份与取得状态分开：以目标 build 客户端数据为候选骨架，用角色已取得 ID、AtlasLootClassic MoP 与 ATT 的固定版本数据交叉核对；第三方目录是辅助证据，不是绝对权威。无法确认当前取得路径的项目保留在目录中并标“未知/待修订”，来源版本、哈希、ID 映射和差异清单须落盘。

### 首轮样本事实

- 登录且未打开专业窗口时，旧版列表为 0 行；不能从登录时的空列表推断角色没有已学配方。
- `C_TradeSkillUI.GetAllRecipeIDs` 与 `GetRecipeInfo` 在此构建中不存在；探针必须继续使用旧版 `GetNumTradeSkills`、`GetTradeSkillRecipeLink` 等接口记录正向事实。
- 本次会话记录 9 次列表快照、178 条事件；其中 `TRADE_SKILL_SHOW` 8 次、`TRADE_SKILL_UPDATE` 144 次、`TRADE_SKILL_CLOSE` 4 次、`SKILL_LINES_CHANGED` 5 次、`SPELLS_CHANGED` 17 次。未出现 `NEW_RECIPE_LEARNED`，故不能确定增量事件路径。
- 重复集合稳定仅适用于这次未改变筛选的样本。尚需实际切换搜索、子类别、折叠状态，并核对历史配方目录；完整性门禁未通过。

### 珠宝加工分类折叠实验

- 同一角色新会话中，开窗及前三次手动扫描均为 765 行、746 个配方 ID、19 个分类标题；配方 ID 集合不变。
- 最后一次手动扫描时玩家已折叠全部分类（玩家确认），旧版 API 返回 19 行分类标题、0 个配方 ID。
- 因此 `GetNumTradeSkills() > 0` 不足以证明扫描完整，旧版列表明显受分类展开状态影响。目标实现只能将这种列表作为部分/不可判定扫描，不能替换完整基线，更不能推断“未学”。
- 此构建的 `GetTradeSkillInfo` 样本没有提供可依赖的折叠布尔值；探针记录空分类组数量（即标题组中没有可见配方行的数量）。这是列表形态证据，不是已证明的完整性判据。

### 旧版专业窗口筛选与展开状态

- [Blizzard MoP Classic 专业界面源码镜像](https://github.com/Gethe/wow-ui-source/blob/classic/Interface/AddOns/Blizzard_TradeSkillUI/Mists/Blizzard_TradeSkillUI.lua)展示了搜索、仅可制造、仅可涨技能、子类别和装备栏筛选，也按 `GetTradeSkillInfo` 的 `isExpanded` 值切换分类折叠。源码用于确定需观察的状态，实际目标构建以客户端实测为准。
- 现有目标构建落盘样本中，工程 11、炼金 8、裁缝 17、锻造 16 个标题的 `isExpanded` 全是 `nil`。因此不能按源码预期把该返回位直接用作本构建的展开证明；“标题下有可见配方”和手动两次相同 ID 集合也不足以证明所有分类已展开。
- 探针现已被动记录各筛选项的 All/选中索引、仅可制造、仅可涨技能、Blizzard 搜索框文本、有效输入状态与占位文字标记，以及标题展开返回值的已知/未知数量；不会修改玩家筛选或折叠。以下裁缝复测验证了其中一部分字段与旧版列表的关系，不能据此把快照升级为完整扫描。

### 裁缝搜索与局部折叠复测

- 目标构建同一会话中，开窗与前两次手动扫描均为 9 行、5 个配方 ID、4 个标题。截图显示 alaTradeSkill 搜索栏输入“衣”后，其界面列表缩短，但探针所读 Blizzard 搜索框仍为空；旧版 `GetNumTradeSkills` 列表与 5 个 ID 均不变。
- 本机 alaTradeSkill 源码的 `ProcessTextFilter` 和自建 `SearchEditBox` 表明它会筛选自己的列表。因此本次只能确认该插件的搜索栏未改变底层旧版 API 列表；探针的 `searchActive=false` 不能代表所有正在显示的第三方搜索框均为空。
- 最后一次手动扫描为 7 行、3 个配方 ID、4 个标题。与前次相比仅少 `3915`（棕色亚麻衬衣）和 `2393`（白色亚麻衬衣）；“衬衣”标题仍在，下面没有可见配方。截图显示该分类已折叠，与 API 差异相符。4 个标题的展开返回位仍均为 `nil`，不能靠该返回位直接判定其它分类状态。
- 这次复测验证了“第三方搜索可只影响自身展示”和“分类折叠可缩短旧版 API 列表”两种不同路径。`onlyMakeable`、`onlySkillUps` 为 `false`，子类别及装备栏为“全部”；完整扫描证明仍未取得，不得将缺失 ID 判为未学。

### 只读可见范围判据

- 探针现将明确的原生子类别/装备栏筛选、仅可制造、仅可涨技能、Blizzard 搜索文本、API 明确报告的折叠标题及 10000 行截断记入 `visibleList.restrictions`，并将 `visibleList.scope` 标为 `restricted`。这是“当前旧版列表范围受限”的正向证据，不是配方学习状态。
- 标题展开返回位缺失、标题下无可见配方、过滤接口不可用及窗口来源未确认记入 `visibleList.uncertainties`。没有明确限制时范围为 `unverified`，不能凭空提升为完整。
- 本机 alaTradeSkill 的清除过滤函数还调用 `ExpandTradeSkillSubClass(0)`；但目标构建无法从 `GetTradeSkillInfo` 可靠读取原有标题展开状态，探针无法无损恢复玩家的折叠布局，因此继续只读。它不自动执行“展开全部/清除筛选”。
- `completeness` 对上述两种范围一律保持 `unverified`。阶段 0 目前可以区分“已知受限”和“未能证明完整”，不能提供“确认完整”基线；缺失 ID 一律未知。可继续采正向已学事实，正式产品的灰色未学状态仍受完整目录与完整扫描双重门禁约束。
- 2026-09-28 裁缝同会话展开实验落盘：本人窗口先为 9 行/5 ID，折叠“衬衣”后为 7 行/3 ID，再执行 `ExpandTradeSkillSubClass(0)` 后恢复 9 行/5 ID。折叠时仅失去 `2393`、`3915`，恢复后 5 个 ID 集合与首次完全一致；三次原生筛选项均为“全部”、仅可制造/涨技能均为 `false`、Blizzard 搜索框为空，4 个标题的展开返回位仍全是 `nil`。这验证了该操作能恢复本次被折叠的两条配方，但还不足以证明全专业扫描完整。
- 探针随后增加同会话对照：如果本人同一专业、同一技能等级的当前 ID 集合是此前列表的严格子集，即使标题展开返回位为 `nil`，也记 `visibleList.scope=restricted`，原因 `subset-of-earlier-own-list`。这条判据只证明本次少了此前可见的配方；不会倒推首次列表已完整，也不会把旧落盘快照改写。

3. 打开其他玩家链接或公会专业列表，执行 `/yct scan`，确认来源标记不会被当作本人学习记录。
4. 学习一项配方前后分别扫描，检查 `NEW_RECIPE_LEARNED`、`TRADE_SKILL_LIST_UPDATE` 等事件顺序及学习字段变化。
5. 对可制造物品、附魔、无直接产物、多个材料候选各取至少一个配方 ID，执行 `/yct recipe <ID>`。
6. 在接口不可用、空列表、部分列表、调用异常各记录样例；确认失败后仍可保留旧的正向学习事实。
7. 对每个专业比较客户端候选目录与独立来源的目标构建目录，核对历史配方、取得状态和例外证据，再确定目录版本标识。
