# YiboCrafting 阶段 0 客户端验证记录

> 状态：首轮与后续多次客户端会话已取得；目标构建候选目录已生成，目录覆盖与完整扫描证明仍待验证。记录来自 MoP Classic 5.5.4、build 69934、Interface `50504`、zhCN；不含角色身份。

## 验证原则

- 目标为实际 MoP Classic、Interface `50504`。每份样本以 `GetBuildInfo()` 的版本、构建号、Interface 和采样时间标识。
- `GetAllRecipeIDs` 若存在，仅作为当前专业窗口的目录候选；不能由某个角色的列表直接推出目标客户端全部专业及历史配方已覆盖。
- 旧版 `GetNumTradeSkills` 所见行可能受筛选和折叠影响；无完整性证明时只能作正向证据。
- 即便有 `learned == false`，在专业目录覆盖和扫描完整性均未验证前也不生成“确认未学”。
- 取得状态、产物关系与材料数量分别记录证据。缺失字段保持“未知”，不根据名称猜测。

### 首轮样本事实

- 登录且未打开专业窗口时，旧版列表为 0 行；不能从登录时的空列表推断角色没有已学配方。
- `C_TradeSkillUI.GetAllRecipeIDs` 与 `GetRecipeInfo` 在此构建中不存在；探针必须继续使用旧版 `GetNumTradeSkills`、`GetTradeSkillRecipeLink` 等接口记录正向事实。
- 本次会话记录 9 次列表快照、178 条事件；其中 `TRADE_SKILL_SHOW` 8 次、`TRADE_SKILL_UPDATE` 144 次、`TRADE_SKILL_CLOSE` 4 次、`SKILL_LINES_CHANGED` 5 次、`SPELLS_CHANGED` 17 次。未出现 `NEW_RECIPE_LEARNED`，故不能确定增量事件路径。
- 重复集合稳定仅适用于这次未改变筛选的样本。尚需实际切换搜索、子类别、折叠状态，并核对历史配方目录；完整性门禁未通过。

### 第二批四角色样本

- 四次登录时旧版列表均为 0 行，开窗后才取得对应专业配方 ID；四次会话分别记录 5、3、4、2 个列表快照。
- 工程学两名角色分别标记为分支 1、分支 2。两者各有 238 个配方 ID，其中交集 207 个、各自独有 31 个。探针尚未读取分支标识，因此只能确认角色列表差异与人工标记的分支相符，不能把差异全归因于分支。
- 第二名角色的烹饪为 239 个 ID，首轮角色为 208 个；同专业不同角色的列表数不同，进一步说明单角色列表不能代表全客户端目录。
- 四名角色的 Core 专业枚举均包含考古学、钓鱼，但本轮没有相应配方窗口样本；另有一个符文熔铸窗口样本，暂不纳入普通专业目录。
- 去角色标识的逐专业 ID 集合已保存为[第二批配方 ID 样本](../../../_NonRelease/YiboCraftingStage0Probe/Samples/2026-09-27-build69934-batch2-recipe-ids.lua)。

### 珠宝加工分类折叠实验

- 同一角色新会话中，开窗及前三次手动扫描均为 765 行、746 个配方 ID、19 个分类标题；配方 ID 集合不变。
- 最后一次手动扫描时玩家已折叠全部分类（玩家确认），旧版 API 返回 19 行分类标题、0 个配方 ID。
- 因此 `GetNumTradeSkills() > 0` 不足以证明扫描完整，旧版列表明显受分类展开状态影响。目标实现只能将这种列表作为部分/不可判定扫描，不能替换完整基线，更不能推断“未学”。
- 此构建的 `GetTradeSkillInfo` 样本没有提供可依赖的折叠布尔值；探针改为记录“无可见配方分类”数量。这是列表形态证据，不是已证明的完整性判据。

### 采矿（熔炼）实验

- 同一角色打开熔炼窗口两次，均得到 33 行、31 个配方 ID、2 个分类标题，ID 集合无变化；玩家确认折叠全部分类后，最后一次手动扫描为 2 个标题行、0 个配方 ID。
- 一次手动扫描时窗口未显示，`GetTradeSkillLine` 为 `UNKNOWN`，但旧版列表仍返回上次的 33 行、31 个 ID。这是**窗口关闭后的残留列表**，不能归入当前角色/专业的成功扫描。
- 因而缓存采集必须校验本人窗口仍显示、窗口不是链接或公会来源、专业名能可靠匹配 Core 专业身份；仅凭行数或配方 ID 非空不能采纳。
- 去角色标识的熔炼 ID 集合已保存为[采矿配方 ID 样本](../../../_NonRelease/YiboCraftingStage0Probe/Samples/2026-09-27-build69934-mining-recipe-ids.lua)。

### 旧版专业窗口筛选与展开状态

- [Blizzard MoP Classic 专业界面源码镜像](https://github.com/Gethe/wow-ui-source/blob/classic/Interface/AddOns/Blizzard_TradeSkillUI/Mists/Blizzard_TradeSkillUI.lua)展示了搜索、仅可制造、仅可涨技能、子类别和装备栏筛选，也按 `GetTradeSkillInfo` 的 `isExpanded` 值切换分类折叠。源码用于确定需观察的状态，实际目标构建以客户端实测为准。
- 现有目标构建落盘样本中，工程 11、炼金 8、裁缝 17、锻造 16 个标题的 `isExpanded` 全是 `nil`。因此不能按源码预期把该返回位直接用作本构建的展开证明；“标题下有可见配方”和手动两次相同 ID 集合也不足以证明所有分类已展开。
- 探针现已被动记录各筛选项的 All/选中索引、仅可制造、仅可涨技能、Blizzard 搜索框文本，以及标题展开返回值的已知/未知数量；不会修改玩家筛选或折叠。以下裁缝复测验证了其中一部分字段与旧版列表的关系，不能据此把快照升级为完整扫描。

### 裁缝搜索与局部折叠复测

- 目标构建同一会话中，开窗与前两次手动扫描均为 9 行、5 个配方 ID、4 个标题。截图显示 alaTradeSkill 搜索栏输入“衣”后，其界面列表缩短，但探针所读 Blizzard 搜索框仍为空；旧版 `GetNumTradeSkills` 列表与 5 个 ID 均不变。
- 本机 alaTradeSkill 源码的 `ProcessTextFilter` 和自建 `SearchEditBox` 表明它会筛选自己的列表。因此本次只能确认该插件的搜索栏未改变底层旧版 API 列表；探针的 `searchActive=false` 不能代表所有正在显示的第三方搜索框均为空。
- 最后一次手动扫描为 7 行、3 个配方 ID、4 个标题。与前次相比仅少 `3915`（棕色亚麻衬衣）和 `2393`（白色亚麻衬衣）；“衬衣”标题仍在，下面没有可见配方。截图显示该分类已折叠，与 API 差异相符。4 个标题的展开返回位仍均为 `nil`，不能靠该返回位直接判定其它分类状态。
- 这次复测验证了“第三方搜索可只影响自身展示”和“分类折叠可缩短旧版 API 列表”两种不同路径。`onlyMakeable`、`onlySkillUps` 为 `false`，子类别及装备栏为“全部”；完整扫描证明仍未取得，不得将缺失 ID 判为未学。

### 只读可见范围判据

- 探针现将明确的原生子类别/装备栏筛选、仅可制造、仅可涨技能、Blizzard 搜索文本、API 明确报告的折叠标题及 10000 行截断记入 `visibleList.restrictions`，并将 `visibleList.scope` 标为 `restricted`。这是“当前旧版列表范围受限”的正向证据，不是配方学习状态。
- 标题展开返回位缺失、标题下无可见配方、过滤接口不可用及窗口来源未确认记入 `visibleList.uncertainties`。没有明确限制时范围为 `unverified`，不能凭空提升为完整。
- 本机 alaTradeSkill 的清除过滤函数还调用 `ExpandTradeSkillSubClass(0)`；但目标构建无法从 `GetTradeSkillInfo` 可靠读取原有标题展开状态，探针无法无损恢复玩家的折叠布局，因此继续只读。它不自动执行“展开全部/清除筛选”。
- `completeness` 对上述两种范围一律保持 `unverified`。阶段 0 目前可以区分“已知受限”和“未能证明完整”，不能提供“确认完整”基线；缺失 ID 一律未知。可继续采正向已学事实，正式产品的灰色未学状态仍受完整目录与完整扫描双重门禁约束。
- 2026-09-28 裁缝同会话展开实验落盘：本人窗口先为 9 行/5 ID，折叠“衬衣”后为 7 行/3 ID，再执行 `ExpandTradeSkillSubClass(0)` 后恢复 9 行/5 ID。折叠时仅失去 `2393`、`3915`，恢复后 5 个 ID 集合与首次完全一致；三次原生筛选项均为“全部”、仅可制造/涨技能均为 `false`、Blizzard 搜索框为空，4 个标题的展开返回位仍全是 `nil`。这验证了该操作能恢复本次被折叠的两条配方，但还不足以证明全专业扫描完整。
- 探针随后增加同会话对照：如果本人同一专业、同一技能等级的当前 ID 集合是此前列表的严格子集，即使标题展开返回位为 `nil`，也记 `visibleList.scope=restricted`，原因 `subset-of-earlier-own-list`。这条判据只证明本次少了此前可见的配方；不会倒推首次列表已完整，也不会把旧落盘快照改写。
- Blizzard 专业界面源码中的搜索逻辑还会调用 `SetTradeSkillItemNameFilter` 或 `SetTradeSkillItemLevelFilter`；搜索框文本并非底层筛选状态本身。探针已加相应 Getter 的只读能力检测和值记录：若底层名称非空或等级范围非零，记为范围受限；Getter 不可用则保留未知。目标构建是否提供这两个 Getter，尚待下次自然重载后的真实样本确认。
- 随后的目标构建 `5.5.4.69934` 裁缝落盘样本确认两个 Getter 均存在。本人窗口自动扫描与手动扫描均为 9 行/5 ID、两次 ID 集合一致；底层名称 Getter 均返回 `nil` 且无调用错误，等级 Getter 均返回 `0/0`，原生类别/装备栏为“全部”，仅可制造/涨技能为 `false`。Blizzard 源码以 `SetTradeSkillItemNameFilter(nil)` 清除名称筛选，因此探针将无错误的 `nil` 视为未设置名称筛选；接口缺失/报错仍为未知。标题展开返回位仍为 `nil`，所以此样本的扫描完整性继续为 `unverified`。

### 固定构建目录差异报告

- 新增只读诊断脚本 [`AnalyzeBuildCatalog.py`](../../../_NonRelease/YiboCraftingStage0Probe/Tests/AnalyzeBuildCatalog.py)：从 wago.tools 按构建号下载 `SkillLine`、`SkillLineAbility`、`SpellReagents` 到内存，校验 CSV 的 SHA-256，再把去角色标识的样本 ID 与专业技能线及其子技能线对照。不写入、复制或发布第三方目录数据。
- 用 `TrivialSkillLineRankHigh > 0` 暂取候选：制皮已见 700 / 候选 944；急救 21 / 24；烹饪 239 / 284；附魔 328 / 369；工程两个角色各 238 / 379；锻造 621 / 842；铭文 583 / 612；珠宝 746 / 873；采矿 31 / 33；附带符文熔铸 10 / 10。全部样本的已见 ID 均在对应候选集合中。
- 烹饪实测的 31 个 ID 属于 `SkillLine` 185 的六条子技能线（975–980）；只查主技能线会错误地把这些 ID 列为缺项。目录生成必须解析 `ParentSkillLineID`。
- 候选集合仍有非制作技能：采矿候选中的 `110955`（Release Spirit）同时归在多个专业技能线，烹饪候选中的 `818`（Cooking Fire）也不应直接算作食谱。`TrivialSkillLineRankHigh > 0` 仅用于差异诊断，尚不是正式目录的纳入条件；候选多于单角色已见数也不能推导“未学”。
- `SpellReagents` 可帮助诊断：普通专业的 10 份样本中，全部已见 ID 均有材料表记录；限定材料表后，烹饪候选由 284 降为 277、采矿由 33 降为 32，其中剔除了上述非食谱技能。但附带的 10 个符文熔铸 ID 均无材料表记录，因此“必须有材料表”不能作为所有技能线通用的正式目录规则。材料表存在也不能单独证明配方可取得或角色未学。
- 用 `TradeSkillCategoryID != 0` 筛选会漏掉 17 条实测 ID：制皮 5、锻造 12（包含此前旧目录缺少的 6 条）。按已见配方的 `SpellEffect` 类型筛选也会误伤候选：制皮 `74493` 有额外效果类型 `238`；工程 `82207` 则只有效果类型 `2`、`68`，其是否属于可显示配方还需单独核实。
- 与本机旧目录只读比较 `SkillLineAbility ∩ SpellReagents`：锻造新增候选 16、制皮 32、裁缝 16、附魔 1；其它普通专业数量及 ID 集合相同。旧目录另含制皮 `19566`（Salt Shaker），目标构建没有其专业 `SkillLineAbility` 归属。进一步核对 [使用筛盐器的效果 `19566`](https://www.wowhead.com/mop-classic/spell%3D19566/salt-shaker) 与 [工程制作配方 `19567`](https://www.wowhead.com/mop-classic/spell%3D19567/salt-shaker) 后，后者已在工程角色客户端样本中出现。`19566` 保留为已结清的旧目录差异，不并入专业配方。

### 考古学独立界面边界

- 固定构建 DB2 的考古学技能线 `794` 有 173 个 `TrivialSkillLineRankHigh > 0` 候选，其中 24 个有 `SpellReagents` 记录，名称为考古项目/古物。它不是已实测的普通交易技能窗口配方集合。
- [Blizzard 考古界面源码镜像](https://github.com/Gethe/wow-ui-source/blob/classic/Interface/AddOns/Blizzard_ArchaeologyUI/Blizzard_ArchaeologyUI.lua)使用 `GetNumArchaeologyRaces`、`GetNumArtifactsByRace`、`GetArtifactInfoByRace` 等独立接口，并提供项目完成次数。源码所示接口形态仍需在目标构建实测；不能把考古项目的完成次数解释成普通配方“已学/未学”。
- 探针增加手动 `/yct archaeology`：只读记录当前考古界面是否显示、种族/项目数、项目法术 ID、稀有度和完成次数；`completeness` 固定为 `unverified`。目录与状态模型仍需独立定稿。
- 实测关闭、打开考古界面各执行一次命令，均返回 13 个种族、103 个项目、103 个法术 ID、98 个有完成次数的项目。SavedVariables 中两次的 ID 集合和每项完成次数完全一致；另外 5 个项目完成次数为 0。去角色标识的[考古项目 ID 样本](../../../_NonRelease/YiboCraftingStage0Probe/Samples/2026-09-27-build69934-archaeology-project-ids.lua)只保留 103 个法术 ID，不含角色或完成次数。
- 目标构建 [`ResearchProject` CSV](https://wago.tools/db2/ResearchProject/csv?build=5.5.4.69934) 有 179 行、177 个唯一项目法术 ID，实测 103 个全能匹配；其中 10 个螳螂妖项目法术 ID 不在考古学 `SkillLineAbility` 中，但存在于 `ResearchProject`、`SpellName`、`SpellReagents`、`SpellEffect`。因此考古项目目录应以 `ResearchProject` 为基础，不得从技能线表单独生成。
- 同构建 [`ResearchBranch`](https://wago.tools/db2/ResearchBranch/csv?build=5.5.4.69934) 有 13 行，其中一行标为 `UNUSED`；`ResearchProject` 另有 6 行种族/分支字段为 0。客户端 13 个索引里有 3 个未列出项目。静态表中的每行并不必然是此角色当前可见、可完成的项目。
- 按分支拆开后，`ResearchProject` 有 173 个归属明确的唯一项目法术 ID，另有 6 行未归属记录（4 个唯一法术 ID）；标为 `UNUSED` 的分支无项目。单角色已见 103 个归属项目，另外 70 个归属项目未由该角色 API 返回，主要分布于矮人 24、托维尔 12、德莱尼 10、兽人 10 等分支。这些差额只说明当前角色未返回，不能推断未完成、不可取得或目录不完整。
- [考古界面完成历史代码](https://github.com/Gethe/wow-ui-source/blob/classic/Interface/AddOns/Blizzard_ArchaeologyUI/Blizzard_ArchaeologyUI.lua)在展示完成项目时跳过 `completionCount == 0`。本次 98 个完成次数大于 0 的项目可作为该角色“已完成”的正向事实；其余 5 个返回项目均为 0，分别来自不同分支，仅可记为“当前 API 返回但无完成记录”。静态目录剩余 70 个项目保持状态未知，不用普通配方“已学/未学”语义。考古目录版本可固定到该 DB2 构建，但是否排除全部未归属/测试记录及完整历史判据仍待定。

| 配方 ID | 产物物品 ID | 直接材料 ID × 数量 | 客户端来源 |

### 附魔产物形态样本

- 本人附魔窗口展开时，配方 `7418`（附魔护腕 - 初级生命）的配方链接类型为 `enchant`；旧版列表 342 行、328 个配方 ID、14 个分类标题，手动重扫集合未变化。

- 对外数据契约需要分别表示配方已学事实、配方链接类型、直接材料事实与产物物品关系。没有产物物品 ID 的附魔配方仍应能被目录和角色学习缓存表示；按物品反查时不能虚构一个产物 ID。

## 必须留存的样例

1. 同一角色登录但未打开专业窗口，执行 `/yct scan`，记录 API 是否返回空表或报错。
2. 打开本人每个专业界面，执行 `/yct scan`；依次改变搜索、已学/未学、子类别、折叠状态，再次扫描，比较全部 ID 集合和筛选数。
3. 打开其他玩家链接或公会专业列表，执行 `/yct scan`，确认来源标记不会被当作本人学习记录。
4. 学习一项配方前后分别扫描，检查 `NEW_RECIPE_LEARNED`、`TRADE_SKILL_LIST_UPDATE` 等事件顺序及学习字段变化。
5. 对可制造物品、附魔、无直接产物、多个材料候选各取至少一个配方 ID，执行 `/yct recipe <ID>`。
6. 在接口不可用、空列表、部分列表、调用异常各记录样例；确认失败后仍可保留旧的正向学习事实。
7. 对每个专业比较客户端候选目录与独立来源的目标构建目录，核对历史配方、取得状态和例外证据，再确定目录版本标识。
