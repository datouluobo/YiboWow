# YiboCrafting 产品边界与开发路线图

> 状态：产品方向已确认；阶段 0 已取得专业列表、折叠状态、熔炼和附魔材料样本，目标构建全配方目录与完整扫描证明仍待完成。正式插件已开始仅采正向已学事实的缓存底座；完整目录、确认未学和账号页面仍待后续阶段。
>
> 目标客户端：当前 Yibo 系列主要支持的 MoP Classic（Interface `50504`）。跨资料片的数据模型可预留，但首轮不承诺多版本配方全集。

## 一、产品定位

YiboCrafting 是 Yibo 系列的账号级专业与制造能力索引。它记录玩家正常登录和访问专业时可确认的角色专业及已学配方，以目标客户端可识别的全部专业配方作为比较目录，并通过 YiboCore 统一账号工作台集中查看。

它主要回答：

> 账号哪些角色学会了哪些配方？我想要一件物品时，哪个角色可以制作？

YiboCrafting 不是通用拍卖行或自动制造工具。它为 YiboBuilds 的装备提升提供跨角色配方信息，也为后续 YiboVault、YiboMail 等插件提供经过缓存的配方事实。

## 二、用户价值与首版目标

首版首先完成一个基础但独立有用的能力：**建立各角色的已学配方缓存，以客户端完整配方目录为基准区分已学、未学和未扫描，并在 Core 统一账号业务面板展示。**

玩家无须为了查配方逐个登录角色；曾经登录并完成配方扫描的角色，可在账号页面集中浏览。数据只代表该角色最近一次成功采集的专业快照，不声称涵盖从未登录或从未成功扫描的角色。

首版提供同一业务页的两种模式：“配方”以配方为行、角色为列比较学习状态；“专业”先选择专业，再浏览该专业的配方和选中配方的账号角色状态。首次进入默认“配方”，并记住玩家上次使用的模式。两个模式的切换按钮固定在页面内容区右上角，位置不随模式改变。页面始终遵循 Core 当前角色/服务器范围；要查看全账号时，玩家在 Core 中切换为所有服务器。

之后再建立反向查找和联动：

- 输入物品，查询账号内哪些已缓存角色有对应配方；
- 查看配方产物与材料需求；
- 查询 Vault 已缓存材料及分布；
- 由 Builds 判断当前装备是否适用，并决定当前角色能否执行。

## 三、职责与数据所有权

| 领域 | 责任方 | 说明 |
|---|---|---|
| 角色身份、服务器、角色目录 | YiboCore | 作为角色键和范围过滤的权威来源。 |
| 角色专业与技能等级 | YiboCore | Core 的 `professions` 领域已有此类中性事实；Crafting 消费它，不再建立第二份专业等级权威数据。 |
| 各角色已学配方快照 | YiboCrafting | 由 Crafting 采集、保存、标记采集时间与数据状态。 |
| 配方目录、产物关系、配方材料 | YiboCrafting | 属于专业/配方业务数据，按客户端版本标注来源和覆盖程度。 |
| 已有物品库存及位置 | YiboVault | Crafting 查询已有库存，不重扫背包、银行或邮件。 |
| 装备目标匹配、候选执行和客户端操作 | YiboBuilds | Crafting 只提供配方事实和可制造角色信息，不接管装备规则或施加操作。 |
| 周期冷却与待办状态 | YiboTodo | Todo 独立判断任务是否可执行、何时恢复及是否完成。 |

Crafting SavedVariables 使用 `YiboCraftingDB`。Core 负责页面外壳、角色目录、服务器范围、设置工作台、入口与缓存清理注册；Crafting 负责业务数据、配方表格和配方查询服务。

正式插件清单需在 `.toc` 使用统一 `[Yibo]` 青绿色标题前缀，并声明 `## RequiredDeps: YiboCore`；插件显示名和页面顺序按技术名排序。若后续增加诊断 Slash 命令，必须先搜索全工作区 `SLASH_*` 注册，使用未占用的三个英文字母命令，不保留旧命令别名。

## 四、缓存阶段：各角色已学配方与 Core 账号页

此阶段位于客户端 API/数据来源验证之后、按物品查制造者之前，是首版的基础交付，不依赖 Vault 或 Builds。

### 4.1 采集边界

- 角色登录/进入世界时尝试采集客户端当时可确认的已学配方；结果仅在客户端明确支持完整列表时标记为完整，否则记为部分/待确认。
- 玩家打开相应专业界面后扫描并刷新该专业；若此时可取得完整列表，成功后标记该专业快照完整。不要为了刷新而自动打开窗口或执行受保护操作。
- 专业配方窗口打开期间若学习配方、切换专业或客户端明确发出配方更新事件，合并事件后局部刷新受影响专业。
- 扫描失败或客户端接口不可用时保留最后成功快照，并单独记录最近一次尝试的失败/不可用状态；不得用空结果覆盖旧快照，也不得因此抹掉此前已确认的学习状态。
- 玩家未登录的角色不被强制登录；不要求为新消费者重新遍历所有角色。没有角色扫描数据的目录项显示“？”，不推断为未学。

阶段 0 必须确认目标客户端可识别的专业配方目录是否完整、哪些配方状态可读取、是否需要打开专业界面才可获得完整角色列表，以及客户端如何证明一次扫描完整。依据验证结果定义 `complete`、`partial`、`unscanned`、`unavailable`、`error` 等状态；不得假设一次读取必然返回专业的所有配方。

### 4.2 推荐数据模型

语义模型如下，实施时可按客户端 API 调整字段：

```lua
YiboCraftingDB = {
  schemaVersion = 1,
  characters = {
    [characterID] = {
      professions = {
        [professionID] = {
          learnedRecipes = {
            [recipeSpellID] = {
              recipeSpellID = 0,
              outputItemID = 0, -- 若客户端数据可确认
            },
          },
          lastCompleteSnapshot = {
            catalogVersion = "50504",
            observedAt = 0,
            learnedRecipeIDs = {},
          },
          lastAttempt = { at = 0, state = "success" }, -- success | partial | unavailable | error
        },
      },
    },
  },
}
```

- 角色、服务器和专业技能值优先引用 Core 对应事实；Crafting 快照只存角色的正向已学配方、最近一次完整扫描基线及目录版本、最近一次采集尝试状态。
- 按客户端版本维护一份插件级全配方目录，不为每名角色重复保存未学目录。配方以稳定 ID 为键，名称和图标按客户端本地化数据按需解析。
- 配方目录记录输出物品和材料等客户端可确认事实；可取得/不可取得状态以客户端数据为基础，人工补充已核实例外，证据不足时标为“未知”。目录包含目标客户端可识别的历史配方，不因其可能已不可取得而从全量视图隐藏。
- 配方在完整且覆盖已验证的目录中，但角色专业完整扫描基线不含此配方、且没有后续正向已学记录时，派生为“未学”；正向记录派生为“已学”。没有匹配当前目录版本的完整扫描基线或目录覆盖不完整时，相关状态为“？”/待确认。
- 登录或开窗产生的部分扫描只追加正向确认的已学配方，并更新最近尝试状态，不覆盖完整扫描基线，也不据此得出未学结论。完整扫描成功后，原子替换该专业完整扫描基线和学习记录。
- 后续失败扫描不使仍有效的最后完整基线失效；已确认的状态继续显示，同时可查看最近一次尝试失败提示。配方目录版本改变后，旧基线不对新增/变化目录项作未学判断，直到重扫确认。
- 不把派生的未学状态重复保存到每个角色缓存；它由目录、专业扫描状态和已学快照共同计算。
- 配方新学会时并入该角色的正向已学记录；刷新完整成功时才替换完整扫描基线。局部失败不得清掉未触及专业。
- Core 确认角色不再拥有某专业后，删除该角色该专业的配方缓存；Core 数据不可用、过期或读取失败时不得据此删除。

### 4.3 Core 统一业务面板

YiboCrafting 注册一个 Core 账号业务页；页面在 Core 的统一窗口中显示，插件不创建独立窗口壳或第二套设置。

页面提供“配方 / 专业”两态切换，默认进入“配方”，并记住玩家上次模式。两个按钮在两种模式下始终固定于页面内容区右上角；专业模式将按钮与配方详情标题放在同一顶行，左侧专业目录保留“专业”标题，中间配方列表直接从搜索与筛选控件开始，不另设重复的专业/配方标题行。搜索与 Core 范围筛选在两种模式之间共用。

页面概念图：[配方模式](Assets/YiboCrafting-配方模式-概念图.png) · [专业模式](Assets/YiboCrafting-专业模式-概念图.png)。图中配方、角色、版本和学习状态均为布局示例，不代表已验证的客户端数据。

**专业模式：**

- 内容区先提供专业目录；选中专业后显示该专业的全量配方列表，并可按资料片、适用分支和名称缩小结果。
- 选中配方后显示其专业/分支、资料片、产物与可取得状态等已核实详情，以及当前 Core 范围内各角色的学习状态和专业扫描证据。
- 当前没有角色数据、没有已确认掌握者，或所有角色状态均待确认时，仍保留目录配方与详情；“已确认掌握者为 0”不得写成“账号无人会做”。

**配方模式：**

- 矩阵以全量客户端配方目录为行、当前 Core 范围内的角色为列，逐格展示学习状态：已学为正常图标；确认未学为灰色图标；未扫描、部分扫描、错误或目录覆盖未知时显示“？”。
- 每个配方行可查看配方名称/图标、专业、产物（可确认时）、可取得状态、采集状态及角色归属。取得状态单独呈现为“可取得 / 不可取得 / 未知”等次级信息，不改变学习状态图标。
- 支持按角色、专业、配方名称和学习状态筛选；长列表使用搜索、分组与分页/有界列表组织，不使用横向滚动或按固定角色数截断结果。
- 页面角色列遵循 Core 当前服务器/角色范围和排序；要查看所有服务器的角色，使用 Core 范围切换。

此处“全量”指**目标客户端配方目录中的全部配方**，不依赖账号是否有角色、是否有角色快照，或是否已有角色学会该配方。角色集合为空时仍显示目录配方，并在角色区域说明当前范围没有可显示的角色；配方筛选无结果时才显示配方空状态。未登录或未完成专业扫描的角色仍显示“？”，不要求所有账号角色实时在线。只有当客户端目录完整性与角色专业扫描完整性均得到验证时，目录缺项才可显示为“未学”。当前候选目录尚未通过完整性验证，不能作为已交付的全量正式目录。

## 五、阶段 2：按目标物品查询可制造角色

在阶段一缓存基础上，建立目标物品与配方的反向索引。玩家或其它业务插件给出物品 ID 后，返回所有已缓存且确认学会相应配方的角色。

结果至少区分：

- 已知配方，且产物可确认；
- 配方已学，但产物关系尚未验证或目录未覆盖；
- 没有可确认的已学配方（不能推断全账号没人会做）。

对同一物品多个配方、配方多种产物和职业专属限制，保留原始配方及来源关系，禁止错误合并成一个无法追溯的条目。

## 六、阶段 3：材料需求与 Vault 联动

- Crafting 按配方返回直接材料需求及可靠性/来源信息。
- Vault 通过只读 API 返回已采集库存、角色、服务器和容器位置；未采集位置不推断为空。
- Crafting 或调用方可比较需求与可查询库存并呈现缺口；材料需求和库存快照必须分开显示来源及状态。
- 首轮可先展示直接材料清单。不承诺递归拆解所有中间产物、成本估算、拍卖价格或全账号最优调配。
- 若配方材料数量或来源不可靠，应明确标记未知/未核实，不呈现伪精确缺口。

## 七、阶段 4：YiboBuilds 集成

YiboBuilds 装备提升面板可以按产物查询已学配方及制造者。Crafting 返回角色、专业、配方、产物和已知材料需求；Builds 继续负责：

1. 当前装备槽位和物品目标是否适用该提升；
2. 当前角色是否拥有所需专业/配方及是否满足技能等级；
3. 当前背包物品和材料是否足够；
4. 客户端是否允许执行，以及实际施加和成功后重扫。

跨角色配方只用来提示“可由某角色制作”，不得为非当前角色或历史装备显示可执行操作。Crafting 缺席时，Builds 沿用现有的客户端实时检查及版本目录回退逻辑。

## 八、YiboTodo 职责边界

YiboTodo 负责周期任务定义、商业冷却配方子集、冷却状态、可执行状态和完成记录。YiboCrafting 负责账号配方目录与角色已学配方。两个插件各自维护本职业务数据；YiboTodo 只依赖 YiboCore 即可完整工作。

## 九、其它后续消费者

- **YiboMail：** 在玩家选择目标制造者后，未来可将材料寄送建议交给 Mail 的操作流程；Crafting 不发邮件，Mail 不负责配方判断。
- **YiboMounts：** 对制造类坐骑来源显示会制作的角色；由 Mounts 决定坐骑目标展示，Crafting 提供制造事实。
- **YiboVault：** Vault 可消费配方需求来展示相关材料线索，但不承担配方目录或制造建议。

这些都是后续只读集成方向，不属于首版必须交付。

## 十、明确不做

- 拍卖利润、制造成本、拍卖行价格追踪或完整经济系统；
- 自动制造、自动采购、自动邮寄、无人值守专业操作；
- 代替 YiboTodo 管理周期冷却、活动状态和待办完成；
- 代替 YiboVault 采集或保存角色物品库存；
- 代替 YiboBuilds 判断具体装备目标适配或执行增强；
- 在数据不完整时推断某角色没学配方、材料库存为零或账号无人会做；
- 首版承诺全资料片配方全集和所有配方学习状态跨角色实时同步。

## 十一、实施阶段与门禁

### 阶段 0：客户端能力、全配方目录与数据来源验证

验证专业列表、目标客户端可识别的全部专业配方目录、配方学习状态、产物关系、材料读取、取得状态证据、事件刷新时机，以及只在打开专业界面时可读的数据边界。逐专业确认目录覆盖完整度，并明确能否判断一次角色扫描完整。客户端数据作为取得状态基线，人工核实例外；没有证据的取得状态保持“未知”。输出目录数据样例、状态模型、扫描完整性证明和查询 API 草案。

**门禁：** 只有经验证目录覆盖完整、且角色专业扫描为完整的范围，才进入“未学配方”推断。未达门禁的配方/专业继续显示“？”，不得产生虚假的未学状态。

### 阶段 1：全配方目录、角色学习缓存与 Core 账号页

建立目标客户端全量配方目录、角色级正向已学配方缓存、专业扫描状态与局部刷新/失败保留；在 Core 页面提供“配方 / 专业”两种模式、全目录状态图标、取得状态说明、角色/专业/名称/状态筛选及有界列表。支持 Core 当前范围，不重复制作角色或服务器筛选。Core API v6 注册、统一设置与角色缓存清理接入按仓库现行指南执行。

**交付：** 玩家可在 Core 统一账号业务面板查看全量配方目录中每项配方对当前范围内每个角色的已学、未学或“？”状态，也可从专业进入配方列表和单条配方详情。角色集合为空或没有已确认掌握者时，目录配方仍可查看。

### 阶段 2：目标物品反向查找

基于已学配方快照和经过核实的产物目录，查询哪些角色可以制作给定物品，形成供 Builds 等调用的只读查询接口。

**交付：** 能从目标物品查到已确认的配方与制造角色，并携带数据状态和采集时间。

### 阶段 3：材料需求与 Vault 查询

建立配方材料信息，按只读 Vault API 查询已缓存库存，展示材料需求和可见缺口。

**交付：** 配方需求与缓存库存可并列核对，数据来源和未知范围明确。

### 阶段 4：Builds 配方信息集成

Builds 消费配方/制造者查询作为可选能力。Crafting 不加入 Builds 的强制依赖；没有 Crafting 时，Builds 继续使用现有本地实时配方检查与目录回退，装备提升仍可用。

**交付：** 安装 Crafting 时，Builds 装备提升流程可利用跨角色制造信息；未安装 Crafting 时，Builds 仍保持 Core-only 安装可用。

## 十二、验收原则

- 专业技能等级只以 Core 专业领域为权威，不因 Crafting 重复扫描产生冲突值。
- 一次成功扫描只更新对应角色/专业；失败或部分扫描不清空已有有效记录。
- Core 账号页覆盖所有当前已缓存角色记录，尊重 Core 服务器与角色筛选；页面状态能区分有数据、部分数据和不可用。
- 已学配方显示正常图标；完整目录中的确认未学配方显示灰色图标；未扫描、部分扫描、扫描失败或目录覆盖未知显示“？”。
- 配方取得状态与学习状态分开呈现；客户端数据加已核实的人工例外作为依据，无证据时为“未知”。
- 未缓存角色、未扫描专业及未覆盖目录不会伪装成“未学”；“未学”要求目录覆盖和角色扫描均已确认完整。
- “配方”模式逐配方显示当前角色范围内的状态；“专业”模式从专业进入全量配方列表和单条详情。两个模式按钮固定在内容区右上角。首次打开为“配方”，随后记住上次选择。
- 配方目录不以角色或已学记录为准入条件；角色集合为空或所有角色都未确认掌握的配方仍显示，角色区域单独说明状态。
- Core 当前服务器/角色范围对 Crafting 生效；所有服务器通过 Core 范围切换查看。
- 确认角色移除专业后清除该专业缓存；专业领域读取失败/不可用时保留缓存。
- 同一配方被多角色掌握时，每名制造者均可识别且能保留服务器归属。
- 反向查询只报告正向确认的配方，不把无结果解释成账号没人会做。
- Crafting 未安装时，Builds 仍能使用现有装备提升功能；YiboTodo 仅依赖 YiboCore 即可完整工作。
- 所有角色删除和缓存清理均通过 Core 统一角色清理入口，并符合统一设置工作台及破坏性操作规范。

## 十三、待确认事项

1. 目标客户端对不同专业的配方目录完整性、角色已学列表完整性和“完整扫描”证明能力，须由阶段 0 实测决定；不能满足门禁的范围保持“？”。
2. “可取得/不可取得”目录属性的客户端数据覆盖率与人工核实规则，须在阶段 0 清点后定稿；证据不足时保持“未知”。
3. 公共 API 的方法名、版本号、查询结果状态与变更通知需在阶段 0 数据契约验证后冻结，不在当前产品方案中预设实现细节。
