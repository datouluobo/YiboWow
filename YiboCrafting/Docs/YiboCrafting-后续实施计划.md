## 实施顺序与阶段门

### 阶段 A：冻结目录范围与证据规则

**工作：**

- build `5.5.4.70032` 的目标 DB2 哈希和候选目录已固定。继续逐技能线复核纳入、排除、旧配方、分支解锁及隔离项；`5.5.4.69934` 保留作差异核对，不与新构建样本混算。
- 以新构建候选和按 build 标记的去身份客户端样本为输入，逐技能线复核纳入、排除、旧配方、分支解锁及隔离项；明确符文熔铸、采矿熔炼等边界如何进入 Crafting 的目录和账号页。
- 为每条技能线记录来源构建、源数据哈希、生成器版本、候选数、已核实数、排除/隔离原因和覆盖状态。材料表缺失本身不作为排除配方的理由。
- 已固定 [AtlasLootClassic MoP v5.3.1](https://github.com/snowflame0/AtlasLootClassic_MoP/tree/v5.3.1)（commit `ecaa6bd7958fa43ebeb917a0bb330f3ba7c46841`）与 [ATT 5.3.15](https://github.com/ATTWoWAddon/AllTheThings/releases/tag/5.3.15)（commit `694a22cd1ab2b7a56cb360e51b5a20e11f883540`）。ATT 发布记录中的 MoP 数据构建为 `5.5.4.69934`，与本机 `70032` 五张 DB2 表内容哈希一致。生成脚本从指定 Lua 数据中提取 ID 和 SHA-256；为审查而记录上游数据，不把第三方代码复制进插件。
- 已将 build `70032` DB2 候选、角色正向 ID、旧 MoP 目录、AtlasLoot、ATT 做逐 ID 差异表，详见[报告](../../_NonRelease/YiboCraftingStage0Probe/Candidates/5.5.4.70032-external-sources-review.md)和[CSV](../../_NonRelease/YiboCraftingStage0Probe/Candidates/5.5.4.70032-external-source-diff.csv)。5282/5337 候选至少命中一类四类对照源；55 个未命中项已逐项列出。54 个旧 CTM 产物候选已全量与当前 Vicious 候选建立 family/slot 配对，详见[54 项替代映射表](../../_NonRelease/YiboCraftingStage0Probe/Candidates/5.5.4.70032-ctm-replacement-map.csv)；其中 3 条由用户截图直接确认，其余为外部来源和 Item ID 对齐的高可信推定。
- 已落盘的 build `70032` 样本覆盖炼金（264 行 / 254 ID）和两名角色的裁缝（453 行 / 436 ID、540 行 / 523 ID）。旧版探针把本地化占位文本“搜索”当作非空搜索；修复已写入探针源码，截图确认搜索框视觉上为空。无需为保留这些正向 ID 重扫；仍不能把角色实见数量当作目录完整证据。
- `66587`、`405005` 均已归档为历史技能候选，不作为当前 MoP 配方行；后续发现目标构建的直接配方/产物证据时再修正分类。首版审查清单保留两项 ID 和历史依据，避免静默丢弃。

**证据判定规则：**

- **候选身份/形态：** 目标 build 的 `SkillLineAbility` 证明技能线关联；`SpellName`、材料、效果类型和产物 ID 可相互补强“这是哪种专业技能”。它们本身不证明当前可取得或目录完整。旧目录和角色正向样本只作交叉旁证。
- **当前可取得：** 不要求为发布而在游戏内实际取得每个未学配方。可使用固定 build 客户端数据、角色已取得配方的正向样本，以及 AtlasLootClassic MoP、All The Things（ATT）的配方/来源数据交叉核对。客户端已学样本证明该 ID 在该客户端可被学习；AtlasLootClassic/ATT 的条目和来源证明其数据集中收录及记录的来源，不单独证明当前版本来源仍有效。只有来源被目标版本数据支持时才标“可取得”；来源未确认时保留“未知”，不阻止目录发布。
- **已移除/不可取得：** 需要目标 build 的明确证据，如当前客户端明确不可学、来源已被验证移除，或该 build 明确将法术标为废弃；单纯未被角色学会、未出现在 AtlasLootClassic/ATT、未找到来源/名称/样本都不算证明。目录历史记录和取得状态分开保存。
- **目录完整与首版发布：** 固定 build、源表、哈希和筛选规则；枚举 DB2 专业候选并逐项分类制作配方、专业动作、分支解锁、历史项、替代项与排除项，再用已取得角色样本、AtlasLootClassic MoP、ATT 做 ID 级交叉核对。所有来源、版本/提交、文件哈希、映射规则和差异清单可复现；差异不能静默丢弃，未解决但已分类的条目保留在目录审查记录并标 `unknown/provisional`。达到该可审计的来源覆盖标准即可发布首版，不再要求游戏内穷尽取得验证；发布后按新证据逐条修正并提升目录版本。未完成来源对账或仍有未分类 DB2 候选的专业，仍标 `partial`。
- **替代关系：** `SupercedesSpell` 仅证明旧新 ID 有关联。AtlasLootClassic/ATT 或角色正向数据若仍收录旧 ID，应作为保留旧项的交叉证据；无论是否被替代，都先保留目录身份并将取得状态单独标注，后续有目标版本失效证据时再更新。
**交付：** 可重现的目录生成输入与工具、逐专业审查表、稳定的 `catalogVersion` 规则，以及候选/部分/完整的判定说明。

**阶段门：** 只有目标范围内每条技能线的纳入与排除都有依据、未决 ID 不会被静默漏掉、生成结果可复现时，才发布为正式目录。若仍有未决项，该专业覆盖标为 `partial` 或 `unknown`，不允许使用“全量”标签。

### 阶段 B：验证配方学习状态来源

**工作：**

- 已通过首轮正/负样本：目标 build 的 `IsPlayerSpell` 对裁缝 Spell `1224167` 返回 true、对 `101922` 返回 false；两者均不依赖专业窗口可见列表。`GetRecipeInfo.learned` 在两样本中为 nil，`IsSpellKnown` 对两个样本均为 false，不参与判定。插件按目录内法术逐项调用该 API 并分批保存。
- 旧版列表继续用于补充产物与分类，不再用于负向学习状态判定；其受搜索/折叠等影响的限制仍有效。
- 建立扫描判定表，至少覆盖完整候选、明确受限、无法证明、接口缺失、调用异常、空列表、链接/公会窗口及专业不匹配。空列表只有在独立证据证明完整时才可成为完整结果。
- 不自动清过滤或展开分类来制造完整列表，除非已能可靠保存并恢复玩家原界面状态，且实测确认不触发受保护操作或破坏现有 UI 状态。
- 如果只能可靠识别“受限”或“未知”，就保留这些状态并停止该专业的负向推断；将其记录为阶段结果，不以猜测补齐完整性。

**交付：** 已学/未学 API 样本、按目录版本的完整逐法术快照和三态 UI；目录覆盖完整性仍由阶段 A 单独决定。

**阶段门：** `IsPlayerSpell` 快照只有在 Core 专业归属明确、候选目录的每个 Spell ID 都收到布尔结果且快照原子保存后才可用于该目录项。尚未拥有该专业、API 异常、快照不完整或目录版本不符时保留待确认；候选目录未完整不妨碍已列条目的直接状态，但不能证明全量目录没有漏项。

### 阶段 C：正式目录、完整基线与状态派生

**工作：**

- 将通过阶段 A 的目录生成正式运行时目录数据，包含稳定 ID、专业/分支、可核实的名称/产物/材料/取得状态、证据来源和 `catalogVersion`。未核实字段明确为未知；分类补全表继续只负责分类。
- SavedVariables schema v2 已增加 `recipeSpellSnapshot`，按角色专业记录 `catalogVersion`、时间、来源 `IsPlayerSpell`、条目数及完整布尔状态集合；每专业仅在当前目录 ID 全部成功查询后原子替换。原有正向 `learnedRecipeIDs`、旧版窗口最近尝试信息继续分开保留。
- 为新增基线字段升级 `YiboCraftingDB` schema；迁移保留现有正向记录、产物映射、分类和设置，不把旧缓存伪造为完整扫描结果。旧数据迁移、重复迁移和未知 schema 版本都要有明确行为。
- 新版本目录不匹配旧基线时，旧基线只可用于能证明兼容的 ID；新增或变化项显示未知，直到对应专业完成匹配版本的完整扫描。失败或部分扫描保留旧基线及正向记录。
- UI 从匹配版本的逐配方法术快照派生已学/未学/待确认；目录未完整影响是否可称“全量目录”，不否定对已列 Spell ID 的 API 直接返回值。缺专业、快照失败/过期或版本不匹配继续显示待确认，不另存派生的未学表。
- 更新配方矩阵、专业详情、筛选、说明文案和计数，让正式完整目录成为列表准入来源；没有角色、没有已学角色或没有扫描记录时仍显示目录项目，并明确解释未知范围。
- Core 明确确认角色不再拥有专业后删除该专业 Crafting 缓存；Core 专业数据缺失、过期或读取失败时保留缓存。

**交付：** 正式目录、版本迁移规则、角色专业完整基线和三态 UI。已通过的专业可以给出确认未学；未通过专业继续显示待确认。

**阶段门：** 离线验证目录版本升级、完整扫描原子替换、部分/失败扫描保留、无角色/无数据、角色删除及 Core 专业数据不可用等情形后，才将相应专业标为可推断未学。

### 阶段 D：Core 公共注册机制与 Crafting 查询 API

**工作：**

- 接入前依据 [Core API v9 Service 契约](../../YiboCore/Docs/API-v9-业务服务与刷新.md)检查现有方法，并确定 Crafting 所需的最低 Core API/能力版本；不得把普通 `Capabilities` 当作提供者注册表，也不得让消费者直接绑定 Crafting 全局对象。
- Service 契约须支持重复注册不重复生效、稳定来源标识、版本检查、冲突拒绝、晚注册/注销和提供者缺席。Core 只管理通用连接与生命周期，不保存配方业务数据、不按插件名分支。
- 为 Crafting 的配方查询定义业务 API 自身的稳定名称和版本，不用 Core API 版本代替。首批只实现已确认需要的只读查询，例如按物品 ID 返回匹配配方及明确角色范围内的已确认制造者；范围、目录版本、扫描时间、数据完整度、未知原因和失败状态进入返回契约。
- 查询返回新建/只读结果，不暴露 SavedVariables 表引用。无提供者、契约不兼容、目录覆盖不足、角色数据过期或没有匹配项时返回可区分状态；无结果不得解释成账号无人会做。
- YiboBuilds 作为可选消费者评估接入；不向 Builds 增加 Crafting 强依赖。Crafting 缺席、未注册或不兼容时，Builds 现有装备提升功能继续工作。
- 同步更新 Core 公共 API 指南、Crafting API 契约和相关插件接入记录；只有能力真实新增/接入后再更新公共能力迁移台账，不提前将计划写成已交付。
