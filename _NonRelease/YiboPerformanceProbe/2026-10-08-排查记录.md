# 2026-10-08 Core 高占用与业务调用来源

## 已发现并修复的后台路径

YiboMail.RuleSendController:OnEvent 在邮箱关闭时仍响应 BAG_UPDATE_DELAYED 与 GET_ITEM_INFO_RECEIVED 调用 Scan。Scan 扫全部背包并进入 SendRules:Match；每次匹配读取 Core 当前角色，各有效规则的 Recipients:CanRuleSend 又读取当前角色。Core Characters:GetCurrent 经 Get 返回整角色递归拷贝。因此普通拾取及物品信息事件可触发 Mail 的业务工作，并把共享 API 耗时记到 Core。

已增加邮箱打开条件，保留打开邮箱的匹配以及 sending/filling 保护。该路径是确定的多余工作，不等于已经证明它解释用户当前全部卡顿。没有修改业务规则、角色存档或其它插件启用设置。

RuleSendSpec 新增真实匹配回归：关闭邮箱时连续 20 个相关事件扫描次数及 Core 读取次数均为零；打开邮箱时两个事件继续匹配；发送和装填期间不重匹配。MailRuntimeSpec、RuleSendUISpec、Lua 5.1 语法检查及探针 Smoke 均通过。

## 更新与数据检查

最近发布主要为 YiboMail 1.1.0/1.1.1 与 Core 1.7.1。检查 Core 更新差异，主要是名称格式化、物品选择界面与版本声明；角色拷贝、领域分发没有在这几次更新中改变。不能仅凭发布时间直接归因。

旧探针在 2026-10-07 仓库清理提交中移除；本次为当前需求重新建立 v0.4.0，不恢复旧诊断结论。客户端同名目录联接仍指向该路径，恢复文件后可重新加载。

当前本机性能存档最后写入为 2026-10-07，不是今天的现场，不能用它识别今天的业务耗时。离线 Lua 5.1 对当前 Core 角色保存记录做递归节点统计，最大的几条约 2100 节点，单次复制本机平均约 0.4–0.8ms；只是静态规模与本机基准，不代表游戏内耗时，也未发现可直接支持巨型单角色数据的证据。

## Core 调用来源统计

v0.4.0 在指定 Core 公共 API 调用入口读取 debugstack，按外部插件、来源文件行号、Core API 分组；报告前八条累计耗时最高的来源。包括 Characters GetCurrent/Get/GetAll/GetAllCached、Profile RefreshCurrent、DataDomains Dispatch、DomainStore Commit、ItemResolver Request。

不修改 Core 或业务接口行为，不读取业务 SavedVariables；Core 公共边界仅在探针启动期间被计时包装。沿用旧探针的其它方法计时属于诊断覆盖，不是跨业务功能集成。stop 还原原函数，启动清空上一轮统计，保留 nil/多返回值。烟雾测试覆盖不同业务归属、Windows/斜杠/带引号的栈来源、溯源自身耗时、还原与重启。

这是调用来源的包容耗时，包含下游工作，不是业务插件独占 CPU。嵌套 API 行不可相加；例如 GetCurrent → Get 不代表两份独立耗时。Core 分发事件到业务回调、异步边界、Lua 尾调用及缺少可识别栈帧可能使归属不完整；Core/unknown 不等于证明 Core 自己是根因。原生 CPU 统计和调用来源应结合长帧看。

每次调用会有栈读取开销，报告单独列出溯源累计耗时；计时仍可能扰动被测状态。仅短时复现使用，不建议常驻开启。第一轮保持全插件 CPU 关闭，避免此前观测到的原生统计 API 明显开销。

操作：启用 YiboPerformanceProbe，RL；若 scriptProfile 开启，先 /ypf cpuoff 自动 RL；/ypf start 后在实际卡顿场景复现约 30–60 秒，/ypf stop、/ypf report，截图 Core 调用来源与长帧区块；退出/RL 后可读取完整存档。若普通计时仍不足以解释长帧，再考虑短时全插件 CPU。

用户的“Core 占用”尚待区分是 CPU 还是内存 MB，二者不能混用。来源报告回答 API 调用耗时归属；不会直接测出垃圾回收、内存分配所有权或客户端本机/GPU 等待。
