# Business-addon release check brief (API14 wave, 2026-11-22)

Repo `D:\Development\YiboWow` (WoW addons, Lua 5.1, Windows PowerShell 5.1, no git). Read `发布包约定.md` (section 覆盖更新与升级验收) and the AGENTS.md TOC/运行入口 rules first.

Context: YiboCore Mists 1.13.0 / Forever 0.3.0 / Retail 0.2.0 (API14, `pixel-line:1`) is **already published**. In this session every business addon below was migrated to Core pixel lines and its minimum Core raised to API14 (code complete, offline tests pass, user verified in-game). Now each addon gets a new version and a release check. Packages: `Builds/<Addon>-<target>-v<version>-curseforge.zip`; old packages are in `Builds/` (current previous release) and `Builds/Archive/<Addon>/`.

## Steps per addon/target
1. **Version bump** to the exact version assigned to you: update every place the builder checks (TOC `## Version` of the target source TOC, the default hint `<Addon>.toc` if it carries a version, and the source version constant the profile reads — see `Tools/ReleaseProfiles.psd1` `VersionFile`/`VersionPattern` for your addon/target). Do NOT edit `Tools/ReleaseProfiles.psd1`. Mail/Vault keep their `-api1` suffix exactly as the existing scheme produces it (check how the current version string is formed before editing). Update any test that asserts the old version string.
2. **Before building**, note the previous package for overlay: the package currently in `Builds/` for that addon/target (it will be moved to `Builds/Archive/<Addon>/` by the builder).
3. **Build** the CurseForge package: `powershell -NoProfile -ExecutionPolicy Bypass -Command "$env:Path += ';C:\Program Files (x86)\Lua\5.1'; & 'D:\Development\YiboWow\Tools\Build-ReleasePackages.ps1' -Addon <Addon> -Target <Target>"` (BeastPaths: `-Target Mists` and `-Target Retail`, see its profile; if the builder refuses a target, report exactly). Run it from a .ps1 file written to %TEMP% if quoting gets awkward. Record version, ZIP SHA256, size, SourceSHA256, RequiredCoreAPI. Do not write any docs or changelog files under the addon between building and finishing (it changes the source digest); write docs **first**, then build. If you must change sources after building, rebuild (move your own just-built zip to `_NonRelease/<Addon>Release-20261122/Superseded/` first; never delete).
4. **Package checks** (from the actual ZIP): only the default `<Addon>.toc` + that target's files; no other-target TOC, `_NonRelease`, tests, WTF.
5. **Clean install + overlay replay** in `_NonRelease/<Addon>Release-20261122/`: extract new zip (Clean-<Target>); extract previous package then extract new zip over it keeping old files (Overlay-<Target>); list old-only residual files and confirm none is referenced by the new TOC / can be selected as a TOC. Then run a Lua replay that loads the **real Core from the published package** (`Builds/YiboCore-<target>-v...-api14-curseforge.zip`, extract to `_NonRelease/<Addon>Release-20261122/Core-<Target>/`) plus the addon from Clean and Overlay roots in TOC order, using an existing harness if the addon has one (search `_NonRelease/` and the addon's tests for harnesses that load real Core TOCs, e.g. `_NonRelease/CoreRetailR2/Harness.lua`, `_NonRelease/<Addon>Forever/Smoke.lua`, `<Addon>/_NonRelease/Tests/*Real*`, Vault/Mail acceptance scripts under `_NonRelease/VaultForever`, `_NonRelease/MailForever`). Check at minimum: addon initializes once with Core API14; its saved variables from a previous-version store are kept; wrong target stops before writing; an API13 Core is refused with the upgrade message. If an existing harness cannot be pointed at package roots, write a minimal one; if a real replay is infeasible, say so precisely and fall back to the existing real-manifest tests — do not fake results.
6. Run the addon's offline tests once more after the version bump; syntax check.
7. Write a release record `Docs/Publishing/<Addon>-<versions>-20261122.md` (Chinese, follow `Docs/Publishing/YiboCore-1.13.0-API14-20261122.md` structure: 产物表, 发布内容, 兼容性 (requires Core API14: Mists 1.13.0 / Forever 0.3.0 / Retail 0.2.0), 检查结果, 待办). Status "发布检查通过，待用户上传" only if all checks passed; otherwise state blockers. Also add a short changelog entry if the addon keeps a CHANGELOG file — write these BEFORE building (step 3 note).
